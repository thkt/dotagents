# テスト設計

実装単位の受け入れテストまたは検証ゲートを決めるときに、このリファレンスを読む。

## テスト対象

- 新規 module を含む tested unit では、計画した全テストを discoverable かつ runnable にし、新しい behavior は assertion で失敗させる。
- 許可された production file が無ければ、それらの実行に必要な最小の API scaffold だけを作り、pass する behavior は実装しない。import/module-resolution、syntax/parse、typecheck、discovery の失敗は無効な Red evidence とする。
- このリファレンスよりリポジトリ固有のテスト方針を優先する。
- テスト名には条件と観測可能な結果を書く。実装をリファクタリングしても成立する名前にする。
- バグでは原因を変更する前に報告された挙動を再現し、その挙動に対して追加テストが失敗することを確認する。
- 結果を変え得る状態遷移と境界値の両側を確認する。
- 認可、課金、主要な判断で独立した条件が組み合わさる場合は、各条件の組み合わせを確認する。
- タイムアウト、依存先の失敗、不正なレスポンスは、対象がその依存境界を越える場合だけ確認する。

## テストの層

失敗を観測できる最も低い層を使う。

| 失敗を観測できる場所             | テストの層  |
| -------------------------------- | ----------- |
| 純粋な判断または変換             | Unit        |
| 動作するコンポーネント間の接続   | Integration |
| 実行中の利用経路だけで見える破損 | E2E         |

E2E は主要な利用経路と、下位層で観測できない失敗に限定する。依頼の完了状態に関係する場合は、状態依存 UI、認可、空状態、外部接続を含める。

## テストダブル

副作用を閉じられる実物、Fake、Stub の順に選ぶ。外向きの呼び出し自体が観測対象の場合だけ Mock を使う。
