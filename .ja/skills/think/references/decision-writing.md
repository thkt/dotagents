# 設計判断の文章

完了状態と Plan の文言を決めるときに、このリファレンスを読む。共通の[契約の粒度](../../../workflows/README.md)に従う。

## 具体的な主張

- 「正しい」「正常」「意図どおり」ではなく、条件と観測可能な結果を書く。
- 「処理」「データ」「情報」ではなく、実際の操作と内容を示す。
- 「速い」「大きい」「最新」などの相対的な語ではなく、測定値と比較対象を書く。
- 1 文には 1 つの主張を書く。
- 不足する証拠は未確定事項として示す。文章を具体化するために数値、担当者、日付、失敗条件を作らない。

## 完了状態とPlan

- 実装方法を含めず、対象が完了時に示す観測可能な状態を書く。
- 各実装単位の目標は単独で観測可能にし、契約には必要な動作と維持する制約を書く。互換性または安全性のために特定の選択が必要な場合を除き、内部設計の選択は担当に残す。
- 各`unit.tests[]`には、`test_command`で確認する観測可能な受け入れ条件を書く。
- 調査の citation、repository rule の複製、代替案、一般的な rationale は Plan に含めない。正確な format・identifier・digest の動作は、明示した外部要件・永続データの互換性・安全要件に必要な場合だけ含める。完全さを求めて内部 API を列挙しない。

## 削除対象

進捗説明、スキーマの言い換え、コードの言い換え、変更履歴、内容のない見出し、成果物を繰り返す末尾の要約を削除する。
