# 人の注意に依存する条件を機械で守る

通常の要求整理・実装・修正・独立評価で、繰り返す注意や人の記憶に依存する条件を見つけたときに使う。[Issue #385](https://github.com/thkt/dotagents/issues/385)で合意した共通手順の正本とする。個別に「機械化して」と指定されることを前提にせず、機械化の件数や全注意のコード化を目的にしない。

## 条件と既存の保証から選ぶ

1. 守る条件を具体化する。対象の入力・状態・操作、成立すべき結果、必要な理由と根拠、適用範囲を確認する。既存指示の注意をそのまま新しい規則と扱わず、現在の要求・合意・コードへ照合する。
2. 既存の保証を調べる。型、標準API・ライブラリ、lint、実行時検査、スクリプト、テストの実装・設定・呼出経路と適用条件を確認する。検査の存在と実際の接続、対象除外、検出力を区別し、未接続や故障を同じ検査の新設で補わない。
3. 条件に合う方法と現状維持を比較する。保証できる範囲、検出漏れ、誤検出、実行・保守の費用から必要な最小の方法を選ぶ。既存の保証で十分な場合、根拠が不十分な場合、追加の負担が効果を上回る場合は見送るか保留する。
4. 判断に必要な違いを確かめる。既存資料・コード・結果で足りない場合だけ、許可された範囲の小さな正常例・違反例・適用外の例で確認する。失敗が狙った条件によるものかを確認し、一例の成功を全条件の保証にしない。検証資産の作成・更新は下記の独立テスト経路に従う。

| 方法 | 向いている条件と限界 |
| --- | --- |
| 型・データ構造 | 不正な値や状態の組合せを表現できなくする。外部入力や変化する外部状態は、型の宣言だけで保証しない |
| lint | コードから判定できる規則を守る。設定・対象・認識できる構文と例外を確認する |
| 実行時検査 | 外部入力や、その時点で変わる状態を確認する。観測時点と副作用の前後、失敗時の動作を保つ |
| スクリプト | 反復する操作をまとめ、確認漏れを減らす。正常終了だけで処理内容や要求充足を保証しない |
| テスト | 振る舞い・順序・失敗時の結果を確かめる。要求から決まる判定根拠と、既存検証との差を確認する |

この表を固定の優先順位にしない。条件によって組み合わせ、既存の説明に残すべき理由・例外・未確認事項も保持する。機械で判定しにくい意図・好みは、無理に規則へ変換しない。費用や改善効果の見積りと実測を区別し、未確認の保証を確認済みにしない。

## 担当と戻り先を保つ

scopingは今回の要求・範囲・完了条件を判断するために調査・比較する。候補発見を本実装や新しい規約の制定への許可にしない。判断に関係する結果だけをIssueまたは下書きへ渡す。

implementの初回実装・追加修正・既存PR修正は、合意範囲内の通常の選択を進め、許可を聞き直さない。規則追加や依存導入は候補発見だけで自動採用せず、対象repo・Issue・既存の担当分担と検証契約に従う。要求・権限・規約の変更や範囲外の改善は、根拠と影響を伴う提案として分け、人の判断へ戻す。範囲外の提案があるだけで今回の完了を待たせない。採用した指摘の原因と再発性から検討する場合も同じ手順を使う。

テスト・fixture・検証接続定義の作成・更新は[独立テスト担当](../../scripts/README.md#テスト作成の独立セッション)へ戻す。実装・修正担当は不足や不一致を既存のfindingsへ具体的に残し、資産を変更しない。独立テスト担当は[設計・選定手順](../implement/references/testing.md#検証命題とケースの設計手順)で合意済みIssue・仕様から守る条件と既存検証との差を判断する。実装担当の案・会話・自己評価は期待値の根拠に渡さない。

独立評価は、機械化を行った場合と見送った場合の両方について、守る条件、既存の保証との差、適用範囲、検出できない条件、誤検出と維持の負担を要求・コード・証拠へ独立して照合する。保留も根拠不足と必要な確認を区別する。機械化案を採らなかったこと自体を欠陥にせず、確認できた保証不足や要求違反を既存の指摘へ戻す。範囲外の改善や好みを今回の必須修正にしない。

判断に関係する守る条件、既存の保証との差、採用・見送り・保留の理由、適用範囲、未確認事項を、既存のIssue・findings・独立評価・PR説明へ必要な範囲で残す。候補ごとの帳票、候補がない場合の定型報告、新しい応答項目は作らない。設定済み検証、対象と版の照合、停止と証拠保全、公開後確認、人の承認・マージの責任は変更しない。

## 代表例から判断を辿る

以下は手順と担当の照合例であり、新規テストや実モデル実行を一律に要求しない。

| 条件 | 判断と戻り先 |
| --- | --- |
| 状態に応じた必須値が未保証 | 要求から許される状態と必要値を具体化し、型・データ構造と境界の検査などを比較する。実装は合意範囲内で進め、必要な検証資産は独立テストへ戻す |
| 同じ条件を既存の型・lint・検査が保証 | 実装・設定・対象・実行経路と検出力が十分なら重複追加を見送る。未接続や故障なら原因を調べ、検証接続定義の修正は独立テストへ戻す |
| 外部入力・変化する外部状態 | 型宣言だけで保証せず、実行時の境界・観測時点・副作用の前後・失敗時の動作を確認する。証拠不足なら適用限界と必要な確認を残して保留する |
| 機械判定に適さない意図・好み | 根拠なく規則化せず、必要な説明や人の判断として扱う |
| 範囲外の規約・依存・共通設定の変更 | 調査結果と影響を提案として分け、人へ戻す。今回の必須修正や完了待ちに混ぜない |
| テスト・検証接続定義の変更が必要 | 不足・誤りをfindingsへ具体的に残し、独立テスト経路へ戻す。実装担当の説明を期待値の根拠にしない |

## 根拠と未確認の効果

正本は#385（本文更新日時: 2026-10-13T13:12:46Z）とする。Issueの調査基点`fd28ac54d7d089f494d8d7be7ffe15bb8b5c8092`に対し、実装開始版`31851ee6fc1e459134de92221437856d54838c28`には#386の前提検証、#387の設計理由、#388の利用例の参照がある。今回、その信頼する実体からの参照解決と独立テストの入力境界を再利用し、詳細の重複を避けて本資料へ接続する。これは今回の選択理由であり、過去の作者の意図を推測した説明ではない。

#385は、指摘採用後の再発防止と情報の表現先選択に加え、指摘を待たない候補発見と方法選択を合意した。着手時はIssueの調査基点だけで判断せず、現在のコード・方針・合意へ照合する。過去の設計理由が判断に関係する場合は[根拠と確度](documents.md#設計理由の根拠と確度)、安全性が未確認の前提に依存する場合は[前提の検証](premise-validation.md)を使い、別Issueの範囲を追加要求にしない。

参照の照合や模擬制御テストは、実モデルの自発的な候補発見、判断品質、検出率・費用の改善を実証しない。効果は実測まで未確認とする。追加の実モデル実行は必須にせず、必要になった場合だけ[既存の同条件eval](../../scripts/README.md#指示変更時の同条件eval)へ戻る。目的・ケース・モデル・対象版・有限の上限・送信先・公開範囲を依頼者と確定してから、個別に機械化を指示しない同じ入力で比較し、候補発見と方法選択、見落とし・誤候補・不要な仕組み・範囲逸脱、準備・失敗・再試行を含む時間と取得できる使用量を分けて確認する。必要な要求は隠さず、採点用の正解は担当へ渡さない。新しい評価基盤や全PRの必須ゲートは設けない。
