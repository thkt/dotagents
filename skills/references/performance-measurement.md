# 性能測定の妥当性を確認する

## 適用する場面

性能数値が方針・設計・改善の採否・回帰判定・公開説明の断定を左右する場合に使う。数値で判断しない文書・名称の変更などには、資料全文の読込み、計測や定型報告を要求しない。同じ対象版・条件・仕事を十分に扱う既存証拠があれば再測定しない。新しい数値がなくても、既存証拠による判断や比較不能という結論を認める。

[改善効果の比較](../../docs/wiki/development-policy.md#改善効果の比較)を共通方針とし、ここでは測定固有の確認を具体化する。前提に不足があれば[前提の検証](premise-validation.md)を使い、新たな観測が必要なscopingは[小さな実験](../scoping/references/experiment.md)へ戻る。合意済みの性能要求・閾値・必須検証は維持し、測定不能を未達の免除にしない。

## 1. 主張と測る対象を対応させる

何を判断する数値かを先に定める。指標・単位・分母、入力と処理量、開始・終了、成功・失敗・取消の扱い、対象版と適用範囲を明らかにする。呼出し開始までの時間、完了までの時間、throughput、局所処理、利用者が待つ経路、準備込みの総費用を混同しない。

計測スクリプト・設定・呼出経路を読み、何を計時・集計し、何を除外するかを確認する。保存記録を再利用する場合も、今回の主張を同じ条件で判断できるかを確かめる。

## 2. 実際の処理・完了・正しさ・処理量を確認する

必要な仕事が計時範囲内で実行・完了し、結果が要求を満たすことを確認する。Promiseを待たない、iteratorを消費しない、結果を利用しない、cacheから返すだけ、要求が対象へ未到達、保存完了前に計時を止める、といった経路を照合する。保存や外部処理の完了の意味は、その課題の契約へ照合する。

要求数・成功数・失敗数・実際に処理した件数やbyte数など、主張を区別する観測を選ぶ。結果が存在するだけでは正しさを保証しない。拒否やエラー応答の速さを成功処理の高速化へ変換せず、失敗・再試行・結果欠落を黙って除外しない。意図した拒否の測定なら、その指標として区別する。cacheや省略が要求上の改善なら、意味と条件を示し、別の仕事を同じ処理量として比べない。

比較する仕事は要求上の結果と処理量で定め、内部命令数の一致を求めない。アルゴリズムやcacheによる正当な省力化を、未実行・要求違反と混同しない。

## 3. 比較条件と観測の影響を確認する

版・データ・処理量・並行度・実行環境、buildと最適化、設定・batch・接続pool、cacheとwarm/cold、機器負荷と実行順のうち、今回の判断を左右する条件を揃えるか、差として明示する。比較相手だけ不適切な設定の結果を、実装そのものの優劣や一般的な採用判断へ広げない。条件を変えること自体が比較目的なら、設定差の効果として説明する。

実行順や初期化・温まり・負荷の偏りを考慮し、必要な範囲の交互実行などを選ぶ。profiler・trace・詳細ログで律速箇所を調べた観測は、その影響を受けない性能比較の計時と区別する。既存の有効な条件と証拠を再利用し、全環境の調整やprofilerの常時実行を要求しない。

## 4. ばらつきと全体への効果を解釈する

試行数・実行順・分布やばらつき、比較した代表値と判断できる範囲を残す。必要な反復・集計は問いと不確実さから選び、固定の5回、固定の改善率や統計手法を全課題の必須条件にしない。単回の概算は単回の観測と示し、安定した改善や採用の根拠へ一般化しない。現在の記録で差を区別できなければ、その不足を残す。

数値を制約する資源・コード経路は、必要なら実行中のカウンターや別のprofileから確認する。対象処理の全体時間に占める割合、転送量や帯域など、主張と整合する範囲を確認し、不自然に大きい改善は計時・仕事・条件の取り違えを調べる。局所の改善率を全体の改善率にしない。

割合からの上限計算は前提付きの整合確認とする。変更が並行度・待機・律速を変える場合へ、他の経路が変わらないとする単純な計算を一律に適用しない。

律速や原因が未確認でも、条件を限定した実測値は保持できる。原因仮説と確認した観測差を分け、未確認を埋めて因果関係や全体効果を断定しない。profiler未実行だけで妥当な観測を無効とせず、全体への実測がない局所結果はその範囲に留める。

## 5. 判断と不足を既存の記録へ残す

速くなった・遅くなった・差を確認できない・比較を判断できない、を証拠の範囲で説明する。計測の不成立、取得不能、未実行と、要求違反、妥当な測定の差が小さい結果を区別する。新しいstatus・応答Schema・候補台帳は作らない。

主張に必要な数値・単位・条件・試行数・ばらつき・測定範囲、正しさと処理量の根拠、制約・未確認、次に必要な確認を既存のIssue・findings・独立評価・PR説明へ残す。実測と推定を分け、公開説明にも条件と未確認を保つ。生ログは既存のcheckout外保存先へ置き、共有が必要な非機密の根拠だけを公開する。既存証拠で足りれば止め、理由なく追加測定しない。

## 担当と戻り先

| 担当 | 役割と戻り先 |
| --- | --- |
| scoping | 判断に必要な条件・根拠・未確認事項と検証方法をIssueまたは下書きへ残す。測定不足の発見を、本実装、未合意の負荷試験、規約・依存・検証契約の変更の許可にしない |
| implementの初回実装・追加修正・既存PR修正 | 合意範囲と既存の実行契約内で確認し、通常の選択は許可を聞き直さず進める。不足する証拠と影響をfindingsへ残す。要求・性能の許容範囲・権限・実行上限の変更は人へ、テスト・fixture・検証接続定義の作成・更新は独立テストへ戻す。合意外の改善を必須修正へ混ぜない |
| 独立評価 | 性能主張を測定コード・対象版・実行と完了・出力・比較条件・保存結果へ独立して照合する。数値や担当の説明だけで改善と認めない。不足や過大な主張は条件・影響・根拠と戻り先を既存の指摘へ残す。妥当な記録の再利用や適用外の作業に追加実験を要求せず、read-only権限を維持する |
| 独立テスト | 性能の計測・検証資産に関係する場合、Issue・仕様から完了・正しさ・処理量の区別を独立して定め、必要な正常対照と狙った失敗を選ぶ。実装担当の数値・測定方法・自己評価を期待値の正本にしない。既存検証で十分なら追加せず、計時境界や実処理への到達の検証を不安定な壁時計時間の閾値で代用しない |

独立テストは[既存の入力境界と成果物保護](../../scripts/README.md#テスト作成の独立セッション)と[設計・選定手順](../implement/references/testing.md#検証命題とケースの設計手順)に従う。通常check・captureに含まれない受入検証は[ホスト検証後の再評価](../../scripts/README.md#ホスト検証後の再評価)へ接続する。起動入口だけでなく実際の測定コマンド・子ツールの版を生ログへ照合し、同じ固定環境を親子へ渡す。版の不一致や未観測を成功にしない。設定済みsetup・check・capture、停止と証拠保全、公開確認、人の承認・マージの責任は変更しない。

## 代表例で判断を照合する

次は判断経路の代表例であり、全例の新規テスト、実benchmarkや実モデルevalを要求しない。文書・記録とコードで足りなければ、許可された最小の非同期処理・件数カウンター等で失敗と正常対照を確かめる。必要な資産は独立テストへ戻し、小さな模擬例を実アプリ性能やモデル判断品質の証明にしない。

| 条件 | 確認する判断と証拠 |
| --- | --- |
| Promiseを待つ前に計時終了、iterator未消費 | 呼出し開始と仕事の完了を分け、実処理の件数・完了順序・結果利用を確認する。完了まで測る正常対照と区別する |
| エラー応答や結果欠落で数値が速い | 正常・失敗・処理量と要求上の正しさを確認し、成功処理の改善にしない。意図した拒否の測定は別の指標として保持する |
| 片側だけwarm cache・build・batch等の条件が違う | 実装差と条件差、揃えられない条件や採用判断への限界を示す。設定差を目的とする比較も認める |
| 現記録では観測差とばらつきを区別できない | 速いと断定せず、必要な追加確認または判断できない理由を残す。固定回数や特定の統計検定を要求しない |
| profiler付きとなしの計時を比較、または律速未確認 | 観測の影響、観測差と原因仮説を区別する。別profileの必要性を問いから選び、既存証拠で足りれば止める |
| 全体時間の10%の処理だけを除去したのに全体が半減したという主張 | 同じ仕事・構成という前提と計測範囲を確かめ、割合では説明できない改善の原因を調べる。並行度・待機・律速の変化も照合し、局所結果を全体へ格上げしない |
| 同じ対象版・条件・仕事を十分に扱う保存記録がある | 証拠を再利用し、再判定と新しい実行を区別する。新規測定や専用帳票を要求しない |
| 単回の概算依頼、または性能と無関係な小変更 | 概算は単回の観測と示し、完了・正しさ・処理量と適用限界を保持する。無関係な変更には性能工程を加えない |

## 根拠と効果の限界

正本は[Issue #398](https://github.com/thkt/dotagents/issues/398)（本文更新日時: 2026-10-16T15:43:47Z）。調査基点`1147c672196efa640e47099e674fe0e670e08848`と実装開始版`bdd76761f03c1a92b388f607a9275d1152a3cdca`の比較方針・担当入力・参照経路を照合し、既存の#145の比較方針と#386の前提検証を置き換えず、測定固有の確認と入口を加えた。共通詳細を一か所に置くのは今回の合意に基づく選択であり、過去の作者の意図を補作したものではない。

外部の発想の出典は、Issueにあるpstack固定版`11713c683fe4add4fd403ea880580abbc9e0875f`の[benchmark-checklist](https://github.com/cursor/plugins/blob/11713c683fe4add4fd403ea880580abbc9e0875f/pstack/skills/benchmark-checklist/SKILL.md)・[explain-the-number](https://github.com/cursor/plugins/blob/11713c683fe4add4fd403ea880580abbc9e0875f/pstack/skills/principle-explain-the-number/SKILL.md)。採用する意味と条件はIssueを正本とし、固定の5回や律速未確認の数値の一律棄却は移植しない。現行の測定不具合や実モデルの見落としを今回実証したわけではない。

参照検査の成功は、文書の意味や実モデルの適切な選択の証明ではない。実モデルの遵守・誤認の減少・性能や費用の改善は実測まで未確認とする。[#393](https://github.com/thkt/dotagents/issues/393)の8課題、A/B固定版、corpus、実行順、モデル・上限・送信先・裁定は変更せず、本手順を黙って比較条件へ混ぜない。その実装・実行・結果を本Issueの前提にせず、性能課題やeval基盤も追加しない。追加の実モデル比較が必要になった場合だけ、対象・目的・ケース・版・モデル・有限上限・送信先・公開範囲を別途確定し、[既存の任意eval](../../scripts/README.md#指示変更時の同条件eval)へ戻る。
