# 利用例から型・API・責任分担を設計する

利用者・呼出元が渡すもの、操作、受け取る結果、失敗時に担う責任を先に具体化し、その例から必要な構造を導く。[Issue #388](https://github.com/thkt/dotagents/issues/388)で合意した共通scoping・implementの手順の正本とする。利用例は要求と設計を照合する資料であり、新しい要求の正本ではない。

## 適用条件

入口や責任の境界を新設・変更する場合、または呼出側が覚える順序・設定・状態管理・失敗処理が設計の選択を左右する場合に使う。既存の使い方と契約で判断できる小さな内部変更や文書修正には、新しい例・比較案・設計工程を一律に要求しない。固定の例数や全条件の列挙も求めない。

## 利用例から設計する手順

1. **実際の利用を確認する。** 影響する呼出元、公開された使い方、既存部品・標準API・導入済みライブラリ・近い実装例と互換性の制約を読む。架空の利用者や将来あるかもしれない用途を必要性の根拠にしない。
2. **必要な例を先に書く。** 入力や前提状態、操作、期待する結果・副作用・完了の観測時点を短く示す。正常な使い方に加え、今回の判断を変える失敗・取消・再試行・並行操作だけを選ぶ。現行の実例、提案する使い方、合意した振る舞いを区別する。
3. **型・署名・責任の境界を導く。** 主なデータの読取り・更新と処理の流れを追い、必要なデータ構造・状態、生成・更新・終了を担う主体、呼出側へ公開する能力を例へ対応させる。入力、結果、失敗、状態・資源の所有と終了が型・署名・実装に対応するか確かめる。未実装のスケッチは提案と明示し、実在するAPIや実行済みの証拠として説明しない。
4. **判断が変わる場合に案を比べる。** 既存の形を保つ案も含め、利用側の順序・設定・分岐・後始末と、実装・互換性・移行・検証・保守の負担を比較する。短いAPI、内部へ隠す複雑さ、型の厳しさを無条件に優先せず、必要な能力と制約を保つ。
5. **選んだ理由と不足を残す。** 例と構造の対応、必要な比較、条件・制約・未解決事項を、既存のIssueまたは下書き、findings・独立評価・PR説明へ必要な範囲で残す。実装後は実際の呼出元と結果へ照合する。新しい条件が分かれば例と設計を照合し直し、例を守るためだけに不適切な構造を維持しない。

## 担当と戻り先

- scopingは現行の利用と要求から例を先に置き、入出力・失敗・非同期処理と、状態や資源を誰が持ち、更新し、終了させるかを具体化する。未確定の要求と設計上の選択を分け、判断に必要な例と条件をIssueまたは下書きへ渡す。内部の関数名・型・ファイル分割まで一律に要求として固定しない。
- implementの初回実装・追加修正・既存PR修正は、合意済みIssueと実際の呼出元を起点に同じ手順を使う。構造や例が要求と合わなければ見直し、未合意の振る舞いを例だけで追加しない。合意範囲内の通常の設計は担当が進め、要求・公開契約・許容範囲・権限を変える必要がある場合だけ、具体案と影響を示して人へ戻す。
- 独立評価は設計案や実装担当の説明を検証すべき主張として扱う。例をIssue・仕様・実際の呼出元へ照合し、現在の型・API・データの流れ・状態遷移・失敗処理がその利用を支えるか確認する。呼出側へ判断・設定・検査を移しただけの変更、所有や終了が不明な設計、例と実装の不一致は、具体的な条件と影響を既存の指摘へ戻す。短い呼出しや型検査の成功だけで使いやすさ・安全性・費用の改善を認定しない。

必要なテスト・fixture・検証接続定義の変更は、機械的な接続修正も含め[独立テスト経路](../../scripts/README.md#テスト作成の独立セッション)へ戻す。実装・修正セッションで期待値や接続を変更しない。設計用の例と合意した振る舞いを区別し、実装担当の例・会話・自己評価や詳細な内部設計を期待値の正本へ流し込まない。必要な仕様・公開インターフェースは現行の入力境界に従って扱い、[テスト設計手順](../implement/references/testing.md#検証命題とケースの設計手順)を再実装しない。

## 代表例での照合

以下は概念例であり、現行ハーネスにそのAPIや不具合があるという主張でも、全例の新規テスト・実アプリ起動を求めるものでもない。

| 利用例・条件 | 設計への対応と確認・戻り先 |
| --- | --- |
| 資源を生成→処理→終了するAPIと、一回の呼出しで終了まで担うAPI | 入力資源で処理し結果を受け取る例に、正常終了・途中失敗・取消の終了責任を対応させる。一回のAPIが所有する案と呼出側が所有する案を比較し、呼出側が寿命を制御する必要を保つ。短い方を自動採用しない |
| 真偽値のオプションと任意の結果項目が増え、呼出側が組合せを覚える | 実際に許す入力と操作に期待結果を対応させ、必要な型・境界を検討する。利用例だけを理由に合意した入力や能力を削らず、削る必要があれば人へ戻す |
| 非同期処理の失敗・再試行・並行呼出しで共有状態が変わる | 前提状態から開始し、完了・失敗を観測する時点と、各操作の更新・後始末の所有者を追う。正常な一回だけで設計を承認しない |
| CLI・設定・公開APIの既存利用がある | 既存の入力・操作・結果・失敗条件と互換性へ照合する。内部exportを一律に固定せず、新たな実利用が見つかれば保証と範囲を再評価する |
| スケッチは型検査を通るが、取消時に実装が例と異なる | 型の整合と実行時の振る舞いを分け、必要な条件で確かめる。提案を実装済み・検証済みとせず、不一致を通常の指摘へ戻す |
| 提案例が未合意の振る舞いを含む、または保護テストの接続に影響する | 要求変更は人へ、テスト・fixture・接続の変更は独立テスト経路へ戻す。例を通すために期待値を緩めない |
| 名前の局所整理、文書修正、呼出側へ設定・検査を移しただけの短縮 | 判断が明らかな整理には新規例や複数案を求めない。負担の比較が必要な短縮では経路全体を確認し、行数だけで改善を認定しない |

## 根拠と効果の限界

合意範囲は[Issue #388](https://github.com/thkt/dotagents/issues/388)（本文更新日時: 2026-10-13T15:53:30Z）を正本とする。Issueの調査基点は`fd28ac54d7d089f494d8d7be7ffe15bb8b5c8092`で、実装開始版`803e79996df30e7cf6065fed7fe9c94c6f4f2deb`の十分性判断、開発方針、担当入力と再照合した。開始版には#386の前提検証と#387の設計理由の入口があるが、それらの手順を置き換えず、#385・#386・#387の実装・完了や未作成参照に依存しない。#180の共有入口と互換性、#362の独立テスト設計・入力分離は既存の経路を使う。

Issueは既存の利用側負担の評価に、利用例を先に置いて構造を導き、実装後も照合する順序と担当への接続を加える理由を明示している。これは現在のAIが設計できないという実測結果ではない。今回、既存の十分性判断やテスト設計とは役割が異なる詳細を共通参照へ置き、両スキルと担当入力から同じ実体へ接続する。過去の作者の意図を現在のコードから補作しない。

外部の発想の出典はIssueにある固定版pstack `11713c683fe4add4fd403ea880580abbc9e0875f`の[architect](https://github.com/cursor/plugins/blob/11713c683fe4add4fd403ea880580abbc9e0875f/pstack/skills/architect/SKILL.md)と関連資料である。ここではIssueで合意した具体化だけを採用し、外部の「利用例が仕様」という扱い、固定例数、複数モデル、常時の候補探索は移植しない。

手順・参照の照合と模擬制御テストは、実モデルが適切な設計を選ぶことや品質・費用の改善を実証しない。効果は実測まで未確認とする。追加比較は必須完了条件にせず、必要な場合だけ[任意eval](../../scripts/README.md#指示変更時の同条件eval)へ戻る。目的・ケース・対象版・モデル・有限上限・送信先・公開範囲を依頼者と確定してから、同じ要求と既存利用で変更前後を比較する。要求の維持、例と設計の整合、失敗・所有、利用側と実装側の負担、不要な工程と手戻りを確認し、この手順の採用だけでモデル実行を開始しない。
