# 知識と判断を読む・残す

ClaudeとCodexで同じ分類と手順を使う。本文は作業対象のGitリポジトリ内に置き、スキルのインストール先や別repoの文書へ集約しない。

形式の基点はdotclaude `3eceb99e555044da5c7b48af080ad21dafc11c5e`のwiki・MADRテンプレートとする。[dotagents #258](https://github.com/thkt/dotagents/issues/258)・[dotclaude #753](https://github.com/thkt/dotclaude/issues/753)の合意で、調査原本を`docs/research/`へ揃え、識別可能な出典を残す。テンプレートの版を変えるときは、両環境の読み方・更新方法・既存文書への影響を照合する。

| 残すもの | 対象repo内の場所 | 更新方法 |
| --- | --- | --- |
| 現在の手順・規約、構造・契約と適用条件 | `docs/wiki/` | 現行コード・合意と照合して書き直す |
| 重要な選択の理由・代替案・結果・見直し条件 | `docs/decisions/` | proposedは改訂できる。accepted以降の本文は保ち、変更は後続DRで置き換える |
| 調査の観測・比較・未採用案と詳しい根拠 | `docs/research/` | 原本と対象版・状態を保ち、wiki・DRから参照する |

要求と許可はIssueと合意記録に置く。README・AGENTS.md・CLAUDE.mdは入口、既存の開発方針は守る条件を案内する。同じ説明を複数箇所で手修正しない。機械利用のために生成する文書は正本と生成コマンドを示す。

## 読む

1. 要求整理または実装を始めるとき、対象repoのwiki・decisionsの入口、作業の用語、変更対象のパスから関連ページを選ぶ。存在しない場合は通常のコード・Issue調査を続ける。
2. wikiの`globs`は対象ファイル、`scenes`は作業場面を示す。場面は`plan`、`implement`、`issue-create`、`pr-create`、`issue-close`を使う。要求整理は`plan`、実装は`implement`として読む。選択用のhelperがない環境では検索と本文確認で選べる。
3. 選んだwikiの適用条件・参照コード・根拠と、関連DRの状態・適用範囲・置換先を現在のIssueとコードへ照合する。過去の結論を別の目的へ無条件に適用しない。原本と対象版が必要なら辿る。未確認事項は推測で埋めない。
4. 実装・修正・独立評価へ必要な同じ参照を渡す。版を固定する場合はrepo相対path・Git blob・開始commitを使う。版一致は内容の正しさや今回の合意を保証しない。

全文書の一律読込みや、文書がないrepoでの作成を開始条件にしない。

## 設計理由の根拠と確度

過去の設計・防御処理・閾値・制約の理由が、今回の変更・維持・削除・要求整理の判断に関係する場合に使う。通常の新規実装や、理由を確認しても判断が変わらない変更には歴史調査を求めない。必要な記録で判断できれば止め、「理由不明」も有効な結論とする。新しいSchema・enum・点数・必須帳票を作らず、すべての区分を毎回出力することも求めない。

### 調べて説明する

1. 問いと対象変更・時期を定める。「なぜ導入されたか」「いつ変更されたか」「現在も必要か」を分け、今回の判断に必要な問いを選ぶ。
2. 対象コードと履歴を対応させ、必要な範囲の差分・blame・log、関連PR・Issue・判断記録を読む。最終編集のcommitを導入時の決定と決めつけず、renameや後日の変更が関係する場合は辿る。
3. 理由を述べた箇所と間接証拠を分け、下表の区別を文章に反映する。コードが現在そう動くこと、テストがその条件を検査すること、作者がその理由で選んだことを混同しない。依頼者の仮説も調査対象として扱い、確認済みの意図へ置換しない。
4. 矛盾・代替説明・欠落を判断へ結び付ける。整った物語にするために片方の資料を捨てず、対象や時期の違い、複数の理由、解消できない点を確認する。後日の回顧はその記録時点の説明として扱い、当時の記録と無条件に同一視しない。
5. 判断に必要な理由・出典・確度・適用条件・不明点だけを、既存のIssueまたは下書き、findings、文書へ残す。過去の理由の調査と、今回選ぶ案の理由・合意を別に記す。会話全文や資料一覧を定型で転記しない。

| 区別 | 根拠と説明のしかた |
| --- | --- |
| 記録に明示された理由 | 理由を述べたPR・Issue・判断記録・コメントなどの出典、対象変更・時期・主体を示す。「当時のPRではXを理由としている」と説明し、その記録だけで唯一の動機や全員の合意まで断定しない |
| 根拠からの推論 | 間接証拠と推論のつながり、他の説明が成り立つ余地を示す。「AとBからXと考えられる」と記し、作者の意図を確認した事実へ置換しない |
| 仮説・推測 | 薄い根拠に基づく可能性として示す。今回の判断に役立つ場合だけ、代替仮説と区別する確認を挙げる |
| 理由不明 | 関係する何を調べ、理由に答える根拠がなかったか、または資料にアクセスできなかったかを示す。未調査の資料まで検索済みや不存在としない |

出典数や多数決を確度の根拠にしない。同じ原資料の転載や要約を、独立した複数の証拠として数えない。理由の記述があること、その理由が事実として正しいこと、チームが合意したこと、現在も適用できることは分けて扱う。記録が見つからないことと、理由が存在しなかったことも区別する。

コードと関連資料で足りる場合は、外部サービスや全情報源へ調査を広げない。権限のある関連資料を必要時に選び、外部への問い合わせ・通知・追加接続をこの手順から自動実行しない。理由の発見やすべての資料の収集を完了条件にしない。

### 現在の判断と更新へつなぐ

設計や防御処理を見直すときは、過去の理由の根拠と確度を保ち、現在の必要性を現行の契約・利用・検証へ照合する。理由の記録がないことだけで不要と判断せず、過去に理由があったことだけで現在も必要と判断しない。新しい変更の理由は今回の選択として記し、過去の意図を補作しない。

今回の根拠で変更を判断できるなら、歴史が完全に解明されるまで完了を待たせない。未確認の理由が要求・許容範囲の判断を左右する場合だけ、具体的な不足と影響する判断を示し、事実不足は調査へ、要求・範囲・権限の変更は人へ戻す。[残す・更新する](#残す更新する)の保全・置換規則を維持し、accepted以降のDR本文へ後付けの理由を書き込まない。必要なら今回の根拠と選択を後続DRへ残す。

### 独立評価と公開説明へ渡す

初回実装・追加修正・既存PR修正は同じ手順を使い、既存のfindingsと参照経路で独立評価へ渡す。独立評価は設計理由の主張を、出典の内容・対象版・時期・主体と説明の断定の強さへ独立して照合する。推論を明示的な理由へ格上げした説明、矛盾の隠蔽、合意の捏造は具体的な指摘へ戻す。不明という結論自体は欠陥にせず、今回の判断に必要な不足かを区別する。

公開用のassessments・documentsのreason・指摘への回答へ要約するときも、出典と推論、条件、否定、合意状態、未確認事項を保つ。理由の確度を内部findingsだけに残して、公開本文では断定する形にしない。Issue固有の残る条件は既存のhandoffへ渡す。テストの期待値は合意済みIssue・仕様から独立して決め、歴史的な意図の推論や実装担当の説明を新しい要求としてテスト担当へ渡さない。

### 代表例で照合する

以下はコード・資料・指示の意味を照合する例であり、全例の新規テスト・本物の外部サービス・作者への問い合わせを求めない。

| 例 | 必要な根拠・説明と調査の終了条件・戻り先 |
| --- | --- |
| 導入時PRに「上流の制限への対応」と明記 | PRの対象変更・導入時期・主体を確認し、その記録の理由として引用する。現在も制限があるかは現行契約・利用・検証で別に判断し、必要な根拠が揃えば止める |
| テスト名とコードから性能目的に見えるが理由の記述がない | 間接証拠と推論、別の説明の余地を示し、作者が性能のために選んだと断定しない。推論で今回の判断に足りるなら止め、必要な事実が不足する場合だけ調査へ戻す |
| 防御処理の理由が見つからない | 調べた関連資料と不足・アクセス不能を示す。理由不明を不要・削除可能という結論にしない。現在の必要性を確認し、要求・許容範囲を左右する不足だけ人の判断へ戻す |
| IssueとPRで理由が異なり、後日の説明もある | 両方の内容・対象・時期・主体を保持し、回顧と当時の記録を区別する。解消できない点が今回の判断に影響しなければ残して止め、影響する事実不足は調査へ戻す |
| 同じPRを複数資料が引用し、履歴の最終編集だけが見える | 独立した証拠数を水増しせず、最終編集と導入時の判断を区別する。必要ならrenameや導入差分を辿り、見えていない履歴を確認済みにしない |
| 当時の理由は不明だが現行契約と要求で変更を判断できる | 今回の選択理由を現在の根拠から説明して止める。過去の意図を補作せず、不要な歴史調査を続けない |
| 公開説明への要約、acceptedのDRの見直し | 推論・否定・未確認を要約で落とさない。原記録本文へ理由を後付けせず、必要なら既存規則に従う後続DRへつなぐ。説明の欠陥は既存の独立評価・修正へ戻す |

[Issue #387](https://github.com/thkt/dotagents/issues/387)の合意に基づく具体化であり、#385の機械化や#386の前提の実行検証を完了条件にしない。手順・参照の照合と模擬制御テストは、実モデルの歴史調査・分類の正しさや、誤説明・費用の改善を実証しない。効果は実測するまで未確認とする。追加比較は必須にせず、必要な場合だけ[任意eval](../../scripts/README.md#指示変更時の同条件eval)へ戻り、目的・ケース・対象版・モデル・有限上限・送信先・公開範囲を依頼者と確定してから実行する。同じ資料で変更前後を比べ、意図の捏造、推論の格上げ、矛盾の見落とし、不要な探索、失敗・再試行を含む負担を確認し、正誤ラベルや他条件の回答を担当へ渡さない。

## 残す・更新する

要求整理で判断が固まったときと、実装差分が揃ったときに、次の作業でも使う説明と既存ページへの影響を確認する。必要な更新を既存の独立評価へ含める。毎回新規ページを作らず、既存ページを更新するか、残す内容がなければ更新しない。

- wikiは[テンプレート](../templates/wiki.md)の共通項または構造ページを使い、現在も有効な手順・条件を書く。未検証の効果や単発の推奨を現行ルールに変えない。候補は原本または既存の`_candidates.md`に状態付きで残す。scribeの自動抽出は別途その昇格条件に従う。
- DRは[テンプレート](../templates/decision.md)を使う。後で変える費用がある、文脈なしでは理由が分からない、実際の代替案とのトレードオフがある、の三条件が揃う選択を記録する。軽微な判断はIssue・PRの説明で足りる。
- DRは`proposed`、`accepted`、`rejected`、`deprecated`、`superseded by DR-NNNN`を区別する。合意や採用の出典を確認できないものをacceptedにしない。accepted以降を変更するときは後続DRを作り、元DRのstatusとdateだけを更新する。
- wikiの「由来」は、そのDRが置換されたら本文の変更が必要になる場合だけ張る。DRを置換するときは、由来に持つwikiの本文も照合する。
- 根拠はIssue・PRのURL、または原本を特定できるrepo相対パスと必要な版で示す。研究をすべて`(research)`へ匿名化しない。旧記録の原本が不明なら不明と書き、出典や独立した根拠数を捏造しない。
- 原本の観測日、対象版、条件、却下・保留・未確認を保持する。別repoを題材にした資料はその範囲を明記し、自動で別repoへ移さない。

保存・commit・公開・採用を区別する。未追跡資料、会話全文、生ログ、秘密情報を一括公開しない。既存の要求・権限、検証、公開手順に従う。
