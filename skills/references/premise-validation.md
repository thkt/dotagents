# 変更の安全性を支える前提の検証

## 適用する場面

未確認の前提が崩れると、今回の変更の安全性・要求充足・修正方針が変わる場合に使う。修正が停滞し、共通する前提を見直す必要がある場合も含む。全変更への追加調査・実験・報告や全repoの監査は求めない。既存の契約・型・検証が同じ対象版と条件を保証するなら、その証拠を再利用して止める。

scopingでは[十分性の判断](../scoping/references/sufficiency.md)と[小さな実験](../scoping/references/experiment.md)へ、implementでは[検証命題とケースの設計手順](../implement/references/testing.md#検証命題とケースの設計手順)と既存の独立評価・停止経路へ接続する。正常対照や条件付きの別入力・操作順は既存手順を再利用し、新しい必須工程を設けない。

## 前提と証拠を照合する

1. 変更後の振る舞いと守る結果を特定する。「何が成り立つから安全か」を問い、前提が崩れた場合に影響する結果・副作用・利用者を確かめる。前提の数や調査項目は固定しない。
2. 前提の出典・対象版・成立条件を確かめる。必要な範囲で依存の固定版、実際の導入物とlocal patch、入力・状態・設定、観測時点、利用側の契約を追う。直接の呼出元の検索だけで足りなければ、依存実装、ライフサイクル・非同期順序、API・JSON・DB・wire形式、別言語・設定を介した利用を調べる。一般的なドキュメントの説明を導入版の保証へ読み替えない。
3. 既存証拠が今回の条件を扱うか判断する。契約・型・実装経路・保存済み結果で十分なら追加しない。直接の参照が見つからないことだけで、利用者や問題経路の不在を証明しない。
4. 不足に対応する最小の確認を選ぶ。対象版の実コードを呼ぶ小さな再現や、必要な正常対照・入力・状態・操作順で仮説を区別する。外部環境・永続化・実アプリへの接続が必要な問いは模擬応答だけで保証しない。対象処理へ到達しない結果、異なる版・環境、取得不能は未確認として扱い、無関係な環境・ビルド失敗を反証にしない。
5. 結論と適用限界を残す。支持する根拠、否定する観測、問題経路を除いた変更、未確認事項を区別し、影響する判断と次の確認・戻り先を示す。要求の変更は人へ戻し、過去の評価・旧runを改変しない。

判断に足る根拠が得られたら止める。証拠の取得不能と前提が偽であることを区別し、単回の成功や非再現を全順序・全環境へ一般化しない。

## 証拠の性質と限界

| 証拠 | 確認できることと限界 |
| --- | --- |
| 説明・主張 | 調べる前提の候補。もっともらしさやモデルの自信だけでは成立の根拠にならない |
| 対象版の契約・実装 | 対象コードが保証する条件。実際の導入物・設定・呼出経路との一致を確かめる |
| 問題経路の除去・到達不能の根拠 | 追跡した条件で問題が起きない理由。前提そのものの成立や未調査の利用者の安全性とは区別する |
| 対象版の実コードによる再現 | 実行した入力・状態・順序での結果。単回の成功や非再現では他の順序・環境まで保証しない |
| 実アプリ・実環境の観測 | 接続した実体と条件での振る舞い。起動成功だけでは必要な操作・結果の確認にならない |

この表は一律の順位や、全案件で実アプリ観測まで進む要求ではない。問いに必要な証拠を選ぶ。check成功、検索で利用者が見つからないこと、再現失敗だけでは前提成立を証明しない。

## 修正が停滞した場合

同じ前提の下で修正・前提作業が進まない場合は、最新の原記録と稼働状態を確認し、既存の評価記録・過去の修正結果・現在の成果物を比較する。コードの欠陥、実行環境の制約、要求・権限の不整合を区別し、原因が未確定の部分と、修正で除いた問題経路を分ける。複数の修正に共通する前提と、それを否定・支持する観測を明示し、対立する仮説で結果が異なる確認から次の修正を選ぶ。同じ修正を言い換えて繰り返さない。

原因仮説だけでなく、要求・完了条件・実行手順が衝突していないかも見直す。[scopingの判断](../scoping/SKILL.md#判断)で今回の完了を妨げる問題と別の改善を分け、前提修正が必要な完了条件と、既存機能・既存権限内の操作・小さな修正を照合する。復帰入口が対象外の場合は、[implementの停止原因と続行方法](../implement/SKILL.md#停止原因と続行方法)へ戻る。要求・優先順位の変更が必要なら、影響する判断と具体案を人へ示す。

失敗が続いたことだけで前提を誤りと断定しない。新しい根拠が得られなければ、未確認事項と次に必要な調査・判断を残す。固定の失敗回数による工程移動、新しい必須会議・帳票、全課題での担当別集計・役割変更は加えない。並行処理や役割の偏りが今回の原因仮説に関係する場合だけ、その観測を選ぶ。

## 担当と戻り先

scopingは判断に関係する前提・根拠・適用条件・未確認事項を、既存のIssueまたは下書きへ反映する。implementは確認結果と適用限界をfindingsへ残す。毎回の前提一覧表や独立した帳票は作らない。

独立評価は、実装担当の主張を追認せず、現在の差分・対象版・成立条件・証拠へ独立して照合する。上表の証拠を区別し、今回の安全性・要求充足に必要な保証へ足りるか判断する。既存証拠で足りる判断も認め、あらゆる未確認を必須修正にしない。判断を妨げる不足や矛盾は、影響と具体的な確認・戻り先を既存の指摘へ記し、関係するassessmentsとhandoffへ渡す。

小さな再現も成果物の性質と権限に応じて既存担当へ割り当てる。テスト・fixture・検証接続定義は[独立テストセッション](../../scripts/README.md#テスト作成の独立セッション)へ戻す。必要条件と判定根拠は合意済みIssue・仕様から独立して判断し、実装担当の原因仮説・会話・自己評価を期待値の正本へ渡さない。評価担当のread-only権限と成果物保護は維持する。

通常check・captureの実行だけが残る場合と、それでは実行されない受入検証を区別する。追加の実環境検証は既存権限で[ホスト検証後の再評価](../../scripts/README.md#ホスト検証後の再評価)へ、要求・範囲・権限・実行上限の変更は人へ戻す。実行不能や未実行を成功へ読み替えず、旧記録を保全する。この手順を例外許可にしない。

## 代表例での照合

以下は手順の適用例であり、全例の新規テスト・実アプリ観測を求めない。

| 例 | 必要な証拠・省略理由・未確認事項と戻り先 |
| --- | --- |
| 中断後は完了通知が届かないとして防御処理を削除 | 導入版の中断・通知契約と実コードを確認する。不足する場合だけ中断前後の順序を変えて観測する。単回の通知なしやモックの非再現は全順序の保証にしない。再現資産は独立テスト、実環境は必要に応じてホストへ戻す |
| 型名・プロパティ名の変更で参照検索に利用者がない | 関係するAPI・JSON・DB・wire形式、別言語・設定を追う。既存契約が同じ境界を保証すれば再利用する。検索だけで互換性を保証せず、未知の利用が要求・範囲を変えるなら人へ戻す |
| 契約・型・既存検証が同じ対象版と条件を保証する | 出典と適用条件を確認して再利用し、新しい再現や報告を要求しない。条件の一致が未確認なら、その不足に対応する確認だけを選ぶ |
| 問題経路を削除して前提への依存をなくす | 対象経路の除去と必要な正常動作の維持を確認する。「前提が真」と「前提に依存しない」を区別する。未調査の利用者へ一般化せず、正常動作の検証不足は独立テストへ戻す |
| 同じ原因仮説で修正が効かない | 共通前提と対立する仮説を区別できる観測から次の修正を選ぶ。失敗回数だけで誤りと断定しない。新しい根拠が得られなければ必要な調査・判断へ戻す |
| 対象処理へ未到達、異なる環境・版、証拠が取得不能 | 未確認として不足を示す。必要な独立テスト・ホスト検証へ、要求や権限の変更は人へ戻す。非該当や成功へ落とさない |

## 根拠と効果の限界

[Issue #386](https://github.com/thkt/dotagents/issues/386)の前提検証と、[Issue #436](https://github.com/thkt/dotagents/issues/436)の完了範囲・停滞時の判断順序の合意に基づく。#385の機械化や未作成参照に依存せず、#350の現行の正常対照・条件付き検証と#362の設計・選定手順を再利用する。関連Issueの未採用提案を要求へ加えない。

手順・参照の照合と模擬制御テストは、実モデルの前提発見、見落とし・誤指摘・時間・使用量の改善を実証しない。効果は実測するまで未確認とする。追加比較は必須にせず、必要な場合だけ[任意eval](../../scripts/README.md#指示変更時の同条件eval)や[review-probe](../../scripts/README.md#実モデルによるレビューの確認)へ戻り、目的・ケース・対象版・モデルと設定・有限の上限・送信先・公開範囲を依頼者と確定してから実行する。
