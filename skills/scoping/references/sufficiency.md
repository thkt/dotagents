# 十分性の判断

次に何を決めるかを先に特定し、六つの問いで必要な根拠と不足を判断する。調査開始と実装開始に同じ情報量を要求しない。

| 観点 | 問い |
| --- | --- |
| 目的 | 誰の何を改善し、次の判断と達成した状態を説明できるか |
| 根拠 | 出典・対象版・鮮度・適用範囲を確認できるか |
| 制約・代替案 | 判断を左右する制約・依存・代替案を確認したか。既存部品・標準API・導入済みライブラリ・実装例の再利用と不足分を検討したか |
| 不確実さ | 未確認事項で次の判断が変わり得ないか。影響しないとする根拠があるか |
| 整合 | 要求・事実・方針・合意の矛盾を解消したか |
| 権限 | 次の作業に必要な対象・範囲の合意と権限があるか |

全項目の回答を別の帳票へ保存する必要はない。未確認を充足に含めず、今回に関係しないと判断する場合も理由を説明できるようにする。点数の合算で重大な不足を相殺しない。

現行実装・出典・合意を参照し、その情報が今回の判断にどう寄与するかを説明する。LLMの自信、資料数や検索回数は根拠ではない。判断を左右する不足や根拠変更があれば依存作業を止め、影響する判断と解消方法・再開条件をIssueまたは下書きへ必要な範囲で残す。調査や回答で不足を解消してから再評価する。書式を埋めたことや保存成功は進行許可にならない。

## 観測で解消できる不明点

既存の資料・コード・ログ・テストで判断できず、観測結果によって次の方針が変わる場合に限り、小さな実験・試作・再現を選ぶ。既存の根拠で足りる場合は追加実験を求めない。目的・好み・許容範囲・権限は人が決めるものであり、観測した事実と区別する。

実験を選ぶときは、決めることと、仮説ごとにどの結果なら支持・除外できるかを観測前に明らかにする。出力、処理の順序、操作後の状態など、結果を区別できる観測を選び、「動いた」だけで問いに答えたとしない。既存ログやコードから始められる調査は進め、安定した再現の完成や固定数の仮説を調査の前提にしない。

問いを確かめる最小の試作を、本番コードから分離した一時領域で扱う。状態や概念の境界を確かめる場合は、自由に操作する入口、同じ操作順を辿れる例、操作後の状態表示を組み合わせる方法もある。画面の完成度ではなく、どの曖昧さが解け、判断がどう変わったかを見る。HTML化や複数のUI案を一律に求めない。

観測対象の版・環境・入力と、その観測で分かること・分からないことを明らかにする。実際の並行実行・中断・外部状態・永続化が問いなら、それを観測できる環境を選ぶ。インメモリの試作や模擬応答の成功を実システムの保証へ一般化しない。

技術的に実験できても、未許可の外部操作や本番への書込みを行う根拠にはならない。必要な権限が未確定なら、その操作は止め、選択肢と影響を人へ返す。未確定の権限に依存しない調査は続ける。許可された環境では問いに答えられない場合も、観測の限界と残る判断を示し、実験結果を合意の代わりにしない。

判断に十分な根拠が得られたら止める。実験の網羅性や一定数の比較案を目的にしない。結果を区別できなければ未確認として扱い、次の調査で区別できるかを見直す。新しい根拠が得られない試行を繰り返さず、残る不足と次に必要な判断を示す。

結論と判断に必要な証拠・適用限界を既存のIssue下書きへ反映し、必要な根拠だけを[保存と改訂の手順](session.md#保存と改訂)でresearchへ残す。観測した事実、提案、人が合意した範囲を区別する。試作コードは実装成果物や合意済み仕様として渡さず、試作の成功を本実装・採用の完了とは扱わない。[scopingの合意とIssueへの反映](../SKILL.md#issueへの反映)へ戻り、合意済みIssueと必要な根拠から既存の実装入口へつなぐ。

## UI実装に必要なコンテキスト

デザインシステム、Storybook、既存画面、関連テストを探し、今回利用する部品と状態を選ぶ。Storybookの存在自体を必須条件や合意の証拠にはしない。

| 観点 | 確認する内容 |
| --- | --- |
| 対象と対応 | Story・部品・デザイントークンが今回使う実装版に対応するか。試作や廃止予定の例ではないか |
| 適用と合意 | 今回の利用場面が部品の適用範囲に含まれ、利用方針の合意に辿れるか |
| 状態と操作 | 要求に関係する通常・空・エラー・読み込み等の状態、キーボード・フォーカス・画面幅の扱いが分かるか |
| 組み合わせ | 単体部品の既知の挙動に加え、今回の配置・データ・遷移で何を確認する必要があるか |
| 証拠 | 部品の既存検証をどこまで再利用でき、画面接続のE2E・画像・動画で何を追加確認するか |

適用できるStorybookと合意済み部品が揃えば、既知の見た目や挙動を再設計せず、今回の組み合わせと差分に集中する。これはブレを減らすための方針であり、減少量や品質を自動的に保証しない。

Storybookがなくても、現行の部品・テスト・仕様・承認された画面例で必要な判断ができれば進める。見た目しか分からず操作仕様が判断を左右する場合は、その不足を解消する。根拠が足りなければUI案を具体化して合意を得る。Storybookの新設を毎回の前提にしない。

## ロジック実装に必要なコンテキスト

「ベストプラクティス」という評価語だけで採用せず、具体的な実装例・方針・公式文書と、今回に適用する理由を示す。

| 観点 | 確認する内容 |
| --- | --- |
| 入出力と境界 | 型だけでなく、必要な値の制約、失敗、非同期処理、責任の所在が分かるか |
| 適切な見本 | 近いユースケースの現行実装・テストがあり、その設計理由と今回との差が分かるか |
| ライブラリの使い方 | lockfile等で導入版を特定し、対応する公式文書・型・実装で推奨APIと制約を確認できるか |
| リポジトリの方針 | エラー処理、依存の向き、責任分担など今回に関係する規則が分かるか |
| 検証方法 | 期待する結果と失敗条件を、実装の記述方法に依存せず確かめられるか |

既存コードは現状の根拠にはなるが、適切な見本とは限らない。重複、非推奨API、根拠のない型アサーション等をそのまま模倣しない。公式文書も製品の要求やチームの合意を決めるものではない。矛盾する場合は差と影響を調べ、重要な方針変更が必要なら判断を求める。

今回の処理に無関係な設計原則や全ライブラリの文書を読み込ませない。適用する見本・根拠・差分を選び、レビューでも同じ参照を使えるようにする。

## 基準の調整

基準はリポジトリのレビュー可能な変更として管理する。必要な問い・適用条件・判断例を更新し、理由と見逃し・過剰停止への影響をPRで説明する。実行担当が通過するために緩めない。

進めた後の情報不足による手戻りと、止めたが確認不要だった例、評価者間で判断が割れた例から調整する。進行中の判断に影響する変更があれば依存作業を保留し、合意した要求と現在の根拠に照らして再評価する。過去の完了表示を新しい判断の充足として再利用しない。

十分性と根拠の鮮度は担当AIが判断し、重要な判断と権限は人へ戻す。機械が全項目の入力や評価版の一致を確認する保証はない。
