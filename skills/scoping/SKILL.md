# 要求と実装範囲の整理

次の判断に必要な根拠を揃え、不足する作業を止め、合意した範囲をIssueへ引き継ぐ。固定の工程列ではなく、今回の判断に必要な仕事だけ行う。

## 進行と完了

要求整理の開始から、合意した要求・完了条件・検証方法をIssueへ反映するまで作業を続ける。調査・評価・保存・Issue更新の区切りでは進捗を伝え、続行指示を求めず次の必要な仕事へ進む。完了時にIssueと合意範囲を報告する。成果物Issueは実装待ちとして残す。

質問機能で提示した後は回答を待つ。非同期の質問機能では、利用可能な待機手段で回答を待ち、回答待ちを最終応答で閉じない。受領後は決定の記録・再評価・次の作業へ続ける。受付成功は表示や回答の証拠ではない。未回答・取消は未決定として扱い、表示できない場合はチャット本文の回答も受け取る。ユーザーの停止・方向変更に応じ、実行不能なら障害と再開に必要な条件を伝える。

## 開始・再開

依頼本文と対象リポジトリを受け取る。対象の指定がなければ現在のリポジトリを使い、元の依頼がなければ何を実現したいかを質問する。既存Issueや設計案が指定されていれば先に読み、合意済みのことを聞き直さない。対象repoのREADME・開発方針・適用される指示を確認する。小さな変更と文書変更もIssueへ引き継ぐ。

[保存・評価CLIの手順](references/session.md)に従い、対象repo、checkout外のcontextDir、referencePaths、基準、元の依頼で開始する。既存セッションでは最初にstatusを読み、依頼・対象・決定事項・未解決事項を確認する。開始した基準を実行途中で置き換えない。

[十分性の判断](references/sufficiency.md)と、セッションに保存された基準を使う。UI・ロジックの具体的な観点は必要な部分だけ読む。資料の存在やモデルの自信を充足の根拠にしない。

## 調査と方針の整理

1. 誰の何を改善するか、次に何を決めるか、その判断を変え得る不明点を明示する。
2. referencePathsとcontextDir/researchから関連する根拠を選ぶ。現在のコード・テスト・依存版・合意と照合する。過去の結論を無条件に採用せず、外部資料は必要な範囲で確認する。
3. 既存部品・標準API・導入済みライブラリ・適切な実装例で目的を満たせるかを調べる。今回への適用条件と不足分を示す。自前実装を選ぶなら既存機能で満たせない理由を説明する。導入・適応・保守の複雑さを含めて判断する。
4. 確認した事実・推測・提案・合意を区別し、出典、対象版や確認日、適用範囲、未確認事項をnoteへ保存する。調査量を増やすことを目的にしない。
5. 目的に対する最小の解決案と、観測できる完了条件、対象外、既存検証と追加検証を整理する。事実不足なら調査へ戻り、重要な選択や権限は人の判断を求める。

## 不足・質問・再評価

人の判断が必要なら、Codexの利用可能な質問機能で、質問と選択肢をチャットへ提示する。回答待ちでは依存する作業を進めず、独立した調査は続けられる。回答を捏造・補完せず、回答の受領を要求全体や実装の合意へ読み替えない。答えが不十分なら不足を具体化して確認する。

質問・回答を専用ファイルへ逐一転記しない。方針が決まった区切りで、[開発方針](../../DEVELOPMENT.md#対話と方針の決定)に従って決定を記録する。セッションには正本への参照と次の判断に必要な根拠・未解決事項をnoteに残し、Issueや文書の全文を複製しない。

次の判断や引き継ぎの前にstatusを読み、現在のrevisionに対して全基準を評価してassessで保存する。不足にはその影響、止める作業、解消方法・再開条件をnextへ具体的に記す。評価後に判断を変える回答・根拠が増えたらnoteで旧評価を無効にし、再評価する。

次の判断へ進む直前にgateを実行し、非zeroなら依存作業を止める。gate成功は保存済みの十分性評価を表すだけで、人の合意・実装の許可・要求達成の保証ではない。質問の提示・回答の確認や実装入口の制御をCLIが強制するものではない。

## 蓄積と引き継ぎ

調査が完了したら、問い・根拠・結論・残る制約を簡潔なMarkdownへまとめ、[日本語確認の方針](../../DEVELOPMENT.md#issuepr文書の日本語確認)に従ってGeminiによる確認・修正と意味の照合を終え、評価を経てarchiveで保存する。ユーザーから保存依頼を受けるまで待たない。既存記録と重なる場合は参照を使い、不要な全文複製を避ける。自動公開はしない。

要求の正本はIssueと合意記録とする。提案を合意済みとして渡さず、誰がどの対象・範囲を合意したかへ辿れるようにする。合意済み資産で再利用する条件と、今回固有の条件を分ける。実験の回数・計測手順は成果物要求へ混ぜない。

要求の抜け・矛盾・判断の偏りを確認する必要がある場合は独立評価を使い、未実施なら未実施と記録する。実装に必要な要求・完了条件・検証方法と合意が揃うまで、次の判断に必要な仕事を進める。同じ調査・質問で新しい根拠や判断が得られない場合は、障害・確認済みのこと・必要な判断を示して相談する。CLI自身は評価モデルを起動しない。今回のCLIからIssue作成や実装CLI起動は行わず、対象・合意・実行条件を照合した担当者が既存の運用へ引き継ぐ。

## Issueへの反映

合意した要求をIssueへ反映する際に実行する。要求整理・Issue作成の依頼はその範囲での公開を含むが、「案だけ」「公開しない」などの指定があれば、本文をリポジトリ内の設計・計画文書として残して終了する。スキルの自動選択だけを公開許可とせず、依頼と既存の許可範囲に従う。

1. [対象repoの設定](../../scripts/README.md#対象repoの設定)を照合し、信頼するスキル実体から解決した `scripts/target.ts CHECKOUT [ISSUE_URL] --write` をBunで実行する。checkout・設定のrepo・fetch/push remote・base branch・ghの主体と権限を確認し、不一致や未設定は公開前に解消する。`gh api user` の主体がIssue作成・更新を行う。Issue URLのrepoを数字だけへ変換して別repoへ流用しない。`gh issue list --repo OWNER/REPO --state all --search '関連語'`と候補の本文で重複を調べる。指定されたIssueは`gh issue view NUMBER --repo OWNER/REPO --json title,body,state,url`で読む。
2. 目的、今回の範囲、完了条件、対象repo固有のセットアップ・検証方法・必要媒体と保存先、合意の根拠を、リポジトリ内のMarkdown本文へまとめる。実装方法の細部や試行管理の条件を要求へ混ぜず、未合意事項を合意済みと書かない。
3. [日本語確認CLI](../../scripts/README.md#日本語の確認と修正)で本文案と合意・根拠を渡す。Geminiの修正候補は意味の確認を通してから公開する。利用不能でスキップした場合は原文を通常の要求・合意確認に通し、未実施の理由を報告する。それ以外の失敗時は原文・候補・停止理由を残し、公開しない。
4. 公開直前にも対象とghの主体・権限を再照合する。Issueと後続のimplementによるPRは、確認したユーザーのgh認証で作成する。新規なら`gh issue create --repo OWNER/REPO --title '要求を表すタイトル' --body-file PATH`で作成する。既存Issueの更新が依頼範囲なら最新本文を読み、既存の要求・他担当の内容を保持して`gh issue edit NUMBER --repo OWNER/REPO --body-file PATH`で反映する。重複候補の範囲が異なる場合は勝手に統合しない。
5. 返されたIssueを`gh issue view`で読み、対象repo・本文・URLを確認する。通信断などで作成結果が不明なら一覧と本文を照合してから再試行し、重複作成しない。権限不足の場合は本文を保持して、必要な対応を伝える。
6. セッションのnoteへIssueの参照と今回の決定を残し、再評価・調査保存を終え、Issue URLと合意範囲を報告する。商品実装や実装CLIの起動はこの呼び出しに含めない。
