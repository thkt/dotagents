# 今回必要なテストを選ぶ

[共通のテスト方針](../../../docs/wiki/development-policy.md#実装とテストの整理)と対象repoの方針に従います。この資料は、[Issue #362](https://github.com/thkt/dotagents/issues/362)で合意した設計・選定手順の正本です。初回実装、追加修正、既存PR修正で影響するテストに適用します。作成・更新は[独立セッションの経路](../../../scripts/README.md#テスト作成の独立セッション)で行い、実装側の説明から期待値を作りません。

まず次の手順で必要な保証とケースを照合し、変更が該当する失敗条件を持つ場合にだけ後半の例を使います。既存検証で十分なら追加せず、正常な対照と狙った失敗を必要な最小の層で確認します。

## 検証命題とケースの設計手順

### 1. 観点と検証する性質を分ける

観点は検証を探す分類、命題は成立を確かめたい性質、ケースは具体的な入力・操作・期待結果です。「異常系」という分類名だけでは保証もケースの十分性も説明できません。今回の要求・リスク・変更に関係する軸だけを選びます。

| 分類軸 | 選ぶ内容の例 |
| --- | --- |
| 品質特性 | 正確性、信頼性、性能、セキュリティ、使いやすさなど要求に関係する性質 |
| 対象 | 関数、API、画面、データ、外部接続、業務フロー |
| 条件 | 正常・異常、入力、権限、状態、環境、負荷、時間 |
| 検証アングル | 境界、状態遷移、順序、並行実行、再試行、復旧、条件間の相互作用 |
| 方法・レベル | 同値分割、境界値分析、状態遷移、組合せ、探索などの方法と、単体・結合・システムなどの実行範囲 |

全分類の入力、全直積、固定ケース数は求めません。境界の何点、どの遷移、何因子の相互作用が必要かは、要求・対象repoの方針・既存検証から定めます。既存の必須検証を同値性や費用を理由に省略しません。特に[UI変更時の幅掃引](#ui変更時の幅掃引)の適用条件と1px刻みを維持します。

### 2. ドメイン知識から命題と必要条件を定める

合意済みIssueと必要な仕様を起点に、業務ルール・不変条件、状態と禁止遷移、データ整合性、システム境界、障害・運用条件、過去の欠陥を今回の変更へ照合します。出典・対象版・適用条件を残し、確認済みの制約と仮定を区別します。

検証する単位は、命題と必要条件・判定基準の組です。「重複した振込を実行しない」なら、再試行・並行要求・障害後の復旧のうち今回必要な条件まで特定します。同じ命題でも条件が違えば同じケースで守れるとは扱いません。必要条件が不明な箇所は未確認とし、判断への影響を残します。要求の漏れや矛盾は事実を調べ、要求・許容範囲の変更が必要なら人へ戻します。

### 3. ケースと判定根拠を対応させる

既存検証を含む候補について、入力・前提状態・操作と、要求から実装とは独立に定めた期待結果を対応させます。返却値・表示だけでなく、必要な保存状態、副作用の発生・抑止、停止理由、データ保全、観測時点を確認します。実装の出力やモックに設定した返答を、そのまま期待値の根拠にしません。

正常な対照が対象へ到達し、想定する誤動作を区別できるかを確かめます。対象外の不正入力や環境・ビルド失敗で先に遮られたケースは、狙った条件の検証に数えません。不具合再現では修正前の狙った失敗と正常対照、実装後の同じ条件での成功を区別します。検出力を判断できない箇所だけ、既存方針に従って一時コピーへの不具合注入などを検討します。

### 4. 採用・維持・統合・省略を選ぶ

小規模な変更は文章や小さな表で、命題・必要条件とケースの対応を説明すれば十分です。分類表・対応行列・テストごとの台帳を一律に求めません。

採用・維持は守る保証と既存検証との差を、統合・省略・削除は代替ケースが守る条件と失う検出条件を根拠にします。入力や名前の類似、仕様上の同値クラスだけで欠陥検出能力も同じとは断定しません。リスクを受け入れて未検証にする判断と、既存ケースで検証済みという判断を分けます。必要な許容範囲を変更する判断は人へ戻します。

実行・準備・保守の費用、不安定さを保証と比較し、見積りと実測を区別します。整理では実装・テスト・文書・実行時間を同じ条件で比較し、行の圧縮やファイル移動を改善に数えません。安心感・件数・カバレッジ数値だけを維持理由にしません。失敗条件のない文書整理や既存検証で十分な変更は、テスト追加・分類表・数式化が不要と判断できます。

### 5. 独立評価と実行証拠へ渡す

独立テスト担当は設計・選定理由、失う検出条件、残る検証と未確認の限界を既存の`findings`へ残します。実装・修正担当は不一致をIssueへ照合し、不足・誤りや機械的な接続変更も別のテストセッションへ戻します。新実装の説明・会話・自己評価を期待値の根拠に渡さない入力境界を維持します。

独立評価は担当者の対応関係や省略理由を追認せず、要求・必要条件・実際のケースへ照合します。未検証の条件、観測の不足、根拠のない同値性、誤った期待値は、既存の指摘と修正ループへ戻します。妥当な削除やテスト不要の判断も評価します。

設計上の被覆と、対象版・環境・入力に対応する実行を分け、成功・失敗・未実行・実行不能を区別します。既存のrun記録から入力・成果物・実行結果を辿り、`assessments.tests`とPR説明、Issue固有の残る条件は`handoff`へ接続します。探索や失敗で新しい命題・条件が見つかれば設計・選定を見直します。形式の充足やcheck成功だけで意味上の十分性を認定しません。

## dotagentsの制御テストの置き場所

対象repoがdotagentsのとき、`scripts/tests`のテストは`quality`・`assurance`の2分類に置きます。ケースが前提にする状況と保証を読み、中断・環境障害・後始末やrepo全体の整合をassuranceに分け、ほかの要求・契約はqualityにします。異常系、速さ、import先、実Git・子プロセスの使用だけでは分類しません。基準・例・分割の条件は[開発方針](../../../docs/wiki/development-policy.md#制御テストの階層)を正本とします。他の対象repoでは、そのrepoの方針に従います。

共有support・fixtures・runnerは分類外に置き、各分類の下を従来の責務別ディレクトリに分けます。分類外や未知の分類はassuranceの構造検査で拒否します。移動・分割時は、既存の検証命題・正常対照・検出を削らず、前後のケースと実行結果を照合します。移行前のファイル数を固定件数にしません。

通常のAI実装ではlint・型検査等と`bun run test:affected`を実行します。これは品質候補の関連実行であり、固定feedback集合はありません。安心テストやその検証対象の修正では該当安心テストを直接実行し、品質内の影響先が不明なら品質全件、安心への影響を判断できなければ全体checkへ広げます。提出前・CIは引数なしの`bun run check`です。選択漏れ、古い記録の退避・再生成は[CLIガイド](../../../scripts/README.md#変更に影響されるテストだけを実行する)に従います。記録を作り直しても未実行分岐の依存までは保証しません。

### 差分変異で検出を確かめる

dotagentsでは`bun run mutate:diff`で、変更差分を品質全件が検出するかを任意に調べられます。通常feedback実行やCIへは追加せず、固定集合の認定には使いません。使い方は[CLIガイド](../../../scripts/README.md#制御テストの選択と計時)を参照してください。

実行した場合は報告を既存の`findings`へ渡します。独立テスト担当は生き残った変異と変異を作れなかった差分を読み、要求に基づく追加、等価と判断する理由、範囲外とする理由と残る検証を記します。テストの作成・変更は既存の独立テスト経路へ戻します。

報告は検出・生き残り・不安定・作れなかった差分を区別します。実行0件の生き残り0件を検出できる結果として扱いません。品質全件だけを実行するため、旧`--quality`は互換指定として受理し、同じ集合を二段階で追試しません。共通check・CIの成否とマージの判断を変えず、スコア・台帳・除外リストは保存しません。

## 選定を照合する例

以下は設計判断の例であり、架空の業務実装や全例のテスト追加を求めるものではありません。後半の失敗条件の例と併せ、今回必要な条件・期待結果の根拠・未確認事項を照合します。

| 例 | 守る条件と選定根拠 | 未充足・未確認を判断する点 |
| --- | --- | --- |
| 18歳以上で登録可能 | 17歳の拒否と18歳の許可だけでは誤った`age === 18`も通る。19歳や30歳の許可はその誤りを区別する | 境界直上の確認が必要なら30歳は19歳の代替にならない。必要な境界は要求から定める |
| 外部入力の形と対象ID | 形の拒否と対象ID照合は別の保証。他項目を正常にして欠落・余分な項目・ID違いを個別に与える | 別の不正項目で先に拒否されたケースをID照合の検証に数えない |
| 純粋な入力判定と停止・保全 | 関数テストは解析の拒否を守る。実際の入口・保存状態・後続抑止は結合テストで守る | 例外だけでは停止理由・記録保全・副作用の抑止を確認できず、両層を類似だけで統合しない |
| 同じ対象の異なる版・観測時点 | 同じ版での成功再利用と、成功後の対象変更による停止・state保全を区別する | 名前・入力の類似だけで古い成功の流用抑止を削除しない。対象版と観測時点を証拠へ照合する |
| 必須条件にケースがない、対応の根拠が不明 | 前者は未充足、後者は未確認。候補・根拠・環境を補うか既存の停止・判断経路へ戻す | 必要条件を削ったり、未確認の対応を検証済みとして算入したりしない |
| 既存検証で十分な変更、失敗条件のない文書整理 | 既存検証が必要条件を守るなら維持し、新しいテストを追加しない | 指示の意味はIssue・現行コードと独立評価で照合する。文字列一致やcheckだけでは意味の十分性や実モデルの効果は未確認 |

## 選定の補助モデルと限界

意味上の照合を先に行い、目的・制約の説明が必要な場合だけ対応関係と費用を明示します。数式への翻訳は必須作業ではありません。

$$
T^{*} \in \arg\min_{T'\subseteq T}\sum_{t\in T'}c(t)
$$

$$
\forall r\in R(D),\qquad \sum_{t\in T'}a(t,r,D)\geq k(r,D)
$$

| 記号 | 意味 |
| --- | --- |
| $D$ | 今回に適用するドメイン知識・要求・方針とその前提 |
| $R(D)$ | 命題と必要条件・判定基準からなる有限の検証対象集合 |
| $T$ | 既存ケースを含む比較対象の有限な候補集合 |
| $T'$、$T^{*}$ | 選ぶケース集合と、この制約を満たす最適集合の一つ |
| $c(t)$ | 比較基準を揃えた非負の費用。実行・準備・保守の見積りと実測を区別する |
| $a(t,r,D)$ | ケースが必要条件と判定基準を検証できると根拠から判断した場合に1、それ以外は0 |
| $k(r,D)$ | 根拠を持って要求するケース数。1以上の整数で、単なる繰り返し実行回数ではない |

すべての`c(t)=1`、`k(r,D)=1`ならケース数最小化の集合被覆です。`k>1`は複数ケースを要求する拡張ですが、その数だけではケースの独立性や異なる欠陥を検出する多様性を保証しません。

- `R(D)`の漏れは最適化では発見できません。`a=1`は意味上の根拠が必要で、作成側の自己申告や実行済み・成功済みの印ではありません。未確認の対応は被覆へ算入しません。
- 最適性は与えた候補・費用・対応関係に対するものです。仕様の完全性、欠陥不在、削減後の検出力を証明しません。「これ以上一件も削れない」と「費用が最小」は異なります。
- 費用の単純和は共通準備・実行順・環境依存を十分に表さない場合があります。その条件を無視して削減効果を断定しません。
- 必須条件を満たす候補がなければ、候補・根拠・実行環境を補うか未充足として戻します。解を作るために必要条件を黙って削除しません。

専用ソルバー、自動合否判定、全repoへの最適化、新しいSchema・台帳・評価スコア・CIゲートは今回の範囲外です。具体的な不足が確認された時点で依頼者が別途範囲を判断します。代表例と変更後の手順の照合は、実モデルの遵守・検出率・費用改善の実証と区別します。追加比較実験は必須ではありません。必要な場合だけ[既存の任意eval](../../../scripts/README.md#指示変更時の同条件eval)へ戻り、目的・ケース・モデル・有限の上限と許可を確定します。品質・費用の改善は実測するまで未確認です。

分類・判定根拠・集合削減の参考資料と適用限界は[Issue #362の参考資料](https://github.com/thkt/dotagents/issues/362)にあります。この数式と運用は本Issueの設計提案であり、外部標準や論文が今回のLLM指示の効果を実証したものとは扱いません。

## 対象repoでのe2eの条件付き採用

[Issue #351](https://github.com/thkt/dotagents/issues/351)（合意本文の更新日時: 2026-10-05T01:12:12Z）に基づくメタフローです。対象repoのUI操作の検証方法を選ぶ必要があるときだけ使います。dotagents自身にe2e（TesterArmy）を導入する手順ではありません。対象repoの個別導入は、そのrepoの要求と許可を別途確定します。新規スキル、専用の共有設定キー、共通runner・撮影アダプターは追加せず、既存契約の不足が実証された場合だけ別途範囲を整理します。

### scopingで比較して合意する

対象repoの技術構成、既存E2E、操作仕様、修正履歴、利用可能な実行環境を確認します。固定ロケーター・test idによる既存検証で十分なら、それを継続し、依存・設定・検証工程を追加しません。UI変更という理由だけでe2eを自動採用せず、対象外のrepoや変更ではこの判断工程を増やしません。

候補は、見た目やラベルが変わっても同じ結果へ到達すればよく、操作手順の修正に負担があるフローです。特定のボタン、キーボード、フォーカス、操作経路を守る場合は固定した操作とコード検証を優先します。初期導入は必要な少数フローに絞り、既存方式との保証・導入費用・実行費用・保守負担を比較します。負担軽減の仮説を採用しても、その効果を確認したことにはしません。

採用する場合は、次を対象repoのIssueへ残し、要求と許可を確定してからimplementへ引き継ぎます。

- 対象フロー、守る結果・副作用・永続化、AIに任せる操作、必須操作と維持する既存検証。
- 依存・設定・検証コマンド・CIの変更範囲。通常checkへの組込みか、明示的な追加検証か。
- 対象環境で確認するツール版、モデル・推論設定、認証方式、モデルへ送るデータの範囲、有限の時間・呼び出し・再試行の上限。
- 正常系と狙った不具合の検出、未実行の拒否、必要な証拠と保存先、実行不能時の対応。

既存Issueに必要な条件があれば再利用し、通常の実装選択を繰り返し確認しません。要求・許可・費用・送信範囲を変える場合は、影響と具体案を示して人の判断へ戻します。必要な報告の版と共有状態は[調査成果の引き継ぎ](../../scoping/references/session.md#調査成果の引き継ぎ)に従います。

### implementで導入と実行をつなぐ

合意済みIssueと検証定義に従い、対象repo内の依存・設定・テスト・結果判定を導入または再利用します。導入版はその環境で確認して固定し、限定比較の版を全repoへ適用しません。テスト・fixture・検証接続定義の作成・更新は[独立テストセッション](../../../scripts/README.md#テスト作成の独立セッション)で扱い、不足や誤りは具体的な根拠とともにfindingsへ残します。

AIは主に`agent.act`による操作へ使い、重要な結果・副作用・永続化はコードのexpect等で確認します。AIの説明、操作ステップの成功、キャッシュ命中、撮影成功だけでは受け入れません。別の操作で目的へ到達しても、合意した必須操作の保証を満たしたことにはしません。

実行は[対象repoの設定](../../../scripts/README.md#対象repoの設定)で指定した既存setup・check契約で扱える場合、その経路を使います。通常経路に含まれない合意済み受入検証が残る場合は、`needs_host`のfindingsへ必要な検証、不足理由、対象版、期待する証拠を記し、[ホスト検証後の再評価](../../../scripts/README.md#ホスト検証後の再評価)へつなぎます。通常check・captureの実行待ちだけなら`repaired`、要求・許可・実行上限などの変更が必要なら`needs_human`として具体的な選択と影響を示します。

認証・ブラウザー起動・モデル接続の失敗は実行不能として理由を残し、既存権限内で環境を解消します。過去の成功で補わず、人へ引き継ぐだけで完了としません。担当AIが許可済みの準備・検証・証拠保存を進め、新しいrunの独立評価へ戻します。起動入口と測定コマンド・子ツールの版、生ログ、結果要約を照合し、親子に同じ固定環境を渡します。actor runtimeや絶対パスだけで子ツールの版も固定・確認できたとは扱わず、版の不一致・未観測は原因を解消して新しい外部ログと証拠で再評価します。

### 対象repo側で受入を判定する

e2eを実行する対象repo側のコマンドまたは判定処理が、選択した対象の0件・skip・未完了・失敗・flaky、レポート欠落・不正を成功にしないことを確認します。終了コードだけで実行完了を保証せず、期待した選択と実際に実行したフローを照合します。対象外のfilteredによるskipと選択対象の未実行を区別し、既存Playwright用判定器との互換性は推測しません。正常な対照と狙った不具合・未実行の拒否を、上の[設計・選定手順](#検証命題とケースの設計手順)へ照合します。

runの版・入力・モデル・実行条件、取得できた使用量、失敗理由、キャッシュ再生・担当間の引き継ぎの別を記録します。失敗と再実行を分け、古いrunを上書きしません。現在の版と条件に適用できない成功や実行不能を、現在の成功へ読み替えません。比較では初期導入と実行ごとの費用を分け、取得不能な使用量・費用は0としません。

モデル操作で代替しない既存テストを明示し、重複も守る保証を照合してから整理します。撮影と動作検証は分け、必要媒体は既存capture契約と[公開後の実表示確認](../../../scripts/README.md#公開後確認とreadyへの切替)に従います。e2eのtraceを撮影媒体として自動流用しません。UI実装・変更では、下の[幅掃引](#ui変更時の幅掃引)も維持します。

独立評価は同じ差分の文書、対象repo側の判定、選択対象、コード検証、実行証拠をIssueの必要条件へ照合します。設計上の保証と実行結果、未充足・未確認を分け、既存findings・`assessments.tests`・PR説明、Issue固有の残る条件は`handoff`へ渡します。check成功や形式の充足だけで意味の十分性を認定しません。

| --- | --- | --- |
| ラベル変更に追従すればよく、操作手順の修正負担がある少数フロー | scopingが上の比較と合意項目を対象repoのIssueへ残す。implementと独立テスト担当が合意した部分導入とコード検証を準備する | 対象repoのsetup・checkで実行し、結果判定と証拠を同じ差分の独立評価へ渡す。負担軽減の効果は実測まで未確認 |

## UI E2Eの待機と独立性

非同期に描画・再取得するUIのE2Eテストを作成・更新するときだけ、上の設計・選定手順に沿って次を選びます。

- テスト間で可変データを共有するなら、各テストが独立に準備・後片付けできるか確認する。
- 表示や応答を待つときは、成功判定のための固定時間ではなく、操作に対応する状態・応答を待つ。不在を確認する前には、画面の準備完了を示す要素などの陽性条件を確認する。準備前にも対象が存在しない画面では、不在だけで成功としない。
- 再取得後も同じ値が表示され得るなら、表示値だけで更新完了とせず、その操作に対応する応答などを確認する。

既存テストが同じ失敗を防ぐ場合、非同期UIを扱わない場合、撮影動画を読みやすくするためだけの間隔には適用しません。動画の間隔と正しさの判定に使う待機を区別し、固定待機の一律禁止や全E2Eの構造変更は求めません。

## 外部入力の拒否

| 項目 | 説明 |
| --- | --- |
| 適用 | モデル応答や保存JSONなど、外部から来る値を受け入れる境界を変更するとき。 |
| 守る振る舞い | 必要な形と対象IDを満たす応答だけを現在の評価として扱う。構造の妥当性と、対象・権限などの意味上の照合は別の保証とする。 |
| 対照と失敗入力 | 完全なレビュー応答に対し、必須項目の欠落、余分な項目、異なる`targetId`をそれぞれ与える。 |
| 観測と理由 | 正常応答は解析でき、不正応答は形の不正または対象不一致として拒否される。別の不正項目に先に遮られた結果を、狙った拒否の証拠にしない。 |
| 既存例 | [review.test.ts](../../../scripts/tests/quality/implement/review.test.ts)の`parseReview rejects`群と[review.ts](../../../scripts/implement/review.ts)の`parseReview`。有効な応答との対照、strictな構造検査と対象ID照合がある。 |
| 最小層と費用 | 値の解析は関数テストで足りる。拒否後の保存・公開抑止まで変える場合だけ、実際の入口を通す結合テストを選ぶ。 |
| 適用しない条件 | 外部入力の契約を変えない文書・表示の整理や、同じ不正条件を既存テストが既に検出する変更。 |

## 停止時の副作用と記録保全

| 項目 | 説明 |
| --- | --- |
| 適用 | 評価失敗後の停止、修正の起動、保存履歴の更新など、失敗後の経路を変えるとき。 |
| 守る振る舞い | 不正な再評価を現在の成功にせず、直前の完全な評価と原ログを残し、後続の修正・公開を起動しない。 |
| 対照と失敗入力 | 有効な再評価が次へ進む条件と、前回指摘の更新が欠けた再評価を区別する。 |
| 観測と理由 | 後者は`invalid_review`で停止し、前回の`reviewHistory`と作業を保ち、次の修正入力を作らない。単に例外が出たことだけでは足りない。 |
| 既存例 | [review.test.ts](../../../scripts/tests/quality/implement/review.test.ts)の`invalid re-evaluation retains the last complete review and prevents another repair`。 |
| 最小層と費用 | 保存状態と後続起動を守るため、この条件ではホストの入口を通す結合テストが必要。純粋な解析の拒否は上の関数テストで確認し直さない。 |
| 適用しない条件 | 停止経路や永続状態に触れず、既存の結合テストが同じ失敗後の結果を観測できる変更。 |

## 対象版の変化

| 項目 | 説明 |
| --- | --- |
| 適用 | 検証・評価・公開の前後で対象や根拠を再取得し、以前の成功を使う条件を変えるとき。 |
| 守る振る舞い | 確認後に対象が変われば、古い成功を現在の対象へ流用せず、保存済みの結果を保って停止する。 |
| 対照と失敗入力 | 同じ対象での再確認と、成功後に追跡ファイルを変更した再確認を比べる。変更を実際に検出対象へ加える。 |
| 観測と理由 | 前者は成功を再利用でき、後者は`target_changed_after_stop`を返し、以前の検証stateを変えない。別の設定不正による停止を版変化の検出と数えない。 |

| 最小層と費用 | Gitの対象と保存状態をまたぐ契約なので結合テストを選ぶ。純粋な比較関数だけでは成功の流用抑止を確認できない。 |
| 適用しない条件 | 対象版の読み方や再利用条件を変えない内部整理、または既存テストが同じ時点・対象・副作用を守る変更。 |

## UI変更時の幅掃引

UIを実装・変更した初回実装と追加修正では、対象画面の主要な表示状態を対応幅の範囲で1px刻みに計測する。中間幅の確認が必要かを判断して省略しない。同じ画面・状態・対象版・高さ・ブラウザーなどの条件を検証する既存の幅掃引があれば、結果を再利用できる。固定ビューポートのテストだけでは代用しない。[#358](https://github.com/thkt/dotagents/issues/358)の合意を適用する。

対象repoの要求から最小・最大の整数幅と高さを選び、主要状態の準備方法を決める。ログイン、空・読込後・エラー・展開状態など、その画面で必要な状態を対象repoのfixtureや操作で準備する。初期表示だけを全状態の確認としない。リサイズで状態が失われる画面は、`ready`で状態を再準備し、陽性条件で描画完了を確認する。非同期更新・アニメーション・画像などの待機は対象repoで定義する。共通入口はその待機後にフォントと2回の描画フレームを待つが、アプリの完了条件は推測しない。

[TSの計測入口](../../../scripts/ui/width-sweep.ts)の`widthSweep(page, options)`を対象repoのPlaywright specから呼ぶ。対象repoのpage fixtureを使い、認証・データ・ブラウザー・webServerはその既存構成に従う。共通repoや対象repoへPlaywrightを無条件に追加しない。具体的な定義とホストでの起動は[CLIガイド](../../../scripts/README.md#ui変更時の幅掃引)を参照する。

- ページ全体は`documentElement`と`scrollingElement`の`scrollWidth`の最大値が`documentElement.clientWidth`を超えたら失敗とする。許容は設けない。
- 要素境界は左が`-1px`未満、右が`clientWidth + 1px`超の候補を記録する。境界、要素を辿るselector、祖先の横方向の`auto`・`scroll`・`hidden`・`clip`とその境界を残す。専用スクロール・クリップ領域内の候補も消さず、ページ全体の失敗と分ける。
- 候補は担当AIが該当する幅・状態の実画面で確認し、不具合なら修正して再掃引する。祖先領域の存在だけで意図した表示とは判断しない。クリップ内で文字が読める保証、重なり・文字切れ・キーボード操作・印刷表示・全UIの正しさの保証にはしない。
- 結果には各整数幅のDOM計測と候補、状態・実URL・高さ・ブラウザーと版・対象版・条件・未確認事項を残す。対象版はcommitだけでなく未commit差分の識別値も含める。失敗は`failed`、入力不正など計測開始前の実行不能は`unavailable`。途中の失敗は部分計測を残す。未実行・時間切れで結果が完成しない場合は成功ではなく、ホストログに理由を残す。

通常checkに含まれる実行は既存のホスト経路を使う。設定済みcheck・captureに含まれない実ブラウザー検証が必要なら`needs_host`に検証対象版・条件・不足理由・期待する証拠を記し、[ホスト検証後の再評価](../../../scripts/README.md#ホスト検証後の再評価)へ戻す。実行予定だけで完了にせず、新しい工程・担当・ゲートは加えない。生ログ・合成HTML・ブラウザー結果はcheckout外の新しい場所へ保存し、証拠への参照と候補の確認結果を既存の`findings`へ渡す。独立評価は同じ差分と証拠の適用条件を確認し、`assessments.tests`とIssue固有の`handoff`へ引き継ぐ。

Issueに記載された2026年10月8日のローカル試行（高さ900px、320〜1440px、1,121幅、図・ガイド5状態、TS/Pythonの6ケースの計測一致）は限定した観測であり、この入口の実ブラウザー検証の代わりにはしない。849〜851pxだけ崩れる合成例を粗い40px刻みでは見逃したという観測が、1px刻みの合意の根拠である。対象repoでの実運用効果、他ブラウザー・高さ・フォント・全状態への一般化は未確認である。
