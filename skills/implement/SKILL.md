# 実装と検証

合意済みIssueの要求を実装・検証し、独立評価とPR公開後の確認まで進める。

## 開始

依頼と会話から対象Issueを特定する。特定できなければ確認する。小さな変更や文書変更もIssueに紐づけ、今回に関係するリポジトリ指示・README・開発方針を読む。[対象repoの設定](../../scripts/README.md#対象repoの設定)でcheckout・Issue・remote・base branch・検証・必要媒体と実効ghユーザーの権限を照合する。不一致や権限不足では依存作業を止め、別の主体へ切り替えない。

[共通の文書利用手順](../references/documents.md#読む)で関連wiki・判断記録を選び、Issueと現行コードへ照合する。[調査成果の引き継ぎ](../scoping/references/session.md#調査成果の引き継ぎ)で必要な報告の内容・版・共有状態と合意範囲を確認する。判断を左右する事実不足は調べ、要求・権限の変更は人の合意へ戻す。

## 実装と検証

実装・修正中にも、人の注意に依存する条件を見つけたら、[機械化の共通手順](../references/mechanization.md)で検討する。合意範囲内の通常の実装選択は進め、要求・権限・規約の変更や範囲外の改善は、根拠と影響を伴う提案として分ける。既存の保証で十分なら追加しない。規則追加や依存導入を候補発見だけで自動採用せず、対象repo・Issue・既存の担当分担と検証契約に従う。テスト・fixture・検証接続定義の変更は独立テスト担当へ戻す。

設計や防御処理を見直し、過去の理由が今回の判断に関係する場合は、[設計理由の根拠と確度](../references/documents.md#設計理由の根拠と確度)を使う。過去の理由と現在の必要性を分け、今回の選択理由で過去の意図を補作しない。実装・追加修正・既存PR修正、文書更新と独立評価へ同じ参照を渡し、公開説明にも確度と条件を保つ。

信頼するスキル実体から[実装CLI](../../scripts/implement/development.ts)を解決し、対象repoを指定する。対象repoにBunやPlaywrightの構成を推測で追加しない。

変更の安全性が未確認の前提に依存する場合は、[前提の検証](../references/premise-validation.md)で導入版の実装・契約と成立条件へ照合し、必要な境界と最小の証拠を選ぶ。実装・修正の確認結果と適用限界はfindingsへ残す。修正が停滞して原因仮説を見直す場合は同参照の共通前提の見直しを使う。独立評価は差分・対象版・成立条件・証拠を独立して照合し、既存の検証・停止経路と担当境界を維持する。

性能を測定し、その数値を報告または判断に使う場合は、[性能測定の共通手順](../references/performance-measurement.md)で計測の意味と適用条件を確認する。処理未完了・エラー・結果欠落・処理省略を高速化へ読み替えない。合意範囲と既存の実行契約内で確認を進め、不足する証拠と影響をfindingsへ残す。局所と全体、観測値と原因仮説、実測と推定を分け、公開説明にも条件と未確認を保つ。既存証拠で足りれば再測定せず、適用外には工程を増やさない。要求・性能の許容範囲・権限・実行上限の変更は人へ、検証資産の作成・更新は独立テストへ、通常check・capture外の受入検証はホスト検証後の再評価へ戻す。

対象repoのIssueでe2e（TesterArmy）の部分導入を合意している場合は、[条件付き採用と検証の手順](references/testing.md#対象repoでのe2eの条件付き採用)を読み、合意した導入・コードによる結果確認・対象repo側の実行判定を通常checkまたは既存のホスト検証経路と独立評価へつなぐ。未採用repoの依存・設定・検証工程は増やさない。

```sh
bun /absolute/path/to/trusted/scripts/implement/development.ts 99 --repo /absolute/path/to/target-checkout
```

報告が必要なら[CLIの引き継ぎ手順](../../scripts/README.md#調査報告を指定した実装開始)で同じpath・blob・開始commitを初回実装・修正・独立評価へ渡す。テスト作成・更新は[独立セッションの方針](../../docs/wiki/development-policy.md#実装とテストの整理)と[ホストの経路](../../scripts/README.md#テスト作成の独立セッション)に従います。実装・修正担当の履歴・判断をテスト入力へ渡さず、期待値や機械的な接続修正を実装セッションで変更しません。UIを実装・変更した場合は、対象画面の主要な表示状態を対応幅の範囲で1px刻みに幅掃引する。[幅掃引の手順](references/testing.md#ui変更時の幅掃引)を読み、同じ画面・状態・対象版・条件の既存結果を使える場合以外は実行する。中間幅の必要性判断で省略せず、実行待ちを完了にしない。この条件は追加修正にも適用する。初回実装・追加修正・既存PR修正で影響するテストは、[設計・選定手順](references/testing.md#検証命題とケースの設計手順)で観点、命題と必要条件、ケースと判定根拠、選定理由の順に照合する。独立テスト担当はfindingsへ根拠と未確認事項を残し、独立評価は要求と実際のケースへ照合してassessments.testsへ渡す。既存検証で十分なら追加せず、必須条件は維持する。差分が揃ったら[文書の更新手順](../references/documents.md#残す更新する)を確認し、変更文書を含めて[日本語確認の方針](../../docs/wiki/development-policy.md#pr本文人向け文書の日本語確認)と独立評価を適用する。

型・API・責任の境界を設計する初回実装・追加修正・既存PR修正と、その独立評価は、[利用例から設計する手順](../references/caller-first-design.md)を使う。構造の採用を表明・実装する前に、合意済みIssueと実際の呼出元に基づく例、または既存例と今回の判断との対応を進捗説明などへ残し、必要な形を導く。実装後も例と実際のデータの流れ・失敗・所有・終了を照合する。独立評価は対応と事前の記録を分けて確認し、順序不明は未確認とする。合意範囲内の通常の設計は進め、要求・公開契約・許容範囲・権限の変更だけ人へ戻す。小さな内部変更や文書修正へ一律の工程を追加せず、例を独立テストの期待値の正本にしない。不一致は既存の指摘へ、検証資産の変更は独立テスト経路へ戻す。

`host_verification_required`で返ったら、[ホスト検証後の再評価](../../scripts/README.md#ホスト検証後の再評価)に従って担当AIが検証する。要求・対象版・既存権限を照合し、生ログをcheckoutと旧runの外へ保存する。必要な検証要約・文書更新をcheckの前に反映し、同じcheckoutと元の差分基準を使う新しいrunで独立評価へ戻す。通常check・captureの待機、追加検証待ち、人の判断待ちを区別する。検証失敗は原因の修正、実行不能は環境の解消へつなぎ、要求・権限・許容範囲を変える必要がある場合だけ人に具体的な判断を求める。引き継ぎや証拠の提出だけで完了とせず、実行と復帰を人の手作業に転嫁しない。

初回独立評価が`invalid_review`で止まった場合は、原応答と最終対象・実在行範囲・応答契約を照合する。評価担当は応答前に最終ファイルを番号付きで読み、末尾と各`path/start/end`の内容を確認し、未確認の範囲を推測しない。ホストの範囲検査は切詰め・自動補正で緩めない。応答生成側を修正した信頼するハーネスから[初回不正評価後の新しい検証](../../scripts/README.md#初回不正評価後の新しい検証)の`--review-run`で旧runを指定し、新しい保存先で同じ成果物を検証する。対象は未公開・評価1回・有効な履歴なし・追加修正なし・active予約とlockと稼働プロセスなしの初回停止だけで、履歴のある評価や他の復帰入口に転用しない。旧run・原応答・停止ガードを保全し、過去の成功や受入を流用しない。新しいcheck・独立評価からの指摘は既存の独立テスト・修正経路へ渡す。

初回評価がactive予約を残して終端中断した場合は、[中断した初回評価の照合と新しい検証](../../scripts/README.md#中断した初回評価の照合と新しい検証)の`--interrupted-run`を使う。通常初回とホスト復帰後の、未公開・評価予約1回・有効な履歴なし・追加修正なしだけを対象に、実プロセス・remote ref・全状態のPRと原出力を照合する。旧stateと内容・モードを保全し、同じ親の新runで現在sourceのcheck・独立評価へ渡す。旧予約・計上済み時間と中断分の不明量を保持し、旧成功を流用しない。必要な追加証拠・独立テストを照合し、復帰自身の再中断や他のactiveを自動で飛び越えない。意味上の照合不能は停止し、記録編集やlock解除で条件を満たさない。

初回checkが時間切れで終端停止した場合は、[初回check時間切れ後の新しい検証](../../scripts/README.md#初回check時間切れ後の新しい検証)の`--check-timeout-run`を使う。独立評価済みの信頼するハーネスの版・実体パスを明示し、未公開・check 1回・review/repairなし・activeなしの旧runと現在の要求・対象・主体・権限を照合する。同じ親の新runでsetup・check・独立評価へ進み、初回実装は繰り返さない。旧9分設定・原記録・消費量と祖先の期待hashを保持し、新runの15分設定と区別する。lock・稼働プロセス・remote ref・全状態のPR、証拠や保護テストの不一致・照合不能では停止する。旧記録を編集せず、他の復帰入口へ偽装しない。再度停止しても自動連鎖せず、新しい指摘は通常の独立テスト・修正経路へ渡す。実適用と公開後の同じheadのCIは模擬制御テストと分けて確認する。

## 公開と引き継ぎ

明示的な開発依頼は、検証・独立評価と対象の再照合を経たdraft PR作成、その後の[公開後確認とreadyへの切替](../../scripts/README.md#公開後確認とreadyへの切替)までを含む。合意済みの作業ごとに許可を聞き直さない。スキルの自動選択だけを公開許可としない。「公開しない」指定は`--no-publish`へ渡し、独立評価後のローカル完了で止める。人のレビュー・承認・マージは代行しない。

人が採用した既存PRの修正は[既存PRの修正](../../scripts/README.md#既存prの修正)から同じCLIへ接続する。前回runと採用した指摘・期待する結果・許可範囲を渡し、PRコメントを自動採用せず、旧runを再開しない。停止した実行は[結果と再実行](../../scripts/README.md#結果と再実行)で理由と残る条件を確認し、停止条件や上限を緩めて続行しない。

採用した指摘の原因と再発性を確認し、[文書の更新方針](../../docs/wiki/development-policy.md#ドキュメントの更新)に従って、必要な場合だけ既存wiki・判断記録と、[機械化の共通手順](../references/mechanization.md)で選んだ型・lint・実行時検査・スクリプト・テストへつなぐ。検証資産の変更は独立テスト担当へ戻す。今回の合意範囲を超える改善を既存PRの完了条件に加えない。

公開後は最新本文・必要媒体・同じheadのCIを確認し、ready直前と切替後も対象を読み戻す。PR URL、確認した版と検証結果、残る人の判断、または停止理由と記録の場所を返す。terminal runでは`report.html`の絶対パスと開き方も案内する。生成に失敗した場合は成功と扱わず、残る`result.json`と[再生成コマンド](../../scripts/README.md#結果と再実行)を示す。
