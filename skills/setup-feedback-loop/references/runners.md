# 分類と関連テストの接続

設定形式は[呼出し仕様](../../../docs/wiki/setup-feedback-loop-contract.md)を使う。`.dotagents.json`へ分類やrunnerの設定を追加しない。通常checkが収集する自動テストを既定のquality集合にし、内容を確認したassuranceだけを理由付きで指定する。実サービス・手動検証等は別扱いのまま一覧へ残し、呼出し方と範囲を保つ。

qualityは要求、入出力、権限、保存、状態遷移、公開契約を確認する。assuranceは環境障害、中断・復帰、後始末、履歴保全、repo全体の整合等を主目的とする。異常系・DB・結合範囲・遅さだけでassuranceにしない。混在ファイルはqualityに残すか、必要性を確かめて独立テスト担当が分割する。意味分類をOxlintへ任せない。

`collect`は通常checkと同じ収集処理からJSON文字列配列を返す。`check:classification`でglob集合と実収集の差、重複、存在しない指定を拒否する。通常checkの対象が導入前後で減っていないことも照合する。globの誤設定と収集側の同時変更までは集合比較だけで防げない。

通常runnerが許可する条件付きskipは既定で維持する。対象repoのcheckがskipを禁止している場合は`allowSkipped: false`を指定し、その失敗条件も照合する。skipを許可していても、選択した全テストがskipで一件も実行されなければ非ゼロ終了にする。package managerとrunnerは別々に確認し、npm管理のBunテストもBunで起動する。

テスト収集・準備処理とBun・Vitestは、親とのIPC接続を監視する子プロセスから起動する。直接の取消とホストによる親の強制終了で、子孫の終了と出力用pipeの解放を確認する。1秒後も残る処理は強制終了する。監視側で対象コマンドのpreloadや`.env`を重ねて読み込まず、元の環境変数がコマンドへ渡ることも照合する。監視側のstderrが切断された場合も、取消と強制終了を続ける。

`apply`時の収集も同じ監視を使う。収集の診断をstderrへ分け、`classification`のstdoutはJSONだけに保つ。収集中の取消では準備処理・テスト実行・記録更新へ進まず、次回実行で復帰できることを確認する。

## 全テストの分類と確認記録

導入担当AIは収集集合の全テストファイルを読んで分類する。現行の実行単位はファイルなので、各ファイル内のテストの主目的を確認し、ファイル単位で判断する。目的の判断にhelper・fixtureの内容が必要なら、それも読む。一括移動や不要な分割を前提にしない。

qualityの各ファイルにも確認する要求・入出力・状態等を具体的に書いた理由を残す。他のファイルへそのまま流用できる理由は、内容を確認した根拠にならない。目的が混在するファイルは上の規則どおりqualityへ置き、混在の内容と判断理由を書く。assuranceへ置くファイルが対照や他のqualityファイルと重なる検査を含む場合は、混在と扱わない理由を書く。

記録は[呼出し仕様の確認記録](../../../docs/wiki/setup-feedback-loop-contract.md#分類の確認記録)の形で`.feedback-loop-review.json`へ置く。`sha256`は`check:classification`の出力から転記する。`check:classification -- --complete`は、未確認、内容が変わった後の古い記録、収集集合外の記録、`.feedback-loop.json`との分類の食い違いを拒否する。重複・理由の欠落など記録ファイル自体の誤りは、日常の`check:classification`でも拒否する。この検査は記録の集合と形だけを照合し、理由の意味が正しいことは判定しない。

再導入や追加の分類では、前回の記録を現在のファイル内容と照合する。`stale`のファイルは読み直し、前回の判断を現在の内容の確認結果として転記しない。

## Bun

固定Bunの公開CLI`bun test --changed=<baseとの分岐点>`へquality候補を渡す。信頼できる記録があり、各変更の影響を対応付けできる場合に、標準選択と実行時記録・明示依存の和集合を実行する。標準選択で実行済みのファイルは重複実行せず、標準選択から漏れた補完対象を追加実行する。利用版の`--help`と実行結果を照合し、公開されていない一覧取得やdry-runのAPIを仮定しない。

既存の`scripts/test-runtime/record-modules.ts`を配置し、通常のモジュール読込み、JSON・非ASCII・動的import・子Bunの帰属を再利用する。quality候補を一度の`bun test --changed --isolate`へ渡し、未実行の補完対象だけを追加する。Bunの実行版は対象repoの固定runtimeを使い、`prepare`を一度完了してからテストを起動する。分類検査では準備を行わない。

`bunWorkers`でBun標準のworker数を指定する。省略時は4、1なら直列とし、補完と全qualityへのfallbackにも同じ設定を使う。`bunArgs`と`testArgs`の既存引数を保ち、隔離と並列の指定はこの接続へ集約する。`--isolate`はファイルごとにglobalとmodule cacheを分離するが、workerのOSプロセスは再利用する。導入時には対象repoの全qualityを実行し、ファイル別の完了と記録の帰属、並列実行との互換性を確認する。

JUnitのファイル別結果と記録されたownerを照合し、読み込んだファイルの結果欠落や0件を成功にしない。補完と全件実行では指定した全ファイルの完了を要求する。失敗・取消では起動した処理の終了を待ち、部分成功の記録を採用しない。終了や結果が確定しない候補の旧記録は、原文を残したうえで無効化する。導入時の小さい対照で、この経路と既存のskip条件を確認する。

テストを起動するBunには`--no-orphans`を付け、ホストが親を強制終了した場合もleader・workerを残さない。直接の取消に加え、ホストの取消・タイムアウトによる子孫の終了と出力用pipeの解放を確認する。実行開始時に未完了を示すファイルを作り、結果と依存記録を確定してから削除する。強制終了でこのファイルが残った場合は原記録を保持し、次回は全qualityへ広げる。全件の正常完了後に関連選択へ戻ることも確認する。

関連選択は分岐点以降のcommit、staged／unstaged、未追跡、削除・改名の旧パスを含める。変更したqualityテスト自身も選ぶ。通常のファイル読込み、変数import、子プロセス・Python・生成入力は、明示した`dependencies`か`globalChanges`で補う。対応できない変更が一つでもあれば全qualityへ広げる。

Bunの標準選択が一部のテストを選んでも、すべての変更の影響を特定できたとは限らない。実行記録や明示対応等で届き先を確認できない変更が混じる場合は、全qualityへ広げる。未実行分岐等では標準CLIだけなら絞れる場合もあるが、この保守的な判定を省略しない。Bun 1.4.4では関連0件も終了0になるため、選択診断・依存記録・JUnitの有無を照合する。実際に選択されたテストの結果欠落は失敗とし、補完を含めて一件も実行されなければ成功にしない。

記録はworktree固有のGit dirへ保存する。HEAD、実行runtime、記録器・runnerの内容、読込みモジュールのhashを照合する。現在の変更一覧へ含まれる入力は選択処理で扱い、それ以外の内容不一致や基点不明は記録を信頼しない。commit後の基点変更では全件へ広がる。旧形式には基点がないため、新しい成功の証拠に変換しない。失敗時は直前の原記録を内容別の`.previous`へ保持し、失敗したテストの利用中の記録を無効にする。

記録の有効性は現在のquality候補について判定する。削除済み・assuranceへ移したテストの原記録は保存するが、その古い基点だけで現行quality全体を無効にしない。対象外のテストをqualityへ戻した場合は、その時点で再び基点を照合する。

実行されなかった分岐、環境変数を引き継がない子、ファイル読込み等を完全追跡するものではない。担当AIはassuranceやその検証対象を変えた場合に該当テストを直接実行し、影響を判断できなければ`fullCheck`を実行する。`test:affected`はこれらを自動実行しない。提出前・CIには全体checkを使う。

## Vitest

対象repoのローカルVitestで、公開APIの`createVitest`と`getRelevantTestSpecifications`を使い、変更ごとの関連qualityをテスト本体を実行せずに確認する。明示対応もVitestの到達先もない変更が混じれば全qualityへ広げる。実行は公開CLIの`related ... --run`を使う。既存のconfig・global setup・環境変数・codegen・DB準備を保つ。収集用コマンドは導入版の`list`の出力をrepo相対パスのJSON文字列配列へ整え、通常checkと照合する。[Vitest 4のAPI](https://v4.vitest.dev/advanced/api/vitest.html#getrelevanttestspecifications)と[CLIガイド](https://v4.vitest.dev/guide/cli.html)を導入版へ照合する。公開APIの対応が確認できない版では、正常に選択できたと扱わない。

補助スクリプトは変更テスト自身と明示した依存先を関連入力へ含め、assuranceを除外する。設定・lock・選択器・削除、依存先不明の入力は全qualityへ広げる。静的importで追えると推測しただけの入力を、関連選択の根拠にしない。JSONレポートで完了・実行集合を確認し、選択した全ファイルの結果を要求する。関連0件の終了0や、一部の結果だけの成功を全体の完了に数えない。skip等は対象repoの既存契約へ照合する。

## 導入時の確認

変更・削除・改名・未追跡、新規テスト、記録なし・破損・古い記録、設定変更、不明な入力と既知依存が混じる場合を独立テストへ照合する。Bunの通常実行と記録付き実行の値・assertion・成功失敗、並列の帰属も確認する。既存の保証が十分なら重複ケースを増やさない。診断・対象・再実行方法と、変更なし・候補0・選択不能・失敗・成功を区別する。

導入用設定の変更が残った実行は、通常ソース変更の絞り込みの証拠と分ける。隔離した検証用checkoutで導入後の版を比較元にし、信頼できる記録を用意してから、通常のソースだけを変更する。通常importに加え、子Bunやファイル読込みの補完対象が選ばれ、無関係なqualityとassuranceが実行されないことを実行ログで確かめる。全ソースを`globalChanges`へ指定した全件成功だけで導入完了としない。

時間を報告する場合は準備とテスト本体を分け、実行した版・対象・件数・終了状態を生ログへ残す。未実行・失敗・処理省略を高速化へ読み替えず、固定閾値や変異スコアを合否条件にしない。
