# 検証とレビューの方針

この共通ハーネスでは、機械的な検証と説明を揃えた上で、人が変更をレビューしてマージを判断します。
人のレビューを省略する運用は導入しません。この文書を現行のレビュー・開発方針の正本とします。
セットアップと検証範囲は[README](../README.md#セットアップと検証)を、制御CLIの操作・上限・中断は[scripts/README.md](../scripts/README.md)を参照してください。

- 小さな変更もIssueに紐づけます。
- GitHubへのIssue・PR作成、push・添付はユーザーの既存gh認証を使います。このrepoではPR作者本人が差分と検証結果を確認し、マージを判断できます。GitHubの必須Approve件数は0件です。他repoではそのrepoの承認条件に従い、必須レビューがある場合は別の適格レビュアーが条件を満たします。
- 要求・公開範囲への人の合意と独立評価を維持します。エージェントは人の判断・承認・マージを代行しません。
- 秘密鍵やtokenをコード・文書・ログに残しません。

## 変更に応じた確認

通常の変更では、合意済みの検証を再利用します。人は要求の達成、検証の適用条件、今回残る観点を確認します。

検証自体を変更する場合は、守る条件、変更理由、検出できなくなるケースとその対応をPRで説明します。
workflowだけでなく、検証コマンド、対象の選択、lint設定、テスト、依存関係など、結果の意味に影響する変更を含みます。
人はこの説明と差分・証拠を確認し、CI成功だけを根拠にした承認はしません。

機械は合意済みの検証定義に従い、実行結果とCIを確認します。人がレビューとマージを判断し、対象repoの必須承認条件を満たします。
実行コマンドは[README](../README.md#セットアップと検証)、main保護の条件は[CIとmain保護](#ciとmain保護)を参照してください。

検証定義もPRから変更できるため、人がその無効化を見落として承認した場合まで防げるとは扱いません。
`verify`自体のスキップ、検証コマンドの置き換え、step単位の省略は、現在の判定jobだけでは防げません。
PRから独立した強制判定は対象外です。

## PR本文・人向け文書の日本語確認

執筆担当は、人向けMarkdown（README、設計書、操作説明、研究・検証記録など）とPR本文の事実、数量、否定、条件、範囲、権限、断定の強さ、未確認事項、参照を原資料と照合します。事実・合意・提案を区別し、読者が判断できる平易な日本語で説明します。事実不足は調査へ、要求や権限の変更は人の合意へ戻します。

変更文書は、既存の最終独立評価でIssue・コード・検証結果との整合と説明の十分性を確認します。具体的な欠陥は修正へ戻し、成果物を変更したら必要なcheckと独立評価を更新します。scopingの調査報告は既存の評価へ、Issue本文と下書きは要求精査と必要な独立評価・人の合意へつなぎます。文書だけの変更にも同じ責任を適用します。

PR本文は既存のacceptedな評価と検証済みcommitから生成します。公開担当は、公開直前にIssue・根拠・commit・本文・公開先・主体・権限を照合し、公開後も実際の本文・リンク・添付を読み直します。本文を直接変更した場合も最新本文をIssue・根拠・対象commitと照合し、変更前の成功を流用しません。成果物の不備が見つかれば修正・check・独立評価へ戻し、媒体の実表示確認が必要な場合は担当AIが[公開手順](../scripts/README.md#prへの画像動画の添付)に従います。人がレビュー・承認・マージを判断します。

[Issue #84](https://github.com/thkt/dotagents/issues/84)の合意により、専用Gemini校正、保護対象の機械比較、別モデルによる校正前後の意味照合は終了します。執筆・既存の独立評価・人の確認へ責任を集約しますが、従来と同じ独立検査を維持するものではありません。文書やPR本文のためのモデル呼び出しは追加しません。この方針は[#59](https://github.com/thkt/dotagents/issues/59)・[#67](https://github.com/thkt/dotagents/issues/67)の専用校正部分を置き換えます。利用先ごとの方針確認と旧設定・記録の扱いは[切替手順](../scripts/README.md#専用校正の廃止と切替)に従います。

## 旧資産の保全と登録変更

旧未追跡資料、ignored資産、別worktree、保存庫、過去のrun・失敗記録は保全し、日常の整理や受入完了を削除許可として扱いません。旧stateは新runtimeへ変換・再開しません。個人情報を含むバックアップや実行ログはホスト側に保持し、公開repoへ取り込みません。

共通環境の登録切替や、稼働中の実行・復帰に影響する依存・hookの変更では、保全・復元の確認を変更や復帰の対象となる資産に限って行います。対象のcheckout・保存庫・稼働プロセス・所有者と登録先を確認し、復帰に必要なcommit・依存・設定・symlinkの対応を保全します。ファイルのハッシュ・モード・symlinkを照合し、変更中なら切替を止めます。SQLiteはオンラインbackupとintegrity_checkを使い、稼働中DBやGitの部分コピーを整合した保全とは扱いません。隔離した復元先ではGitのworktree参照だけを復元先へ結び直し、元環境の参照は変更しません。その上でHEAD・差分・履歴・worktree参照、DB整合性、旧依存・CLIリンクを確認します。切替直前にも変化を確認し、追加の変更があれば保全と復元確認を更新します。

共通環境の登録切替は人がマージした採用commitを対象とし、新規タスクと旧writerの起動を止めてから行います。未追跡・ignored資産を上書きせず、対象の旧入口や重複登録だけを整理します。無関係なスキル・hook・別worktreeは変更しません。採用版の依存導入とcheckが成功してから新入口を使い、新しいタスクからのスキル検出・CLI実行・対象解決を別に確認します。実際の変更や公開を伴う試行は、対象repo・Issueと既存の許可範囲を照合します。

対象や主体の不一致、資産の衝突・欠落、合意した受入の未達があれば新規実行を止めます。復帰時は新側の差分・状態・公開結果を先に保全し、旧commit・依存・登録設定の対応へ戻します。別worktreeと旧runの所有関係を維持し、公開済みIssue・PRはGitHub上の実状態を照合します。ファイルの復元だけで公開を取り消したとは扱いません。

完了した移行の採用版・受入結果・未実施範囲は[Issue #54](https://github.com/thkt/dotagents/issues/54)に記録されています。実施時の詳細は[当時の移行文書](https://github.com/thkt/dotagents/blob/0301814dee086317328e86c6bbffd0862c9e9cd1/docs/migration-54.md)から参照できます。これらは過去の記録であり、後続変更の検証成功を示すものではありません。

## ドキュメントの更新

このリポジトリに関する設計・計画文書もリポジトリ内に置きます。提案を保存しただけで現行方針や実装許可とは扱いません。

基本ドキュメントには、現在有効な要求・方針・手順と判断に必要な理由を記載します。変更時は現在の説明として書き直します。変遷や過去との比較は、移行や互換性の判断に必要な場合に限ります。経緯、個別の実行条件、結果は対象Issue・PRと対象repoで合意した証拠保存先へ残します。[trialの検証記録](https://github.com/thkt/dotagents-workflow-trial/blob/93b38f0bc690373b4b1f68e37a42f721929d6386/trial/evidence/README.md)は採用元の過去実測として参照します。

文書単独の整備でも実装に伴う更新でも、読者のどの判断や操作に必要な説明かを基準にします。要求を確認する段階で操作・仕様・設定・制約・方針への影響を見立て、差分が揃った時点で見直します。必要な更新は独立評価の前に成果物へ含めます。説明に影響しない内部整理などでは、PRの説明に理由を短く示し、文書を更新しない判断もできます。

更新先は[READMEの正本の分担](../README.md#読む順序)に従い、既存の正本を書き直します。再利用する調査根拠と未採用の提案は[research/](../research/README.md)へ置き、採用した仕様・方針・設計判断は関連する既存の正本やIssueへ反映します。提案と採用済みを区別し、文書が必要になった時点で内容に合う配置を選びます。現在のコード・設定・実行入口、Issueの合意、対象版の検証結果と照合し、根拠のない保証や未合意の仕様を追加しません。事実が不足していれば調査し、要求や方針の判断が必要なら[対話と方針の決定](#対話と方針の決定)へ戻します。

完了時は、今回影響する説明・例・コマンドが根拠と一致し、古い記述と重複を整理し、読む順序と関連リンクから現在の手順・理由・未確認範囲を辿れることを確認します。文書の内容不足は修正へ戻し、成果物が変われば関係する検証や評価を更新します。PRへの配置・添付と人の承認は[レビューを助ける説明](#レビューを助ける説明)と公開手順へ引き継ぎ、文書内容の確認と区別します。

合意済みの文書整理Issueも[implement](../skills/implement/SKILL.md)で扱います。何を文書化するかが未確定なら要求整理へ、レビューだけの依頼ならレビューへつなぎます。確認結果は既存のPR説明や評価結果に含め、全文書の毎回監査や専用の帳票は求めません。

## コンテキスト整備の設計原則

人とAIが、判断に必要な意味、根拠、合意、不明点をたどり、今回必要な部分を取り出し、新しい事実から見直せる状態を目指します。目的、概念と関係、規則や仮説、根拠、合意と未確定事項を、判断に必要な範囲で関連付けます。これらは情報を整理する観点であり、すべての作業に追加する必須帳票や工程にはしません。

観測した事実、守ると合意した規則、検証する仮説を区別します。出典、対象版、適用条件と、提案、合意済み、未確認などの状態を必要に応じて残します。仮説の採用を事実の確認とは扱わず、不明点は推測で埋めずに調査や人への確認へ戻します。

JSONやYAMLなどの構造化は、ID、関係、状態、参照など、機械が扱う必要のある部分に絞ります。理由や背景は文章で残せます。各情報の正本を定め、そこから人向けの説明とAIへ渡す情報を取り出し、同じ情報の手作業による二重管理を減らします。具体的な形式、分割、生成方式は、実際の利用と更新負担を確認して選びます。

機械は定義した形式、参照、状態遷移などの制約への適合を確認します。AIは根拠の適用や意味の整合を評価し、人は目的、許容範囲、権限と重要な変更を判断します。形式検証やAI評価の成功を、事実の正しさや人の合意の保証とは扱いません。

dotagentsの実装開始については[共有モデルのJSON](../docs/knowledge/implementation-start.json)を知識の正本とし、[生成した説明](../docs/knowledge/implementation-start.md)とAI入力を同じ抽出処理から作ります。選択は既存の要求整理で行い、[Issue内の参照](../scripts/README.md#共有知識の選択)から必要なIDと版を渡します。形式・ID・関係の整合は抽出処理、実行対象の版と場所は既存のGit照合、意味と適用はAI、人の要求・権限の変更は合意で扱います。改訂の観測・影響する定義・判断・未確認事項は既存の差分と評価へ残し、モデルを実行制御や新しい必須台帳にしません。モデルのないrepoは従来のIssue・報告だけで開始できます。

要求の正本はIssueと合意記録とし、プロダクトの知識から今回必要な根拠を参照します。対象repoの実行方法は`.dotagents.json`で扱います。コンテキスト整備のために実行の区切りやゲートを増やすことは前提にせず、既存のIssue・PRへの受け渡しを使います。

## 実装とテストの整理

実装の構造・命名・責任分担は、現在の要求と処理の流れを直接表すものにします。テストは現在の公開された入口を通し、利用者や呼び出し元が観測する結果や失敗条件を検証します。不具合の回帰テストも、現在守るべき振る舞いとして記述します。

分岐・補助関数・fixture・検証項目は、現在必要な振る舞いや境界を根拠に残します。移行や互換性に必要な処理は、適用対象と必要な条件を明示します。変更の経緯はIssueやPRへ記録します。

独立評価では、初回・再評価とも現在の差分と関係する呼出元・呼出先を追い、取得・検査・分岐・状態・受け渡しの冗長性を確認します。同じ対象・入力でも観測時点、外部状態の鮮度、失敗時の動作が違う場合は、必要な保証を区別します。具体的な無駄と影響が確認でき、合意範囲内の局所修正で保証を保てるものは公開前の必須修正とし、既存の指摘に整理案と残る保証を示します。好みや行数だけで指摘せず、共通化で増える引数・分岐・状態・保守も比較します。要求・権限の判断は人へ戻し、再評価を前回指摘の解消確認だけで終えません。

実装・修正担当は、テストを作成・更新する前に既存の検証で守れる条件と不足する条件を確認し、次の観点を設計と自己確認に使います。独立評価担当も、今回変更した振る舞いと関係するテストを同じ観点で評価します。

判断の中心は「このテストを削除すると、どんな現実的な不具合を見逃すか」です。必要な保証を得られる小さい実行範囲を選び、次の観点で追加・維持・統合・削除を判断します。

| 観点 | 確認すること |
| --- | --- |
| 防ぐ不具合 | 削除すると見逃す現実的な不具合を説明できるか。「念のため」、件数やカバレッジ数値の維持だけを理由にしない |
| 追加の保証 | 既存テストでは守れない利用条件・境界・失敗があるか。同じ条件を繰り返すだけなら整理し、既存検証で十分なら追加しない |
| 観測する結果 | 成果物、返却値、表示、保存状態、停止理由などが要求と一致するか。内部構造や説明文の綴りだけを固定しない |
| 検出力 | 期待値を要求から独立に定め、想定する誤動作で失敗するか。実装をコピーした期待値や、設定したモックの返答だけの自己検証にしない |
| 失敗の理由 | 対象外の条件を正常にした上で、意図した理由で停止し、必要な副作用の抑止とデータ保全も確認しているか。任意の例外や別の不正入力で通る形にしない |
| 費用との釣り合い | 追加の保証は実行時間・不安定さ・修正負担に見合うか。純粋な入力判定にGit・プロセス・フロー全体が必要かも検討する |

実行順・呼出回数でも、予算上限、二重実行防止、工程間で渡す成果物、外部APIの引数や権限など、要求上必要な契約は検証します。同じ対象でも観測時点や外部状態の鮮度、停止・保全の保証が違えば区別し、見た目の類似だけで削除しません。

型検査・ライブラリ・ブラウザー自身が保証する動作だけを再確認しません。ただし、アプリとの接続や設定の誤り、外部入力の不正、環境による失敗など、こちらのコードが対処すべき境界は結果を検証します。期待値を実装の比較関数・変換処理で生成せず、原文と修正候補、元の順序と昇順など、区別すべき結果が異なるデータを使います。文書変更と根拠変更のように別々に働く条件は、一方だけを変えても検出できるようにします。

検出力を判断しにくい箇所では、一時コピーでの不具合注入など範囲を絞った確認を使います。全テストへの不具合注入や、毎回のテスト追加は求めません。テストファイルは対象の責務で分け、各ケースの操作と期待値をそのファイルで読めるようにします。共有する試験環境や外部応答の組み立てだけを必要に応じて補助ファイルへ移し、ケースごとの状態と後片付けを独立させます。行数だけを理由に分割しません。

初回実装・修正では、今回影響する検証が防ぐ具体的な不具合、既存検証との差、追加・維持・統合・削除の理由、失う検出条件と残る検証、未確認事項を既存の `findings` に残します。独立評価では実装側の説明を追認せず、要求と関係するテストを確認し、同じ観点の判断を `assessments.tests` に記載します。この欄は既存のPR生成で本文へ渡ります。テスト整理の前後は同じ条件で実装・テスト・文書の増減と実行時間を比較し、行の圧縮やファイル移動だけを効果と扱いません。単回の実測や未測定の効果を一般的な改善と断定しません。

独立評価では、共通checkの成功だけでテストが要求を守ると判断しません。具体的な見逃しや保証に見合わない費用があれば、対象と理由を通常の指摘として修正へ戻します。件数やカバレッジ数値の低下だけを差し戻し理由にしません。「テストを弱めない」とは、合意した振る舞いの必要な保証を失わせないことです。不要なテストの削除・統合を禁止する意味ではありません。今回と無関係な全テストの監査、専用の帳票・Schema・評価スコア、監査CLIやモデル呼出しは追加せず、既存の実装・評価・PR説明を使います。評価文の形式検査は、判断の妥当性や実モデルの方針遵守を保証しません。

共通ハーネスは `scripts/`、スキルは `skills/` に置きます。対象repoの検証・必要媒体はそのrepoの `.dotagents.json` で指定します。試行商品・ブラウザーの検証・媒体・旧App版コードと履歴は[trial repo](https://github.com/thkt/dotagents-workflow-trial/blob/d0134086ad9bdddb5ed2693327cb1ffb0859c4a2/README.md)に残し、このrepoのcheckには含めません。

## 対話と方針の決定

要求を整理する質問は、Codexの利用可能な質問機能を用いて、選択肢とともにチャットへ提示します。チャットとの二重管理を避けるため、質問や回答を専用ファイルへ逐一転記しません。方針が決まった区切りで、決定内容と適用範囲、理由・根拠、合意者と確認できる記録、必要な見直し条件を残します。選択の理由を理解するために必要なら、見送った案も簡潔に記します。回答を受領したことだけで要求全体や実装の許可が合意されたとは扱いません。

個別変更の決定、合意した要求、完了条件はIssueへ、継続して適用する開発方針はリポジトリの基本ドキュメントへ反映します。提案・未合意と合意済みを区別し、基本ドキュメントには現在有効な方針を載せ、経緯はIssueやPRから辿れるようにします。合意者を特定できない場合は推測せず、未確認として扱います。

要求整理には[六つの問い](../skills/scoping/references/sufficiency.md)を使い、現在の依頼、Issue・下書き、関連コード・根拠から次の判断と不足を整理します。決定、参照、未解決事項、次の判断は既存のIssue・下書きへ必要な範囲で反映します。公開前の下書きはローカルで扱い、保存を公開許可にはしません。中断や担当交代もこの参照から再開し、現在のコード・要求に照らして再評価します。根拠変更や不足が判断を左右する場合は依存作業を止め、解消後に再評価します。

Issueの記述と出典リンクで足りれば報告書は作りません。再利用する根拠や長い検証結果が必要な場合は対象repoのresearch/へ直接保存・改訂し、既存内容、差分、版、共有範囲を確認します。既存ファイルを無確認で上書きせず、内部評価、会話全文、秘密情報、生ログを自動で取り込みません。必要な報告を含むコミットと公開先をIssueから辿れるようにし、確認済みblobと開始commitの照合を維持します。ローカル保存だけで共有完了とせず、チャットだけをチームの合意の正本にはしません。

[Issue #83](https://github.com/thkt/dotagents/issues/83)の合意により、専用セッション・評価保存CLIと機械入力の基準JSONを廃止します。全基準の入力漏れ、評価revisionの不一致、保存先binding、archiveの上書き拒否などを専用CLIで検出する保証は終了します。十分性と根拠の鮮度は担当AIが判断し、重要な判断と権限は人へ戻します。代替の状態管理CLI、必須帳票、再開台帳は作りません。実装入口のIssue・報告版・公開対象の照合と最終独立評価は維持します。旧記録と進行中のタスクは[保全方針](#旧資産の保全と登録変更)に従います。旧セッションは参照資料として必要な事実だけ読み、旧CLIの実行や評価の自動移行を新しい通常経路にしません。

要求整理は、実装に必要な要求・完了条件・検証方法と、その範囲の合意が揃うまで、必要な調査・対話・評価を進めます。事実が不足していれば調査し、意図・優先順位・許容範囲は人に確認します。実装方法の細部は既存方針や資産に基づいて担当者が判断します。

要求整理は、合意した要求・完了条件・検証方法をIssueへ反映するまで続けます。作業中は進捗を伝え、人の判断が必要なときに質問して回答を待ちます。受領後は次の作業へ進みます。Issueへの反映を終えた時点で完了を報告し、成果物のIssueを実装へ引き継げる状態にします。

独立評価は、要求の抜け・矛盾・判断の偏りを確認する必要がある場面で使います。同じ調査や質問を繰り返して新しい根拠や判断が得られない場合は、障害、確認済みの事項、必要な判断を示して相談します。

## レビューを助ける説明

PRの概要では、何が変わり、なぜ必要で、どのように確かめたか、何が未確認かを伝えます。
人が構造・意図・影響を把握し、重点的に読むコードを絞れるようにします。
ローカルcheck、最新commitのCI、独立評価、人の承認、フロー試行の結果は分けて記録します。

画面変更のPRには、対象repoで合意した検証・captureに従い、対象commitの媒体、検証コマンドと結果、未確認事項を添付します。取得と保存は[撮影手順](../scripts/README.md#prへの画像動画の添付)と対象repoの設定を参照し、人は変更した操作・表示と合意した確認点を照合します。

必要に応じて、アーキテクチャや依存関係の図、変更前後の比較、フロー図・シーケンス図、具体的な入力と結果・境界条件を使います。
画像は比較する観点に応じてtable等で並べ、変更前後・状態・画面幅の対応を読み取りやすくします。縮小して判読しづらくなる場合は分けて掲載し、原寸画像へ辿れるようにします。
画面の操作や遷移を変更する場合は、主要な利用手順の動画を撮影し、対象commitと確認する操作・状態を対応づけます。撮影準備時に、レビュアーが操作と確認点を理解するために必要な説明手段を選びます。見出しや短い説明で十分ならそれだけにします。押したキーが重要なら撮影用のキー表示、注目箇所や状態変化を示すなら字幕、操作の意図や流れを説明するなら音声を加えます。必要に応じてこれらを組み合わせ、毎回すべてを付けることは求めません。
E2E検証と定型デモ撮影は対象repoで合意した手段を使います。入力途中の挙動を示す場合は、キーボードイベントで1文字ずつ入力し、変化を見取れる間隔を設けます。
音声を付ける場合はmacOS標準音声のKyokoを使い、FFmpegで映像と合成します。操作・結果と解説のタイミングを合わせ、合成音声であることを明記します。
画像・動画のPR添付には`gh pr edit --attach`を使います。添付後は公開担当が実際のPR画面で、表示や再生に加えて、比較対象の対応、画像の判読性、動画の見出しと確認する操作の説明、縦に長すぎる配置を確認します。キー表示・字幕・音声を付けた場合は、実際の操作との一致、映像との同期、判読性や聞き取りやすさも確認します。説明が不足する場合は撮影・説明の作成担当へ戻します。配置の不備は公開担当が本文を整えて再確認し、レビュアーが比較・判断しやすい状態で完了とします。tableの使用自体は必須とせず、動画はPR内で直接再生できる状態を維持します。コマンドと確認手順は[PRへの画像・動画の添付](../scripts/README.md#prへの画像動画の添付)を参照してください。
agent-browserは、LLMによる探索的な画面確認で必要な場合に使う任意の補助手段とし、通常の検証や撮影の必須依存にはしません。
図や動画を全PRの必須項目にはしません。
図はMermaidを基本とし、そのPRで理解してほしい変更箇所・責任範囲・データの流れに絞ります。複雑な図は分割し、それでも読みづらい場合や配置が重要な場合はSVGやPNGなどの別形式と編集元を使います。図の要点は文章でも説明します。

説明は対象commitの実装と整合させ、関連コードや検証結果へ辿れるようにします。
図や成功例の動画でコードレビューや動作検証を代替したとは扱いません。

## CIとmain保護

CIの`checks`は依存を固定して導入し、このハーネスの`bun run check`を実行します。`verify`は`checks`がsuccessのときだけ成功します。PRはhead commitを検証し、コードを実行するjobに書込みtokenを渡しません。

このrepoの[main保護](https://github.com/thkt/dotagents/rules/23268675)はPR経由、GitHub Actionsの`verify`成功、最新mainとの整合、未解決会話の解消を要求します。PR作者本人が内容を確認してマージを判断できるよう、GitHubの必須Approve件数は0件です。新しい差分では古い承認を取り消します。直接push・force push・削除を制限し、bypass対象は設けていません。

公開時には対象repoの保護設定と実際のcheck登録を確認し、[対象設定](../.dotagents.json)の`checks`・`verify`が同じPR headで実行成功したことを照合します。他repoの保護・承認条件はそのrepoに従います。人が差分と検証結果を確認してマージを判断し、確認後に差分が更新された場合は最新commitの差分とCIを再確認します。エージェントは人の判断・マージを代行しません。

## TypeScriptの書き方

`scripts/**/*.ts`の書式はOxfmt 0.66.0に統一します。`bun run format`で整形し、`bun run format:check`で書き換えずに確認します。共通の `bun run check` にも書式確認を含めるため、CIでも同じ条件を適用します。2スペース・single quote・セミコロン・行幅100を基本とし、importの並べ替えは有効にしません。

Oxlintはcorrectness検査に加え、同じTS範囲で次をerrorにします。

| ルール | 揃える書き方 |
| --- | --- |
| `typescript/consistent-type-imports` | 型だけに使うものは`import type` |
| `typescript/no-explicit-any` | 明示的な`any`を使わず、必要なら`unknown`から絞り込む |
| `typescript/no-non-null-assertion` | `!`で省略せず、存在条件を確認する |
| `prefer-const` / `no-var` | 再代入しなければ`const`、再代入には`let` |
| `eqeqeq` | `===` / `!==`で比較する |
| `curly` | 制御構文の本体を波括弧で囲む |

strict型検査はtscで行い、認知的複雑度の上限15はBiomeの`noExcessiveCognitiveComplexity`だけで検査します。OxfmtとOxlintに型の整合性や要求達成まで保証させるものではありません。ルールの追加や緩和は検証定義の変更として、目的と検出力への影響をPRで説明します。

Oxlintの`typeAware`を有効にし、TSには`no-floating-promises`（`ignoreVoid: false`）、`no-misused-promises`、`await-thenable`、`no-unsafe-assignment` / `call` / `member-access` / `argument` / `return`をerrorで適用します。correctnessの型情報を必要とするルールも有効です。設定は[.oxlintrc.json](../.oxlintrc.json)、型検査の対象・条件は[tsconfig.json](../tsconfig.json)で確認できます。

設定・保存状態のJSONは[input.ts](../scripts/input.ts)でunknownから必要な形・値を確認し、テスト側も期待値を独立に検証します。型アサーション、明示的any、disableでの回避はしません。型検査は外部データの正しさを保証せず、不正入力の拒否も保存履歴の真正性や完全な意味的一貫性を保証しません。

## テストの実行完了

`bun run test:control`は`scripts/test.ts`からBunを実行し、`CI=true`でonlyを拒否します。終了成功後にJUnit集計を読み、テスト0件、skip等の未実行、必要な集計の欠落を失敗とします。レポートはOSの一時ディレクトリへ毎回作成し、終了後に削除します。固定Bunの集計形式を対象とします。

対象を絞った調査には`bun test`を使えます。提出前は引数なしの`bun run check`を実行します。テスト削除や未登録まで自動保証するものではなく、検証定義と意味のある検出力を独立評価します。実モデル、公開、登録切替、復元確認は制御テストとは別の証拠です。
