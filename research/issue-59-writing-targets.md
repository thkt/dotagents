# 目的

Geminiによる日本語の確認・修正を、人向けのMarkdown文書とGitHubのPR本文に適用する。AIへの指示、試験データ、要求の正本であるIssue本文を文章校正の標準対象から外し、不要な処理や意図しない書き換えを減らす。

Issueは、人が要求に合意し、AIが実装・評価するときに参照する正本である。条件・範囲・未確定事項を明確にし、要求の抜けや矛盾を確認する。文章の推敲と要求の精査を分ける。

## 合意した対象

- 対象：README、設計書、操作説明、研究・検証記録など人向けの文書、およびGitHubのPR本文。
- 標準対象外：GitHubのIssue本文とその下書き。Markdownとして保存した場合も用途に沿って対象外とする。
- 対象外：AGENTS.md、SKILL.mdなどAI向けの指示、プロンプト、テスト用データ、Markdown以外のファイル。

依頼者は2026-09-14に人向けMarkdownへの限定を依頼し、当時はIssue／PR本文も含めると合意した。2026-09-16の本対話で、Issue本文は標準対象外とし、PR本文と人向け文書を対象にする方向を提示したところ、依頼者から「その対応もissueにしましょう」と依頼を受けた。このIssueでは対象区分を今回の合意へ更新する。

外部送信の許可と文章確認の対象選択は分け、対象は上の用途によって選ぶ。

## 完了条件

1. documentsモードが拡張子だけで全Markdownを選ばない。対象repoで人向け文書のパスを指定できるようにし、未指定時の保守的な既定値と指定方法を説明する。AI向けの既知のファイル名・指示配置やテストfixtureは除外する。
2. 単一ファイルを明示するfileモードは、人向けMarkdownとPR本文に用いる。既知のAI向け指示と非Markdownはモデル起動前に拒否する。通常のIssue作成・更新ではGemini校正と、その校正候補に対する意味照合を起動しない。Markdownに保存したIssue下書きも、文書の一括確認へ紛れ込まない。
3. 人向け文書、PR本文、Issue本文、AI向けファイルが同時に扱われても、対象の本文だけをGeminiへ送り、対象外は文章確認処理で書き換えない。Issue本文やAI向けファイルだけの作業で、Geminiを起動しない。
4. 校正対象については、候補の意味確認、対象や根拠が変わった場合の採用拒否、保護対象の照合、原文・停止・スキップ記録の保持を維持する。対象選択が変わって新たな文書が入る場合も、古い候補を採用しない。
5. Issueの要求の抜け・矛盾・曖昧さ、合意や根拠との一致はscopingで確認し、必要な独立評価と人の合意を維持する。Gemini校正を外したことを、要求の精査を省略したり、要求が正しいと保証したりする理由にしない。実装の独立評価も変更しない。
6. 新しい依存を追加せず、既存の標準APIとBunを使う。設定・CLI・開発方針・scopingのIssue公開手順と回帰テストを整合させる。引数なしのbun run check、独立評価、同じPR headのchecks・verifyを確認する。
