# Issue #73の参照引き継ぎの確認

## 対象と問い

[Issue #73](https://github.com/thkt/dotagents/issues/73)の実装準備として、根拠・版・適用条件・合意状態が要求整理から実装、修正、独立評価、PR説明へ届くかを確認した。開始commitは`6a3d7a05d9592a7de169ecea12e7c2176c0b8b45`である。本記録はその版に対する今回の差分と模擬検証の記録である。現行操作の正本は[CLIガイド](../scripts/README.md)であり、要求の正本はIssueと合意記録である。

Issue草案と同じ内容の未コミット資料は、別報告として取り込まない。開始版にある[過去のフロー整理](workflow-simplification.md)は歴史的な背景であり、現在の合意や検証成功の代わりにはしない。

## 代表例で見つかった不足

一覧のリセットを例として、マウス操作で観測した結果、未確認のキーボード操作、未合意のフォーカス移動案を選ぶ場合の流れを追った。scopingには出典・版・適用理由を評価へ残す手順があり、#70の入口は必要報告の開始commit・blob・checkout本文を確認する。しかし、開始版のdevelopmentはその参照一覧を初回実装だけに渡し、correctionの修正や独立評価には渡していなかった。そのため、評価側が同じ報告を選ぶことは入力契約として保たれていなかった。また、評価結果の文書選択理由は内部記録に残るものの、PRへ使う要約には含まれていなかった。

| 区切り | 選択・確認する担当 | 今回の対応と次への受け渡し |
| --- | --- | --- |
| 要求整理 | scoping担当が関連資料を選び、現在の実装・版・合意と照合する | 既存の`referencePaths`は候補のまま維持する。内部評価にだけ残る根拠は、Issueまたは選んだ報告からたどれるよう引き継ぎ手順を補足する |
| Issue | scoping担当が要求・適用する根拠・未合意事項を区別し、人が要求と権限を判断する | 既存のIssue反映と報告引き継ぎを再利用する。Issue案の全文と同じ報告や、新しい必須帳票は作成しない |
| 初回実装 | ホストが指定報告の版を確認し、実装AIが適用条件と合意を確認する | #70の版確認を再利用する。初回・修正・評価に共通の参照説明を渡し、仮説採用と効果確認を区別する |
| 修正・独立評価 | ホストが開始版の参照と評価対象を固定し、担当AIが現在の根拠と比較する | 既存の検証設定へ`reports`を渡す。報告改訂は通常の差分として評価し、開始時のblobは保持する。判断を妨げる不足は必須の未解決指摘へ戻す |
| PR説明 | 評価担当が根拠・未確認事項を記し、公開担当が本文へ渡す | 既存の評価要約へ文書の役割と選択理由を含める。公開・添付・人の判断は既存handoffを再利用する |

## 選んだ方法と更新負担

Issueと既存報告の文章を使えば、根拠の意味と適用条件を表せる。ただし、報告を選び直すだけでは、初回実装と評価で同じ参照を使うことが明示されない。そこで、既存の`--report`からパスとblob IDだけを検証設定や評価対象記録へ自動で渡した。独立した参照台帳を作る案や、適用条件・合意を新しいJSON/YAMLへ複製する案は採用しなかった。

たとえばキーボード操作を追加調査したときは既存報告を改訂し、合意した要求を変更する必要があればIssueへ戻る。引き継ぎ用の別文書や設定へ報告本文を更新する必要はない。モデルは開始版と現在の報告を比較できる。`.dotagents.json`の役割や実行の区切り、モデル予算、ゲートは増やしていない。

## 検証と検出範囲

対象は`discovery.test.ts`、`development.test.ts`、`review.test.ts`、`correction.test.ts`である。既存テストを再利用し、次の不足分だけを追加・補強した。

| 条件 | 確認方法と、削除した場合に見逃す不具合 |
| --- | --- |
| 初回から検証への受け渡し | 既存developmentケースに設定の参照一覧・開始commitの照合を追加した。削除すると初回だけが報告を受け取る欠落を見逃す |
| 適用範囲・提案・根拠更新 | 1つの模擬修正・評価ケースで異なる適用範囲と未合意の提案を持つ資料を使い、両プロンプトの参照一致、開始blobの保持、更新後の文書hash、要約への役割・選択理由の反映を確認した。削除すると更新後の本文で開始参照を上書きする不具合や、評価やPR説明で選択理由を落とす不具合を見逃す |
| 古い参照 | 既存developmentの欠落・未commit・別blob・別開始版・setup書換えの拒否を再利用した。単独correctionにも古いblobを渡し、check前に停止してソースを保持することを追加確認した |
| 不定の開始版・重複 | 既存の設定拒否テストへ、報告ありで`baseCommit`がない場合と同じパスに複数のblobがある場合を追加した。削除すると別HEADへの暗黙の結び付けや曖昧な参照を見逃す。あわせて既存ケースの停止理由も具体化した |
| 未評価の根拠変更・矛盾する応答 | discoveryのnote後の評価無効化、古いrevision拒否、reviewの必須未解決指摘を含むaccepted拒否、correctionのIssue・文書変更後の成功再利用拒否を再利用した |

新規の模擬修正・評価ケースは約0.3秒、古いblobの単独入口ケースは約0.1秒だった。実モデルやネットワークは使わない。文章の完全一致で意味判断を検証するテストは追加していない。関連する既存ケースは異なる失敗条件を守っており、削除したものはなく、失った検出条件もない。

対象4ファイルのテストは成功した。型検査と変更したTypeScriptのlint・書式・複雑度も確認した。これらは参照・版・制御の検証であり、モデルが適用範囲や未合意の提案を正確に判断することを実測したものではない。外部資料の真正性・更新、人の合意、実際のGitHub公開も検証していない。

## ホストへ残す確認

合意済みの「コンテキスト整備の設計原則」が[開発方針](../.codex/DEVELOPMENT.md#コンテキスト整備の設計原則)の差分に含まれ、依頼時の本文と一致することを確認した。この方針とコード・文書を合わせてレビューする。他の未公開ローカル資産は取り込んでいない。

スキルのメタデータ検査はPyYAMLがないため未実施である。全体の`bun run check`、変更文書の日本語確認、独立評価、同じPR headの`checks`・`verify`、公開と人のレビュー・マージ判断はホストへ引き継ぐ。内部ログや評価記録は成果物へ追加していない。

#69の公開PR本文生成、#71の結果再利用、#72のCI分類は変更対象外である。PR差し戻しのCLIやQA向け確認ガイドの自動生成・共有は後続方針であり、今回実装した機能とは扱わない。
