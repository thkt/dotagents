# 調査成果

scopingで再利用する調査成果と未採用の提案をGitで管理します。報告には、問い、出典と対象版・確認日、結論、適用条件、未解決事項を残します。別の開発者やcloneでも読める参照先を使い、ホスト内の絶対パスだけを根拠にはしません。採用した仕様や方針は、関連する既存ドキュメントやIssueへ反映します。

新しい報告の保存には[scopingのarchive](../skills/scoping/references/session.md#保存と制約)を使います。現在の根拠が十分な場合だけ、対象checkoutのresearch/へ選んだ報告本文をそのまま保存します。入力Markdownにはscoping-research-storage.mdのように内容を表す名前を付け、その名前で保存します。同じ調査には既存の名前を使います。別名の同一本文をCLIが重複排除するとは扱いません。セッションの絶対パスや内部評価は付加しません。本文自体に含まれる情報の公開可否は担当者が確認します。

同じ調査の改訂は既存ファイルを編集し、Gitで履歴を残します。変更した根拠を[判断前の評価](../skills/scoping/references/session.md#判断前の評価)にまとめ、必要な文章確認を行ってから差分を共有します。評価前に作業が続く場合はnoteで旧評価を無効にします。archiveは同名・同内容の再保存を受け付けますが、同名で別内容のファイルを自動で上書きしません。

保存したファイルは自動でcommit・pushされません。[引き継ぎ手順](../skills/scoping/references/session.md#調査成果の引き継ぎ)に従い、確認済みの報告を通常の変更やPRに含めます。対象Issue、必要な報告のパスと確認済みblob ID、開始commitを実装担当へ渡します。開始HEADに報告本文が含まれ、確認済み内容と一致し、checkoutがcleanであることを確かめます。ローカル保存、commit、公開の状態を分けて報告し、不足があれば引き継ぎ未完了とします。

セッション状態、評価、lockはcheckoutやGit管理領域の外に置きます。別worktreeやcloneへの調査成果の共有はGit経由で行い、過去の評価や合意を自動で引き継ぎません。外部保存庫の調査や旧Research資料は一括移管や削除をせず、必要な根拠を確認して共有用の報告へまとめます。旧stateの変換や再開は行いません。旧資産の保全条件は[開発方針](../.codex/DEVELOPMENT.md#旧資産の保全と登録変更)を参照してください。
