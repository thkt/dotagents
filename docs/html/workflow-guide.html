このガイドについて

AIに開発を任せるとき、何を伝え、どこまで任せ、何を確かめて受け入れるか。このページは、初めてハーネスを導入する人が、一連の流れをつかむためのガイドです。

ここでいうハーネスは、AIの役割、実行手順、検証、停止条件、記録を組み合わせて、開発の進め方を支える仕組みです。dotagentsを例に、依頼から変更を作成し、人のレビューへ渡すまでの流れを読み解きます。

入口は2つあります。要求を整理する scoping と、合意したGitHub Issueから実装・検証・PR作成を進める implement です。まず全体像と導入準備を確認し、次に各工程で誰が何を判断するかをたどります。

記事の範囲には、ハーネスを使って開発するアプリ・サービスのリリース、稼働確認、振り返りまでを含めます。要求整理から人のマージ判断までは、現行の文書やコードに基づく説明です。既存PRの修正は、人が採用した指摘から同じ開発CLIで検証・更新まで進みます。関係者向けの確認資料は、担当AIや人が対象アプリの運用に沿って用意します。資料の自動生成・共有はCLIの機能には含まれません。リリース以降については、アプリごとに異なる運用を検討するための共通の判断や確認の流れを説明します。具体的な手順は、各アプリで定めるものとして区別しています。

01

まず、流れを一枚でつかむ

流れの中心は、要求を揃える → Issueに合意を残す → 実装する → 確かめる → PRで伝える → 人が判断する、という受け渡しです。

  1. 依頼を受け取る。 誰の何を改善するのか、対象はどこかを確認する。
  2. 調べ、対話する。 現状と根拠を調べ、人にしか決められないことを尋ねる。
  3. 要求を合意し、Issueへ残す。 範囲、完了条件、検証方法、実装に必要な許可を合意し、その根拠を残す。
  4. 実装する。 合意済みIssue、対象repoの.dotagents.json、必要な根拠を照合する。新規実装は隔離worktree、既存PR修正は照合済みcheckoutで変更を作る。
  5. 検証し、独立評価する。 必要な撮影・checkを行い、別のAIがコード・テスト・文書を評価する。必須の不備を修正し、最新の成果物を再検証・再評価する。
  6. draftで公開し、確認後にreadyへ移す。 担当AIが実際の本文・必要媒体と同じcommitのCIを確認し、最新の対象を再照合してレビュー可能な状態へ移す。
  7. 人がレビューし、マージを判断する。 要求、差分、検証結果、残る不明点を照合する。

戻り先は、不足の種類によって変わります。事実が足りなければ調査へ、意図や許可が未確定なら人への確認へ、成果物に不備があれば修正へ戻ります。要求そのものが変わったら、古い合意や検証結果をそのまま使って進めません。

scopingはIssueと調査の引き継ぎまでを担当します。その呼び出しの中で商品実装を始めることはありません。implementは合意済みIssueの実装依頼、または人が採用した既存PRの修正依頼から始まります。

人が採用したPRの指摘には、指摘を調べる → 見直す範囲を判断する → 必要な調査・合意・修正へ戻るという往復があります。要求の前提が変われば、Issueの合意から見直します。

関係者への引き継ぎと、その先のリリース → 稼働確認 → 振り返り → 次の要求整理は、担当AIや人が対象アプリの手順に沿って進めます。CLIの自動実行には含まれません。確認ガイドの自動作成・共有もCLIの機能には含まれません。

02

初めて使う前に、揃えるもの

初めて導入するときは、対象のアプリ・サービス、AIに任せる範囲、検証方法、人が判断する場面を揃えます。このハーネスが現在対応するのは、明示的に設定したGitHubリポジトリ、macOSホスト、github.comです。

最初に確認するもの

  1. 対象のリポジトリと要求。 どのアプリを変更するか、どこに要求を残すか、誰が範囲とマージを判断するかを確認します。まだ作るものが決まっていなければ、scopingから始めます。
  2. 実行環境と認証。 ハーネスはBun、Git、gh、Codex CLIを使います。Bunは1.4.2を指定しています。スキルが利用先から検出され、信頼するCLIと対象repoを参照できることも確かめます。
  3. 対象repoの設定。 .dotagents.json に、repo、remote、base branch、セットアップ、check、必要なCI名、撮影の要否と保存先を明示します。対象アプリの技術構成と要求に合わせます。
  4. 検証で確かめる振る舞い。 どの操作や結果が合格なのか、既存テストで何を守れるか、画像や動画が必要かを決めます。CIのないrepoは空のCI配列を明示し、公開しない実行でローカル検証まで進められます。公開する開発実行には、1件以上の必要CI設定が要ります。
  5. 公開と運用の手順。 アプリのマージとリリースの関係、稼働確認、問題があったときの対応を確認します。この記事では共通の考え方を説明し、担当、実行手段、確認条件は対象アプリの運用に合わせて揃えます。

ハーネスの導入時には、信頼するハーネスのcheckoutで依存関係を揃え、共通checkを実行します。これはハーネス自身の確認です。対象アプリのテストや実際の公開が成功したことまでは示しません。

bun install --frozen-lockfile --ignore-scripts
bun run check

日常の入口は scoping と implement です。詳細な設定例、実行コマンド、スキル登録、中断時の手順は出典のCLIガイドと根拠の保存・引き継ぎ手順を参照してください。通常のIssue実装は development.ts を通します。担当者向けの評価試行は review-probe.ts から修正なしのレビュー1回で終了します。

.dotagents.json は何の設定か

このハーネスが、開発対象のリポジトリを扱うために読む設定です。 対象リポジトリのルートに置きます。Codex一般の設定ファイルではありません。ファイル名と読み方はdotagents側の実装で決まっており、対象の照合はscripts/shared/target.tsが担当します。

現在のハーネスは、実装や評価のためにCodex CLIを呼び出します。.dotagents.jsonを読み、対象リポジトリを照合して準備・検証・公開へつなぐ処理は、このハーネスのコードが担当します。設定は、Issue公開時の対象確認、実装の準備、PR公開時の照合で使います。モデルの選択は、現行のreview.tsやcodex-actor.ts側で扱います。

内容の精査は、何と何を比べるのか

設定の検査。 .dotagents.jsonのcheckが空でないシェル文字列または有効なargv配列かどうかは、CLIで検査できます。そのコマンドが今回の不具合を検出できるかは、Issueが期待する振る舞い、実際のテスト、変更後のコードを照らして判断します。

要求整理の精査。 sufficiency.mdの六つの問いを使い、担当AIが出典、対象版、適用範囲と合意を照合します。十分性を判定する専用CLIはありません。判断を左右する不足はIssue・下書きに残し、調査や人の回答で解消してから再評価します。AIの評価を人の合意や実装許可には読み替えません。

文章の精査。 執筆担当と独立評価担当は、読みやすさに加えて、数量、否定、条件、範囲、権限、断定の強さ、参照先を原資料と照合します。「まだ試していない」ことを「確認できた」と説明していれば、修正へ戻します。事実そのものに根拠がなければ調査へ戻します。

実装の精査。 独立評価では、テストの成功や実装担当の説明だけで結論を出さず、現在の差分と影響を受ける呼出元・呼出先、境界条件、失敗時の動作、関連テストを読み、具体的な冗長性も確認します。前回の指摘を修正済みや非該当とする判断も、現在の成果物と必要な検証で確かめ、理由を残します。

たとえば「一覧を名前順にする」という要求なら、表示が変わったことに加え、同名の項目、空の一覧、絞り込みとの組み合わせなど、今回の仕様に関係する条件を調べます。どの条件が必要かは対象アプリの要求と実装から選び、不明な期待値を推測で補いません。この例をすべての変更に対する必須チェックリストにはしません。

既存PRの修正はdevelopmentで検証・更新します。QA・デザイナー・企画向けの確認ガイドの自動生成・共有はCLIの機能には含まれません。担当者や対象アプリ固有の確認条件で未確定のものは、その実装や運用を具体化する際に確認します。

判断の前提を、たどって見直せるようにする

実装開始の条件はwikiで説明し、必要な根拠を同じ版で各工程へ渡します。 要求・許可はIssue、根拠の版付き引き継ぎは報告参照、実行制御はホストが担います。

目的・概念・振る舞いを、根拠と結び付ける

このガイドでは、Teleologyを「何を望ましい状態とするか」、Ontologyを「何が存在し、どんな意味や関係を持つか」、Nomologyを「どんな規則があり、どう動くと考えているか」をそれぞれ問う観点として使います。目的・概念・振る舞いを考えることと、それを型やデータへ表すことは分けます。三つを順番に確定する工程にはせず、分かったことに応じて互いを見直します。

これらに根拠と合意状態を結び付けると、何を前提に判断したのかを説明できます。

観点残したいこと見直すきっかけの例
目的誰の何を改善し、どこまでを望ましい状態とするか利用者の困りごとや優先順位が変わった
概念と関係対象の意味、関係、状態同じ用語を担当者ごとに違う意味で使っていた
規則と仮説守る条件と、検証したい振る舞いや因果の見立て例外が見つかった、想定した結果が得られなかった
根拠出典、観測、対象の版、適用条件引用資料が古い、今回の利用条件には当てはまらない
合意と未確定事項採用済みの判断、提案、未確認のこと、判断する人要求や許可範囲が変わった、必要な判断が残っていた

これは必要な情報を選ぶための見方です。すべての変更に五つの文書や新しいチェックリストを要求するものではありません。

合意した規則と、確かめたい仮説を分ける

依頼の対応漏れを減らすアプリを考えると、例えば次のように整理できます。以下は説明用の仮想例であり、特定アプリの要求・合意や観測結果ではありません。

  • 目的：期限を過ぎた依頼の見落としを減らす。
  • 概念：依頼、担当者、期限、対応状態があり、依頼が担当者や期限と結び付く。
  • 合意した規則の例：「確定した依頼には担当者を割り当てる」。
  • 検証する仮説の例：「期限超過を一覧で強調すると、見落としが減る」。
  • 根拠：実際の利用で何が起きたかを確認する。観測がなければ、効果は未確認とする。

規則は守ると決めた条件であり、仮説は観測によって見直す対象です。仮説を採用して機能を作っても、効果を確認したことにはなりません。画面の変更と、その変更によって困りごとが解消されたかの確認を結び付けます。

機械・AI・人が、それぞれ確かめる

機械は、参照先の存在、IDの重複、定義した状態遷移や入力形式などを確認できます。こうした検査を通っても、目的が適切か、引用した根拠が今回に当てはまるかは、内容を照合する必要があります。

AIは資料の適用範囲や意味の整合を読み、更新候補と理由を示します。人は目的、許容範囲、権限や重要な変更を判断します。機械の検査とAIの評価にはそれぞれ限界があり、事実や合意を自動で保証するものとは扱いません。

必要な根拠を同じ版で渡す

現行の開始条件はwikiを手で更新します。必要な報告だけを選び、path・Git blob・開始commitで照合して初回実装・修正・独立評価へ渡します。適用条件、合意、未検証事項は原本と現在の差分から判断します。

wikiの作成をすべてのrepoの開始条件にはしません。必要な資料を要求と適用条件から選び、内容の意味と対象の版を確認します。

今のフローへつなぐ

04

依頼を、判断できる要求にする

scopingは、依頼本文と対象リポジトリから始まります。既存のIssueや合意があれば読み、すでに決まっていることを聞き直さず、今回決めることを特定します。

調査では、現在のコード、テスト、依存の版、関連する方針を照合します。過去の調査を使うときは、読む条件と参照先も手掛かりに原文を選び、現在への適用を確認します。該当する資料がなければ検索を続けます。UIなら既存部品、画面、操作状態、キーボードや画面幅の条件を確認します。ロジックなら入力と出力、値の制約、失敗や非同期処理、責任の所在を確認します。

資料・コード・ログ・テストで判断できず、観測結果が次の方針を変える場合は、許可された環境で小さな実験・試作・再現を選びます。実行前に、何を決めるか、どの結果で仮説を支持・除外できるかを定め、本番コードから分離した一時領域で確かめます。既存の根拠で足りる場合は実験を増やしません。

観測した版・環境・入力と適用限界を残します。並行実行・中断・外部状態・永続化が問いなら、それを観測できる環境が必要です。インメモリの成功を実システムの保証にはしません。判断に十分な根拠が得られたら止め、結果を区別できなければ未確認として次の調査や人の判断へ戻します。詳しい条件は小さな実験の条件を参照します。

既存部品、標準API、導入済みライブラリで目的を満たせるかも調べます。既存コードがあることだけで、今回の適切な見本と判断することはありません。適用できる理由と、今回足りない部分を選びます。Storybookなどの特定の資料がないことだけで停止する運用でもありません。

事実は調べ、意図は尋ねます。 誰の何を改善したいか、優先順位、どこまでを許容するか、どこへ公開してよいかは、人の判断を確認します。質問には、その答えがどの判断を変えるのかを添えます。回答が必要な作業は待ち、答えに依存しない調査や案の準備を進めます。

次へ進む前に確かめる六つの問い

  • 目的： 誰の何を改善し、次に何を決めるのか。
  • 根拠： 出典、対象の版、鮮度、適用範囲が分かるか。
  • 制約・代替案： 制約、依存、代替案、既存資産の再利用を確認したか。
  • 不確実さ： 残る不明点は次の判断を変えないか。
  • 整合： 要求、事実、方針、合意に矛盾はないか。
  • 権限： 次の作業の対象と範囲に必要な合意・権限があるか。

未確認を充足に含めず、今回関係しない観点はその理由を説明できるようにします。重大な不足を、ほかの項目の充足で相殺しません。調査を始める判断と、実装を始める判断では、必要な情報の深さも変わります。全項目の回答を別の帳票へ保存する必要はありません。

判断の区切りで、要求・完了条件・検証方法、合意の範囲と根拠、観測の証拠・適用限界、未解決事項、次の判断を既存のIssue・下書きへ反映します。試作コードを合意済み仕様や実装成果物として渡さず、試作の成功を採用・本実装の完了とは扱いません。専用セッションの開始、評価JSONの保存、gateの実行は行いません。根拠変更や不足が判断を左右する場合は依存作業を止め、影響と解消方法・再開条件を残します。書式を埋めたことや保存成功は進行許可になりません。

中断・担当交代でも、Issue・下書きの決定、参照、不足から再開します。現在のコード・要求に照らして再評価し、前回の完了表示を自動で引き継ぎません。新しい再開台帳や会話全文のコピーは作りません。

要求の抜け、矛盾、判断の偏りを確かめる必要がある場合は、要求整理でも独立評価を使います。担当者が評価し、未実施なら未実施と記録します。調査や質問を繰り返しても新しい根拠や判断が得られない場合は、障害と確認済みのこと、必要な判断を示して相談します。

ここで残るもの： 現在の根拠、未解決事項、次に判断すること、合意した方針への参照。次へ進む条件は、その判断に必要な情報と合意が揃っていることです。既存の有効な合意は聞き直さず、新しい判断が必要な場合だけ人へ戻します。回答後も現在の根拠・条件との整合を確かめてから進みます。

合意を、Issueと調査報告へ渡す

要求の正本はGitHub Issueと合意記録です。会話で回答を得たことだけで、要求全体や実装の許可に合意したとは扱いません。

Issueには、目的、今回の範囲、完了条件、対象repoのセットアップ・検証方法、必要な画像や動画と保存先、合意の根拠をまとめます。実装方法の細部は担当者が判断できる余地を残します。実験の計測手順や試行回数は、成果物の要求と区別します。

案だけ・公開しない依頼では、必要な調査とIssue本文の下書き・精査まで進め、公開用の書込み権限確認を必須にしません。Issueを公開・更新するときは、既存Issueとの重複を調べ、公開前に対象repo、GitHubの実効ユーザーと権限を確認します。担当AIは要求の抜け・矛盾・曖昧さと、合意・根拠との一致を精査します。必要な独立評価と人の合意を揃え、要求の精査を完了します。公開・更新後はIssueを読み戻し、その結果で本文・対象repo・URLと、今回の決定・合意範囲・根拠・未解決事項・次の判断をまとめて確認します。同じ本文の確認を終えたら、必要な報告の引き継ぎへ進みます。

通信断などで結果が不明な間は、担当AIが一覧と本文で実状態を確認し、再試行や公開完了の扱いを保留します。本文・判明した状態・残る確認を保持し、重複作成を避けます。権限不足では本文を保全して必要な対応を人へ伝えます。本文の不足・不一致は要求精査へ戻し、事実は調査し、要求や許可は人が判断します。判断を左右する不足があれば依存作業を止め、解消後に再評価します。

Issueの記述と出典リンクで足りれば報告書は作りません。再利用する根拠や長い検証結果が必要な場合だけ、問い、出典と版・確認日、結論、適用条件、未解決事項を対象repoの docs/research/ へ直接保存・改訂します。既存内容、Git差分、版、共有範囲を確認し、無確認で上書きしません。内部評価、秘密情報、生ログを自動で取り込むこともありません。

報告の選択・合意・共有状態は保存と引き継ぎの手順で扱い、具体的なGit操作と実装開始時の検証条件はCLIガイドで確認します。報告が未共有でも、必要な版と開始条件を満たせば、許可された範囲の公開しない実装へ進めます。commit自体の許可が不足する場合は、それに依存する引き継ぎを保留します。

06

実装する対象と、検証条件を固定する

implementは対象Issueを特定し、合意済みの要求と、対象repoの .dotagents.json を照合して始まります。この設定には、repo、remote、base branch、セットアップ、check、必要なCI、撮影方針が入ります。

検証方法が未設定なら、実行に必要な設定を推測で補って開始しません。未知の設定キーはモデル実行・公開前に入力形式エラーとして拒否します。対象repoの方針と設定を確認してから新規実行を始めます。対象repoの言語やテストツールは、そのrepoの設定に従います。ハーネス自体はBunで動きます。

ホストは、checkout、設定、fetchとpushのremote、GitHubのrepo ID、base branch、既存のgh認証による実効ユーザーを照合します。公開する実行ではpush権限も実装前に確認します。途中で主体を別のユーザーへ自動で切り替えることはありません。

新規実装は起動時のHEADを開始commitに固定します。ローカルの .dotagents.json は通常ファイルであることが必須ですが、commit・pushは任意です。追跡済みなら開始commitのblob・本文・index・モードへ照合し、開始commitにない場合はindexへの追加を拒否します。読み込んだ設定原文を固定し、未追跡・ignoredなローカル設定も作業用worktreeへコピーします。設定はcommit対象から除外し、実行中の原文変更と追跡状態の変更を検出します。ignoredなローカル設定もsnapshotへ含めます。選択した報告の本文・版・index・モードも照合します。必要入力の不一致、既存の実行保存先や同名branchでは開始しません。無関係な未コミット差分・未追跡ファイルは元のcheckoutへ残せます。

必要な調査報告がある場合、開発CLIへ--start-commitと--report パス=確認済みblob IDを渡します。CLIは開始HEAD、報告がcommit内の通常ファイルであること、確認済みの版、実際の本文を照合します。欠落・未コミット・内容の違いがあれば停止し、確認せず新しいIDへ差し替えません。

新規実装は要求全文と対象情報を保存し、照合した開始commitから分離したworktreeと codex/development-N branchを作ります。worktreeは、元の作業場所と分けて同じリポジトリの変更を作るための作業場所です。設定されたセットアップの後も、隔離先と元checkoutの両方で同じ必要入力を照合してから実装AIを起動します。報告や開始commitの指定がない場合も、起動時に固定したHEADから始めます。

必要な報告のpath・blob・開始commitを初回実装、修正、独立評価へ渡します。報告を改訂した場合は開始版との差分を評価し、根拠・適用条件・合意状態を確かめます。ファイルの一致だけで資料の十分性や意味の正しさを保証するものではありません。

既存PRの修正は、採用済み指摘と前回公開runからの開始条件に従い、同じcheckout・branchと新しい実行保存先を使います。

合意を経てIssue本文を更新した場合も、既存PR修正の開始時に最新のopen Issueを読み、その本文で新runを固定できます。前回runの要求や検証を現在の成功として引き継がず、開始後に要求や実行条件が変われば停止します。

ここで残るもの： 開始時の要求と設定、主体、作業場所、実行記録。以後、要求や対象、設定、主体が変わった場合は停止し、古い条件のまま続行しません。

07

作り、確かめ、必要なところを直す

実装担当のAIは、Issue全文と既存資産を読み、コード、文書、撮影定義を用意します。合意範囲内の通常の実装判断は進めます。要求・範囲・権限・実行上限の変更が必要なら、初回実装も追加修正もneeds_humanを返し、既存のfindingsに問い・人に必要な選択・影響を説明して、回答に依存する作業を止めます。指示ファイルが原因なら、実際に読んだファイルへのリンクと該当文を示し、明示条件と解釈を区別します。

初回実装・追加修正・既存PR修正の前に、ホストが固定した実装前baselineと別workspaceを用意し、履歴を継承しない新しい独立テストセッションを起動します。テスト担当は合意済みIssue、必要な仕様・既存検証、人が採用した固定の修正要求から検出条件を判断します。実装中の会話・判断・新実装の説明は期待値の根拠に渡しません。既存検証で十分ならunnecessaryとして追加せずに進めます。

ホストは応答形式、入力識別値、変更manifestと保護対象を検査して成果物を転送します。工程失敗・不正応答・不一致では後続の実装と公開を止め、原応答と未完了成果物を保全します。実装担当は受け取ったテストを使います。期待値・fixture・機械的な接続の変更も独立担当へ戻し、Issueと照合します。詳細と保証の限界はCLIガイドと開発方針を参照してください。

文書だけのIssueも同じフローで扱います。文章や構成の整備という要求に対して、不要なコードやテストを追加することは求めません。実装に伴って操作、設定、仕様、制約の説明が変わる場合は、その文書更新も成果物へ含めます。

初回はIssue全体の要求を実装し、追加修正は検証や独立評価で見つかった原因を直します。通常の追加修正・独立評価は、回数だけでは止めず、合意範囲の必須指摘を解消します。

人の判断が必要な場合は、問いと影響を示して止めます。理由を欠く応答や形式不正も停止し、作業と記録を保全します。担当者の申告だけで判断済みにしません。応答の形式と停止理由はCLIガイドで確認できます。

ホストによる検証

実装後は、ホストが 必要な撮影 → 対象repoのcheck の順に進めます。実装担当は調査や修正に必要な箇所を確認し、全体のcheck、ブラウザーやサーバーの起動はホストへ渡します。

既存PRの修正では、保存状態と修正対象を確認してから検証します。対象が変わった場合は撮影・check・モデル実行へ進まず、元の作業と記録を保全します。書込みや公開を挟む照合も続けます。

このハーネス自身のcheckは、件数の要約と失敗診断を残します。テストの出力と一時レポートの扱いはCLIガイドを参照してください。

checkが通常の不合格を返した場合や、撮影処理に修正可能な失敗がある場合は、ログを修正担当へ渡します。起動不能、時間切れ、対象の変化などは停止条件として扱います。

同じ時点に得た情報は共用できます。撮影・check・モデル実行などを挟むと対象が変わり得るため、必要な再照合は続けます。

通常の経路に含まれない検証を、担当AIへ引き継ぐ

初回実装と追加修正には、設定済みのcheck・captureの契約を渡します。その実行を待つだけならrepairedです。通常経路に含まれない受入検証が必要なら、担当AIはneeds_hostと、必要な検証・不足理由・対象版・期待する証拠を返します。CLIはhost_verification_requiredで止まり、同じ未解決条件でcheck・評価・修正を繰り返したり公開したりしません。

  1. developmentが停止成果物と記録の参照をhost-stop.jsonとhost-artifacts.jsonへ保存します。担当AIは既存権限と対象版を確認して追加検証を行います。証拠に書かれたコマンドを自動実行する機構ではありません。

  3. development.ts --host-run … --host-evidence … --run-dir …で、旧runの隣にある新しい保存先へ渡します。同じcheckoutの未コミット成果物、停止時HEAD・branch、元の差分基準を保ち、setup後に独立テスト工程へ戻ります。初回実装が済んでいれば再実行せず、初回テスト工程の停止で未実行なら、テスト完了後に未実行の初回実装へ進みます。その後、必要なcapture・check・独立評価へ進みます。

draftでも本文は閲覧可能です。後から修正しても開示は取り消せません。readyへの切替は人の承認・マージを代行せず、操作間の他者変更を完全に防ぐ保証でもありません。

ここで残るもの： PR URL、対象commit、ローカル検証・独立評価・CIの結果、必要な媒体確認の状態、人に残る作業。PRができてもCIを確認できなければ、URLと記録を保って未達として報告します。

人が、変更を受け入れるか判断する

人は、何が変わり、なぜ必要で、何を確かめ、何が未確認なのかをPRから読み取ります。Issueの要求と差分を照らし、検証がその要求を守っているかも確認します。

検証コマンド、テスト、lint設定、対象選択、依存などを変える場合は、検出できなくなる条件とその対応を説明します。CI成功だけで要求達成や検証の妥当性を保証するものではありません。人が検証の無効化を見落とした場合まで、この仕組みが防ぐとは扱いません。

dotagentsリポジトリの方針では、mainへはPR経由で入り、必要なCI、最新mainとの整合、未解決会話の解消を確認します。PR作者本人も内容を確認してマージを判断できる運用です。他のrepoの必須承認条件は、そのrepoに従います。保護設定の実状態は公開時に確認します。

確認後に差分が更新された場合は、最新commitの差分とCIを再確認します。エージェントは人の判断、承認、マージを代行しません。

指摘があれば、まず根拠と影響範囲を調べます。 人が対象PRと指摘を示して依頼し、担当AIが見直す範囲と戻り先を判断する方針です。必要ならIssue作成から見直します。次の章で、この往復と現行CLIとの接続を説明します。

PRの差し戻しを、次の修正につなぐ

合意した既存PRの修正は、同じdevelopmentで進めます。 差し戻しは、人が対象PRと指摘を示して依頼するところから始まります。担当するAIは、指摘の根拠を調べ、何を見直す必要があるかを整理します。原因の名前だけで戻り先を固定せず、調査資料・Issue・設計・実装・検証・説明への影響を確かめます。

修正を始める前に、四つの問いを確かめる

  1. 指摘は何を根拠にしているか。 対象のcommit、引用した資料、その版と適用範囲、コーディングルール、実際の動作を照合します。指摘の内容も、確認すべき情報として扱います。
  2. どこまで見直す必要があるか。 根拠を直したときに、Issueの要求、設計、実装、検証や説明のどこへ影響するかを調べます。
  3. 以前の合意は引き続き有効か。 目的、完了条件、範囲、権限が変わるなら、人との要求整理へ戻ります。既存の合意範囲で対応できることは、その範囲で進めます。
  4. 何を確かめれば、再び進めるか。 更新する成果物、必要な再検証、判断できていない点を整理します。根拠が変わった結果、使えなくなった検証や評価を、そのまま成功の証拠にはしません。

この段階で残すのは、分かったこと、見直す範囲、戻り先の案、必要な判断です。情報が足りなければ、追加で調べることや人への質問を明らかにします。

同じ引用ミスでも、戻る範囲は変わる

例えば、参照資料が古かったと分かった場合、その資料が実装方法だけの根拠だったのか、Issueの要求そのものの根拠だったのかで、見直す範囲が変わります。前者なら根拠・実装・関連する検証を直せる場合があり、後者なら要求整理と合意から見直す必要があります。

コーディングルールへの違反が疑われたときも、適用されるルールと現在のコードを確認します。指摘が古い版や適用外のルールに基づいていた場合は、その根拠を示して指摘の扱いを確認します。これらは判断の例（仮想例）であり、特定PRに起きた事実ではありません。また、すべての原因を網羅した分類でもありません。

調べた結果に応じて、合意や成果物を更新する

調べた結果基本方針として合意した対応
合意済みの要求を満たしていない同じPRで修正し、検証・独立評価・必要な媒体を更新する
目的や完了条件、許可範囲が変わる人との要求整理へ戻り、合意後にIssueと実装への影響を見直す
今回の要求達成に不要な改善今回扱うかを確認し、見送るものは既存の公開許可に従って別Issueへ分ける

Issue作成からやり直すことも戻り先に含めます。 既存Issueの改訂で足りるか、新しいIssueへ分けるか、既存PRを継続できるかは、見直す範囲が分かってから判断します。前の指摘や判断の経緯は、引き続きたどれるようにします。

採用した指摘の原因が再発し得るなら、今回の修正に加えて、次の作業でも使う手順・規則を既存wikiへ、重要な設計判断を判断記録へ反映するか確かめます。具体的な不具合の検出に役立つ場合だけテストやlintを見直します。すべての指摘を文書化せず、今回の合意範囲を超える改善は必要に応じて次のIssueで扱います。詳しくは開発方針を参照してください。

対応後は、最新の変更を人のレビューへ渡す

指摘と対応方針を残し、必要な調査・合意・修正を進めます。文書も含め、その変更に必要な撮影・checkと独立評価を経て、合意したPRへ反映します。draftで最新本文・必要媒体と同じheadのCIを確認し、ready切替後の実状態を読み戻してから、対応内容と残る事項を人へ伝えます。

同じPRで続ける場合も、Issueを見直して進め直す場合も、指摘・変更・再確認の結果を対応づけます。過去の検証結果や中断記録は保持し、現在の成果物に適用できるかを確かめます。

公開済みPRを、新しい修正依頼から更新する

人が採用した指摘・期待する結果・許可範囲を一つの文章ファイルにまとめます。このハーネスで検証・公開したopen PRを対象に、前回公開run、既存checkout、修正依頼、新しい保存先を同じdevelopmentへ渡します。具体的な引数はCLIガイドに従います。

要求を合意してIssueを更新した場合は、開始時に最新のopen Issue全文を取得して新runの要求として固定します。担当ホストが合意と修正依頼の範囲を確認し、前回runのIssue本文と同一であることは要求しません。開始後のIssue変更では停止し、今回の要求と修正依頼でPR全体を再評価します。

checkoutが記録した公開headと一致し、追跡・未追跡の作業差分がないことを確認します。前回の対象・Issue・公開・評価記録とGit/GitHubの実状態を照合し、未完了の実行や結果不明があれば、作業と記録を保って停止します。前回の評価記録には現行の形式を要求します。旧設定の repairLimit・reviewLimit・modelTimeMs は前回公開記録の読取り検査に限って受け付け、元の設定原文とhashを保ちます。新しい実行設定には渡しません。不整合なら拒否します。新runは前回runと同じ親ディレクトリへ作り、旧runは読み取り参照に限ります。初期結果と入力を保存してから、setup直前に対象と並行実行を再照合します。不一致ならsetupや実装AIを起動せず、新runのresult.jsonに停止理由・PR URL・次の対応を残します。setup後も入力とPRの変化を確認し、同じ箇所で取得した対象情報は再利用します。

初回修正後は追加修正・独立評価の回数で停止せず、必要な撮影・check・独立評価・同じPR更新・同じheadのCIへ進みます。PR全体の基点を維持し、Issue全体と採用した修正要求をともに評価します。前回の成功や指摘IDは新runへ移さず、旧runを再開しません。

前回本文の変更説明・未確認事項・添付リンクは、現在も必要な内容を評価して新しい本文へ残します。修正入力やIssue、主体、設定、PRの本文・head・baseが途中で変われば停止します。コメントの自動採用、作業差分の移植、自動承認・マージは行いません。--no-publishは独立評価までで止まります。

13

変更を、次の担当者が確かめられる形にする

担当AIや人が行う引き継ぎです。 PRの説明、確認手順、画像・動画を基に、QA・デザイナー・企画側が変更を確かめられる「変更の説明と確認ガイド」をまとめます。資料の自動生成・共有はCLIの機能には含まれません。

PRで揃えた説明を、受け手の確認へつなぐ

最初に、何のために、誰のどの操作が変わったかを伝えます。その上で、確認する人に必要な情報を揃えます。

  • QA向け： 確認手順と期待する結果、確認済み・未確認の範囲を示します。
  • デザイナー向け： 画面や状態の変化、対応する画像・動画、デザイン意図との差異を示します。差異が分からない場合は未確認とします。
  • 企画向け： 要求との対応、利用上の制約、今回含めなかったことを示します。
  • 全員に共通する確認先： 対象環境、動いている版、公開状況、関連Issue・PRへの参照を揃えます。

複数のPRで一つの機能になる場合は、機能やリリース単位で説明をまとめ、各PRを根拠としてたどれるようにします。資料はPR段階から準備・更新し、引き継ぐ時点の版に合わせます。QAを本番公開前に行うアプリでは、その確認に使える時点で渡します。

次の担当者が、確認を始められる状態にする

引き継ぐ前に、資料と画像・動画が対象の版に対応しているか、受け手が確認先を開けるか、手順と期待結果を読み取れるかを確認します。必要な利用条件、既知の制約、未確認事項と問い合わせ先も、そのアプリの運用に合わせて示します。不明な項目は推測で埋めず、確認が必要な点として返します。

マージ済みか、確認環境へ反映済みか、本番公開済みかを明記します。資料の作成、関係者への受け渡し、実際のQAやデザイン確認について、それぞれ確認できた状態を記録します。

14

リリースし、確かめ、次の改善へ戻す

共通の考え方を説明する章です。 リリース・運用の手順はアプリごとに異なります。ここでは、ハーネスで作った変更を利用者へ届け、動きを確かめ、次の改善へつなぐときに、何を判断し、何を残すかを整理します。具体的なコマンド、担当者、合格値は、対象アプリで定めます。

マージした変更が、いつ、どの版として利用者に届いたか。そして、解決したかった困りごとが実際に解消されたか。この2つをたどれると、開発中の検証と、公開後に分かったことを結びつけられます。

リリース前に、公開する版と判断する人を揃える

公開する版、公開先、必要な検証、実施を判断する人、問題があったときの対応を確認します。マージをきっかけに自動公開するアプリでは、この準備と公開判断をマージ前に置きます。別の操作で公開するアプリでは、その操作の前に置きます。実際のコマンドや権限は対象アプリの手順で定めます。

公開の記録には、どの変更を、どこへ、いつ反映したかをたどれる情報を残します。実装を依頼する範囲と本番公開を任せる範囲は、対象アプリの運用に沿って確認します。ハーネスへの実装依頼だけで、本番公開まで許可されたとは扱いません。

公開した版を、利用者の操作で確かめる

リリース操作の結果を確認し、意図した版が公開先で動き、合意した確認条件を満たすかを確かめます。主要な操作、ログやエラー、データの反映など、何を見るかはアプリごとに選びます。

例えば、入力フォームの改善なら「新しい画面が表示された」に続いて、「入力を完了でき、必要なデータが保存される」を確認対象にする、という考え方です。これは説明用の仮想例であり、特定アプリの事実や確認項目の合意ではありません。実際の確認項目はそのアプリの要求から決めます。確認した環境・版・結果を残し、判定できない点は未確認として扱います。

運用中の変化を見て、問題があれば対応する

公開直後の確認に加え、利用者からの問い合わせ、エラー、主要な操作の状況などから、使われ始めて分かったことを拾います。何を見るか、誰が見るか、どの状態で対応を始めるかを、対象アプリの運用に合わせて決めます。確認の間隔や合格値をこの記事で一律には定めません。

問題があれば、影響している操作や対象、発生している版、確認できた事実を揃え、担当者が対応を判断します。修正を公開するか、前の版へ戻すか、別の対応を取るかは、そのアプリの復旧手順に従います。元へ戻せる範囲、データ変更の扱い、連絡先、復旧後の確認条件も、あらかじめ各アプリで確認しておく項目です。

振り返りを、次の要求整理につなぐ

要求の漏れ、差し戻しの理由、検証で見つけられなかったこと、実行が止まった理由、運用で分かったことを整理します。「何が起きたか」「何を根拠にそう考えたか」「次に何を変える候補があるか」を分けると、観測と推測を混ぜずに相談できます。

改善案を採用するかは人が判断し、合意したものを次のIssueや継続する方針へ反映します。個別アプリの要求を直すのか、検証を見直すのか、ハーネスの進め方を変えるのかも、この段階で整理します。速度や品質の改善量は、計測した根拠がある場合にだけ扱います。

自分のアプリに当てはめるときの確認項目

  • 引き継ぎ： 誰が何を確認できるように、どの環境・版の説明を用意するか。
  • 公開： どの版を、どこへ、何をきっかけに公開するか。誰が実施を判断するか。
  • 稼働確認： どの操作や状態を、いつ、誰が確認するか。合格・未確認を何で判断するか。
  • 問題への対応： 誰が影響を判断し、どこへ連絡するか。修正・復旧の手段と、その後の確認条件は何か。
  • 振り返り： どの記録を根拠に、誰と改善を決め、次の要求へ残すか。

この章は、各アプリの手順を整理するための共通の見方です。現行ハーネスに自動リリースや監視の機能があるという説明ではありません。アプリ固有の手順が不明なら、調べるか担当者に確認し、空欄を推測で埋めずに戻します。

15

止まったとき、何を残してどこへ戻るか

通常の開発では、まずresult.jsonを読み、必要な詳細へ進みます。安全な新規保存先を確保した後は、準備失敗・停止・公開成功・--no-publish完了を同じ場所へ保存します。終端結果を保存できた新しいrunでは、同じ記録からローカルのreport.htmlを生成します。表示は記録の読取りであり、検証や公開を再実行しません。保存先確保前の失敗や結果保存・HTML生成の失敗では、HTMLの存在を成功の根拠にしません。実行結果、下位state、履歴、生ログを保全します。

statusは停止・ローカル検証完了・公開とCI確認完了、phaseとoperationは終了位置です。reasonCode・reason・nextAction・remainingから理由、次の対応、残作業を読み、detailsでsetup・初回実装のログへ進みます。検証停止時と--no-publish完了時のdetailsはverification/state.jsonを指し、公開後はevidenceが示すrun保存先から同じ検証stateへ進めます。下位の予算・active・履歴は元のstateに保持し、以前の成功で今回の停止を上書きしません。

検証stateのfindingsで要約・停止時の診断、reviewHistoryで指摘と評価履歴を確認します。生ログは記録済み試行のevents[].prefix、中断等で予約が残る試行のactive.prefixに.stdout・.stderrを付けたパスです。強制終了や保存障害ではログが存在しない場合もあります。repo外の独自利用者が要約Markdownを読んでいるか、その互換性は未確認です。

担当AIはnextActionと参照された証拠から、既存の許可範囲で事実を調べます。環境変更は許可された範囲でホストへつなぎ、調査の許可を変更の許可へ広げません。要求・権限・上限の変更は人が判断します。支援後も対象・証拠・権限・検証を再確認し、旧run・lock・active予約・上限を書き換えて再開したり、不明な公開を自動再試行したりしません。

保存先確保前、既存runとの衝突、安全性を確認できない保存先には結果を書きません。元の理由と保存不能をstderr／例外で確認します。保存中の割込みは既知の公開情報と元の停止理由を保って停止結果へ更新し、保存失敗では元の理由と保存エラーを併記します。直前の完全な記録が残る場合があるため、ファイルだけで成功と判断せず、stderr／例外も確認します。SIGKILLやOS停止による保存は保証しません。

修正・評価の起動前に回数とactiveを保存します。実装・修正・評価モデル完了直後のstateの中間保存は行わず、次のコマンド予約か終端保存まで起動前の予約を保持します。その間の例外で完了イベントや経過時間がstateに未反映でも、予約・生ログ・成果物は残り、二重実行を拒否します。終端保存も失敗した場合は元の理由と保存エラーを併記します。

独立テスト工程では、完了結果を応答解析前に保存します。追加修正では履歴・経過時間・使用量にも登録します。不正応答を成功へ読み替えず、停止と保全へ進みます。

指摘が反復したら、既存の評価履歴・修正結果と現在の成果物を照合し、原因と方針を見直します。合意範囲内の必須修正を続け、範囲外の改善や好みを完了条件にしません。check失敗も同じ修正経路へ戻り、変更した成果物のcheck・評価を更新します。停滞専用AI・追加レビュー工程・別台帳は設けません。

host_verification_requiredでは、担当AIへの引き継ぎと新しいrunでの再評価へ進みます。成果物と旧記録を保ち、初回実装や公開済みPR修正の開始条件と混同しません。

通常開発、レビュー1回の試行、旧記録を区別する

通常の新規implementと既存PR修正では、初回作業・追加修正・独立評価にモデル時間や回数の上限を設けません。設定は現行の形式で検査し、未知のキーを拒否します。経過時間は記録しますが、初回実装の時間を後工程から差し引きません。合意範囲内の必須指摘を解消し、最新成果物のcheck成功と独立評価acceptedまで修正を続けます。CI待機に総時間上限はありません。各checkと撮影の上限はそれぞれ9分、汎用コマンドとCIの各状態取得・最後の対象照合は11分です。回数・経過時間・指摘・結果・active予約の記録は続けます。時間・使用量・保存量が増える可能性があり、収束は保証しません。

評価試行は review-probe.ts から reviewOnce を使い、check成功後のレビュー1回で終了します。追加修正はせず、reviewTimeMs で各レビューの有限時間を指定します。正常終了の review_completed と時間切れの review_timeout を区別し、通常開発の受入・公開成功とは扱いません。execution_limit は旧記録の読取りだけに残り、新規runでは返しません。

実行条件を変える場合も、停止したrunの設定・state・予約を書き換えず、保存済みの記録を保持します。通常の中断は実行中のコマンドと同一プロセスグループの子を停止し、出力保存を待ちます。強制終了やOS停止では子プロセスが残る場合があり、実状態の確認が必要です。完全自動再開は提供していません。
