# 品質と安心に分類し、feedbackを品質候補の関連実行にする

## 背景と課題

[Issue #463](https://github.com/thkt/dotagents/issues/463)（本文更新日時2026-10-28T03:43:23Z）は、制御テストをquality／assuranceへ移し、固定feedback集合を廃止する合意済み要求です。対象はdotagentsの`scripts/tests`であり、`eval/tests`と他repoは含みません。開始版は`6db226c8573aadf3fd19df318d2b5c0e43ef6974`です。

[DR-0005](0005-define-feedback-tests-by-diff-mutation.md)は当時のIssue #450に基づき、変更差分の変異の検出への貢献をfeedback分類の基準にしました。手作業だけでは報告を再現できないこと、等価な変異や環境の不安定さをCIゲートにしないことを理由として記録しています。当時の文献調査・限定試行を、今回の2分類や関連選択の効果を実証した資料とは扱いません。

## 検討した選択肢

- 3分類と固定feedback集合、全分類を候補にした関連選択を維持する。
- 品質・安心の2分類とし、feedbackは品質候補の関連実行にする（採用）。
- 完全なfs依存追跡や記録の鮮度Schemaを追加して漏れを自動解消する（Issueの対象外）。

## 決定と理由

Issue #463の合意に従い、要求・入力出力・判定・形式・公開契約をqualityへ、中断・環境障害・復帰・後始末・repo全体の整合をassuranceへ分けます。速さや異常系という理由だけで分類せず、独立した両分類のケースは必要な範囲で分割します。構造検査はassuranceです。

既存runnerのパス指定を使い、`test:affected`は品質候補内で選びます。選択エンジンと記録形式は作り直しません。初回・記録不正・固定一覧・影響先不明では品質全件へ戻します。安心は必要なテストを直接実行し、影響不明時は品質全件または全体checkへ広げます。提出前・CIは引数なしcheckで両分類全件を実行します。

README・CLIで案内していた`test:feedback`と変異CLIの`--quality`は互換性のため残します。前者は品質限定の関連実行へ委譲し、後者は品質全件を重複追試しません。外部repoの実利用は未確認ですが、案内済みの呼出しを削除する必要はないと判断しました。変異は品質全件の検出を調べる任意の報告とし、固定集合の認定と通常feedback・CIへの追加は行いません。

この判断はDR-0005の3分類、固定feedbackの認定と追加方針、変異の二段階比較を置き換えます。差分だけの変異、静的検査での破棄、基準失敗時の停止、再実行による判定、一時コピーの復元、CIゲートにしないことは維持します。DR-0005本文と過去の結果は当時の証拠として保全します。

### 影響

記録器の非ASCII・JSONを導入Bunの通常実行と比較し、修正確認してから品質限定の運用へ切り替えます。UTF-8コードとJSONの値・assertion・完了件数・成否を保つ必要があります。動的import・環境を引き継ぐ子Bun・workerの親への帰属も維持します。

部分的な依存記録の漏れは残ります。未実行分岐・待たないimport・fs読取り・環境を分離した子プロセス・古い記録を、単なる再生成ですべて解消したとは扱いません。直接実行と実行範囲の拡大、古い記録の退避・再生成は[CLIガイド](../../scripts/README.md#変更に影響されるテストだけを実行する)へ記載します。速度改善、選択漏れの完全解消、異なるBun版や外部repoでの動作は保証しません。

### 確認方法

独立テストの記録器比較、品質限定CLI、関連選択と全件復帰、部分的な依存漏れ、構造検査、変異CLIの検査を使います。移動・分割前後の検証命題・正常対照と実行結果を独立評価へ渡します。実際の品質・安心全集合の記録あり／なしでの成否・完了件数比較は、通常checkだけの成功とは分けて確認します。文書の確認やテストの準備を、これらの受入成功に読み替えません。

## 関連情報

要求の正本はIssue #463です。調査基点`6b72b3d9068ca2abd6d6d4e5574c72017aff6d32`に対し、開始版では実行基盤が`scripts/test-runtime/`へ移り、旧runner・変異CLIは互換入口です。今回の修正は実体へ適用し、旧入口の検査も維持します。これは現在のコードとの照合結果であり、過去の作者の意図を補う説明ではありません。

### 見直しの条件

- 品質限定の候補範囲や直接実行の運用が、合意した要求を守れないと確認された場合。
- 記録の漏れへの対処や互換入口の維持に、要求・範囲の再合意が必要になった場合。
