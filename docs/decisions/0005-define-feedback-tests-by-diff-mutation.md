# feedbackテストを差分変異の検出への貢献で定義する

## 背景と課題

対象はdotagentsの制御テスト（`scripts/tests`）の`feedback`階層です。#446・#448で3階層に分けたとき、`feedback`は「変更直後に壊れたかが分かる、速くて結果が決まった検査」と定義しました。この定義は、変更が持ち込んだ不具合を`feedback`が検出できるかを基準にしていません。

[調査報告](../research/2026-10-27-feedback-test-definition.md)の限定試行では、手作業の変異9件のうち`feedback`が検出したのは3件でした。検出できなかった6件のうちM4（復帰入口の併用上限を1から2へ緩める変異）は、`feedback`が実行する行への変更でした。`.claude/OUTCOME.md`は、AI担当が開発中に自分の変更の不具合を検出して直してから引き渡すことを完了状態に置いています。

利用者は2026-10-27に、`feedback`をoxlint・oxfmt・biome・fallow・型検査と一緒に回す開発中の検証と位置づけました。そのうえで、基準を不具合の発見への貢献とし、変更差分の変異の検出で測ることを選びました。ここで決めるのは、3階層の定義の基準と、その基準を確かめる仕組みの形です。

## 判断の基準

- 開発中の担当者が、自分の変更差分の不具合を`feedback`が検出できるかを読み取れること。
- 検出・生き残り・変異を作れなかった差分を区別し、見えない穴を「すべて検出」に見せないこと。
- 開発方針の「全テストへの不具合注入は求めない」（`docs/wiki/development-policy.md`の実装とテストの整理）と、「専用の帳票・Schema・評価スコア、監査CLIを追加しない」を、必要な範囲を超えて崩さないこと。
- 新しい依存を入れず、Bun 1.4.4と既存の`scripts/tests/runner.ts`の判定を使うこと。

## 検討した選択肢

- 差分変異のコマンドを1つ追加し、報告だけを行う（採用）。
- 手作業だけの案（A）。必要なときに担当者が一時コピーへ変異を入れて確かめ、常設の仕組みは作らない。
- CIで止める案（C）。差分変異で生き残りがあればCIを失敗にし、マージを止める。
- runnerで`feedback`の速さに上限を設け、超えたファイルを失敗にする。
- 入口のテストを`feedback`へ移す。`quality`・`assurance`だけが検出した不具合について、検出した入口のテストを`feedback`へ移す。

## 決定と理由

選んだ案は「差分変異のコマンドを1つ追加し、報告だけを行う」です。`feedback`は「実行すると変更中のコードの機能の不具合を見つけることに貢献するテスト」と定義します。`quality`は合意した要求と公開契約を入口から守るテスト、`assurance`はまれな事故や環境要因の保険とします。`feedback`への貢献は、`bun run mutate:diff`で変更差分の追加・変更行に入れた変異の検出として報告します。

全文を読んだ23件の文献のうち、検出力を階層や段階の基準にした例は0件でした。速さを挙げた文献は14件、決定性や結果の信頼性を挙げた文献は11件です（調査報告のKey Findings）。この定義は先行例と異なる基準を採ります。一方、変異を変更差分やレビューの単位で使う先行例はあります（調査報告のL26、L27、L32、L33）。生き残った変異を1件ずつ示す形はその使い方に合わせました。

コマンドの範囲は、合意したIssue #450の`## Plan`の規則に従います。

- 変異は変更差分の追加・変更行だけに入れます。対象は`scripts/`の製品コードと`scripts/tests/runner.ts`です。
- 演算子は、条件の否定、比較の境界の入替え、真偽値の入替え、`assert`の条件の否定に限ります。lintか型検査で失敗する変異は破棄し、破棄数を演算子別・ファイル別に報告します。
- カバレッジで変異を除外しません。子プロセスで動く行を誤って除外するためです。
- 基準の`feedback`が3回とも成功しない環境では、変異の報告を出さず専用の終了コードで止まります。変異を入れた実行の失敗は、再実行でも失敗した場合だけ検出に数えます。
- 報告だけを行い、`bun run check`・CIの成否とマージの判断を変えません。スコア・台帳・除外リストは保存しません。

手作業だけの案と入口テストの移動を見送った理由は、Issue #450と調査報告に基づきます。CIで止める案とrunnerでの速さの上限を見送った理由は、Issue #450の計画時に行った設計の批評（critic-design、2026-10-27）の指摘に基づきます。利用者は同日に、この指摘を反映した設計を承認しました。批評の全文はrepo外のセッション記録にあり、ここには要点を残します。

手作業だけの案（A）は見送りました。Issue #450は、`feedback`の貢献を変更差分の変異で機械的に報告するコマンドを求めています（What & Why）。受入条件も、1回のコマンドで検出・生き残り・作れなかった差分を1つの報告に出すことです（Acceptance Criteria）。担当者が変異を選ぶ手作業では、同じ差分から同じ報告を作れず、この条件を満たせません。

CIで止める案（C）は見送りました。整数の件数の境界の入替えや重複した検査のように、振る舞いを変えない等価な変異があると、生き残り0件に届きません。届かせるには除外リストが必要になり、それは`:178`が禁じる台帳です。基準の`feedback`や`quality`の不安定な失敗が、マージを止める原因にもなります。

runnerでの速さの上限は見送りました。CIが実行するのは`bun run check`だけなので、`test:feedback`だけの上限はマージ時には働きません。手元で上限が働くかは、並行して動く担当や sandbox による負荷で変わり、`test:feedback`の結果が決まらなくなります。その結果、基準の3回実行も止まりやすくなります。上限の値も、調査報告の定義案の叩き台で未定のままでした。代わりに、文書の目安と、レビュー時の`--timings`による確認で扱います。

入口テストの`feedback`への移動は見送りました。調査報告の文献では、上位のテストだけが見つけた不具合は下位のテストの欠落とみなし、下位のテストで再現して守るよう勧めています（L2、L5 § Avoid Test Duplication）。合意したIssue #450の`## Plan`のU-004も、`quality`・`assurance`だけが検出した不具合には再現する小さな`feedback`テストを足し、入口のテストは移さないと定めています。M4を検出したのは`assurance`の`check-timeout-recovery.test.ts`で、入口から一連のfixtureを通す保険のテストです。代わりに、検出した不具合を再現する小さな`feedback`テストを足します。M4には`scripts/tests/feedback/implement/recovery-entry-limit.test.ts`を足しました。

### 影響

- 担当者は、変更差分の変異のうち`feedback`が検出したもの・生き残ったもの・作れなかったものを1回のコマンドで読めるようになります。
- 開発方針の「監査CLIを追加しない」記述に、このコマンド1つの例外が入ります。ほかの帳票・スコア・監査CLIの禁止は残ります。
- 生き残りへの処置は人とAIの判断に残り、機械では強制しません。処置を書かなかった場合の検出は、独立評価に頼ります。
- 変異の対象を行単位の文字列で選ぶため、演算子を当てられない行や、lint・型検査で破棄される変異が出ます。これらは報告に件数と一覧で残ります。
- 既存の`feedback`25ファイルを新しい定義で再分類することは、今回は行っていません。dotagents以外の対象repoへの適用も未確認です。

### 確認方法

- `scripts/tests/feedback/checks/mutation-mutants.test.ts`・`mutation-execute.test.ts`・`mutation-cli.test.ts`が、変異の生成と破棄、基準の3回実行と再実行による確認、検証用repoでの報告と終了コードを確かめます。
- `scripts/tests/feedback/implement/recovery-entry-limit.test.ts`が、M4の変異で失敗することを確かめます。
- 独立評価で、`docs/wiki/development-policy.md`の制御テストの階層と、この記録が調査報告の文献対応・食い違いと一致するかを照合します。

## 関連情報

### 根拠と適用範囲

合意は[Issue #450](https://github.com/thkt/dotagents/issues/450)に記録します。文献との対応、限定試行の変異と結果、道具の比較は[調査報告](../research/2026-10-27-feedback-test-definition.md)と同じ名前のフォルダーにあります。調査報告の対象版は`4466983`です。

対象はdotagentsの`scripts/tests`です。`eval/tests`、他の対象repo、#447の対象repo向けのfeedback用check、Strykerなど新しい依存の導入は含みません。

### 見直しの条件

- 生き残った変異の処置が`findings`に残らない事例が続き、報告だけでは開発中の検出に結びつかないと分かった場合。
- 行単位の演算子では、変更差分の主要な誤りを変異として作れない事例が続いた場合。
- StrykerのBun用runnerがTypeScript 7に対応し、新しい依存を入れる判断を改めて比べる場合。
- 差分変異の所要時間が開発中の実行を妨げる長さになった場合。
