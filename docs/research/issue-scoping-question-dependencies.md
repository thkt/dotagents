# scopingで未確定の判断と質問の前提を整理する

## 状態と目的

2026-09-20の「その上でissueとして取り込みを検討しよう」を受けた、採否検討用の下書き。以下の範囲は担当AIの提案であり、採用・実装の合意やGitHubへの公開はまだ行っていない。

同日の、重複していても観点が違えば取り込む価値を検討する依頼を受け、質問の順序に加え、問いの具体化と、用語の意味が判断を変える場合の確認を同じ対話の目的にまとめた。新しい範囲は合意待ちの提案である。

要求整理で、不明点や用語の意味が次の判断を変えるかを具体化し、今答えられる質問を選べるようにする。回答前には必要性や選択肢が決まらない質問の先走りと、回答で不要になった質問の継続を避ける。現行文書との差を根拠とする改善案であり、実運用での失敗頻度や改善効果は未確認。

## 範囲と完了条件

- [ ] 不明点は、今答えを調べられる問い、先行判断待ち、まだ問いを定められないもの、今回の対象外を必要に応じて区別する。全不明点を質問や実装Issueへ変換せず、次の判断に必要なものを選ぶ。
- [ ] 用語の複数の意味が今回の判断を変える場合、既存定義・合意・コードと具体例で境界を確かめる。コードを自動的に正解とはせず、不具合・要求変更・説明違いを切り分ける。定義を記録する場合は既存の正本を使う。
- [ ] `skills/scoping/SKILL.md`の既存の「不足・質問・再評価」へ、質問の前提を確認し、未回答の判断や未完了の調査に依存する質問を後へ送ることを短く記す。
- [ ] 回答を受けたら残る質問の必要性と選択肢を見直し、不要になった質問を外す。新しい根拠や要求変更がなければ、合意済みのことを聞き直さない。
- [ ] 今答えられる独立した質問は、回答負担を考えて必要な範囲でまとめられることを示す。待つのは前提が未確定な質問・作業に限り、独立した調査は進める。
- [ ] 既存の事実調査と人の判断の分担、部分回答を全体合意と扱わない条件、今回の要求・完了条件・検証方法と合意が揃う終了条件との整合を保つ。

本文へ取り込む趣旨の例:

> 質問の前提となる判断・事実を確認し、今答えられる独立した質問を、回答負担を考えて必要な範囲でまとめる。未回答の判断や調査結果に依存する質問は後へ回し、回答を受けて不要になった質問や選択肢を見直す。

実際の文言は既存の説明と統合し、重複を増やさない。必要な確認例だけを`scripts/README.md`の既存のscoping手順確認へ加える。新しいスキル、質問一覧・判断の木の必須保存、質問数の固定、全分岐の解消、常時の委譲、新しい質問UI・runtime・評価基盤は対象外。

問いや用語の条件付きの補足は、必要なら既存の`skills/scoping/references/sufficiency.md`へ置く。CONTEXT.md・ADR・用語集の新設や、既存の共有モデル全体の再設計は含めない。

## 検証

既存の[scoping手順確認](https://github.com/thkt/dotagents/blob/a3f985bb90551b2eaea99126b4ed03e2dc64848c/scripts/README.md#scopingの切替と手順確認)で、採用候補の版と観測した判断・出力を照合する。次は実際の障害報告ではなく、変更の意図を確かめるための代表例である。

| 入力・状況 | 確認する判断・結果 |
| --- | --- |
| 公開するかは未決定で、公開先の選択は公開する場合だけ必要。一方、成果物の利用目的も未決定 | 公開するかの回答を仮定して公開先を尋ねない。独立して答えられる利用目的は、回答負担に応じて同じ回に尋ねられる |
| 前項への回答で、今回はローカルで確認するだけと決まる | 公開先の質問を続けず、今回必要な未解決事項だけを見直す。ローカル確認の合意を後日の公開許可へ広げない |
| 対象repoと利用目的は合意済み。現行の保存先はコードで調べられるが、保存期間の希望は未決定 | repo・目的を聞き直さず、現行コードを調べ、必要な保存期間の判断を人へ返す。回答待ちでも独立した調査は進める |
| 「承認済み」という説明だけで、要求の合意か実行の許可かが分からず、次の操作が変わる | 今回必要な意味と既存の根拠を確認し、一方の合意を他方の許可へ読み替えない。判断に関係しない語まで監査しない |
| 到達点は分かるが、将来の運用条件はまだ具体的な問いにできない | 不明点として保持する。現在の判断を左右するなら具体化を先に進め、影響しないなら架空の実装Issueや質問を増やさない |

観測結果と未確認範囲は既存の実行記録へ残す。文字列一致テストや模擬CLIの成功で質問の妥当性を保証せず、改善率・時間短縮は実測がなければ主張しない。提出時は`bun run check`と既存の独立評価・日本語確認を行う。実モデルの実行や外部送信は、対象と既存の許可範囲を照合する。
