# 検証入口の修正対象照合をcorrectionへ集約する

## 目的と実装方針

外側の検証前照合を1行削除し、correction入口の照合へ集約する案は、正常系の取得を減らし、調べた異常系でも後続処理の抑止と記録の保全を維持した。ただし、複数の異常が同時にある場合の停止理由の優先順位と、停止までに作る一時ディレクトリが変わる。

依頼者の「デメリットがないならソリッドにする」という条件に基づき、必要な停止・保全・公開抑止を維持して検証入口の責任をcorrectionへ集約する。担当者は、下記の診断順序と空ディレクトリの差は手順追加を要せず、今回確認した保証を弱めないと評価した。挙動が完全に同一、または未検証の条件にも不利益がないとは主張しない。**本体は未変更で、実装と最終検証はこれから行う。** 調査は2026-09-20、main `2edaf7bcd47c69bf93df0a951ce0d06ce7ccdd07`の隔離コピーで実施した。#150で未実証として見送ったlock・state・停止記録の境界を今回確認した。

## 確認した正常系・異常系

- 現行と削減案のそれぞれで、既存のrevision・development・correctionの169テストが成功した。
- 調査用の31ケースも両版で成功した。内側の検証全体を成功応答へ置き換えず、実際のcorrection入口・lock・state・check・結果保存を通した。checkはfixtureの実ファイルを調べ、独立評価の応答は模擬とした。
- 通常の修正と終端stateの再照合、対象・修正依頼・Issue・主体・権限・branch・PR・remote refの変化、既存lock、不正state、configHash不一致、active予約、停止済みstate、成果物の変化、保存先障害、並行run、中断を確認した。22種類の単独異常は同じ停止理由だった。独立評価中の本文変更も停止した。
- 異常時に新たなpush・PR本文更新へ進まず、入口での異常ではcheck・独立評価も起動しなかった。既存lockの所有記録、既存state、旧runのresult・state・公開記録、今回の作業内容の保全を確認した。単に例外が出たことだけを成功とはしなかった。

試験準備の割込み状態のリセットと同時異常の注入方法を修正して再確認した。これは調査用fixtureの修正で、本体の不具合として扱わない。調査ケースは一時領域だけに置き、31ケースを常設テストへ追加する提案ではない。全体の`bun run check`、別評価者による独立評価、実GitHubへの公開試行は未実施。

## 採用時に変わる停止順序

現行は外側で対象を照合してからcorrectionを呼ぶ。削減案はcorrectionが自身の保存先・lock・stateを確認できた場合に対象を照合する。このため、7種類の同時異常で次の優先順位の違いを確認した。

| 同時に起きた異常の例 | 現行の停止理由 | 削減案の停止理由 |
| --- | --- | --- |
| PR本文の変更＋既存lock | 本文の変更 | lockの存在 |
| PR本文の変更＋active予約 | 本文の変更 | 未完了の実行 |
| Issue変更＋configHash不一致 | Issue変更 | 設定変更 |
| 修正依頼変更＋不正state | 修正依頼変更 | state形式の不正 |
| 主体変更＋保存先障害 | 主体変更 | 保存先障害 |
| 権限喪失＋既存lock | 権限喪失 | lockの存在 |
| 並行runの未完了＋自身のactive予約 | 並行runの未完了 | 自身の未完了予約 |

どちらも停止し、既存記録と作業を残すが、削減案は最初に発見した保存先・lock・stateの異常で返り、その時点では外部対象の変化を照合しない。以前と同じ停止理由や同じ検出順を維持する変更ではない。

対象不一致や中断を検出するまでに、新runのverificationディレクトリと自分のlockを作る場合もある。自分のlockはfinallyで解放し、既存lockは取得・削除しない。空のverificationディレクトリは残り得る。入口で対象不一致を検出した場合にstateやモデルの実行記録を新規作成することはなく、作業・旧runの上書きや自動再開は行わない。

## 実装範囲と受入条件

- 変更は上記の外側1箇所の照合削除を基本とする。同時異常ではcorrectionの保存先・lock・stateの検査を先に行う。必要な説明だけを既存の正本へ反映し、同じ順序を模倣する追加フラグや管理層は作らない。
- 検証後、setup・モデル実行・commit・push・本文更新・draft/ready切替をまたぐ再照合を維持する。単独correction、並行runの検出、作業・既存記録・既知URL・停止理由の保全、人の要求判断とマージは変更しない。
- 既存テストを再利用し、今回の集約境界に不足する正常系と、必要な停止・保全・公開抑止だけを補う。内部呼出回数の固定や旧処理の不在確認は追加しない。調査用fixtureをそのまま製品へ取り込まない。
- 実装・テスト・文書と、同じ粒度のノード・矢印の増減をPRへ記す。小さなruntime削減のために大きな常設試験基盤を追加しない。
- 調べた正常系・異常系のほかに、対象変更の見逃し、後続処理の誤実行、記録やlockの毀損、利用者の追加作業を生む不利益が見つかった場合は進行を止める。フラグ・状態・補償処理を追加して押し通さず、原因と影響を示して案を再評価する。
- 提出前は`bun run check`と既存の独立評価・日本語確認を行う。公開はdraftで行い、同じheadの`checks`・`verify`、最新本文、対象・権限を照合してreadyへ切り替える。
