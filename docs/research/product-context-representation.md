# 開発に必要なコンテキストの種類と表現先を選ぶ

コンテキストは、人とAIが要求・実装・検証を判断するための情報です。種類ごとに必要な内容を整理し、その性質に合う表現先を選びます。文章、テスト、Storybook、型、静的解析、スキーマなどを組み合わせ、実際の開発での利用と結果から維持・修正・統合・削除を判断します。

記録日は2026-10-06、dotagentsの確認基点は `918aa6ec5a582da43a82bf831240c2f921f6d686` です。以下は分類と表現先の設計案です。分類ごとの対応やAI開発への効果は未検証であり、全項目を別文書にする決定ではありません。

## 合意した方向と今回の保存範囲

依頼者はKAIを見て、ドメイン知識、コードの書き方、暗黙の処理知識、ライブラリの扱い方の整理が必要と述べました。種類と必要な内容を整理し、AI開発への効果を検証し、結果から内容を育てる方向と、表現先を文書に限定しない方向を示しています。必要な情報へ辿れることも判断対象です。KAIの不足は依頼者の観察であり、本記録でKAIのコードや資産を調査した結果ではありません。

今回の依頼で合意したのは、コンテキストの種類と表現先の選択方針をdotagentsへ残すことです。追加の分類、各媒体への対応、具体的な評価課題は設計案として区別します。プロダクトごとの媒体・配置・検証方法の採用や、自動化の実装は今回の範囲に含みません。

dotagentsは共通方針と選択の記録方法を持ち、プロダクト固有の情報と実行可能な資産は対象repoに置きます。恒常的な知識は次の変更でも使う根拠、タスク固有の要求は今回の合意済みIssueとして分けます。知識の追加だけで要求・権限を変更しません。保存先と状態は[共通手順](../../skills/references/documents.md)、廃止した共有JSON正本・ID選択の扱いは[DR-0003](../decisions/0003-retire-shared-knowledge-selection.md)と[DR-0004](../decisions/0004-use-current-document-inputs-only.md)に従います。

## 2026-10-08に確認した見直しの前提

依頼者は整理の継続にあたり、現在のADR・wikiなどの仕組みが最善とは限らないと示しました。この記録にあるwiki・DR・researchの分担は現行の運用であり、今後も維持すべき最適な構成と評価した結果ではありません。共通方針と選択の記録方法も、必要な判断を支えているかを検討対象にします。

比較では、情報の正しさ、対象版と適用条件、要求・権限との区別、判断に必要な根拠を辿れることを維持します。比較候補には、処理の近くへの説明、実行可能な例、状態遷移の表や図があります。コード・スキーマから生成する説明や、用途ごとの入口も検討します。生成や構造化を選ぶ場合も、元の定義で表せない理由・例外を残し、生成物と実行検査の役割を分けます。

不足は、必要な内容がない場合、内容はあるが見つけにくい場合、内容と検査が食い違う場合に分けます。無駄は、媒体の数だけでなく、同じ判断を支える説明の重複、変更時の同期負担、古い内容を使う危険から検討します。利用の証拠が足りない場合は利用未確認として残します。配置や形式が最善かどうかは、比較で改善を確認してから判断します。

最初の具体例として、[ホスト検証後の再評価の追補](context-and-checks-inventory-20261006.md#ホスト検証後の再評価で処理知識と確認手段を辿る)で、現行資産の対応と表現先の比較候補を整理します。今回の更新はローカルの調査記録までで、ADR・wikiの運用変更や新しい仕組みの採用は行いません。

## 種類ごとに残す情報の候補

最初の4種類は依頼者が挙げた観点、以降は会話で補った候補です。重なりを許す点検用の分類であり、網羅性や全項目の必要性を保証しません。今回の判断に関係するものだけを選び、既存資産で足りる場合は新設しません。

| 種類 | 判断に必要な情報 |
| --- | --- |
| ドメイン知識 | 用語、対象概念と関係、状態、守る業務条件、例外、利用者が期待する結果とその根拠 |
| コードの書き方 | 責任分担、依存方向、命名、エラーや非同期処理の扱い、推奨例と避ける例、許容する例外と理由 |
| 暗黙の処理知識 | 実行順序、副作用、所有者、トランザクション、冪等性、競合、再試行・取消、キャッシュや時刻の前提、不成立時の動作 |
| ライブラリの扱い方 | 使用する版、公式仕様への入口、設定、アプリ側の包み方、制約・落とし穴、更新時に確認する互換性 |
| プロダクトの目的と利用者 | 誰のどの仕事を支えるか、優先する成果、対象外、判断の責任者、成果の確認方法 |
| 設計判断と経緯 | 選択した案、理由、比較した代替案、引き受けた制約、当時の条件、見直す契機 |
| データと外部契約 | 型・単位・欠損値、入力の検証、保存・更新条件、APIやイベントの契約、互換性、相手側の責任と失敗時の扱い |
| セキュリティとプライバシー | 信頼境界、認証・認可、権限と主体、機密情報の扱い、保存・削除条件、想定する脅威と許容範囲 |
| UIと操作体験とアクセシビリティ | 表示状態と遷移、主要な操作、空・読込中・失敗の状態、フォーカス、キーボード操作、支援技術、対象環境 |
| 品質と検証 | 守る条件、期待結果、正常・失敗の入力、検証方法と限界、実行結果の対象版、未確認事項 |
| 実行環境と運用 | 起動・検証・配備の入口、設定と依存環境、外部状態、監視、障害時の調査、移行・復帰の条件 |
| 今回の変更範囲と意思決定 | Issueの目的、範囲、完了条件、検証方法、要求と許可の合意、未確定の判断、継続する根拠への参照 |

## 情報の性質から表現先を選ぶ案

種類と媒体は一対一にしません。例えば、業務条件をテストで守り、その理由と適用条件を短い文章で補えます。次の表は選択理由を示す候補であり、各媒体を導入済み・有効と評価した結果ではありません。

| 情報の性質 | 表現先の候補と選ぶ理由 | 確認できる範囲と補完する情報 |
| --- | --- | --- |
| 入力・操作に対する結果を再現して判定できる | 単体・結合・E2Eテスト。期待結果と失敗条件を実行できる形で残す | 成功は対象ケースと環境に限る。なぜ守るか、未検証の境界は文書やIssueで補う |
| UIの状態や操作を具体的に示したい | Storybookなどの状態例。状態間の違いと対象部品へ辿りやすくする | storyの存在は操作やアクセシビリティの保証ではない。必要な操作assertion、画像比較、実環境の確認を別に選ぶ |
| 型、依存方向、書式、禁止パターンとして判定できる | 型・lint・静的解析。反復して確認する規則をコードや設定で表す | 型だけでは実行時の外部入力や業務上の意味を保証しない。規則の適用範囲と例外の理由を補う |
| 外部入力・API・保存形式の契約を判定できる | スキーマと実際の入口での検証、契約テスト。許容する値と互換性を確認する | 定義だけでは入口での検証実行を保証しない。模擬相手の成功と実際の相手との互換性も分ける |
| 理由、背景、判断の経緯、例外を理解する必要がある | 必要なwiki・DR・コードコメント。実行結果だけでは分からない判断を説明する | 文書の存在や読了を、遵守や効果の確認とは扱わない。現行コードと合意へ照合する |
| 環境依存の操作や復帰を再現する必要がある | 既存の設定・コマンド・運用手順と実行記録。操作入口と前提を揃える | 手順の記載と実行成功、模擬環境と実環境を分け、未確認の復帰条件を残す |

表示例、テストの期待値、文章の説明に同じ意味を繰り返し手書きしないよう、何をどの資産で決めるかを定めます。生成する場合は正本と生成方法を示します。機械用の構造化は必要な部分だけとし、共有JSON知識方式や新しい巨大な台帳は作りません。

### 複数の媒体で補完する例

- 検索欄の解除操作：Issueが今回の要求を定め、操作テストが解除・フォーカス・並び順の維持を確認し、storyが検索中・該当なしなどの状態を示します。検索語を保存しない理由が次の判断にも必要なら、既存wikiで説明します。
- 外部イベントの重複受信：スキーマが入力形を、結合テストが重複時の結果を確認します。保存の境界と再試行の理由は設計判断から辿ります。相手側を模擬したテストだけで本番連携を確認済みとは扱いません。

これらは表現の組合せの例です。特定プロダクトでの採用や効果の確認を示していません。

## 読む入口と実行する場面を結ぶ

対象repoの既存README・AGENTS・wiki索引から、用語、変更対象、作業場面に応じて正本や実行入口へ辿れるようにします。wikiの`globs`・`scenes`と検索を使う[現在の読む手順](../../skills/references/documents.md#読む)を再利用し、全文書・全storyの一律読込みは求めません。

要求整理では目的・業務条件・今回のIssueと関連判断を読み、実装では変更対象の契約・コード例・該当テストやstoryを確認します。差分が揃ったら合意した方法で検証し、独立評価では同じ要求と根拠、差分、実行結果、残る未確認事項を照合します。運用の観測や依存更新で前提が変わったら、該当する知識と要求へ戻ります。

表現先を選ぶ際には、誰がどの場面で読む・実行するかと、入口のリンク・コマンドを同時に決めます。既存のcheck・capture・CIで扱う場合は対象repoの合意に従い、媒体を置いただけで通常の検証へ組み込まれたとは記しません。今回の記録は自動選択や自動実行を追加しません。

## 選択は対象repoの既存資産へ短く記録する

恒常的な手順はwiki、重要な理由・代替案はDR、観測と比較はresearch、今回の要求と許可はIssueという分担を維持します。軽微な選択はIssue・PRと正本への参照で足ります。すべての知識に専用ファイルや新しいIDを作りません。

実際に採用する際は、判断に関係する項目だけを既存ページやIssueへ記します。次は最小の記載例で、パスとコマンドは架空です。

```markdown
### 検索解除の操作条件
種類と必要な情報：UI・暗黙の処理知識。検索欄だけを解除し、並び順は維持する。
選択と理由：操作テストで結果を判定し、既存wikiで保存しない理由を説明する。
正本と適用範囲：今回の要求はIssue、継続する操作条件は対象repoのtests/search.test.ts。検索欄と対応ブラウザーに適用する。
入口と場面：実装前にtests/search.test.tsとdocs/wiki/search.mdを読む。変更後に既存のsearchテストコマンドを実行する。
状態と確認版：採用済みの対象commit、環境、結果への参照を記す。未実行なら未確認と記す。
再検証の契機：入力部品、並び順保存、対応ブラウザーを変更したとき。
```

複数媒体ではそれぞれの役割と正本を明示し、古い仕様や根拠が衝突した場合の確認先を示します。参照固定が必要なら[既存の引き継ぎ](../wiki/reference-handoff.md)を使います。非Markdown資産のpath・対象commit・実行結果はIssueや評価説明から辿れるようにし、現行のMarkdown報告参照へ新しい入力形式を追加したとは扱いません。

### 今回実際に選んだ保存先

合意した共通の方向は[開発方針の既存節](../wiki/development-policy.md#コンテキスト整備の設計原則)へ追記し、分類と表現先の候補、選択の記録方法はこのresearchへ置きます。方向と未検証の案を分け、既存の索引から辿れるためです。プロダクトのテスト・Storybook・lint等の新規採用先はまだ選んでいません。新しいDRは作らず、重要な代替案の採用判断が具体化した時点で必要性を判断します。

## 自然な課題で必要性と到達性と効果を分けて確かめる案

比較は[既存の改善効果の方針](../wiki/development-policy.md#改善効果の比較)と[観測範囲の扱い](../wiki/evidence-scope.md)に従います。問いは次の三つに分けます。

1. 必要性：どの判断に何の情報が必要だったか。既存のIssue・コード・資産で足りたか、具体的な不足や矛盾があったかを確認します。
2. 到達性：通常の入口から、担当AIが該当資産の正しい版と適用条件へ到達し、読み・実行し、実装と評価へ必要な参照を渡せたかを確認します。索引の読了だけを成功とはしません。
3. 効果：その情報や表現先を使ったことで、要求の誤認、見落とし、範囲外変更、手戻り、時間・使用量、保守負担がどう変わったかを確認します。AIの自己申告と外部で観測した結果を分けます。

実際の開発課題から、必要な情報を使う場面と守る条件を先に決め、対象版・Issue・モデル・環境を揃えて比較します。採点用の期待結果は実装入力と分け、初めから全条件が容易に満点になる課題だけで効果を判断しません。課題に必要な要求は共通に示し、特定媒体だけへ隠した要求や答えを入れて優位性を作りません。難度を上げるためだけの人工的な矛盾より、実際に発生した判断や不足を優先します。

比べる変更は情報内容、入口、表現先のどれかを明示し、同時に複数を変えた場合は個別の効果を断定しません。まず問いに必要な小さい範囲を観測し、試行数・実行失敗・未実施・検証環境の限界を残します。内容を正しく扱えたことと、媒体の効果があったことも分けます。単発の成功、テスト成功、storyの存在から一般的なAI開発の改善へ広げません。

## 結果から内容と表現先を見直す

要求整理で不足が見つかったとき、実装・評価で不一致が見つかったとき、依存・外部契約・運用の前提が変わったときに、既存のIssue・PRで影響を確認します。AIは該当する資産と差分・根拠を調べ、更新案を作ります。人は目的、許容範囲、要求・権限の変更と重要な採用判断を担います。

役立つ内容は維持し、誤りや到達できない入口は修正し、重複する正本は統合します。不要・置換済みの説明は関連参照と失う確認範囲を確かめて整理します。削除は過去の原本や他担当の差分を消す許可にはしません。履歴・観測は既存の保存方針で保全し、現在の入口から置換先へ辿れるようにします。

更新した内容・理由・確認版・結果・未確認事項は既存の説明へ残し、次の自然な課題で再検証します。毎回の全件監査や新しい進行ゲートは作りません。まず対象プロダクトの一つの判断を選び、この分類と記載例で既存資産の不足・重複・入口を整理し、表現先の採用と評価課題を具体化するのが次の候補です。

## 最初のコード規則で確かめた範囲

[蓄積値コピー規則の限定試行](code-context-pilot-20261006.md)では、既存のコード規約・lint・制御テストを選び、理由と適用境界、読む・実行する入口を接続しました。新しいルールや検査は追加せず、正例・違反例・適用外の例をローカルで確認しています。これは1規則の機械的な検出と記録方法の確認であり、AIの自動発見、自然な開発課題での品質・手戻り・時間の改善は未検証です。分類全体の対応を採用済みへ変更しません。

## 根拠と未確定事項

合意の出典は今回の依頼者との対話です。上記に判断に必要な要旨だけを残し、会話全文、内部ログ、秘密情報は取り込みません。今回の範囲はローカルの文書保存までで、Issue・PR作成、commit・push、チームへの公開は行っていません。

既存の方針として、[コンテキスト整備](../wiki/development-policy.md#コンテキスト整備の設計原則)、[正本の分担](../../skills/references/documents.md)、[検証結果の適用範囲](../wiki/evidence-scope.md)、[Markdown参照の現行形式](../decisions/0004-use-current-document-inputs-only.md)を確認しました。過去の[コンテキスト整備案](context-workflow-alignment.md)は当時の記録として保持し、廃止済みの共有モデル方式を再採用しません。

分類の粒度、対象プロダクトで実際に選ぶ資産と責任者、評価課題、更新による改善効果は未確定です。この対応表の保存や推敲・静的検査は、効果の実証や各媒体の採用完了を意味しません。
