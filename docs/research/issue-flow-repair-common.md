## 目的と現状

同じ実装担当actorを使う二つの経路で、指示や応答の仕様変更を二重に保守する負担を減らす。

[scripts/development.ts](https://github.com/thkt/dotagents/blob/019a25badbcec00a05231267b31fed453a49bf74/scripts/development.ts#L193) の初回実装と [scripts/correction.ts](https://github.com/thkt/dotagents/blob/019a25badbcec00a05231267b31fed453a49bf74/scripts/correction.ts#L768) の修正は、共通する文書・検証・撮影・公開禁止の指示を持ち、`repaired / needs_human` の応答検査を別々に行う。修正側には事前予約と追加修正の上限がある。

## 範囲と完了条件

- [ ] 文書・テスト・撮影・公開禁止など、意味が同じ指示と応答検査を共通化し、両経路が使う。Issue中心／失敗指摘中心という入力の違いは明示する。
- [ ] 初回実装は追加修正2回に数えない。初回のsetup後照合、修正の起動前予約、中断時のactive保持、失敗記録の保全を維持する。
- [ ] 不正応答・プロセス失敗・時間制限・人の判断が必要な応答を、各経路で正しく停止へ結び付ける。共通化のために既存の停止理由や証拠を失わない。
- [ ] 実装担当と独立評価担当を分離し、修正後の必要なcheckと評価を維持する。
- [ ] 起動や結果保存までまとめるのは、同じ責務として既存の差を明示できる範囲に限る。全フローの汎用エンジン化や実行上限の変更は行わない。

## 重点的な検証・順序

共通のコマンド実行をcorrectionから分離した後を推奨。既存の `development.test.ts`・`correction.test.ts`・`correction-process.test.ts` を使う。

両経路の正常応答、不正応答、needs_human、起動失敗・中断を確認する。初回実装と追加修正の回数・予約の意味が変わらないことを守り、同じ準備を重ねるテストだけを増やさない。
