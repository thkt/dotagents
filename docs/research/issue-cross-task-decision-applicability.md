# 別作業の判断を今回の条件に照らしてから使う

状態: 初回と追加の限定試行まで完了した下書き。scopingで検証し、必要なら後続工程へ広げる方針を2026-09-24に依頼者が選択した。現行版に具体的な誤適用は見つからず、Issue公開・実装の判断はしていない。

## 問題と目的

作業Aでは要求が抽象的でも十分だった、という過去の判断が残る。作業Bが似ていても、利用者、失敗時の影響、判断に必要な条件が異なれば、Bには具体的な要求が必要な場合がある。Aの結論をBの合意や十分性判定へ持ち込むことを防ぎ、関連する先例は根拠として活用できるようにする。

## 現状と不足

- `skills/scoping/references/sufficiency.md` は、出典・対象版・適用範囲を確認し、過去の結論を無条件に採用しない方針を持つ。
- `scripts/research-handoff.ts` は選択した報告の版を固定し、「別の範囲の根拠を適用しない」と実装側へ渡す。これは参照の版と明示的な受け渡しを扱うが、似た別作業の判断条件が今回も成立するかという意味判断を機械的に保証しない。
- [Issue #73](https://github.com/thkt/dotagents/issues/73) と [Issue #90](https://github.com/thkt/dotagents/issues/90) は、出典・適用条件・合意状態の受け渡しを整えた。今回の問いは、条件が一部似た先例を見たとき、今回の要求の十分性を先例の結論で代用しないかである。
- 現時点で実際に誤判断が起きた記録は確認していない。以下は予防したい失敗条件であり、現行フローが失敗すると断定しない。

## 提案する最小の仕組み

1. 今回の目的、利用場面、失敗条件、合意済み制約から、今回必要な具体性を先に判断する。参照した別作業の結論は、今回の要求や権限ではなく比較候補として扱う。
2. 先例を使う場合は、その結論を支えた条件と、今回一致・相違・不明な条件を確認する。結論が変わり得る相違や不明点があれば、先例の結論を引き継がず、今回の要求について調査または人の判断へ戻す。
3. 判断に影響した比較だけ、既存のIssueまたは下書きへ「先例の適用条件／今回の相違／今回の結論と根拠」を短く残す。専用台帳、全資料の網羅、毎回の比較表、機械的な類似度判定は追加しない。
4. 初回はscopingで、過去の判断を参照するときの要求十分性判定を対象にする。実装・独立評価へ同じ条件を広げるかは、初回の誤適用・過剰停止・費用を見て別に判断する。

### 仕組みの選択肢と初回の推奨

| 案 | できること | 費用・限界 |
| --- | --- | --- |
| 案1: 判断時だけ先例の適用条件を照合する | 先例が今回の結論に影響する場合に、今回の目的・利用場面・失敗条件と照らし、相違があれば結論を移さない。既存のIssue・下書きに理由を残す | 文書と担当AIの意味判断が中心で、必ず正しく区別できる保証はない。無関係な先例には追加作業をしない |
| 案2: すべての判断に構造化した適用範囲を付ける | 参照や状態の欠落は機械で検査しやすくなる | 全判断の記録・更新が増える。意味の一致は機械で保証できず、今回の合成例で必要性は示されていない |
| 案3: 類似作業の結論を自動的に継承または遮断する | 明示されたIDや版の一致は扱える | 「抽象的で十分」などの適用条件は類似度やIDだけでは判定できず、誤継承または有用な先例の遮断が起こる |

初回は案1を候補とする。ただし現行scopingは合成したB・対照例Cで案1に近い判断を行ったため、同じ文言を重ねるだけの変更は採用しない。先例の範囲が曖昧、複数の過去判断が競合する、今回の違いが小さい等のより厳しい例を事前に定め、現行の見落としまたは過剰停止と、候補がそこを直すかを確認してから変更箇所を決める。実際の誤判断が見つかればその再現を優先する。

次の評価例では、(1) Aが「新人向けレビュー資料は抽象的でよい」とだけ記録し、Bが操作中に参照するか不明な場合は、Aの結論を採用せず用途を確かめる、(2) 同じ「レビュー資料」でもBの対象が操作時の判断表だと分かる場合は必要な条件を具体化する、(3) Aと同じ説明会資料なら過剰な質問をせず先例を活用する、を区別する。期待結果・不足情報を実行前に固定し、評価入力へ正解を混ぜない。

2026-09-24の追加試行では、二つの先例を同時に置く。先例A1は「説明会の導入用、操作しない1枚図なので抽象的な流れでよい」、先例A2は「PRをreadyにできるかを判断するチェック表なので、確認条件と停止条件が必要」。どちらも「新メンバー向けPRレビュー資料」という名前を含める。評価対象への3依頼と期待は次のとおりで、先例・指示・方針は同じ公開版を使い、各依頼を独立した新規セッションとする。

| 依頼 | 実行前に決めた期待 |
| --- | --- |
| 用途不明: 説明会後も使う新メンバー向けレビュー資料。A1と似ていると言うが、操作中の利用は明示しない | A1の結論を確定的に移さず、操作中に判断・作業へ使うかを確認する。用途ごとの条件付き案はよい。曖昧さを勝手に埋めてIssueを確定しない |
| 操作用: 新メンバーがPRのready可否を判断するチェック表 | A2と今回の用途の関係を見て、本文・必要媒体・同じheadのCIと失敗・未確認時の停止を具体化する。A1の抽象度を採用しない |
| 概要用: 説明会冒頭の1枚図で、操作には使わず詳細手順へリンク | A1の用途との一致を見て抽象度を採用し、操作条件の網羅や無用な確認を要求しない。A1の合意は今回の合意に読み替えない |

判定は回答で実際に示した用途・条件差、未確定事項、提案した要求と検証方法を見る。先例のファイルを読んだことや正しい語を含めたことだけでは合格としない。実行失敗・参照不能は判断の誤りと区別する。費用はCLIの使用量・実時間を別に記録し、少数例の結果を一般化しない。

## 完了条件と検証案

- 同じテーマのAとBで、Aは抽象的な要求で十分、Bは異なる失敗条件のため具体化が必要、という例を要求から独立に作る。Aの記録をBが読める状態でも、Bの判断理由を今回の条件から説明し、不足を「Aで十分だった」で埋めない。
- 先例の条件が今回にも成立する対照例では、無用な質問や再調査を増やさず、先例を参照して進められる。
- 変更前後を同じモデル・課題・参照条件で比較する。結論だけでなく、参照の選択、条件差の認識、要求充足、止まり過ぎ、時間と取得できる使用量を確認する。合成例の少数回成功を一般的な防止保証としない。
- scopingの既存のIssueへの受け渡しを壊さず、`bun run check` と必要な実モデル確認を分けて報告する。

初回の評価例は、Aを「開発フローの概要を伝える資料。操作条件は別の手順書にあるため、目的や責任を抽象的に説明すればよい」とし、Bを「同じフローでPRをreadyにする実際の操作手順。本文・必要媒体・同じheadのCIの確認条件と、失敗・未確認時の停止を読者が実行できる具体性が必要」とする。BにはAの判断記録を参照可能な形で置く。対照例はAと同じ目的・読者・利用場面の概要資料とし、Aの判断を有用な先例として使えるかを見る。期待する判断と理由を実行前に固定し、評価対象へ正解ラベルを渡さない。

## 対象外と判断待ち

別作業の情報を一律に隠すこと、過去の判断をすべて無効にすること、汎用的な記憶基盤の新設、モデルの意味判断を機械的に正しいと保証することは対象外とする。

参考: [Bounded Contextの記事](https://debimate.jp/notes/software-architecture/bounded-context/)は語やモデルの適用範囲を区切る考え方の参考。今回の作業単位の判断条件は、同記事のDDD上のBounded Contextと同一ではない。

## 初回の実モデル試行と停止

依頼者は、公開済みscoping Skill・関連方針と合成ケースを既存認証のOpenAI Codexへ送る範囲を許可した。公開HEAD `16d70c23918d69d4dbc01795ac1a886938ee573d` のSkill・十分性参照・開発方針と合成の先例A、B、対照例を一時ディレクトリに置き、Codex CLI 0.156.1の新規・read-only・ephemeral実行をBだけ起動した。

CLIは一時ディレクトリ内の公開版を読んだが、その前に自動発見された元の作業領域 `/Users/thkt/.agents/skills/scoping/SKILL.md` も `cat` し、終了コード0で内容を取得した。そこには未commitの変更がある。したがって、この実行は許可された公開版だけを参照した評価ではなく、回答の良否をベースラインの結果に数えない。この段階では対照例と候補版を起動していない。続行には、ホスト側Skillの自動発見と作業領域外の読取りを確実に遮断できる方法の確認が必要だった。

この汚染されたBの回答は、Aの抽象度は説明会の図に限ると述べ、操作手順には具体的な確認・停止条件が必要と判断した。ただし、公開版のSkillだけでも同じ判断になったという証拠ではない。会話履歴・個人メモリ・他の未commit資料を意図して入力した記録はないが、CLIが何を自動発見するかをこの試行で十分に制御できなかった。
