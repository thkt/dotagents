### 現行の順序と、共用できる範囲

現行の[公開処理](https://github.com/thkt/dotagents/blob/bf29d64d061893cb1db3efd77f9eb115bf4429bc/scripts/development.ts#L268)は次の順で進む。

1. Issue・source・対象・主体を照合し、commitと確認済み本文を作る。push直前にも再照合してbranchをpushする。
2. `publish` が対象・主体・権限を照合し、同じhead/baseのOPEN PRを検索する。主体を再確認し、既存なら再利用、新規なら作成する。
3. [作者・本文をRESTで読み戻す](https://github.com/thkt/dotagents/blob/bf29d64d061893cb1db3efd77f9eb115bf4429bc/scripts/publish.ts#L18)。URLのrepo/番号、実効ユーザーとの作者一致、確認済み本文との完全一致を要求する。単独publishもここを通り、URLを返す。単独publishはCI成功を判定しない。
4. developmentがPR URLを保存する。媒体がある場合は、対象・主体を再照合して添付する。添付は本文を変えるため、添付前の本文観測は次へ使い回せない。
5. [公開結果を取得](https://github.com/thkt/dotagents/blob/bf29d64d061893cb1db3efd77f9eb115bf4429bc/scripts/ci.ts#L144)し、URL・head・base・OPEN・Issue参照を照合する。生応答は `pr.json` と `pr-publication` のログに残る。作者・本文の完全一致は手順3の役割で、ここでは本文中の `Closes #N` を確認する。
6. [CI待機](https://github.com/thkt/dotagents/blob/bf29d64d061893cb1db3efd77f9eb115bf4429bc/scripts/ci.ts#L184)が、同じhead/base/OPENとcheck群を直ちに取得する。未登録・実行中なら最大5秒ごとに再取得し、最後に[PR対象を再照合](https://github.com/thkt/dotagents/blob/bf29d64d061893cb1db3efd77f9eb115bf4429bc/scripts/ci.ts#L172)する。

手順5と6の最初の取得の間に、ハーネスによるpush・作成・本文編集・添付はない。ここが共用対象。手順3は不一致の既存PRへの添付を防ぐためにも必要で、単独publishの保護と合わせて残す。最終対象照合と、待機中の再取得も残す。

### GitHubから取得できる情報と限界

[GitHub CLI公式のJSON項目](https://cli.github.com/manual/gh_pr_view)には `url`、`headRefOid`、`baseRefName`、`state`、`body`、`author`、`statusCheckRollup` がある。実際にPR #116でこれらを一回の `gh pr view --json` に指定し、作者、本文、対象commit、base、状態、checks/verifyの結果が返ることを確認した。PR #116は既にMERGEDなので、これは項目取得の確認であり、OPEN PRの公開フローを新しく試した結果ではない。

一回のCLI応答でも、GitHub上のすべての値が原子的に固定される保証は追加されない。認証主体・push権限はこの応答だけでは照合できず、既存の取得を残す。CLI内部のHTTPリクエスト数は未計測で、以下の回数はハーネスからのPR詳細取得コマンド数を表す。
