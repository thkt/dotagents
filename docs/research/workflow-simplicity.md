# フローを土台に、素材・進行・LLMの仕事を簡潔にする

確認日：2026年9月16日。対象：dotagentsのcommit `674f1a773eb26773a53b789c3d84c47b414504f2`。

この文書は、フローと現行実装を照合した調査結果と整理案です。個別の改修案は未採用であり、新しいIssue作成・実装・公開は未実施です。現行の入口、設定、結果形式を変更するものではありません。

## 目的と判断基準

大きなフローと、素材となる文書・JSON・YAMLを簡潔に保ちます。それらを利用する機械的な検査、工程の進行、LLMへの依頼も、必要な作業を直接表す内容にします。

整理の効果は、ファイル数や行数に加えて、次の観点で判断します。

- 一つの事実を手作業で更新する箇所と、同じ内容を再生成する回数が減るか。
- 一つの変更を理解するために、行き来する文書・設定・処理が減るか。
- LLMが根拠の読解、実装、評価に集中できるか。
- 機械が進行を決める条件と、人へ戻す条件を短く説明できるか。
- 異常時の停止、記録、必要な検証の意味を維持できるか。

Issue作成とPR作成を基本の区切りとします。実行の区切りや上限を追加する設計は後回しとします。

## 整理候補と優先順

### 1. 共通の実行制御と入力判定の依存方向を整える

**確認した事実。** `correction.ts`は修正の進行に加えて、外部コマンドの実行、プロセス群の停止、中断処理を持っています。公開、CI、対象確認、日本語確認などの処理も、このファイルから実行機能を参照します。また、`input.ts`は保存状態の検証のために`review.ts`を読み、`review.ts`は汎用の値判定のために`input.ts`を読みます。

**提案。** 最初の改修候補は、共通のプロセス実行・中断機能を修正の進行から分けることです。呼び出し元はその共通機能を直接参照し、`correction.ts`は検証・評価・修正の順序を表します。続けて、汎用の値判定を置く場所を整理し、レビューと保存状態の循環参照を解消する候補があります。この2点は独立して検証できる範囲で扱います。

新しい実行エンジンやプラグイン層は想定していません。ファイルが増える場合も、一つの変更で理解すべき責任と依存関係が減ることを採用条件にします。

**維持する条件。** コマンドの結果、ログ、子プロセスの停止、中断後の予約と証拠の保持、上限、停止後の再実行拒否を維持します。現行の`activeGroup`は共有されているため、ファイル分割を並列実行の許可とは扱いません。

`writing.ts`の子プロセスは親のプロセス群を引き継ぎ、出力を逐次保存します。`correction.ts`の実行関数とは役割が異なるため、見た目の類似だけで一つの関数へまとめる対象にはしません。

### 2. LLMによる指摘全文の再出力を減らせるか確かめる

**確認した事実。** 現行の独立評価は、前回の指摘をすべて再出力し、変更できる項目を`disposition`と`reason`に限定しています。ホストは前回の指摘の脱落と、変更してはいけない内容の変化を検出します。これは指摘の履歴を残すための仕組みです。

**提案。** ホストが保存済みの指摘本文を維持し、LLMが既存指摘のIDごとの再判定と根拠、新しい指摘を返す方式を比較します。各回の完成したレビュー記録は、ホストが組み立てる候補です。

これにより、LLMに求める固定情報の再現を減らせる可能性があります。一方、ホストに対応付けと記録の組立てが加わります。全体の定義・分岐・説明が増える場合は採用しません。速度、費用、品質の改善は未測定です。

**維持する条件。** 各回の対象版、指摘の発生元、全既存指摘への明示的な再判定、根拠、必須指摘が未解決なら受け入れない条件を維持します。欠落を暗黙の解決として補完しません。保存済みの実行を新形式へ変換したり、終了済み実行を再開したりする設計は含めません。

### 3. 出力形式の重複定義を、狭い範囲で整理する

**確認した事実。** `review.ts`には、LLMへ渡すJSON Schema、TypeScriptの型、実行時の形の検査があります。さらに、対象版や指摘の履歴、受入判定の矛盾を検査する処理があります。

**提案。** まず指摘の再出力方式を検討し、必要な項目を確定します。その上で、同じ項目名や選択肢の変更が何箇所へ波及するかを見直します。現在のSchemaと形の検査は、`reviewStatuses`などの同じ選択肢の配列を参照しています。この共有は維持します。新しいスキーマライブラリや、JSON Schemaなどを生成する仕組みの導入は、保守負担を含めて簡単になる根拠がある場合に検討します。

形式を満たすことと、判断の意味が正しいことには、それぞれ確認が必要です。型やSchemaへまとめても、対象違い、指摘の脱落、未解決なのに受入とする応答の拒否は維持します。

## 初回の改修へ渡せる範囲

最初の提案は「共通のコマンド実行と中断の責任を、修正フローから分ける」です。素材やLLM出力を変更せず、依存方向の改善を独立して確認できるため、着手順として推奨します。個別Issueの合意と実装は未実施です。

完了条件の案は次のとおりです。

- 公開、CI、対象確認、日本語確認の呼出し元が、共通の実行機能を使うために修正フローへ依存しない。
- 検証・評価・修正の順序を現行の入口から辿れ、CLI、設定項目、結果形式、上限を維持する。
- 既存の中断・タイムアウト・子プロセス停止・証拠保持・公開抑止の振る舞いを維持する。
- 新しい必須入力、工程、LLM呼出し、外部依存を追加しない。

[correction-process.test.ts](../../scripts/tests/correction-process.test.ts)には、中断時の予約保持、二重実行の拒否、タイムアウト、子プロセスの残留を確認するケースがあります。[writing-process.test.ts](https://github.com/thkt/dotagents/blob/674f1a773eb26773a53b789c3d84c47b414504f2/scripts/tests/writing-process.test.ts)、[development.test.ts](../../scripts/tests/development.test.ts)、[publish.test.ts](../../scripts/tests/publish.test.ts)、[ci.test.ts](../../scripts/tests/ci.test.ts)も影響に応じて使います。必要な観測が足りない場合だけ追加し、提出前に共通の`bun run check`を実行します。

## 2026-09-23の参考メモ：PDLCスキル

[pdlc-skills](https://github.com/kanfu-panda/pdlc-skills)は、段階ごとの文書と状態ファイル、実行コマンドの終了コード、Red→Green、自己確認を組み合わせる。Issueを要求の正本とし、ホストが検証・停止を担う現行フローへ一括導入すると、正本と進行管理が重なる。Red→Greenは[テスト設計案](issue-test-design-catalog.md)に既に含まれ、全変更への必須化や新しいゲートは合意していない。
