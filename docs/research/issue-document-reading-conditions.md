# 文書更新で前提知識・適用条件・完了判断の読み順を確認する

## 目的と状態

文書を読む人やAIが、今回使う手順、その前提・例外、完了と未完了を判断する根拠を辿れるよう、既存の文書更新・評価の観点を具体化する。

2026-09-20の、重複する内容にも別の観点があれば取り込みを検討する依頼に基づく下書き。担当AIの提案であり、採用・実装は未合意、Issueは未公開。読者の操作・理解の改善は未測定。

### 外部調査を再参照する条件（2026-09-21の参考追記）

[外部調査を、あとから答え合わせに使う](https://zenn.dev/peyangu485/articles/jibun-os-playbook)は、実際のゲーム調整後に保存済みの外部調査と照合した運用例である。依頼者の「進めて」を受け、調査を新しい案の探索だけでなく、既存の設計判断の見直しにも使う観点を残す。記事はこの方法の効果を比較実験で示したものではない。

読む条件には、どの判断を、何をきっかけに見直すかを短く示す。例えば「モデル更新や再読の負担をきっかけに、初回実装担当の役割説明を見直すとき」は[費用比較メモ](issue-harness-cost-comparison.md)を参照する。保存先や索引へ結論を複製せず、元資料の出典・対象版・適用条件・未確認事項へ戻れるようにする。

照合では、自分たちの目的・要求・観測結果と、外部資料が成立した前提の一致点・相違点を確認する。一次資料での確認は、我々への適用可能性や改善効果の確認と分ける。外部事例との一致だけで成功とせず、不一致だけで誤りとも判断しない。判断を支持する材料に加え、反する根拠や条件の違いも残す。

設計前に必要な制約や既知の失敗は先に調べ、「必ず自分で決めてから外部調査を読む」という順番は設けない。既存のIssue・調査メモの参照として扱い、新しいplaybook・確度マークの体系・定期照合は追加しない。今回の合意はこの参考追記までであり、下書き全体の採用・実装・公開や、既存索引の3件を増やす合意とは区別する。

## 範囲と完了条件

- [ ] 今回更新する説明が必要になる判断・操作と、その読者が前提として必要な知識を見立てる。分からない前提を事実として補わず、判断に影響する場合だけ確認する。
- [ ] 共通して必要な責務・重要条件は入口で把握でき、条件付きの詳説は読む条件付きで辿れるようにする。条件とその例外が別経路に隠れて判断を変えないか確認する。
- [ ] 手順で必要な概念を、使う前に説明または参照できるか確かめる。「確認する」「完了」について、何を見れば成立し、未確認なら何が残るかを記す。
- [ ] 説明の十分性を現在の原資料・要求と照合し、文書の短さや生成成功だけで理解しやすさを判定しない。合成例による読み合わせ、AIの役割レビュー、実際の読者による操作は別の結果として扱う。
- [ ] 今回更新する指示が補う能力・好み・repo固有の知識・実行条件と、残す理由を確認する。モデル・ツール・運用の変化や実際の誤動作を見直しの契機とし、削除・移動・保持を選ぶ。必要な合意や完了条件を保ち、移動する場合は読む条件と参照先を確認する。効果の比較が必要なら[#145](https://github.com/thkt/dotagents/issues/145)の方法を使い、全指示の棚卸し・定期実行は要求しない。

主な変更先は`.codex/DEVELOPMENT.md`の既存の文書更新・日本語確認の説明。今回影響する文書に条件付きで使い、毎回の全資料監査、必須の読者プロフィール、理解度試験、新しい校正モデル、文字数制限、すべての段階での人の承認は追加しない。索引全体の拡張、ガイドの全面改稿、教材の新設、共有知識の正本の複製も対象外。

## 検証と引き継ぎ

「手順だけ読むと例外を見落とす」「操作に必要な語が後で初めて説明される」「正常終了の記載だけで残る確認を判断できない」という合成例と、現状で十分な例を使い、既存の文書評価で必要な修正と不要な追記を区別できるか確かめる。実際の利用者が迷った記録とは扱わない。

[teach](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/teach/SKILL.md)の一つの操作とフィードバックは、実際の初読者の理解を調べる依頼がある場合の参考とする。本案の完了に参加者の募集・教材開発・学習効果測定は含めない。[pr](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/in-progress/pr/SKILL.md)の対象に合う図・結果の選択も参考になるが、[#142](https://github.com/thkt/dotagents/issues/142)の本文生成を再実装せず、必要な説明手段を既存方針に沿って選ぶ。

[wizard](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/engineering/wizard/SKILL.md)の操作場所・得る結果・保存先・完了条件と、[to-questionnaire](https://github.com/mattpocock/skills/blob/c55ee46073ed923f86ce59a5eb3b6d895095d1b7/skills/productivity/to-questionnaire/SKILL.md)の回答に必要な背景・不明時の扱いは、人へ操作や非同期回答を依頼する説明の参考にする。対話シェルや常設の質問票を作る要求、第三者への連絡の許可は含めない。

実装時は`bun install --frozen-lockfile --ignore-scripts`、`bun run check`、既存の独立評価・日本語確認、同じPR headの`checks`・`verify`を使う。今回は原資料・現行方針との照合と下書きの日本語確認までで、共通check、独立評価、合成例の評価、実読者による確認は未実施。本案と固定版の出典で根拠を辿れるため、全件比較メモは実装の必須入力にしない。
