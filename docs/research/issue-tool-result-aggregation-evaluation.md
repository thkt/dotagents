## 目的と合意範囲

複数のrun記録やCI結果を読み取る原因調査で、ツール結果をコード内で集約・抽出してからモデルへ返す方法が、必要な証拠と回答品質を保ちながら総費用を減らせるか判断する。

依頼者はProgrammatic Tool Callingの記事の検討を受け、Issue化を依頼した。本Issueは読み取り専用の調査方法の評価を扱う。導入効果は未測定で、API移行や通常フローへの採用を合意したものではない。

## 現状と根拠

確認版はdotagents `16d70c23918d69d4dbc01795ac1a886938ee573d`。

- [codex-actor.ts](https://github.com/thkt/dotagents/blob/16d70c23918d69d4dbc01795ac1a886938ee573d/scripts/codex-actor.ts)はCodex CLIを起動し、イベントと最終結果を保存する。自作ハーネスがResponses APIのツール定義を直接管理する構成ではない。
- [現在の責任分担](https://github.com/thkt/dotagents/blob/16d70c23918d69d4dbc01795ac1a886938ee573d/.codex/OUTCOME.md)では、実行・検証・公開確認・停止条件はホストが管理する。ここを毎回生成されるコードへ移さない。
- [OpenAIの公式仕様](https://developers.openai.com/api/docs/guides/tools-programmatic-tool-calling)は、中間結果の集約に向く処理と、結果ごとの意味判断や承認を要する処理を区別している。本Issueでは前者の読み取り処理を候補にする。
- 通常のfunction callingにも[並列呼び出し](https://developers.openai.com/api/docs/guides/function-calling#parallel-function-calling)がある。ツール10回を必ずモデル10往復と数えず、記事の削減率を我々の期待効果へ流用しない。

## 調べる範囲

まず実際の原因調査の問いと保存記録を確認し、大量の中間出力や繰り返し取得が判断の負担になっている箇所を選ぶ。既存の読み方で十分なら、その根拠を残して見送れる。試行や実装を増やすこと自体を成果にしない。

比較が必要なら、同じ問い・固定した記録・期待する回答を使い、現在の取得方法と、既存ツールをコードでまとめて必要な情報を抽出する候補を比べる。既存の並列取得、CLIのJSON選択、jq等の抽出が使える場合は対照側でも利用できるようにし、全出力を逐次読むだけの不自然に弱い対照を作らない。

変える要因は取得結果の集約・抽出方法に絞る。利用環境で直接呼び出しとProgrammatic Tool Callingを切り替えられなければ、その制約を記録する。既存のJavaScript実行やCLIで行った比較は、その環境での集約方法の評価として扱い、特定API機能の効果を測定したとは主張しない。API移行を評価の前提にしない。

モデルへ返す情報には、問いに必要な事実、対象run・commit・観測時点、取得済み件数と未取得・失敗・未確認、元の証拠の参照先を含める。入力・出力の形式と失敗時の扱いを明示し、取得失敗や不正な形式を空配列・ゼロ・「問題なし」に置き換えない。引用や原本確認が必要な判断では、抽出結果から原資料へ戻れるようにする。

## 完了条件

- [ ] 調査の問い、対象版・入力、実際の負担または既存手段で足りる根拠、比較する要因を示す。負担を確認できなければ、試行せず見送る理由を残す。
- [ ] 比較を行う場合、期待する事実・回答と根拠を候補出力とは独立に定め、モデル・設定・有効な指示・ツールの版等を揃える。別条件の回答や評価用の正解を持ち越さず、揃えられない条件は限界として示す。
- [ ] 必要な情報の見落とし・誤った断定・根拠欠落を原資料と照合する。問いに関係する取得失敗、記録欠落、解析失敗、異なる対象版の混在を成功へ変換しないことを確認する。取得できた範囲の成功で、上位runの停止や未確認を取り消さない。
- [ ] 要求充足を先に判定し、その後にモデルとの往復数、ツール呼出し数、実時間、取得できる入力・キャッシュ・出力使用量、金額を比べる。往復数とツール回数を分け、準備・集約処理・失敗・再試行・追加調査を含む総費用と集計範囲を残す。金額の実測と推定を分け、使用量や料金の取得不能をゼロ扱いしない。試行数・ばらつき・測定不能を示し、少数例の結果を一般化しない。
- [ ] 品質と費用、準備・保守の負担から、採用候補・見送り・判断保留を根拠付きで示す。効果を区別できなければ保留できる。通常フローへの変更が必要になった場合は、変更箇所と守る条件を提示して別途合意する。

## 実行条件と成果の保存

このIssueの作成時点では、実モデル比較やハーネス変更は行っていない。別評価者による本Issueの独立評価も未実施。

着手時に、対象記録と問い、許可された実行環境、測定可能な項目を具体化する。モデルを呼ぶ比較では、送信する資料・対象版・実行条件と費用の上限を既存の許可範囲と照合し、不足する許可を解消してから実行する。私的なrunログ・未commit資料・会話履歴を自動で外部へ送らない。保存済みrunや外部状態を変更せず、必要な試作は隔離した場所で扱う。

結果は本Issue、関連PR、または必要な場合のみresearchの既存方式で残す。対象版・比較条件・判定根拠・費用の範囲・未確認事項を辿れるようにし、生ログ・秘密情報・ホスト内の個人パスは公開しない。ローカル下書きの存在を後続作業の必須条件にしない。

ハーネス変更を提出する場合は、既存のセットアップ`bun install --frozen-lockfile --ignore-scripts`、`bun run check`、独立評価・日本語確認、同じPR headの`checks`・`verify`を用いる。模擬コマンドの成功と実モデル比較の結果は分ける。画面変更・媒体は不要。
