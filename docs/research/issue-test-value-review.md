## 目的

テストを作成・変更するたびに、必要な不具合検出へ費用をかけているかを既存の実装・修正・独立評価で確認する。件数やカバレッジの維持を目的にせず、不要なケース、過剰な実行環境、変更に弱いアサーションを整理する。

依頼者の2026-09-18の指示「テストの価値判断をまとめて、常にそれに沿ってテストが作られているかを確認して欲しい」に基づく。今回の調査では、常時監視を増やすのではなく、テストに関係する変更ごとに既存フローで確認する形へ整理した。具体的な削除・統合先は以下の候補であり、個々の削除を決定済みとは扱わない。

## 価値判断の要約

正本は[開発方針の「実装とテストの整理」](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/.codex/DEVELOPMENT.md#実装とテストの整理)。次の問いはその要約であり、別の採点基準を作るものではない。

| 判断すること | 残す・追加する理由 | 整理する理由 |
| --- | --- | --- |
| 防ぐ不具合 | 削除すると見逃す現実的な不具合を説明できる | 「念のため」、件数、カバレッジだけが理由 |
| 追加の保証 | 既存テストでは検出できない条件・境界・失敗を守る | 同じ条件を同じ層で繰り返すだけ |
| 観測する結果 | 返却値・成果物・保存状態・停止理由などが要求と一致する | 実装の内部構造や説明文の綴りだけを固定する |
| 検出力 | 期待値が要求から独立して定まり、想定する誤動作で失敗する | 実装から期待値を生成する、設定したモックだけを確認する |
| 失敗の理由 | 対象以外の条件は正常で、意図した理由で停止し、必要な保全も守る | 別の不正入力や任意の例外でも通る |
| 費用との釣り合い | 必要な保証を得られる小さい実行範囲で、安定して維持できる | 純粋な入力判定に毎回Git・プロセス・フロー全体を用意する |

呼出回数・順序・外部API引数でも、予算、二重実行防止、権限、工程間の受け渡しを守るものは必要な契約である。見た目の類似やテスト件数だけでは削除しない。

## 現在の接続と残る改善

調査版は `69780d0f118b954d69a8ad76c80d93e3b0cf48a5`。既に[共通の実装・修正指示](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/repair.ts#L28)と[独立評価の指示](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/review.ts#L233)に、現実的な不具合、追加の保証、実行・保守費用、不要なテストの削除・統合が含まれている。

新たな監査工程を足す必要はない。改善対象は、変更に関係するテストの価値判断を既存の実装報告と `assessments.tests` へ具体的に残し、独立評価とPR説明で確認しやすくすること。現在のtests欄への具体的な指示は主に実施した検証と限界であり、残す・追加する・統合する理由との接続を明確にできる。

機械的な形式検査は評価文の存在を確認できても、その判断が妥当かまでは保証しない。実モデルが毎回この方針へ従っている割合は今回測定していない。

## 現行テストの監査結果

14テストファイルと共通fixture、対応する実装・指示文を確認した。`bun run check` は成功し、制御テストは255件成功・失敗0件、Bunのテスト実行表示は44.81秒だった。単回のローカル実測であり、実モデル、GitHubへの実公開、実ブラウザーの確認を含まない。

「大半が不要」とは結論しない。具体的に整理を検討できるのは次の3点。

### 1. プロンプトの言い回しに依存するアサーション

[初回実装](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/development.test.ts#L120)と[修正](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/correction.test.ts#L54)は、共通指示文の複数の英文を部分文字列で照合している。

一時コピーで `Explain any lost detection conditions and the remaining verification.` を `Describe detection conditions lost through removal or consolidation, and explain the verification that remains.` へ変更すると、`development success` と `normal` が失敗した。失う検出条件と残す検証を説明する要求は保持しており、ここでは表現変更が修正負担になることを確認した。

候補: 文言ごとの重複照合を減らし、初回・修正それぞれに必要な入力と指示が届く接続を確認する。外部公開の禁止、要求・根拠の受け渡しなどの必要な契約は残す。共通ヘルパーの出力をそのまま期待値にして意味の検証ができたと扱わず、指示の意味は既存の独立評価で確認する。これはモデルの実際の遵守を証明する試験ではない。

### 2. 不正なレビュー応答の全ケースで結合フローを起動する費用

[初回の不正応答](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/review.test.ts#L28)10ケースと[再評価の不正更新](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/review.test.ts#L119)6ケースは、それぞれGitリポジトリと外部コマンドを用意する。今回のcheckにおける16ケースの表示時間合計は3.28秒だった。

対象外の文書を参照する1ケースを除く15種類の不正応答は、公開関数 `parseReview` へ直接渡す一時テストでも、意図した拒否理由を確認できた。正常な対照入力も受理されることを確認し、15件成功、Bunの実行表示は82ミリ秒だった。比較する保証は完全には同じでなく、この差をそのまま全体の短縮効果とはしない。

さらに対象ID照合、kindの値検査、更新IDの重複検査を一つずつ欠落させると、対応する現行の結合テストと直接テストが共に失敗した。試した3種類について、不正値の検出を軽い層へ移せる根拠が得られた。すべての変異や組合せの同等性を証明したわけではない。

候補: 入力の組合せは直接テストへ移し、初回・再評価それぞれの停止、ログ・直前の完全な評価の保全、後続修正の抑止、文書参照の版照合は結合テストで残す。

[#100](https://github.com/thkt/dotagents/issues/100)は新規指摘の固定メタデータをホストへ移すため、この整理と重なる。着手時の採用状況へ照合し、現在の15種類を固定の維持件数としない。廃止する応答項目の検査は、採用後のホスト付与・保存の保証へ置き換える。

### 3. spec欠落のCLI確認が二つのファイルにある

[capture.test.ts](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/capture.test.ts#L186)と[correction-capture.test.ts](https://github.com/thkt/dotagents/blob/69780d0f118b954d69a8ad76c80d93e3b0cf48a5/scripts/tests/correction-capture.test.ts#L320)は、共に `capture.ts` のCLIを直接実行してspec欠落を確認する。後者もcorrection経由の結合確認ではない。

前者は相対パスで、configも存在しない。後者はconfigを用意し、絶対パスのspec欠落と `ENOENT`、起動不能への誤分類がないことを確認している。

候補: captureの責務へ集約し、configなど対象外の条件を正常にしたケースを残す。相対・絶対パスの受け渡しは既存のCLI正常系を含めて検出条件を確認し、単に二つあることを理由に片方を削除しない。削減効果は小さく、主眼は責務と失敗条件を明確にすること。

## 維持する保証

- 変更を挟む要求・対象・権限の再照合、古い成功の拒否、公開済みPRとCIの対象照合。似たassertでも確認時点が違う。
- 中断・時間切れ・子プロセスの終了、予約済み予算、二重実行防止、ログと既存データの保全。実プロセスやGitが必要な確認を、模擬応答だけへ置き換えない。
- captureの実行要否と再利用条件。文書、コード、実行モード、symlink、定義、必要媒体の違いを消さない。
- 外部JSON・保存状態・テスト未実行の検出。型検査や同じ名前の正常系があることは代替にならない。

## 範囲と完了条件

- [ ] 価値判断を既存の開発方針で読み取りやすく整理する。必要な例外も維持し、上記の要約を新しい別正本にしない。
- [ ] 初回実装・修正・独立評価で、今回影響する検証が防ぐ具体的な不具合、既存検証との差、追加・維持・統合・削除の理由と未確認事項を確認する。既存の `findings` と `assessments.tests`、PR説明を使い、全テストの個別帳票は求めない。
- [ ] 独立評価では実装側の説明を追認せず、関係するテストと要求を確認する。具体的な見逃しや保証に見合わない費用は通常の指摘として修正へ戻す。必要な保証が既存テストで足りる場合は追加しない。
- [ ] 上記3候補を着手版へ照合し、必要な保証を維持できる範囲で整理する。残す場合も費用と検出条件を理由として示し、一律削減率や件数目標を置かない。
- [ ] 削除・統合する対象は、失う検出条件と残る検証をPRで説明する。実装・テスト・文書の増減と実行時間は同じ条件で比較し、行の圧縮やファイル移動を効果と扱わない。工程の追加は予定しない。
- [ ] 新しい監査CLI、モデル呼出し、テスト評価スコア、専用Schema・台帳、全件mutationの必須化は追加しない。無関係なテストの整理へ広げない。

## 検証と引き継ぎ

対象は `thkt/dotagents`。セットアップは `bun install --frozen-lockfile --ignore-scripts`。提出前は引数なしの `bun run check` と、差分に対する独立評価、同じPR headの `checks`・`verify` を確認する。人がレビュー・マージを判断する。

テスト整理では代表的な現実の不具合を引き続き検出できることと、失敗理由・保全・後続動作の抑止を確認する。判断が難しい箇所だけ、一時コピーで範囲を絞った不具合注入を使う。意味を保ったプロンプト修正で不要な期待値の一斉更新が発生しないかも確認する。評価文の形式が通ることを、テスト価値の意味的な保証としない。

このIssueに判断基準、調査版、対象コード、実験条件と結果を含めるため、別の調査報告を必須入力にしない。ローカルの一時試験と生ログは共有する要件に含めない。今回の調査では実コードの編集・テスト削除、実モデルの評価、別担当による独立評価は未実施。具体的な成果物は通常の実装・独立評価・PRへ引き継ぐ。

## 後続の参考: テスト観点カタログ

2026-09-23に[「AIのテスト観点を『決定論的』にする - テスト観点カタログを作った」](https://zenn.dev/aldagram_tech/articles/316c4d944fd9d5)を確認した。記事は、仕様書に書かれにくい定番の振る舞いを「UI要素種別 × 役割」に対応する観点として定義し、役割を判定する手がかり、適用条件、未確認値の扱いも持たせている。単一施策の途中集計では、レビュー通過済み188観点のうち92件がカタログ由来だった。ただし、これだけで不具合の見逃し削減や他の対象への効果は確認できない。

このハーネスでは、まず現行方針どおり変更ごとに現実的な失敗条件と既存検証の不足を確認する。複数の変更で同種の見逃しが実際に生じた場合は、共通化を検討する有力な根拠となる。記事の観点数を目標にした全域カタログ、新たな必須工程や専用台帳は、この資料だけを根拠に追加しない。これは完了済みIssue #115の要求変更ではなく、後続の判断材料である。

同日、依頼者は[型とテストで不変条件を守る事例](https://zenn.dev/takabo/articles/ai-guardrails-with-tests)も踏まえ、テストの作り方と観点のカタログ化に価値があると示した。同種の見逃しが複数回起きることを着手の必須条件とはしない。初回はこのハーネスの既存テストから、外部入力の拒否、停止時の副作用と記録保全、対象版の変化、検査自体の空振りを候補にする。各観点には適用条件、守る振る舞い、正常な対照入力と失敗入力、観測結果、既存検証との差、必要なテスト層と費用を記す。候補の存在だけで新しいテストを必須にせず、適用先で今回守る条件を判断する。

初回の配置案では既存の`.codex/DEVELOPMENT.md`を判断基準の正本として維持し、`implement`から必要時だけ参照する短い資料へ具体例を置く。テスト作成時は、今回の失敗条件を定め、カタログの適用を判定し、既存テストとの差から最小の検証を選ぶ。異なる既存変更へ試しに当てはめ、見落としと不要なテスト追加の両方を確認する。専用の実行基盤・新しい必須ゲート・全テストの写経は含めない。これは初回の範囲を決めるための担当案であり、Issue公開や実装の合意とは区別する。
