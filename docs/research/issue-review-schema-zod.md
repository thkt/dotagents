# レビュー応答の定義をZodへ集約し、検証の重複を減らす

## 目的と根拠

独立レビュー応答の項目を変更するとき、[現行の`review.ts`](https://github.com/thkt/dotagents/blob/53b38db77233ad1b45f90cdad1aa24562750463c/scripts/review.ts)ではCodexへ渡すJSON Schema、TypeScript型、実行時の構造検証をそれぞれ更新する必要がある。レビュー応答の形を一つの定義から扱い、更新漏れと保守負担を減らす。対象はこのレビュー応答に限る。

2026-09-23の小さな試作では、Zod 4.5.4（現行`node_modules`にある間接依存）でレビュー応答を定義し、正常例と代表的な拒否例の10ケースで現行パーサーと同じ採否になった。[Zod公式のJSON Schema変換](https://zod.dev/json-schema)を利用できたが、生成結果は現行Schemaと完全一致せず、nullable項目は`anyOf`になり、`$schema`も追加された。この試作では、実際のCodex CLIでのSchema受理、既存拒否条件の全件、保存済みレビュー記録との互換性は確認していない。Zodは直接依存として宣言されていない。

[Issue #100](https://github.com/thkt/dotagents/issues/100)は新規指摘の固定メタデータをホストへ移す変更であり、その時点では新ライブラリを対象外としていた。本Issueはその完了後の現行応答について、定義重複の保守費用を減らす別の変更である。

## 範囲

1. レビュー担当が返す応答の項目・型・許可値・余分な項目の拒否をZodの定義に集約し、受信時の構造検証、TypeScript型、Codexへ渡すJSON Schemaを同じ定義から得る。必要な依存とlockfileを明示する。
2. 対象IDの一致、過去指摘の全件更新・欠落・重複・未知IDの拒否、文書参照の重複、ホストによるID・状態・総合statusの付与は、現在のホスト側の検査・構築責任として維持する。Zodの構造検証だけで意味や実行権限を保証したとは扱わない。
3. 保存される完全なレビュー記録と再評価・修正への受け渡しについて、現在の形式と停止・保全の振る舞いを維持する。今回の対象外のactor応答や一般のJSON読込へ一括適用しない。

## 完了条件と検証

- [ ] 生成したJSON Schemaを、現行と同じCodex CLIの`--output-schema`入口で確認する。変換差分を照合し、必要な制約が弱まらず、実際のレビュー応答を受け取れる。Schema生成の成功だけで互換性を確認済みとしない。
- [ ] 既存の正常・不正応答テストで、余分な項目、欠落、enum、空白だけの値、locationのpath/lineの関係、対象ID、更新ID、文書参照などの採否と、停止・直前記録の保全・後続修正の抑止が保たれる。不足する現実的な失敗条件だけ追加する。
- [ ] JSON Schema・型・実行時検証の定義箇所と、その変更に必要な作業を変更前後で示す。変換用の特例や新しい依存まで含めて保守が実際に簡単になったか評価し、単なる行数減少を成功条件にしない。
- [ ] 引数なしの`bun run check`と差分の独立評価を実施する。Codex CLIの実応答確認と制御テストを区別して報告し、PRでは同じheadの`checks`・`verify`を確認する。人がレビューとマージを判断する。

## 対象外と未確認

全JSON境界のZod化、汎用スキーマ基盤、レビューの意味判断の自動化、モデル出力の権限付与、保存済みrunの自動変換は含めない。実装時にCodexのSchema制約へ適合させるための変換が複雑になり、重複と保守費用を減らせないと分かった場合は、無理に置き換えず差分と理由を示して範囲を再判断する。

依頼者は2026-09-23の比較と限定試行の結果を受け、レビュー応答に限るZod移行をIssue化するよう指示した。実装方法の細部と依存版は着手時の現行環境で確かめる。実モデルでの本番相当の意味評価や、他の応答形式への適用効果は未確認。
