## 目的と実装方針

人のレビューで求められた既存PRの修正を、既存のdevelopmentの修正・検証・独立評価・公開確認へ接続する。毎回の検証設定と公開用スクリプトの組み直しを不要にし、最新の差分・本文・同じheadのCIを人へ渡す。

最小化の対象は追加差分ではなく、完成後に残るコード・分岐・状態・受け渡し・テスト準備・説明の全体。必要な保証と当初の目的を維持する。入口を一つに見せるだけの集約、対応範囲を狭くして見かけの工程数を減らすこと、ファイル移動や行の圧縮は削減効果に数えない。

既存developmentの開始対象と公開先の違いを扱い、初回作業・修正ループ・check/capture・独立評価・公開後確認・終了結果を共用する。第二の実行エンジン、共通処理を包むだけの層、旧state変換器、別の再開台帳は追加しない。CLIの引数名や内部構成はこの条件内で実装担当が決める。

## 実装範囲


1. 対象は、このハーネスで検証・公開したopen PRで、現在のgh主体が作者と一致する同一repoのbranchに限る。前回runの既存記録からPR・Issue・公開commit・checkout・評価基点と参照を取得し、Git/GitHubの実状態と照合する。#103後の必要な記録が揃うrunを対象とし、旧形式の変換器は追加しない。
2. 修正要求は、人が採用した指摘・期待する結果・許可範囲を一つの文章入力にまとめる。必要な過去指摘と出典を含め、初回の修正担当・後続の修正担当・独立評価が同じ固定入力を参照する。PRコメントの自動収集・自動採用、新しい要求台帳は追加しない。
3. 既存checkoutが公開headと一致し、追跡対象・未追跡の作業差分がない状態から始める。新しいrunへ証拠を保存し、前回run・state・ログは読み取り参照に限る。別checkoutの自動生成、stash、未commit差分の移植、rebaseは今回の入口に含めない。作業が残る場合は保存したまま原因と次の対応を示す。
4. 新しい明示的な修正依頼には、通常developmentと同じ初回作業1回・追加修正上限2回・独立評価上限2回を適用する。モデルの20分制限は復活させず、check等の既存時間枠を使う。旧runの途中再開、上限消費の書換え、失敗後の自動新規runによる再試行は行わない。過去のaccepted・check・capture成功は新runへ流用しない。
5. 合意したIssueと修正指摘について、修正後の成果物全体を既存のcheck/capture・独立評価に通す。PR全体と今回の修正の対応を確認できる評価基点を維持する。過去の指摘IDや判定履歴を新runの評価stateへ移植せず、必要な事実は今回の修正入力の参考として渡す。
6. 最新のacceptedと検証済みcommitに対応する説明を用意し、同じPRへ通常pushと本文更新を行う。既存本文を入力として照合し、必要な変更説明・未確認事項・添付を脱落させない。更新前の本文・作者・head・base・Issueが変わった場合は停止し、未確認の手編集を上書きしない。更新後は本文・ref・PR headを読み戻して同じheadのCIを既存処理で確認する。自動コメント投稿、会話のresolve、承認、マージはしない。
7. 終了案内は#103の `result.json` に集約する。既知のPR URLを保持し、更新未試行・結果不明・確認できた更新を今回の修正について区別する。push成功後の本文更新失敗や割込みでも、旧headを最新成功として案内せず、実状態を確認する次の対応を残す。安全な保存先の確保前や保存自体の失敗は既存の診断方針を使う。

前回の公開結果が不明、PR headと記録が不一致、未完了の実行がある場合は、新規修正を開始する前に照合する。Issue・対象repo・base・主体・権限や修正範囲の変更は人の判断へ戻す。GitHubへの複数操作を原子的に実行できる保証は設けず、各境界の再照合と公開後の読戻し、曖昧な結果からの自動再試行禁止で扱う。

## 受入条件


- [ ] 上記の対応範囲で、修正入力から同じPRの最新head・本文・CI確認まで進み、人のレビューへ渡せる。既存の新規Issue実装と `--no-publish` の保証は維持する。
- [ ] 異なるrepo・PR・作者・head・base・Issue、開始後の修正入力変更、未commit作業、過去runの未完了・不整合を検出したら、後続の変更・公開を止める。元の作業・証拠を保持する。
- [ ] 修正指摘が評価から抜ける、PR全体の要求が見落とされる、古い成功が新しい修正に流用される不具合を検出できる。指摘対応の意味の妥当性は独立評価が確認する。
- [ ] commit/push・本文更新・CI取得・結果保存の境界での失敗と割込みを、最新の判明状態と次の対応へ結び付ける。新しい停止用ファイルや復帰台帳を追加しない。
- [ ] 既存のdevelopment・publish・correction・CIのfixtureと検出力を再利用し、入口差と公開副作用の境界に絞って追加する。セットアップは `bun install --frozen-lockfile --ignore-scripts`、提出前は `bun run check` と成果物の独立評価を行う。制御テストの模擬GitHub応答と、実際のPR更新の試行を区別する。
- [ ] CLIガイドとimplementの案内を既存の正本で更新する。既存PRの手動接続を新しい必須手順と並置しない。コード・テスト・文書の増減と同じ範囲のフローをPRで示す。


## 検証と削減の評価

セットアップは `bun install --frozen-lockfile --ignore-scripts`。提出前に引数なしの `bun run check` と成果物の独立評価を行う。変更する人向け文書は現行の日本語確認方針で確認し、既存の正本を更新する。スキルの詳細な操作説明はCLIガイドを参照させ、両方に重複して書かない。

- [ ] 不要になる設定作成・個別公開処理・手順説明を新しい運用の必須手順として残さない。旧run・個別スクリプトは履歴として保全する。
- [ ] 実装・テスト・文書の行数増減と、同じ対象範囲・粒度のノード・矢印の増減をPRへ短く記す。必要な再照合は維持し、新しい対象分岐・停止経路も数える。全項目の純減はノルマにせず、増えるコードによって不要になる実際の作業・受け渡しを説明する。別の測定基盤や必須帳票は追加しない。
- [ ] 既存fixtureと検出力を使い、実装をなぞるだけのテストや同じ準備の複製を避ける。削除・統合する検証がある場合は、残る検証が守る現実的な振る舞いを示す。

CIだけの再確認は #105、構造図の編集元の整理は #106 で扱う。PRコメントの自動採用、任意の旧runの復帰、未commit作業の自動移植、汎用のPR操作CLIは含めない。このハーネス変更自体にプロダクト画面媒体は不要。制御テストの模擬応答と実際の既存PR更新の試行は区別し、後者を未実施のまま実測済みとしない。
