# `implement`の独立レビューを明確にし、指摘と対象版を記録する

## 目的と合意

実装はメイン主体で進め、既存の最終独立評価を維持する。その評価について、何を読み、どの版の何が問題で、修正後にどう判断したかを追えるようにする。計画との一致だけでなく、コードとしての欠陥、テストの検出力、文書・証拠との整合を評価する。

依頼者は2026-09-15の比較結果を受けて「その方向で計画を固めましょう」と依頼し、初回範囲として「レビュー基盤を先行し、索引は次段階」を選択した。この文書はその初回実装の要求と後続方針を定める。後続の索引や並列化まで実装する合意ではない。

## 今回の範囲

### 1. 最終独立評価の観点を明示する

変更差分だけでなく、影響する呼出し元、共有型、状態遷移、エラー処理、関連テストを読み、具体的な欠陥を評価する。対象外の機能追加や好みの書き方を要求しない。変更と関係のない全コードや全テストの監査は求めない。

次の観点を区別して評価する。

- コードとしての正しさ。入力の境界、状態の更新、非同期処理、失敗時の副作用など、変更に関係する振る舞い。
- 合意したIssueの要求、完了条件、変更範囲との一致。
- テストが現実的な不具合を検出するか。実装からコピーした期待値や、別の理由でも成功する失敗テストを見逃さない。
- 必要な文書・証拠と実装版の一致。現行方針、過去の実行結果、未採用の提案を区別する。

コードの欠陥は、対応する要求項目がIssueに明記されているかどうかにかかわらず評価する。指摘なしや`check`成功を、欠陥が存在しないことの保証とは説明しない。

### 2. 指摘と判断を構造化して保存する

指摘には対象位置、問題が起きる条件、影響、根拠、必要な対応を持たせ、証明できた不具合と未確認の懸念を区別する。コードに行番号を付けられない文書不足なども表現できるようにし、架空の位置や再現実行を埋めない。

各指摘とその後の判断を対応付け、「修正した」「根拠を示して非該当とした」「未解決である」を追えるようにする。次の最終評価は、実装担当の自己申告だけでなく、現在の成果物と必要な検証でその判断を照合する。未解決の必須修正指摘が残る結果を`accepted`として処理しない。人の承認やPR公開など、後続担当の作業は不具合と分ける。

モデルは所見と判断理由を返し、ホストは形式、必須項目、対象との対応、結果の矛盾を検査して保存する。形式検査だけで指摘の真偽まで保証したとは扱わない。最終`review`の形式と検証を対象にし、`repair`や文章の意味照合の結果形式を不要に変更しない。

### 3. 評価対象をホストの記録と結び付ける

各レビュー結果を、ホストが確認したIssueの版、差分の基準コミット、ソースの識別情報、`check`の定義・結果、モデル設定と関連付ける。モデルが自己申告した対象版をそのまま正本にしない。必要な差分と対象情報から、修正前後のどの成果物への所見かを辿れるようにする。

現在の対象同一性チェックを再利用し、追跡ファイルとGitで無視されていない新規ファイル、削除、`rename`、実行属性などの扱いを狭めない。対象が変わった場合、不正な結果が返った場合、評価が失敗・中断した場合は、古い`accepted`や指摘なしへ読み替えない。記録は既存の実行ログ保存先へ残し、過去の実行を変換・再開したり、上限をリセットしたりしない。

今回参照した主要なリポジトリ内文書は、位置、版、役割、参照理由をレビュー記録から辿れるようにする。これは当該レビューの参照記録であり、全文書の索引ではない。ホストが内容の同一性を確認できても、モデルが十分に読んだことの証明にはならない。

### 4. 既存のフローへ接続する

メイン主体の実装、文書確認、必要な撮影、共通`check`、最終独立評価、必要な修正と再評価、公開条件、人のレビューとマージ判断を維持する。既存のログとPR説明から指摘、対応、未確認事項を辿れるようにし、新しい専用帳票や重複するレビューエンジンを作らない。

主な変更候補は`scripts`の既存実装入口、評価、actor、入力検証と関連テスト、操作説明である。共通化が必要な処理だけ内部モジュールへ分ける。スキルには判断に必要な案内を置き、JSON検証や保存の手順を重複記載しない。

## 完了条件と検証

1. 最終独立評価が4つの観点を扱い、コード独自の欠陥と要求不足、懸念、後続担当の作業を区別した結果を残せる。
2. 指摘の根拠と対応を対象版に結び付けて保存でき、`accepted`と未解決の必須修正が矛盾する応答、必須項目不足、別の対象の結果を成功として受け入れない。
3. Issueだけ、あるいはソースだけを変更した場合に以前の評価を使わず、未追跡の追加や削除、`rename`、実行属性変更も対象識別へ反映する。失敗理由と公開抑止、ログ保全を確認する。
4. 修正後の評価は最新の成果物と以前の指摘を照合できる。文書だけの変更も扱え、対象外のテスト追加を必須にしない。`repair`、文章の意味照合、既存の終了・上限・公開条件を維持する。
5. 既存テストを再利用し、変更した境界に必要な回帰テストを加える。不正応答の拒否と同時に、妥当な`accepted`、具体的な`needs_changes`、根拠付き非該当の正常例も確認する。単に常時拒否する実装が通る検証にしない。
6. 公開可能な小さな課題で実モデルの結果を確認する。不具合を含む変更と正しい変更を使い、指摘の真偽は再現入力とコードで裁定する。制御テスト成功と実モデルの検出結果を分け、見落とし、誤指摘、時間、親子合計の使用量、未確認範囲を記録する。欠陥検出率100%や速度改善を完了条件にはしない。
7. `thkt/dotagents`の設定に従い、`bun install --frozen-lockfile --ignore-scripts`で依存を揃え、引数なしの`bun run check`、独立評価、同じPRの最新コミットの`checks`・`verify`を確認する。このrepoの`capture`設定は`null`で、画面媒体は要求しない。変更する人向けMarkdownは既存の日本語確認方針を適用する。人がレビューしてマージを判断する。

機械検証は既存のOxlint、型検査、書式・複雑度検査と振る舞いのテストを使う。lintで分からない意味上の境界を、同じ`check`の反復だけで保証しようとしない。新たなlintルールや解析ツールの一括導入は今回含めず、検出したい不具合と既存検証の不足が具体化した変更として別に判断する。

## 後続の計画

第2段階は`docs/evidence`の索引である。文書の位置、版、役割、適用範囲、現行・過去・提案の区別を持ち、その時点のIssueと変更範囲から必要な原文を選ぶ。索引は要求の正本や原文読取りの代替にしない。必要文書の欠落、文書追加、内容・役割・適用範囲の変化が選択結果に与える影響と再評価条件を、レビュー基盤の記録形式を確認して別Issueへまとめる。

途中の並列レビューは保留する。独立評価が必要で、対象を固定でき、メインに独立した次の作業がある場合の選択肢として残す。実Issueで品質と全体時間・使用量の利点を再現でき、対象の固定、複数プロセスの終了・中断、予算、古い結果の扱いを検証できてから採用を判断する。今回の直列ホストへ並列呼出しを追加しない。

独立した`review`スキル、実装単位の分割プロトコル、モデルや予算の変更、外部サービスによるレビュー、全文書の一括取り込み、既存のGemini対象選択Issue #59の変更は今回の範囲に含めない。
