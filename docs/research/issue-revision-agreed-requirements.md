## 目的と合意

合意して更新したIssueを、同じPRの新しい修正runへ引き継げるようにする。実行中に要求が変わった場合の停止と、前回runの保全は維持する。

2026-09-21、#149で評価方法・記録・UIの具体案を依頼者が採用し、Issue本文を統合した後、PR #170の既存PR修正を開始したところ、担当AIの起動前に`Agreed Issue changed during revision; result not saved: no safe new run directory was confirmed.`で停止した。

原因と下記の最小案を提示し、「このCLI修正を別Issueとして先に進め、その後#170へ戻ってよいですか」と確認したところ、依頼者は「進めて」と指示した。この開始条件の整理を別Issueとして実装・検証し、採用後に#149の修正へ戻る範囲で合意済み。合意は既存の照合を今回だけ無効にする許可ではない。

## 原因

調査版はmain `59e9f7374c18dba415f9c1512e1b9116a9e8a28d`。[development.ts](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/development.ts)の`prepareRevision`は前回runのIssue本文を`revision.issueText`へ設定し、[checkRevision](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/revision.ts)は現在のGitHubのtitle/body/state/updatedAtと照合する。`selectStart`も前回との完全一致を要求する。そのため、新しい修正依頼の前に人が要求変更を合意していても拒否する。

前回公開headは`4a6ff31e77e35adff6eed4cdc7d50483d8908bdc`で、停止後もcheckoutは同じhead、作業差分なし。新runディレクトリは未作成で、setup・修正AI・検証・公開は始まっていない。前回runの保存記録は変更していない。

## 最小案

既存の明示的な修正依頼の入口で、担当ホストが現在の合意済みIssueと修正依頼の範囲を確認し、新しいrunにそのIssueの内容を固定する。前回Issueとの一致は、その前回の保存記録の整合性を検証するために使う。前回の要求と新しい要求は区別して保持する。

新しいrunの開始後は、固定したIssue・修正依頼・対象・主体・権限に変更があれば従来どおり停止する。PRのheadとcheckoutが前回公開版に一致すること、作業差分がないこと、同じrepo・Issue番号・PRであること、前回の検証・公開記録が整合することも維持する。本文に要求変更があることだけで、その変更が人の合意済みと自動判定しない。

既存の要求精査・修正入力・独立評価を使い、新しいCLI、承認ファイル、再開台帳は追加しない。独立評価は現在の合意済みIssueと採用した修正依頼でPR全体を評価し、前回acceptedを再利用しない。

## 完了条件

- [ ] 人が合意したIssue更新後、新しい明示的な修正依頼で同じPRの修正を開始できる。新しいrunは今回のIssueを保持し、古いrunと保存stateを書き換えない。
- [ ] 開始後のIssue変更では停止し、後続の実装・検証・公開を進めない。開始前後の変更を分け、現行の正常系・異常系として直接検証する。
- [ ] 現在のIssueが同じ対象のOPENな要求であることを確認し、閉じたIssueや無効な要求で作業を開始しない。
- [ ] 未完了run、前回記録の改変、dirty checkout、公開head・対象・主体の不一致等の既存の保全・停止条件を維持する。必要な既存検証を再利用し、過去の禁止そのものを固定するテストを新契約へ更新する。
- [ ] READMEの開始条件と変更後の扱いを現在の契約として整理し、`bun install --frozen-lockfile --ignore-scripts`でセットアップして、`bun run check`、独立評価、日本語確認、同じheadの`checks`・`verify`を通す。

新しい条件は採用後に開始する新runに適用する。今回停止した実行の再開、旧記録の変更、照合の無効化、未合意の要求変更の自動採用は対象外。採用前のPR #170はdraftを保持する。本変更の採用後に、#149の合意済み修正を新しいrunとして開始する。

対象はCLI・検証・手順で、商品画面の変更はない。このIssueに画像・動画や実モデルの能力比較は不要。模擬コマンドを使う制御テストと、ハーネスによる実装・独立評価・実際のGitHub公開は区別して報告する。既存のrun・ログはcheckout外へ保存し、必要な共有根拠はPRへ記す。ローカル下書きを実装の必須入力にせず、このIssueと固定版の根拠を使う。

## 代替案

現行CLIを変更せず、新しいIssueと新規PRへ作業を移す方法もある。今回だけの移行で済む一方、既存のPR・要求・証拠の引き継ぎが増える。同じPRで要求を合意してから修正する運用を今後も使うなら、上記の開始条件の整理を推奨する。コードやノード・矢印の純減は未確認。
