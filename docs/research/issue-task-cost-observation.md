# 要求充足までの使用量をrun記録から集計できるようにする

## 目的と根拠

ハーネス改善を採用する前に、同じ課題・モデル・評価条件で、要求を満たした作業1件あたりの負担を比較できるようにする。2026-09-24、依頼者は[Cursorのtoken効率改善](https://cursor.com/blog/improved-token-efficiency)に関連して、比較には先に観測の実装が必要ではないかと指摘した。従来の「新しいIssueは不要」という判断を改め、今回の具体的な不足に限って扱う。

[比較評価の方針 #145](https://github.com/thkt/dotagents/issues/145)は要求充足を先に判定し、失敗・再試行を含む総費用と成功率を併記する。[役割説明の比較 #171](https://github.com/thkt/dotagents/issues/171)では保存済みのactorイベントから工程別の`input_tokens`、`cached_input_tokens`、`output_tokens`を手作業で照合できた。一方、6 runはCI待機停止または人の判断待ちで、全工程の完了1件あたりの費用とは言えなかった。[実行レポート #177](https://github.com/thkt/dotagents/issues/177)は1 runの行動・結果を読むためのもので、複数runを通した費用集計は対象外だった。現行の`codex-actor.ts`はCLIのイベントを保存するが、ハーネスはモデルへの実際のリクエストやツール定義の組立てを所有しない。

## 今回の範囲

1. 保存済みの`implement` runを明示的に選び、上位の`result.json`、検証state、actorのイベントを読み取って、run・工程・actor実行ごとの使用量と記録の対応を再現可能な形で集計する。既存の生ログを正本とし、変更しない。`cached_input_tokens`は`input_tokens`の内数として扱う。失敗・停止・再試行を集計から落とさず、同じ実行やイベントの二重計上を防ぐ。
2. 各runの記録済み終了状態と、評価で確認した要求充足を分ける。`verified_local`、`published_draft`、CI成功、レビューaccepted、人の承認・マージを一つの「完了」にしない。比較時の課題ID、対象commit、モデル・設定、試行と再試行の対応、要求充足の判定・根拠を明示し、判定不能を成功に含めない。
3. 同条件の比較では、全試行数、実行失敗・判定不能、要求充足件数、各工程と全試行の使用量、実時間を示す。完了作業あたりの費用を出す場合は、失敗と再試行を含めた分子と、独立に要求充足を確認した課題数という分母を明示する。必要なusageや子モデル分が欠ける場合は総額・比率を確定値にせず、欠損箇所と測定範囲を出す。
4. 金額換算は入力・キャッシュ入力・出力の単価、通貨、適用モデル、算定時点を明示した**推定**に限る。単価がなければtoken区分のまま示す。Codexの認証方式による実請求額と推定を混同しない。CLIから分からないシステム文・ツール定義・履歴・ツール結果別の請求tokenを推測して埋めない。
5. まず既存記録を読む集計手段で満たす。必要な対応関係やusageが実際に記録されていないと判明した場合だけ、その問いに必要なrun時の記録を追加する。常設ダッシュボード、全ツール呼出しの詳細記録、定期計測、Cursorの内部最適化の模倣は含めない。

## 完了条件と検証

- 成功・停止・再試行を含む模擬runから同じ集計を再現でき、actorごとの原記録に遡れる。欠損・不正・重複・対応不能はゼロに置き換えず、理由を示して確定集計を止める。
- 既存の実runから少なくとも1組を読み取り、実際に集計できた値と不足した値を報告する。私的な生ログ・認証情報・絶対パスを公開しない。
- 要求充足が独立に確認された課題と、CLIが終わっただけのrunを区別した例で、分母と失敗・再試行を含む分子を検証する。料金の推定例がある場合は単価と計算式を示す。
- 導入前後の比較は同じ課題・モデル・設定・判定条件で行い、要求充足・失敗条件を先に確認する。集計器そのものは改善効果を証明しない。
- 既存の結果・HTMLの意味と保存状態を壊さず、必要なCLI案内を更新し、`bun run check`と関係する独立評価を通す。

## 実装時に確認すること

現行mainの保存形式とactorイベントを再確認し、初回実装・修正・評価をディレクトリ名だけで分類しない。子モデルの使用量が親のイベントに含まれるかは前提にせず、実際の記録とCLI仕様で照合する。比較対象の選択と要求充足判定は評価担当が根拠を持って行い、runtimeの終了状態を自動的な品質判定にしない。
