## 目的と現状

CIの成否判定を変えず、待機中のGitHub取得と同じ状態のログを減らす。

[scripts/ci.ts](https://github.com/thkt/dotagents/blob/019a25badbcec00a05231267b31fed453a49bf74/scripts/ci.ts#L200) は未完了の応答を得るたび、最大1秒待って再取得する。確認回数は通信時間にも依存し、現在の実運用の回数・負荷は未測定。

## 範囲と完了条件

- [ ] 初回確認は直ちに行い、未完了の通常待機は固定5秒を基本とする。残り時間が短ければ期限に収める。新しい設定項目や汎用監視機構を追加しない。
- [ ] 現行の待機期限、コマンドの残り時間制限、中断、head・base・OPEN状態の照合を維持する。期限到達と重なって観測した失敗を単なる確認待ちにしない。
- [ ] 必須checkの全件成功、同名checkの全件確認、他の登録済みcheckの失敗・実行中の判定を維持する。必須のSKIPPED／NEUTRALを成功にしない。
- [ ] 未登録・実行中・失敗・時間切れ・取得不能・対象変更の区別と、最後の観測・次の対応を維持する。
- [ ] 固定した模擬時間で取得回数の減少を示し、実GitHub負荷の実測と区別する。検知が従来より数秒遅くなり得ることを手順へ反映する。

## 重点的な検証・順序

終端照合の削減後、他のPR生成変更とは独立して着手できる。[#72](https://github.com/thkt/dotagents/issues/72)のCI分類を変更しない。

`ci.test.ts` の模擬時計・応答を再利用し、初回即時確認、繰り返し間隔、期限付近の成功・失敗・取得不能、中断と対象変更を確認する。固定件数の維持や実時間での長い待機テストは求めない。

## 検証と引き継ぎ

セットアップは `bun install --frozen-lockfile --ignore-scripts`、提出前は引数なしの `bun run check`。既存の関連テストを再利用し、不足する現実的な失敗条件だけを追加・更新する。独立評価と同じPR headの `checks`・`verify` を確認し、人がレビュー・マージを判断する。模擬コマンドの検証、実モデル、実際の公開は別の証拠として報告する。

プロダクト画面媒体は不要。必要な共有根拠はIssueまたは `research/`、内部ログは既存のcheckout外保存先へ置く。既存のrun・失敗記録・他作業の差分を削除・変換せず、新しい必須台帳を作らない。対象・権限・版の照合と、要求変更を人へ戻す責任を維持する。

### このIssueで狙う削減

- 固定間隔の見直しを最小差分で行い、設定・バックオフ管理・新しい監視クラスを足してコードを増やさない。既存の待機・期限処理で足りる部分を使う。
- 主な効果は取得とログの繰り返し回数の減少。ノード・矢印やコード行数が変わらない場合は0と記し、取得頻度の削減で代用しない。ノード削減のために必要なCI分類を消さない。
