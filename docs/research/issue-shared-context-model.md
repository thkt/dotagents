# 目的・概念・規則の共有モデルを土台に、要求整理から実装・評価までのフローを整理する

## 目的

要求整理・実装・独立評価の担当が、同じ目的・概念・規則と根拠を参照し、前提の変更がどの判断に影響するかをたどれるようにする。その共有モデルから人向け説明とAI入力を取り出し、同じ情報の転記、再整理、重複定義を減らす。

実コード・スキル・実際の受け渡しを整理する。図のノードをまとめたり、原則を文書へ追記したりするだけでは完了としない。全体の方向は共有モデルを中心とし、初回は一つの具体例を通して必要な機能を実装する。

## 初回の適用対象と着手範囲

初回は **thkt/dotagents自身の実装開始条件** を扱う。具体例は採用済みの[#85](https://github.com/thkt/dotagents/issues/85)「必要入力を固定し、無関係な作業を保全して実装を開始する」。アプリ・サービス固有の知識の導入は初回に含めない。

依頼者thktは2026-09-17、この対象・具体例と、同じ正本から説明とAI入力を取り出して重複定義・転記を削除する提案に対し、「進めましょう。コード、手順（ノードと矢印）をソリッドにしたい」と指示した。初回対象の未確定は解消した。以下はその方向を現行コードに照らして具体化した範囲・受入条件であり、要件や権限の追加、既存保証の緩和は含めない。

| 共有する情報 | この具体例で扱う内容 |
| --- | --- |
| 目的 | 確認した要求と開始条件で実装し、今回無関係な作業を失わない。開始のためだけの退避・準備・やり直しを減らす |
| 概念と関係 | Issueと合意、元checkout、開始commit、対象設定、選択した必要報告、隔離worktree。どの版・場所を照合し、誰が内容・合意・実行を判断するかを結ぶ |
| 合意済み規則 | 開始HEAD・設定・必要報告の一致、必要入力の差分や欠落で停止、確定commitから隔離、無関係な作業を保全、setup後の再照合。報告参照の一致を要求の合意と同一視しない |
| 根拠と未確認の仮説 | #85・PR #89の要求・コード・検証を根拠にする。「準備が減れば時間や手戻りも減る」という効果は未計測の仮説として区別し、改善値を作らない |
| 前提を見直す例 | 本文が一致していても必要入力のindex・モードが変われば停止する例から、「本文一致だけで開始可能」という説明の不足へ戻れる。実際の新しい障害が発生したとは扱わず、既存の検証条件による確認例とする |

初回はこの知識の関連部分だけを選び、同じ内容を各工程で書き直さず、scopingの参照、Issueの要求との関連、初回実装・修正・独立評価への入力、結果から前提を見直す参照へ接続する。知識の選択は既存の要求整理の中で行い、別の必須作業にしない。対象の既存定義を正本へ移し、人向け説明を生成または参照へ置き換える。別正本として手書きの同じ定義を残さない。

## 設計の土台

三つの概念すべてに、前提を問い直す面と、実務で扱えるように表現する面を持たせる。これは本フローへの応用上の整理であり、六つの工程や必須帳票を追加する要求ではない。

| 概念 | 哲学的に問い直すこと | 形式的な利用 |
| --- | --- | --- |
| テレオロジー | 誰にとって何が望ましく、何を目指すか | 目的、望ましい状態、成功条件、必要な評価指標・優先順位を、要求と結び付ける |
| オントロジー | 何を対象として捉え、どの区別や関係を重要とするか | 主体、対象、役割、型、属性、関係、状態の定義を共有する |
| ノモロジー | 何がどの条件で成立・変化し、その理解は妥当か | 規則、制約、状態遷移、因果仮説と予測を表し、検証や観測と照合する |

三概念は相互に関係する。企画・デザイン・エンジニアリングのどこからでも、根拠を示してモデルの更新を提案できる。観測した事実、適用する規範、検証中の仮説、合意・未確定を区別する。規則の採用を効果の確認と扱わず、不明な目的・条件・数値をAIが補完しない。

共有モデルは継続して使う知識の正本とする。今回の要求・完了条件・許可範囲はIssueと合意記録を正本とし、必要な知識を参照する。根拠と合意記録は三概念へ横断的に結び付ける。モデルの更新によってIssueの合意範囲を自動変更しない。

## 範囲と完了条件

- [ ] **一つの具体例で三概念を関連付ける。** 初回の対象について、既存の目的・概念・規則や仮説、根拠、合意・未確定を選び、最小限の構造化した正本を作る。ID・関係・参照・対象版・適用条件・状態など、取り出しや検査に必要な情報を定義し、理由と背景は文章として保持する。
- [ ] **同じ正本から人向け説明とAI入力を取り出す。** 正本を変更したときに両方へ反映でき、対象とする定義を別々に手修正しない。派生物から元の情報と版へたどれ、未合意・未確認の内容が確定事項へ変わらない。図への出力は初回の必須機能にしない。
- [ ] **既存のフローへ接続する。** scopingで関連知識を選び、Issueに今回の要求と参照を残す。実装・修正・独立評価が同じ要求と選択した知識の版を利用できるように、既存のスキル・プロンプト・ホスト処理を整理する。参照を別の必須台帳へ転記する運用や、毎回全資料を読み込む運用を追加しない。独立評価者は実装者の解釈をうのみにせず、追加の根拠・矛盾を調べられる。
- [ ] **結果を前提の見直しへ戻せる。** 一例を通し、根拠→仮説・変更案→合意した要求→実装・評価結果→見直す目的・概念・規則を追跡する。前提の不一致が見つかった場合、観測、影響する判断、必要な調査・人の判断を示してモデルの更新を提案できる。更新は既存の差分・レビュー・合意の扱いを使い、古い評価を新しい内容へ流用しない。報告パスと版の受け渡しだけで完了としない。
- [ ] **機械・AI・人の責任を保つ。** 機械は定義した形式・ID・参照・版・制約を確認し、AIは意味・適用条件・成果物との整合を評価する。人は目的、許容範囲、要求や権限の重要な変更を判断する。形式検証の成功を事実の正しさや合意の保証とせず、仮説を自動的に必須ゲートへ変換しない。
- [ ] **置き換える既存作業を削除・統合する。** 同じ内容を編集する箇所、工程間の転記、LLMに固定内容を再現させる処理を確認し、新しいモデル・抽出処理が代替するものを実際に整理する。同じ定義を複数の文書・プロンプトで手修正する作業を実際になくす。変更前後の操作・更新箇所・機械処理・LLMの仕事と、残る確認の理由をPRで説明する。正本や必須工程を追加するだけの変更は完了としない。
- [ ] **既存の利用と確認を維持する。** `.dotagents.json` は対象repoの実行設定として保ち、知識本体を入れない。モデルを持たない対象repoへ一律に整備を要求せず、既存のIssue・参照で始められる利用を維持する。今回必要と選んだモデルや参照が欠けている場合は黙って無視しない。要求・対象版・公開権限の照合、独立評価、人のレビュー・マージ、無関係な未コミット作業の保全を維持する。
- [ ] **説明を実装へ合わせる。** 関係する既存の開発方針・スキル・CLI手順を更新する。何を機械で確認し、何をAI・人が判断し、どの情報を次へ渡すかを実装からたどれるようにする。HTMLや構成図は実コード・フローの整理後に同期する対象とし、その表示変更だけを本Issueの成果にしない。

## 実装判断と対象外

YAML・JSONの選択、ファイル配置、ID粒度、関数分割、抽出の入口は、既存資産と最初の具体例から実装担当が比較して決める。組み込み機能と既存の参照・検査・生成処理を優先して検討する。追加の依存や機構を選ぶ場合は、減らせる作業と保守負担を説明する。人の要求・権限・運用負担を変える判断は人へ戻す。

初回から全資料・全repoを変換すること、汎用知識管理基盤・専用エディター・検索サービス、新しい進行エンジン、六つの必須文書、数値指標の一律必須化は含めない。#83で廃止した専用状態管理を代替する台帳やゲートも作らない。

アプリ固有のリリース・計測基盤、関係者への自動配信、終了済み実行の再開、既存PRの修正再開CLIは別範囲とする。新しい観測を前提の見直しに使えることは扱うが、観測の自動収集まで初回の必須機能にはしない。旧run・未追跡資料・他担当の差分を一括移行・削除しない。

## 検証

既存のdevelopment・correction・review・evidence関連の検証を再利用し、不足する振る舞いだけを追加・更新する。次を重点的に確認する。

1. 同じ正本の変更が説明とAI入力に反映され、参照・版・適用条件・未確定状態が失われない。
2. 未知ID、参照欠落、確認後の内容変更など、今回機械が扱うと定義した不整合を検出する。選択しなかった知識や未合意の案を要求へ混入させない。
3. 適用範囲の違い、反する観測、未確認の仮説について、影響する前提と判断へ戻れる。意味・適用の評価は機械的な形式検査と分ける。
4. 同じ例を要求整理から実装・独立評価へ渡し、結果からモデルの更新提案へ戻せることを、入力・出力と変更差分で示す。実モデルによる意味判断を試していない部分は未確認と明記し、模擬コマンドの成功で代替しない。
5. 不要になった定義・転記・処理を示し、残すテストがどの失敗条件を守るかを説明する。件数・行数・構成図のノード数や削減率だけを成功条件にしない。

### 初回の受入例と簡素化の確認

- 同じモデルの選択済み定義・適用条件・合意状態を、人向け説明と初回実装・修正・独立評価の入力から辿れる。正本の一つの定義を変えると、派生物へ反映または既存checkで古さを検出できる。派生物を別々に手修正して一致させる手順にはしない。
- 選択した知識の参照と版を既存の入力・対象記録へつなぎ、元の定義と根拠を辿れる。今回必要と選んだIDの未知・重複、参照欠落、確認した版と内容の不一致を黙って受理しない。未選択の知識、未合意の案、未確認の効果は要求や開始条件へ混入させない。モデルを持たないrepoの既存入口は維持する。
- #85の開始例を、無関係な差分だけがある場合、必要入力の本文・index・モードやHEADが変わる場合、setup中に必要入力が変わる場合で照合する。前者は保全して開始し、後者は既存の停止条件を保つ。新しいモデルを通した説明と、実コードの結果が対応することを確認する。
- 同じ例について、要求整理で選んだ目的・概念・規則、Issueの要求、実装・評価結果、見直す前提までを既存の記録から辿る。前提に反する結果では影響する規則と判断を示し、事実不足は調査、要求・権限の変更は人へ返す。モデルを自動承認・自動改訂せず、以前の成功を変更後へ流用しない。
- 比較の単位を揃え、実装コード・テスト・手書き文書・生成物を分けて増減を示す。手順は「一つの操作・判断・受け渡し」を単位に、人／AIの操作、ホストの処理、分岐と戻りを区別する。減らした手修正・転記・再組み立てと、追加した抽出・検査を両方示す。図の箱をまとめる、関数やファイルを移す、生成物を集計から隠すことで削減扱いにしない。
- 対象範囲のノードと矢印の変更理由を示し、全体の数を述べる場合は対象外を含めて同じ粒度で数える。コード純減は一律の条件にしないが、増える場合は実際に省けた作業と維持負担を説明する。利用者の必須入力・引き継ぎ先・承認工程を増やさず、新しい仕組みが置き換える作業を確認できない場合は完成扱いにしない。数値の改善は実測前に約束しない。

セットアップは `bun install --frozen-lockfile --ignore-scripts`。ハーネス提出前は引数なしの `bun run check`、独立評価、同じPR headの `checks`・`verify` を確認し、人がレビューとマージを判断する。モデル整備だけを理由にプロダクト画面媒体を一律に要求しない。共有する説明・検証結果は対象repoの既存の保存方針に従い、内部ログはcheckout外の既存保存先へ置く。
