# 現行の正常系・異常系に絞り、重複と実装依存のテストを整理する

## 目的と合意

ハーネスの現在必要な振る舞いを少ない保守負担で検証できるようにする。ユーザーの依頼「現行の正常系、異常系に絞ること。冗長、実装をなぞるだけのテストを整理すること」を今回の範囲とする。新しい機能や保証は追加せず、現在必要な正常結果・停止理由・副作用の抑止・データ保全を残す。

対象は `thkt/dotagents`。調査時点は main `e0264ad7803965074af5e998e06f04643408ed88`。既存の[テスト整理の方針](https://github.com/thkt/dotagents/blob/e0264ad7803965074af5e998e06f04643408ed88/.codex/DEVELOPMENT.md#実装とテストの整理)を適用する。新しい方針、監査工程や台帳は作らない。

## 確認した整理対象

- `scripts/tests/development.test.ts` は、多数のケースで廃止済みの `verification-summary.md` と `stopped.txt` の不在を繰り返し確認している。現行の `result.json`、下位state、生ログと元の作業の保全を検証するテストへ絞る。
- `development.test.ts` と `correction.test.ts` は、実装側の `repairInstructions()` から期待する文字列を作り、固定指示の文章も照合している。実装と一緒に変わる期待値や指示の綴りだけの確認を除く。Issue・報告・検証エラー・撮影設定など、工程間で渡す実データの確認は残す。
- `correction.test.ts` は、純粋な設定の不正値をケースごとにGitリポジトリと子プロセスを作って検査している。既存の `assertConfig` で判定を直接検証し、CLIが不正設定を拒否して処理や書込みを始めないことは代表ケースで残す。
- CI対象の初回照合には `development.test.ts` と `ci.test.ts` で同じ入力・停止理由を重複して調べるケースがある。同じ時点の同じ保証は責務に近いテストへ集約し、developmentから停止結果・公開済みURL・記録を返す接続は代表ケースで検証する。初回と待機中・終了時の照合を同一視しない。
- `target.test.ts` の廃止設定の複数形状と、`correction.test.ts` の旧state版の列挙は、現在の未対応入力を拒否する境界へ整理する。旧機能の全形状を維持するための列挙はやめ、他の条件が正常な入力で、意図した理由の拒否と必要な保全を確かめる。

全15テストファイルを確認した。他のテストでも、同じ観点で具体的な重複が確認できれば整理するが、見た目が似ていることだけで統合しない。汎用的なテストDSLや新しい抽象化の追加、ファイル移動や行の圧縮だけによる削減は目的にしない。

## 残す保証と対象外

- 現在の正常な実装・修正・検証・独立評価・公開の結果、および工程間の実データの受け渡し。
- 不正入力と状態変更の拒否、公開対象・主体・権限・head・Issueの照合、二重実行の抑止。
- 観測時点が違う失敗、timeout・割込み時の子プロセス停止、生ログ・元の作業・既存stateの保全、記録の保存失敗でも元の原因を失わないこと。
- 検証出力、skip拒否、撮影結果など、現在の外部境界を守る検証。

実行コード、CLI、スキル、開発方針、フロー図の機能や遷移は変更しない。現行の異常系を削って件数を減らすことや、停止タイミングの異なるケースの一括削除は対象外。全テストへの不具合注入、実モデルの追加評価や新しい監査CLIも行わない。

## 完了条件と検証

1. 削除・統合・軽量化したテストについて、重複していた保証、失う確認、残す現在の検証を既存の実装報告とPR本文から辿れる。
2. 期待値を実装のプロンプト関数から生成する確認と、廃止済み出力ファイルの不在確認を除く。実データの受け渡しを検証する期待値は要求から独立に定める。
3. 純粋な不正設定の複数ケースを直接検証し、実CLIでの拒否と副作用抑止は代表ケースで残す。旧形式に由来する入力拒否も、現在の境界として必要な確認を残す。
4. テストと補助コードの保守量を実質的に減らし、削除のための新しい実装APIや制御分岐を作らない。行数・件数・時間だけで必要性を判断しない。
5. `.dotagents.json` のセットアップと `bun run check` を実行し、既存の独立評価と同じheadのCIで確認する。実装・テスト・文書の増減と、同じローカル環境での整理前後のcheck結果を報告する。

整理前のローカル `bun run check` は354 pass、0 fail、テスト実行104.23秒。単回計測のため、前後差を一般的な速度改善とは断定しない。テスト件数・assert件数の維持目標は設けない。今回は画面変更がないため媒体は不要。

Issue内の根拠と既存コードで実装へ引き継げるため、別の調査報告は作成しない。要求上の未解決事項はなく、実装方法の細部と残す検証の妥当性は既存の実装・独立評価で確認する。公開前の独立した要求評価は未実施。
