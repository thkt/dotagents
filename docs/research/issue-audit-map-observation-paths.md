# 構成図のIssue更新・読戻しと新しい合意の経路を揃える

## 目的と根拠

ローカル構成図で、Issue本文の不備、参照追記、新しい合意が発生した後の確認経路を辿れるようにする。説明文にある責任を、既存の接続と担当へ揃える。

確認日: 2026-09-24。`docs/workflow-map.html`はコード版`7134d2ffa441985ee00d2dd1a6b6e79f5e9cc4ae`を参照する。

- `I13`は本文不足を要求精査へ戻す説明を持つが、接続は引き継ぎの`H01`と公開結果確認の`Z10`だけで、要求精査への戻り先を辿れない。
- `H07`は共有先・未完了操作をIssueに記すノードだが、`H08`へ直行し、Issueを書き換えた場合の読戻しへの接続がない。
- `S25`から`S23`へ戻る接続は#131で意図して採用された。新しい合意が既存のIssue・下書きの更新へ届く説明で足りるかは、今回あわせて確認する。上記2点と同じ確度の接続不備とは断定しない。

根拠は[本文不足時の精査・更新・読戻し](https://github.com/thkt/dotagents/blob/7134d2ffa441985ee00d2dd1a6b6e79f5e9cc4ae/skills/scoping/references/issue.md#L13)と[判断後の決定記録](https://github.com/thkt/dotagents/blob/7134d2ffa441985ee00d2dd1a6b6e79f5e9cc4ae/skills/scoping/SKILL.md#L34)。実運用で確認が省略されたとの観測ではなく、図の接続・説明の不足である。

## 範囲と受入条件

ローカルの図と、対応するガイド説明の必要箇所を整理する。確認専用の新ノードを増設する前に、既存の要求精査・Issue反映・読戻し・決定記録を再利用する。

- [ ] `I13`で要求・根拠との不一致が見つかった場合、事実調査、要求・許可の判断、本文修正の既存経路へ条件付きで戻れる。通信結果不明だけを扱う経路と混同しない。
- [ ] `H07`でIssue本文を書き換えた場合は、更新後の最新本文を読み戻して確認する経路を通る。変更前の読戻しを流用せず、変更がない場合の再公開・再確認を強制しない。
- [ ] `S25`で生じた新しい合意が既存のIssue・下書きの更新へ届くことを確認し、足りなければ既存経路・説明で補う。S13を毎回の必須経由にせず、既存合意の再利用と、回答ごとの逐一転記を求めない方針を保つ。
- [ ] 調査できる事実は担当AI、要求・権限は人という分担、未解決事項による停止、結果不明時の保全と重複公開の抑止を維持する。
- [ ] 既存ID・検索・直接参照・停止理由を維持し、新しいgate・台帳・runtime経路を追加しない。矢印の純減を達成条件にしない。

## 検証と対象外

着手時に最新HTMLを読み直し、checkout外に比較用コピーを保全する。図の確認時SHA-256は`9ff7de1d20c845922d5103fd3268cecd6c38d2b492ea51688a7aac88b5185407`。通常の公開成功、本文不備、報告参照の追記、新しい合意、変更なしの各経路をたどり、通常幅・390px幅で検索、選択、戻り先、停止表示を確認する。日本語と担当・条件を原資料・既存の独立評価へ照合し、変更提出前に`bun run check`を実行する。

HTML・画面証拠・生ログはローカルに保持し、公開repoへ追加しない。旧下書き・無関係な未追跡資産、runtime、GitHub公開権限、要求整理の仕組みは変更しない。
