## 目的と段階

dotagentsの合意済み設計規約について、既存の機械検査で検出できない重要な違反があるか調べ、追加検査の必要性を判断する。レビューで繰り返し確認する負担を減らせるかを、検出力・誤検出・保守費用から評価する。

2026-09-19、ZOZOのArchUnit運用記事を受けた調査Issue・定期チェックの依頼に基づく。初回は単発の調査と採否判断を対象とする。具体的な規約や検査の追加は未決定であり、候補がない、または既存検証で十分という結論も完了とする。時間ベースの定期実行は設定せず、採用候補があれば変更時の既存check・CIへの接続を優先して検討する。

## 現状と根拠

調査時のdotagentsは[28ab29118e9d060114498dee6dc29d8508618045](https://github.com/thkt/dotagents/tree/28ab29118e9d060114498dee6dc29d8508618045)。着手時には最新の規約・コード・検証と採用状況を確認し、実際に調べた版を記録する。

- [共通check](https://github.com/thkt/dotagents/blob/28ab29118e9d060114498dee6dc29d8508618045/package.json)にはlint・format・複雑度・型検査・生成文書照合・制御テストがあり、[CI](https://github.com/thkt/dotagents/blob/28ab29118e9d060114498dee6dc29d8508618045/.github/workflows/ci.yml)でも実行する。検査の入口を新設する必要性は確認されていない。
- [開発方針](https://github.com/thkt/dotagents/blob/28ab29118e9d060114498dee6dc29d8508618045/.codex/DEVELOPMENT.md)と[独立レビュー](https://github.com/thkt/dotagents/blob/28ab29118e9d060114498dee6dc29d8508618045/scripts/review.ts)は、文書・検証・コードの整合、現実的な不具合検出と費用、必要に応じた不具合注入を既に扱う。
- [#98](https://github.com/thkt/dotagents/issues/98)では、共通のコマンド実行処理から上位フローへ戻る依存や、inputとreviewの実行時importの循環を解消する要求があった。現在の[process.ts](https://github.com/thkt/dotagents/blob/28ab29118e9d060114498dee6dc29d8508618045/scripts/process.ts)はNode標準APIをimportしている。これは調査の出発点であり、現在の違反や既存チェックの見逃しを確認したという意味ではない。
- [ZOZOの記事](https://techblog.zozo.com/entry/verify-ai-agent-coding-rules-with-archunit)は、規約の機械検査、型参照とメソッド呼び出しを区別した誤検出対策、文書・テスト・コードの整合、意図的な違反による検査確認を紹介する。[ArchUnit](https://www.archunit.org/userguide/html/000_Index.html)はJavaバイトコードを対象とするため、TypeScript主体の本repoへ製品をそのまま導入する提案ではない。

## 調査範囲

まず#98で扱った依存関係を題材に、現在も守る理由がある責務境界と、既存検証が実際に検出する違反を確認する。現在のファイル名や配置をそのまま固定せず、型だけの参照・実行時依存・間接的な依存を必要に応じて区別する。関連範囲だけを調べ、全repo・全ルールの網羅監査や新しい設計規約の制定へ広げない。

候補について、合意済みの規約と理由、具体的な違反例、正常な対照例、既存検査の有無を結び付ける。現行コードに違反がある場合と、将来の再発を想定した一時的な不具合注入は区別する。必要な規約自体が曖昧なら、検査を実装して意味を決めず、未確定事項として残す。

候補の検出力を確かめる必要がある場合だけ、同一基準版の隔離したコピーで小さく試す。既存のlint・型検査・テストで足りるかを先に確認し、不足があれば既存ツールの設定、限定的な構造検査、現状維持を比較する。構造上の参照があることと、実行時の権限・鮮度・停止・データ保全を守れることを同一視しない。

## 完了条件

- [ ] 調査した規約・根拠・対象版と、既存検査で守れる範囲、レビューや実行時検証に残る範囲を示す。未検出の違反があるとする場合は、具体例と観測結果を添える。
- [ ] 追加検査を提案する場合は、隔離したコピーで違反を入れたときに意図した理由で失敗し、正常な対照では成功することを確認する。検査対象からの漏れ、誤検出、適用除外・例外の範囲、未確認事項を示す。既存検査が同じ保証を持つ場合は重複して追加しない。
- [ ] 追加の保証と、実行時間、導入・調整・例外管理・保守の費用を比較する。取得できない費用は未確認とし、準備や失敗・再試行を隠さない。短さや検査件数を採用理由にしない。
- [ ] 「追加不要／限定した検査を提案／根拠不足で保留」の結論と理由を本Issueへ残す。提案する場合は、既存check・CIへの接続先、文書の保証範囲・例外の更新箇所、受入条件を具体化する。検査の採用・実装は別途合意する。

## 対象外と引き継ぎ

今回の対象は調査・採否判断まで。常設の解析ツール・依存関係・hook・MCP・定期自動実行、新しい必須ゲート、規約台帳、全ルールの文書複製、専用のモデル評価工程は追加しない。検査を通すために規約や既存テストを弱めず、要求・権限・意味判断の独立レビューを置き換えない。

調査用の一時コードや不具合注入は隔離したコピーで扱い、既存の作業差分・過去runを保全する。実モデルやGitHubへの試験的な公開を前提にしない。結果は本Issueを基本とし、長い再利用可能な根拠だけを既存のresearch/またはdocs/evidence/へ残す。生ログ・秘密情報・ホスト内パスは公開しない。プロダクト画面媒体は不要。

#115は既存のテスト価値判断、#120は独立レビューでの冗長性検出、#141はCodeGraphによる探索の比較、#145は改善案の比較評価方法を扱う。本Issueはこれらを作り直さず、設計規約の機械検査に追加価値があるかという個別の問いを扱う。未完了の関連Issueの採用を前提にしない。

今回はIssue作成までで、調査用の不具合注入・追加検査の試作は未実施。本文は執筆担当が原資料・現行コード・依頼範囲と照合し、別評価者による独立評価は未実施。Issue整理だけにハーネスのテストは課さない。後続で変更を採用する場合は、対象repoの`bun install --frozen-lockfile --ignore-scripts`、`bun run check`、既存の独立評価・日本語確認、同じPR headの`checks`・`verify`を行い、人が承認・マージを判断する。
