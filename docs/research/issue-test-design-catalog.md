# ハーネスのテスト作成手順と初期観点カタログを整える

## 目的と現状

テストを作成・更新するとき、今回守る失敗条件から必要な検証を選び、既存テストとの重複や検出力のないケースを避けられるようにする。現行の[開発方針](https://github.com/thkt/dotagents/blob/674e059269461efe3a71fcb8108c2aa99fcacb93/.codex/DEVELOPMENT.md)はテストの価値判断を定めているが、別の変更へ適用しやすい具体的な失敗条件の索引はない。方針を別の正本へ複製せず、既存のテストを材料に短い参照資料を作る。

[Aldagramのテスト観点カタログ](https://zenn.dev/aldagram_tech/articles/316c4d944fd9d5)からは、対象と役割、観点の適用条件を明示し、当てはまらない項目を増やさない考え方を参考にする。[型とテストによるガードレールの事例](https://zenn.dev/takabo/articles/ai-guardrails-with-tests)からは、不正入力で実際に落ちることと検査対象0件の空振りを確かめる観点を参考にする。両記事の観点数や有効性をこのハーネスの実測結果として扱わない。

2026-09-23、依頼者はテストの作り方とカタログ化を有用と判断し、初回はこのハーネスの既存テストに基づく4観点と必要時参照の形を選んで「進めて」と指示した。[#115](https://github.com/thkt/dotagents/issues/115)はテストの価値判断と既存テストの整理を扱った完了済みIssueであり、本Issueは次の変更で具体的な失敗条件を選ぶための参照を追加する。

[デブサミ福岡2026のATDD事例](https://speakerdeck.com/o3/2026-devsumi-ozono)を検討し、同日、依頼者は振る舞いの追加・不具合修正ではテストを実装前に置き、Red→Greenで進める方向を選んだ。今回採用するのは、要求に基づき、実装から独立した期待値を先に定め、テストが狙った失敗を検出することを確かめる順序である。全変更をATDDにすること、受け入れ条件ごとにE2Eテストを作ること、専用のテスト担当AIや新しい実行ゲートは合意していない。

[pstackのテスト観点](https://github.com/cursor/plugins/blob/70b2dc8b4b85c8d5648624ca40d692c421fff32f/pstack/skills/principle-test-behavior-not-implementation/SKILL.md)からは、対象の処理が意味ある結果を返さなくても通るテストや、実装の定数・モックの呼出しだけを確かめるテストを疑う具体例を参考にする。これは既存の「観測する結果」「検出力」の判断を助ける問いであり、一律の合否条件や追加ゲートにはしない。

## 初回範囲

1. `implement`でテストを作成・更新する際の短い手順を示す。今回の要求から見逃したくない失敗条件を定め、該当する観点の適用条件と既存検証との差を確認する。振る舞いの追加・不具合修正で既存検証がその条件を捉えない場合は、要求から期待値を定め、必要な最小の層のテストを実装変更より先に作る。変更前の対象で意図した理由による失敗（Red）を確認し、実装後に同じ条件で成功（Green）を確認する。正常な対照入力と識別できる失敗入力を使い、環境・設定など別理由の失敗をRedの成立と扱わない。既存テストで足りる場合や該当する失敗条件のない変更では追加しない。先に作ったテストに誤りが見つかったら原因と要求を照合し、要求変更は人の合意へ戻す。Greenにするためだけに期待値を緩めない。
2. 初期カタログは次の4観点に限る。各項目には「いつ適用するか」「守る振る舞い」「正常対照と失敗入力」「観測する結果と失敗理由」「既存テスト例」「最小のテスト層と費用」「適用しない条件」を書く。現在のコード・テストへ照合し、実在しない保証や汎用的な必須ケースを作らない。
   - **外部入力の拒否**: 例としてレビュー応答の欠落・余分な項目・対象ID不一致。構造検査と対象・権限の意味上の照合を区別する。
   - **停止時の副作用と記録保全**: 例として不正な再評価後に直前の完全な評価を残し、後続修正を起動しない。
   - **対象版の変化**: 例として検証・評価の前後に対象が変わった場合、古い成功を現在の対象へ流用しない。
   - **検査自体の空振り**: 例としてテスト0件の拒否、意図した不正入力で検査が失敗するかの確認。
3. テスト方針の正本は`.codex/DEVELOPMENT.md`に維持し、具体例は`implement`からテストに関係する作業で必要時だけ読める短い参照資料へ置く。`scoping`への一律読取や新しい実行ゲートは追加しない。

## 完了条件と検証

- [ ] 4観点から今回必要なテストを選ぶ読み順と、該当しない場合の扱いが分かる。各観点の条件・観測結果・失敗理由を既存のテスト・コードと照合でき、リンクと対象版が一致する。
- [ ] 性質の異なる既存の変更例へこの資料を当てはめ、振る舞いの追加・不具合修正では要求から定めた期待値、Redの意図した失敗理由、Greenで守る結果を説明できるかを確認する。既存検証で十分な場合や文書・内部整理では不要なケースを勧めない。新しい不具合の検出や作業時間の削減は、実測しなければ効果として主張しない。
- [ ] 既存の方針・スキルと同じ要求を二重に保守せず、参照の入口から該当する具体例へ辿れる。カタログが全変更のチェックリスト、全テストの一覧、追加テストの義務になっていない。
- [ ] 人向け日本語を記事・現在のコード・テストと照合し、`bun run check`と差分の独立評価を実施する。PRでは同じheadの`checks`・`verify`を確認し、人がレビューとマージを判断する。

## 対象外と引き継ぎ

全テストの写経、UI要素カタログの移植、全変更のTDD化、受け入れ条件ごとのE2Eテスト、専用のテスト担当AI・実行基盤・監査台帳・評価スコア、毎回の不具合注入、新しいCIゲート、記事の数値の再現は含めない。文書の追加だけで既存テストの検出力が上がったとは扱わない。個別変更で具体的な見逃しが見つかった場合のテスト追加・修正は、その変更の要求と検証に従って別途判断する。

対象repoは`thkt/dotagents`。セットアップは`bun install --frozen-lockfile --ignore-scripts`。実装着手時には現在のmainと関連テストを再照合し、保存・参照する場所は既存の読む順序と保守負担から決める。今回のIssue更新は実装開始やPR公開を意味しない。
