# 設計レビューで呼出側の知識と変更負担を確認する

## 目的と状態

部品の共通化・分離・削除を評価するとき、呼出側が正しく使うために覚える条件と、変更・検証が広がる範囲を見る。短い実装や小さいAPIでも、複雑さを呼出側へ移しただけの整理を見分ける。

2026-09-20の、重複していても異なる観点をIssueへ取り込む検討依頼に基づく下書き。担当AIの提案であり、採用・実装は未合意、Issueは未公開。現行コードの新たな欠陥や保守費用の減少は確認していない。

## 範囲と完了条件

- [ ] 抽象化の変更が判断対象のとき、呼出側が知る必要のある順序・不変条件・設定・失敗処理を、実際の呼出箇所から確認する。型やメソッド数だけで使いやすさを判断しない。
- [ ] 部品の削除・統合案は、必要な振る舞いと保証を保った場合に、どの判断・検査・状態管理がどこへ移るかを比べる。複雑さの移動を削減と扱わない。
- [ ] 関連する変更・検証をどこで直す必要があるかを比較し、実際の困りごとがある範囲に絞る。レビュー指摘では根拠のある欠陥と設計上の懸念・別案を区別し、好みだけを必須修正にしない。
- [ ] 既存の`.codex/DEVELOPMENT.md`の評価方針と通常の`assessments.code`・指摘へ統合する。実装の呼出順、外部状態、停止・保全・権限の保証を維持する。

追加モデル、常時の複数設計案、全repo監査、新しい評価欄・点数・必須帳票は作らない。用語の統一、パッケージ再編、差し替え実装数による入口の禁止、上位テストがあるだけでの下位テスト削除は対象外。`.codex/DEVELOPMENT.md`を主な変更先とし、既存レビューへの参照が不足する場合だけ必要な案内を直す。

## 検証と関連

必要な保証を維持しつつ、単なる転送だけをまとめた部品と、順序・失敗処理を一か所で引き受ける部品を対照例にし、残す・整理する理由を既存評価で説明できるか確かめる。例は合成例と明記し、未確認の実コードの欠陥として報告しない。行数、指摘数、レビューのacceptedだけを効果の証拠にしない。

[#145](https://github.com/thkt/dotagents/issues/145)は改善案同士の効果・費用の比較、[#147](https://github.com/thkt/dotagents/issues/147)は合意済み境界違反の機械検出の調査。本案は通常の設計レビューで読む呼出側の契約を具体化する。既存Issueの採用を前提にせず、閉じた冗長性整理Issueの再実装にも広げない。

実装時は`bun install --frozen-lockfile --ignore-scripts`、`bun run check`、既存の独立評価・日本語確認、同じPR headの`checks`・`verify`を使う。制御テストと実モデルの意味判断を分け、モデル試行は既存の対象・許可範囲を照合する。商品画面媒体は不要。

今回は原資料・現行方針との照合と下書きの日本語確認まで。共通方針の変更、対照例の実行、共通check、独立評価は未実施。本案と固定版の出典で判断を辿れるようにし、全件比較メモを実装の必須入力にはしない。

## 変更の影響に応じて確認するリスクの候補

2026-09-21、依頼者は[Alejandroの投稿](https://x.com/AlejandroRomaan/status/2096610078837141569)の検討を受け、取り入れられる観点の整理・追加を依頼した。本節は既存の設計レビュー案への候補追加であり、通常フローへの採用や実装の合意ではない。

投稿者が補足した[final-reviewの契約](https://github.com/aromanarguello/roman-skills/blob/eb2b0dffdee01fda2467a417f23cf236f2b3d422/final-review/references/review-contract.md)では、変更した振る舞いと利用側から確認観点を選び、ファイルの配置だけで適用外とせず、選んだ理由・対象外とした理由・確認できない範囲を残す。これは確認日に読んだ公開版であり、9月6日の投稿時点と同じ実装とは確認していない。

dotagents `59e9f7374c18dba415f9c1512e1b9116a9e8a28d`の[独立評価指示](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/review.ts#L228)にも、呼出元・呼出先・共有型・状態遷移・失敗時の副作用を追い、四つの評価欄へ適用条件と未確認事項を記す責任がある。評価工程の欠落が確認されたわけではない。追加候補は、本案で部品の責任を移すときに、何を追うと判断に役立つかを具体化することである。

| 変更の影響 | 追う候補 |
| --- | --- |
| 権限や外部操作の責任が移る | 入力・主体・対象の確認がどこに残り、どの条件で操作を止めるか。境界をまたぐ間に権限や対象版が変わる場合も扱う |
| 保存・再試行・復帰の責任が移る | 失敗時に何が保存され、再実行で二重処理やデータ欠落が起きないか。DBがある利用先では関連する移行・制約も確認対象にする |
| 共有型・設定・返却値が変わる | 直接の変更箇所に加え、利用側が期待する値・順序・エラー・互換性へ影響するか。特定ディレクトリを変更していないことだけで対象外にしない |

関係する観点だけを既存の評価説明へ含め、「適用外」「確認したが指摘なし」「必要だが確認できない」を理由とともに区別する。必要な証拠へのアクセスや専門的な判断が不足する場合も、影響する判断と不足を示す。全観点の定型表、別の評価欄・Schema・状態・モデル呼出しは追加しない。要求や権限の判断を妨げる不足は、既存の必須指摘と人への差し戻しに従う。

採用を検討するときは、本案で扱う実際の変更または明示した対照例一組を選び、現行の評価だけで必要な境界と未確認事項を説明できるか先に確かめる。たとえば同じ型のまま権限確認を呼出側へ移した例と、必要な確認を部品内に保つ例では、型の一致だけで同等としない。現在の運用で具体的な見落としや説明不足は確認しておらず、既存指示で十分なら追加しない。実モデル比較が必要になった場合は、対象・入力・判定・費用・送信範囲を具体化し、既存の許可範囲を照合してから行う。今回の追加では対照例の評価も実モデル試行も行っていない。

人のレビューを残す判断は維持する。[引用元の運用](https://x.com/mikejulian/status/2096450480167948306)でも公開API/MCP、認証、デザインシステム、非追加型DB変更、エージェントスキルは人のレビュー対象である。全E2Eのpre-commit実行、監視サービス、複数レビュー担当や外部スキルの一括導入は、今回確認した不足への対応ではないため追加しない。スキルの評価を通じた指示整理の事例は[#171](https://github.com/thkt/dotagents/issues/171)へ補足し、レビュー方法の変更を同じ比較へ混ぜない。

本補足は執筆担当が出典・現行指示・既存の提案範囲と照合した。別評価者による独立評価は未実施。公開済みIssueはなく、本ファイルへの候補追加までを今回の保存状態とする。
