## 目的と位置付け

優先度: 高。停止した事実と、誰が何を確認・解消するかを分け、誤った原因調査と人への不要な受け渡しを減らす。#123の局所整理に続く候補。#124の要約ファイル廃止とは別の責務であり、本Issueでは保持する記録の保存障害を扱う。

## 根拠

- [レビュー結果の採用処理](https://github.com/thkt/dotagents/blob/0fec56c536763f8ccbd4bc4a9080c19beb14862d/scripts/correction.ts#L580)は応答の検査と `review-N.json` の保存を同じcatchで扱う。保存失敗も `invalid_review` になる。
- [CI初回取得](https://github.com/thkt/dotagents/blob/0fec56c536763f8ccbd4bc4a9080c19beb14862d/scripts/ci.ts#L90)は `pr.json` の保存失敗も `unavailable` にする。[次の対応](https://github.com/thkt/dotagents/blob/0fec56c536763f8ccbd4bc4a9080c19beb14862d/scripts/ci.ts#L63)は認証・権限・接続を調べる案内になる。
- [developmentのverify](https://github.com/thkt/dotagents/blob/0fec56c536763f8ccbd4bc4a9080c19beb14862d/scripts/development.ts#L485)は人の判断待ち、環境問題、応答不正などに共通の `nextAction` を返し、具体的な対応先は下位の記録から読み取る必要がある。

隔離した現行コードの試験で、正常なaccepted応答の記録保存だけを失敗させると `invalid_review` となった。生応答は残り、修正実行は0回だった。CIでは正常応答を返したまま `pr.json` の保存先をディレクトリにすると、理由はEISDIRでも認証等の確認を案内した。対照例のCIはpassed。前者は保存例外の注入、後者は一時保存先の衝突であり、実モデル・GitHubは使用していない。停止自体が失われる不具合ではない。

## 範囲と受入条件

- [ ] 応答の不正、取得不能、保存不能を、実際に失敗した処理の責任に沿って扱う。正常な応答を保存障害だけで不正応答と説明しない。
- [ ] 保存失敗時も成功扱いにせず、元の原因、失敗した保存先・処理、生応答、以前の完全な評価・履歴を保持する。後続修正・公開を自動実行しない。既存の終端結果による再実行抑止も保ち、誤分類の修正によって同じ実行を再起動できる状態へ戻さない。
- [ ] 既知の停止理由に応じ、既存の `nextAction` と証拠参照で、担当AIが調査できること、ホスト環境の対応、人が決めること、再判定に必要な条件を伝える。例外文から意味を推測して自動ルーティングしない。
- [ ] 人の判断は要求・範囲・許可・上限等の必要な選択に限り、許可範囲内の事実調査を一律に人の判断待ちへ変えない。担当AIの環境調査と、権限が必要な環境変更も区別する。
- [ ] `stopped` と既存の理由・対応の役割を保つ。4分類を新しいstateや全ノード共通の4分岐として追加せず、汎用の復旧管理層を作らない。
- [ ] 支援後は対象・根拠・権限・検証を再確認する。旧run・lock・active・上限の変更、旧runの自動再開、公開結果不明からの自動再試行は追加しない。現行の入口で続けられない場合もその制約を示す。

主な確認は `review.test.ts`、`ci.test.ts`、`development.test.ts`。正常応答と不正応答、取得失敗と保存失敗を区別し、停止理由・案内・後続抑止・証拠保全を観測する。#129のfixture整理は前提にせず、既存の試験方法を使う。runtimeの新しい工程は不要で、コード純減と所要時間の改善は未測定。
