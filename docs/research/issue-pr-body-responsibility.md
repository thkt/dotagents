## 目的と合意

完成したPR本文の意味確認を既存の公開後確認へ集約し、未確認のPRはdraftに保つ。確認責任を実際の実行順序に合わせ、担当・対象版・完了条件の曖昧さを減らす。対象は #128。段階は調査・採用合意済み、実装待ち。

2026-09-19、依頼者は「一時公開がdraftでの公開なら問題なさそう」と回答し、draftでも本文は閲覧可能であることを確認した上で、新規PR・既存PRの修正ともdraftで内容を確認してからレビュー可能へ移す範囲を採用した。この決定により、本Issueを調査用から実装用へ更新する。現行コード・方針・構成図への反映は未実施。

合意した流れは、検証・独立評価 → ホストによる機械照合とdraft公開・更新 → 担当AIによる実際の本文・必要媒体の確認と同じheadのCI成功確認 → ready → 人のレビュー・承認・マージ判断。readyへの切替は人の承認・マージを代行しない。

## 比較と採用理由

| 案 | 得られること | 残る負担・リスク |
| --- | --- | --- |
| A: 現行の公開前・公開後の責務を維持 | 完成本文を公開前にも照合する要求を維持する | 通常CLIにはその専用介入点がなく、責任と実行のずれは残る。公開前の確認を機械的に必須化するなら別の設計が必要 |
| B: draft公開後の既存確認へ意味確認を集約（採用） | 専用の校正モデルや待機用の仕組みを追加せず、実際の本文・媒体を確認する担当と時点を明確にする。確認前のマージをdraftで防ぐ | draft/readyの操作と照合が必要。初回公開時に誤記・省略等が含まれ得て、その内容は閲覧可能。修正は開示を取り消さない |

Bは公開前の意味確認と同じ保証を維持する案ではない。依頼者はdraftでの一時公開を条件にこの差を許容した。[GitHubのdraft PR](https://docs.github.com/en/pull-requests/reference/pull-requests#draft-pull-requests)は非公開化の仕組みではなく、readyになるまでマージできない状態である。readyへの切替でCODEOWNERSへのレビュー依頼等も生じ得る。

## 実装範囲・受入条件

- [ ] 自動生成経路は、既存の独立評価AIが公開用の説明と根拠を記し、ホストが本文を生成する。完成本文の意味確認は公開後の担当AIへ集約し、生成前のacceptedや本文文字列の一致を意味確認済みと扱わない。
- [ ] 新規PRはdraftで作成し、実際の対象・本文・draft状態を読み戻す。既存PRの修正は、pushによるhead更新・本文更新・添付より前に、対象と権限を照合してdraftを確認する。readyならdraftへ戻して読み戻し、既にdraftなら切替を重ねない。必要なdraft状態を確認できなければ後続の公開変更を止める。
- [ ] 公開前の対象・Issue・検証済み成果物とcommit・参照・主体・権限の機械照合、公開後の本文一致・同じheadのCI・必要媒体確認を維持する。`--no-publish`ではdraft/ready操作も行わない。ホストはCI成功だけでreadyへ移さない。
- [ ] 担当AIは実際の最新版本文をIssue・対象commit・accepted評価・検証結果と照合する。事実、数量、条件、範囲、否定、未確認事項、リンク、必要な説明と、省略・内部パス置換・整形の影響を確認する。必要な媒体は実表示も確認する。これらと同じheadのCI成功が揃ってから、既存のGitHub CLIでreadyへ移す。
- [ ] ready直前に対象・本文・head・根拠・主体と権限・CIが確認した版に対応することを再照合し、変更があれば関係する確認へ戻す。切替後も実状態を読み戻してから人へ渡す。GitHub上の複数操作は一括確定できないため、操作間の他者変更を完全に防ぐ保証とはしない。
- [ ] 既存の結果・残作業・次の操作の案内を上記の段階に合わせる。CLI終了やCI成功が本文・媒体確認とready切替まで済んだように見える表示を残さず、未確認事項を既存の返却経路で示す。新しい結果台帳や汎用状態管理の仕組みは作らない。
- [ ] 本文を直接編集する場合も対象PRをdraftにし、書込み前に変更案を現在の本文・head・根拠へ照合し、反映後に読み戻す。他担当の変更を無確認で上書きせず、変更前の成功を流用しない。説明だけの不備は本文修正と再確認、成果物の不備は必要な修正・check・独立評価、事実不足は調査、要求・権限の変更は人の判断へ戻す。
- [ ] 確認失敗・不足ではreadyへ移さず、確立したdraftを維持して既存の停止・修正経路へ戻す。draft/ready操作を含む公開結果が不明なら、記録と判明したURLを保持し、実状態の照合前に再試行しない。他者による予期しない状態変更も、draft維持や完了を推測せず照合する。失敗時に以前のreadyへ自動復帰しない。
- [ ] 実装と方針・操作説明・関連スキル案内を一致させる。実装採用後にローカル図とガイドへ、draft公開・確認・ready、人への引き継ぎ、停止と修正の接続を同じ粒度で反映する。

変更候補は既存の`publish.ts`・`development.ts`・`revision.ts`・`ci.ts`の関係箇所とテスト、`.codex/DEVELOPMENT.md`・`scripts/README.md`・implementの案内。必要な箇所だけ変更する。`reviewed body`等の表現も、機械照合を意味確認と誤解させる箇所に限って整える。標準の[`gh pr create --draft`](https://cli.github.com/manual/gh_pr_create)、[`gh pr ready` / `--undo`](https://cli.github.com/manual/gh_pr_ready)と既存の読戻しを使い、専用校正モデル、新しい確認CLI・待機用の仕組み・校正基盤は追加しない。

人の承認・マージ判断は維持する。HTMLは #106 のローカル限定と旧資産保全を維持し、公開repoへ追加しない。#131 の他の図訂正、#134 のレビュー指摘返却、#142 の構造説明は別範囲とする。

P07の意味確認は既存U01へ集約できるが、draft/readyの操作と接続が加わる。現行206ノード・337矢印からの純減は未確定で、以前の「各1減」を成果として約束しない。モデル呼出しの削減は0。実装後にコード・テスト・文書・ノード・矢印の増減を同じ範囲と粒度で示し、増加分が確認前のマージ抑止と責任の明確化に必要か評価する。

## 検証・引き継ぎ

今回実施したのは現行コード・文書・既存テスト・GitHub公式仕様の読解と保存済み本文の比較。実モデル起動、追加の公開試行、全体check、本Issue自体の別評価者による独立評価は未実施。現在の公開処理にはdraft指定・照合がない。CI workflowにはdraftを除外する条件はないが、この運用での実行成功はまだ確認していない。

- 既存の公開・development・revision・CIテストで、新規draft作成と読戻し、既存readyから公開変更前のdraft化、既にdraftの利用、切替失敗・不一致時の後続抑止、CI成功だけではreadyにしないこと、no-publish、対象版変更・結果不明時の停止と保全を検証する。既存保証を再利用し、文言一致だけのテストや専用の大きな試験基盤は追加しない。
- 担当AIによる本文・媒体の意味確認、直接編集、ready前後の照合と異常時の戻り先は、既存の独立評価・日本語確認でもIssueと実装・案内へ照合する。担当AIの判断を模擬コマンドテストで保証したとは扱わない。
- 実装PRでは、通常の許可範囲でdraft公開 → 本文・必要媒体・同じheadのCI確認 → readyの実状態を確認する。既存PRを戻す実試行は実際の修正対象と許可がある場合に限り、未実施なら模擬検証との区別を記す。試験だけの追加公開PRは求めない。
