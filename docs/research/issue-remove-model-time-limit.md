## 目的

通常の`implement`で、初回実装・修正・独立評価のモデル累計20分を理由に、進行中の作業を打ち切る運用をやめる。初回実装で使った時間によって独立評価の時間が削られず、検証済み成果物を人のレビューへ渡せるようにする。

依頼者thktは2026-09-17、#90の実装で時間上限による停止と明示的な続行を経験した後、「20分で止まるやつやめたいね」と要望した。本Issueはこの固定時間制限の撤廃を扱い、#90・PR #92の共有知識モデルとは分ける。

## 確認した現状

調査版は`765adbb29c51747b2d4ada473ca03a3e40ed7651`。

- `scripts/development.ts`は1,200,000msを初回実装へ渡し、消費時間を引いた残りをcorrectionの`modelTimeMs`へ渡す。
- `scripts/correction.ts`は残り時間でモデルプロセスを停止し、累計時間または回数の上限で`execution_limit`にする。
- #90の初回実装は約1,023秒、独立評価は残り約177秒で停止した。全体checkが成功していても評価未完了のため公開されなかった。これは保持したローカル実行記録の観測であり、コード不良を停止原因としたものではない。
- 時間上限のほかに、修正・評価の回数上限、check・CI・通常コマンドのタイムアウト、対象・要求変更や中断時の停止がある。

## 範囲と完了条件

- [ ] 通常のdevelopment入口では、初回実装・修正・独立評価をモデル経過時間だけで停止しない。20分をより大きな固定値へ置き換える方法にはしない。
- [ ] 初回実装の経過時間を後工程の残り時間へ変換する処理を除き、後工程にも時間上限なしの設定を渡す。既存の経過時間・結果の記録は保持する。
- [ ] 修正2回・独立評価2回の上限、checkとCI待機の各9分、通常コマンド等の既存タイムアウト、要求・対象・権限の照合を維持する。
- [ ] 時間上限のないモデルもSIGINT/SIGTERMによる手動中断で子プロセス群を停止し、ログ・active予約を保全する。二重実行や中断後の自動再開を許さない。
- [ ] 単独correctionやレビュー試行で明示された有限のモデル時間上限は引き続き機能する。時間上限なしを明確に表現し、未指定・不正値との意味を曖昧にしない。通常利用者に新しい必須入力や選択工程を追加しない。
- [ ] 過去のrun・state・設定・予算を変更、変換、削除、自動再開しない。有限設定の既存試行を、同じ記録のまま無制限へ切り替えて成功扱いにしない。
- [ ] CLI説明と関連する現在の文書を更新し、通常フローと明示的に時間を制限する試行を区別する。なくす停止条件と残す条件をPRで説明する。

## 実装と検証

既存のコマンド実行・プロセス群停止、設定検査、消費量記録、回数制限を再利用する。新しい監視機構、無活動時間判定、再開CLI、承認工程、外部依存は追加しない。型・設定形式の詳細は既存資産との整合を見て決める。

既存development・correction・processのテストを修正・統合し、以下の失敗条件を検出する。

- 初回実装の経過時間が20分を超えた観測値でも、時間だけを理由に後工程を拒否しない。実際に20分待つテストにはしない。
- 時間上限なしの修正・評価が正常終了でき、経過時間を記録する。
- 時間上限なしでも中断時の子プロセス停止・予約保全・二重実行拒否が働く。
- 明示的な有限時間、回数、check等の既存上限が残り、設定変更で保存済み状態をリセットしない。

単なる件数維持や内部呼出順のミラーではなく、停止・継続・保全という観測結果を守る。削除・変更する検出条件と理由を説明する。`bun install --frozen-lockfile --ignore-scripts`、提出前の`bun run check`、独立評価、同一PR headの`checks`・`verify`を確認し、人がレビュー・マージする。UI変更はなく撮影は不要。

## 対象外と引き継ぎ

修正・評価回数の撤廃、check・CI・Git/GitHubコマンドの無制限化、途中実行や既存PRの自動再開、#92の変更・マージは含めない。制御コードの変更はレビュー対象の成果物として扱い、進行中のホストの制限を自己改変して通過させない。通常の新規実行への採用はマージ後である。

追加の必須調査報告はない。必要な要求と観測は本Issueに収録しており、私的な実行ログの閲覧を実装の必須条件にしない。
