## 目的と合意

実モデルレビューの確認で、評価用の正誤ラベルを手掛かりに判断できる状態を減らす。通常の要求・コード・テストを評価し、指摘の真偽はホストが再現と根拠で裁定する。

2026-09-19、依頼者はpstack-codexとの比較を受け、A「実モデル評価の正誤ラベルを隠す」とB「scopingで小さな実験を選ぶ条件の具体化」を別Issueにする案を選択した。本IssueはAを扱う。今回は要求確定とIssue公開までで、実装は後続の着手指示で進める。

## 現状と根拠

調査版はdotagents `0fafcb816b5ab34559f551d1fc0fefd121a0f17b`。公開前に`61e1c8ec7e874b66c4922b7cd59e5118beba6efc`への更新を確認し、今回の正誤ラベルとレビュー入力の経路に変更がないことを照合した。

- [verify-review.ts](https://github.com/thkt/dotagents/blob/0fafcb816b5ab34559f551d1fc0fefd121a0f17b/scripts/verify-review.ts#L79)は、不具合の有無に応じて`defective` / `correct`というディレクトリを作り、その配下を評価用checkoutと記録先にする。
- [レビューprompt](https://github.com/thkt/dotagents/blob/0fafcb816b5ab34559f551d1fc0fefd121a0f17b/scripts/correction.ts#L562)は、targetRecord・diff・additionsの絶対パスを渡す。これらに正誤ラベルが含まれる。過去の判断に与えた影響は未測定で、既存結果が誤りだったとは断定しない。
- pstackの[Eval](https://github.com/ScriptedAlchemy/pstack-codex/blob/594acccc740b2bfab7b83a37bf2ffde40dfec050/plugins/pstack/skills/poteto-mode/playbooks/eval.md)は、評価対象から比較や正解のメタ情報を隠す。今回はこの考え方を評価用入口へ限定して取り入れる。
- [#66](https://github.com/thkt/dotagents/issues/66)と[実モデルによるレビューの確認](https://github.com/thkt/dotagents/blob/0fafcb816b5ab34559f551d1fc0fefd121a0f17b/scripts/README.md#実モデルによるレビューの確認)にある独立した再現・裁定、使用量と未確認の記録、少数試行から検出率を主張しない扱いは維持する。

## 範囲と完了条件

- [ ] 評価用checkout・記録先・モデルへ渡すメタ情報から、正誤を示すラベルを外す。識別子や実行順から正誤が固定的に分かる対応を評価対象へ渡さず、ホストはケースと結果の対応を保持できる。
- [ ] cwd、prompt、target record、差分・追加ファイル、参照ログ、実行引数など実際の入力経路を確認する。名前の置換だけで完了にしない。正解との対応表・既知の不具合・裁定結果を既定のレビュー入力へ混ぜない。
- [ ] 通常のIssue要求、対象コード、テスト、レビュー基準、対象版の記録を維持する。`test`や`review`など一般の名称の禁止、実際の欠陥を示すコードやテストの隠蔽は行わない。
- [ ] レビュー終了後、独立した再現入力・期待値・実結果で各指摘と既知の不具合を裁定する。正常ケース、不具合入りケース、見落とし、誤指摘、未確認を区別し、モデル応答のstatusだけで正解としない。
- [ ] 過去の実行記録は書き換えず、既存の操作説明で非盲検条件という制約と今回の変更を説明する。偶発的な手掛かりを減らす範囲であり、意図的な周辺ファイル探索まで防ぐセキュリティ境界とは説明しない。

主な変更候補は`scripts/verify-review.ts`と関連する検証・操作説明。通常のレビューのモデル数、schema、公開処理、予算、停止条件は対象外。新しい評価エンジンや常設の多モデル比較は作らない。

## 検証

1. 実モデルを使わない隔離試行で、生成された実際の引数・prompt・参照資料を捕捉し、正誤ラベルが既定入力へ漏れず、ホストでは両ケースを対応付けて再現・裁定できることを確認する。ソースの文字列一致だけをテストにしない。
2. 正常・不具合入りを各1回、既存規模の実モデル確認手順で実行する。指摘の裁定、時間、使用量、未確認範囲を記録し、制御テストと実モデルの判断を区別する。親子の使用量を確定できなければ未確認とする。精度・速度改善を受入条件にはしない。
3. セットアップは`bun install --frozen-lockfile --ignore-scripts`。提出前は`bun run check`、差分の独立評価、日本語確認を行い、PRでは同じheadの`checks`・`verify`を確認する。商品画面の媒体は不要。人がレビュー・マージを判断する。

実モデル試行は実装後の確認として上記範囲に含む。現在の試行設定と実行条件を着手時に確認し、停止したrunの上限・記録を変更して続行しない。実行結果は既存のcheckout外記録へ保存し、公開可能な裁定と証拠だけを既存の`docs/evidence/`へ残す。
