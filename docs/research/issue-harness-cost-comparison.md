# 実装actorの役割明示による読み込み削減を、品質と使用量で比較する

## 目的と今回の判断

ハーネスの利用者が要求を満たす成果物を得るまでの負担を減らすため、既存の工程別使用量を確認し、初回実装actorへの役割説明を変える価値があるか判断する。指示の短さやモデルの終了成功だけで改善とせず、要求充足、必要な失敗検出、実行時間、キャッシュを区別した使用量を合わせて確認する。

2026-09-21、依頼者は[HarnessTax](https://harnesstax.github.io/)を受け、「既存runの費用内訳を調べる、削減候補を一つ選ぶ、同じモデル・課題で比較する」という提案に対し「対応を進めたい」と依頼した。本Issueはこの調査と限定比較を扱う。通常フローへの変更採用や、独立評価・権限確認・公開前の照合を削る合意ではない。

## 比較する範囲

現行の初回実装指示と、既に開始済みのホスト内の実装担当であることを明示した候補を、隔離した試行で比較する。候補は既存の役割説明を局所的に書き換える。修正・評価の指示、モデル、推論設定、利用できるツール、要求・検証基準は同時に変えない。

候補が伝える内容は次に限る。

- ホストがcheckoutの準備と開始確認を済ませ、今回のIssueと必要な参照を渡していること。
- この担当はそのcheckoutで実装と必要な局所検証を行い、既定のJSONで結果を返すこと。
- 開発開始・引き継ぎ・公開の操作はホスト側の責任であること。

適用されるAGENTS.md、対象の開発・テスト・文書方針、必要な原資料を読む責任は維持する。共通資料やスキルの一律読取禁止、必要な内容の削除、独立評価への実装履歴の持越しは行わない。現在の[共通実装・修正指示](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/repair.ts)にある検証責任・公開禁止・人へ返す条件も維持する。

初回比較は、公開commitを固定したdotagentsの隔離コピーと非機密の小さな課題を候補とする。既存の検証・実モデル評価の記録方法を再利用し、目的に合わなければ一時スクリプトで不足だけを補う。調査用の使用量集計を通常runtimeや共通checkの必須機能へ組み込まない。

- [ ] 要求充足・実行失敗・判定不能を区別し、候補による初回実装後の修正・独立評価まで含めて、要求充足に至る負担を比較する。失敗や再試行も全試行数と使用量に含める。実験の準備・採点費用は実行ごとの費用と分けて残す。

- [ ] 対象版、比較用の差分、判定の根拠、全試行の集計範囲と限界を既存のIssue・PRまたはresearchの記録から辿れる。生ログ、認証情報、ホスト内の個人パスを公開しない。日本語・数量・条件・断定の強さを原資料と照合する。

## 根拠と引き継ぎ

[HarnessTax](https://harnesstax.github.io/)は、同じモデルでもハーネスにより成功率と費用の関係が変わり得ることを示す。公開ベンチマーク各30課題・3反復で、各ハーネスのhigh設定やターン定義は同一ではない。報告された費用倍率を我々の負担や候補の期待効果へ流用しない。

工程の対応方法は、[初回実装の記録](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/development.ts)、[修正・評価のイベント](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/correction.ts)、[actorのイベント保存](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/codex-actor.ts)、[限定レビュー評価の使用量集計](https://github.com/thkt/dotagents/blob/59e9f7374c18dba415f9c1512e1b9116a9e8a28d/scripts/verify-review.ts)を参照できる。今回の集計では初回実装・修正・評価の出力内容を対応付け、各CLIの完了ターンとホストの時間記録を照合した。

内部の集計・照合記録と元ログはホスト側に保持する。上記の要約・方法・限界と固定版コードで比較の準備を開始でき、私的な生ログやこのローカル下書きの閲覧を必須条件にしない。具体的な候補文・課題・実行条件を示した後、限定比較の実施判断へ進む。本Issueの別評価者による独立評価は未実施。

## スキルの評価を通じて指示を整理する参考事例

2026-09-21、依頼者は[Alejandroの投稿](https://x.com/AlejandroRomaan/status/2096610078837141569)の検討を受け、取り入れられる観点の整理・追加を依頼した。投稿で挙げられたスキルの評価と、[引用元のスキル整理の説明](https://x.com/mikejulian/status/2096450484899061982)を、本Issueの参考事例として補足する。引用元は、評価を作り、モデルの既存知識で不要になった指示を調べて削除したと報告している。ただし、この投稿だけでは評価ケース・品質・費用や削除の因果的な効果を検証できない。

この事例から使うのは、指示を短くする前に必要な振る舞いを評価するという観点である。指示の削除と、今回選んだ役割の明示は異なる変更なので、一度の比較へ混ぜない。一般知識で代替できるかという推測から、repo固有の要求・権限・必要な参照まで不要と判断しない。本Issueの比較対象、完了条件、実行前に具体化する送信範囲は維持する。全スキルの監査、人のレビュー廃止、通常フローへの採用は追加せず、今回の補足による実モデル試行も行っていない。

## モデル更新時の指示再評価への適用（2026-09-21）

依頼者の「進めて」を受け、[GPT-6 Astra, Looped Transformers, and Hidden Reasoning](https://magazine.sebastianraschka.com/p/gpt-6-astra-looped-transformers-and)の観点を既存候補へ結びつけた。記事は、古いモデル向けの指示の見直しと、評価時のハーネスの影響を論じている。Astraのループ構造の採用や、それが推論の監視しにくさを生むという因果関係は確認済みの事実として扱わない。[OpenAIの指示整理の解説](https://developers.openai.com/blog/rethinking-skills-and-prompts-for-gpt-6-astra)も、必要な場面で資料を参照することと、固定的な手順・過剰なテスト要求の見直しを勧めている。これらは我々の指示の削減効果を示す実測ではない。

今回確認したcheckoutのHEADは上記調査と同じ`59e9f7374c18dba415f9c1512e1b9116a9e8a28d`。AGENTS.mdとimplementスキルは既に変更に関係する資料を参照する形で、初回実装指示と共通修正指示も局所検証とホストの全体検証を分けている。一方、初回実装指示には、開始済みの実行内の担当であることと、開始・引き継ぎを再実行しないことの明示がない。新たな不要手順を断定せず、既存の役割明示の仮説を比較候補として維持する。過去6runのログ集計は今回再実行していない。

比較時の候補文を次のように具体化する。`scripts/development.ts`の初回実装promptの先頭の文字列だけを置き換える案であり、未適用。残りの指示、共通の`repairInstructions`、対象の規則・資料・ツールは変えない。

```text
You are the implementation actor in an already-started, host-controlled run. The host has prepared this checkout, checked the starting inputs, and supplied the agreed Issue and selected references. Implement the complete agreed Issue using existing code and verification assets. Follow applicable repository instructions; consult the target README and development policy sections relevant to this change. Leave development-start, handoff validation and publication operations to the host; do not launch another development run.
```

この案は指示の文字数を増やして役割を明示するため、短文化の比較とは区別する。上記の完了条件を使い、必要な規則・原資料の参照と要求充足、人へ判断を戻す条件を保てるかを先に確認し、開始・引き継ぎ手順の再読、手戻り、総使用量・時間の差を調べる。効果がなければ見送り、失敗やばらつきで判断できなければ保留する。モデル更新は再評価の契機であって改善の証拠ではなく、モデル変更と指示変更を同じ比較に混ぜない。

推論文の長さ・詳しさを品質や内部計算量の代理にせず、判定理由は要求・成果物・実行結果と照合する。[CoTの忠実性の研究](https://arxiv.org/abs/2305.04388)は説明が判断要因を忠実に表さない例を示すが、Astraでの頻度を測ったものではない。現行の比較方針で扱えるため、新しい共通ルール・監査工程・Issueは追加しない。今回行ったのは参考資料との照合、候補文の具体化、ローカル下書きへの保存までであり、指示の実装・実モデル比較・効果の確認・GitHubへの反映は未実施である。
