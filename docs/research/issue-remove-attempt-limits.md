## 目的と合意

通常の新規開発と既存PRの修正で、修正・独立評価の回数だけを理由に作業が止まり、人が続行を指示する手順をなくす。合意範囲内の必須指摘を解消し、対象成果物のcheckと独立評価が通るまで既存の修正ループを続ける。

2026-09-20の依頼で、この方針の要求整理とIssue化が指定された。単独試行の有限予算、要求・権限に関する人の判断、その他の停止・保全条件は維持する。修正の反復には既存の指摘履歴を使い、原因や方針を見直す。本Issueは実装待ちとし、今回のscopingでは実装を開始しない。

## 確認した事実

調査版は`d9dbf72446e7c2d80cd1d830d3c93933d92f35fc`。

- [通常入口の設定](https://github.com/thkt/dotagents/blob/d9dbf72446e7c2d80cd1d830d3c93933d92f35fc/scripts/development.ts#L459-L480)は、新規開発・既存PR修正とも追加修正2回・独立評価2回を指定する。初回作業は別枠である。
- [修正・評価の制御](https://github.com/thkt/dotagents/blob/d9dbf72446e7c2d80cd1d830d3c93933d92f35fc/scripts/correction.ts)は、回数の残りがなければ`execution_limit`で停止する。そのため、2回目の修正後にcheckが通っても次の評価へ進めない。
- [#129](https://github.com/thkt/dotagents/issues/129)の保存記録では、追加修正2回・独立評価2回・check成功3回の後に`execution_limit`で停止した。別途許可された続行では`review-6`がacceptedとなった。これは保持したローカル記録の観測であり、一般的な収束の保証ではない。
- [#93](https://github.com/thkt/dotagents/issues/93)は通常のモデル時間上限を外し、回数上限を残した。本Issueは、その回数上限を維持する条件を通常の新規runについて置き換える。

## 範囲と完了条件

- [ ] 通常の新規開発・既存PR修正は、追加修正・独立評価の回数で停止しない。より大きな固定上限への置換や、新しい利用者入力・続行承認は設けない。
- [ ] 単独試行では明示した有限の回数上限を使える。既存の`repairLimit`・`reviewLimit`は、それぞれ正の整数または上限なしを示す明示的な`null`を受け付け、通常入口は両方に`null`を渡す。未指定や不正値を上限なしへ読み替えない。有限のモデル時間、check・CI・通常コマンドの制約は変えない。
- [ ] 必須指摘を解消した最新成果物のcheck成功と独立評価acceptedを維持する。成果物が変われば必要な検証・評価を更新する。draft公開後の本文確認・同一headのCI・人のレビューとマージ判断も維持する。
- [ ] 指摘が反復する場合は、既存の履歴と現在の成果物を照合し、原因と修正方針を見直す。合意範囲内の修正を続け、範囲外の改善や好みの変更まで完了条件にしない。停滞専用AI、追加レビュー工程、新しい台帳は作らない。
- [ ] 要求・権限の判断、要求・対象の変更、不正応答、実行・保存の失敗、手動中断など、回数以外の現在の停止・保全条件を維持する。check失敗から修正へ戻る既存経路も維持する。回数・経過時間・指摘・結果・実行中の予約を引き続き記録する。
- [ ] 採用後の新規runへ適用する。過去のrun・設定・予算・stateは書換え、変換、削除、再開しない。本Issueの実装中に、進行中ホストの上限を自己改変して通過させない。
- [ ] CLI説明と関係する文書を更新する。ローカル限定のHTMLガイド・詳細図も採用後に合わせ、通常経路から消える回数上限による停止と、有限試行で残る停止を区別する。

## 最小構成と影響

既存の設定検査、修正ループ、指摘履歴、コマンド実行、予約・結果保存を使う。中心となる変更箇所は`input.ts`・`correction.ts`・`development.ts`と関係するテスト・説明であり、新しいCLIや依存は加えない。人の判断への専用経路を検討する[#134](https://github.com/thkt/dotagents/issues/134)は含めない。

回数による停止・予算判断・続行の手順が通常経路から減る。一方、時間・使用量や履歴の保存量が増える可能性があり、無制限に続ければ必ず解消するとは保証しない。コード純減や全経路のノード・矢印の減少は未確定。PRでは同じ粒度で差を説明し、残す有限試行や保全の分岐を図から隠さない。HTMLは引き続きローカル限定とする。

## 検証と引き継ぎ

現在の機能を守る最小のテスト構成にする。廃止したフローを再現する専用テストや、同じ入力判定のためのCLI全体試験は増やさない。

- 設定の直接テストで、両上限の`null`・正の整数と、不正値の拒否を確認する。
- 代表的な制御テストで、回数上限なしの修正・評価が複数回続き、最後の修正をcheck・評価した後に完了することを確認する。両カウンタが2を超えるケースを使い、修正前の評価による早期完了を検出する。
- 明示した有限予算の停止、手動中断・予約保全、対象変更、不正応答・実行・保存の失敗は既存検証を再利用し、今回不足する境界だけ補う。新規開発・既存PR修正の設定は既存入口テストで確認する。
- `bun install --frozen-lockfile --ignore-scripts`で準備し、提出前に`bun run check`、独立評価、同一PR headの`checks`・`verify`を確認する。実モデルの収束や使用量の予測を、模擬コマンドの制御テストで保証したとは扱わない。

UI変更はなく撮影は不要。Issueと固定版のコード参照で引き継ぎ、私的な実行ログや追加報告書を必須入力にしない。要求・数量・条件・権限・参照は現行コードと保存記録へ照合済み。Issueの独立評価は未実施。次は本Issueに基づく実装であり、実装時に最新のコードとの整合を再確認する。
