## 目的と合意

scopingで、資料だけでは判断できないが実行・観測で確かめられる不明点を、小さな実験で解消する条件を具体化する。人へ尋ねることと担当AIが調べることを区別し、根拠のない方針選択や不要な質問を減らす。

2026-09-19、依頼者はpstack-codexとの比較を受け、A「実モデル評価の正誤ラベルを隠す」とB「scopingで小さな実験を選ぶ条件の具体化」を別Issueにする案を選択した。本IssueはBを扱う。今回は要求確定とIssue公開までで、実装は後続の着手指示で進める。

## 範囲と完了条件

- [ ] 既存の資料・コードで判断がつかず、観測結果が次の方針を変える不明点に限り、小さな実験・試作・再現を選ぶ条件を、既存の十分性判断に組み込む。
- [ ] 決めること、結果を区別できる観測、観測の限界を明らかにし、本番コードから分離した最小の試作を使う。判断に十分な根拠が得られたら止め、実験の網羅性や一定数の比較案を目的にしない。
- [ ] 観測できる事実と、人が決める目的・好み・許容範囲・権限を区別する。技術的に実験可能でも、未許可の外部操作や本番への書込みを行う根拠にはしない。未確定の権限に依存しない調査は進める。
- [ ] 結論と判断に必要な証拠・適用限界を、既存のIssue下書き・必要なresearchへ残す。試作コードを実装成果物や合意済み仕様として渡さず、既存の合意と実装入口へ接続する。
- [ ] 既存資料で足りる場合は追加実験を要求しない。新しいskill、実験用runtime、schema、専用台帳、必須工程・ゲートは追加せず、重複する説明は既存の正本へ統合する。

主な変更先は`skills/scoping/references/sufficiency.md`。scoping本文や既存の手順確認は、案内・説明の整合に必要な箇所だけ更新する。商品側の検証skill生成、多モデルによる設計競争、常時試作、通常の実行制御の変更は対象外。

## 検証

既存の[scoping手順確認](https://github.com/thkt/dotagents/blob/0fafcb816b5ab34559f551d1fc0fefd121a0f17b/scripts/README.md#scopingの切替と手順確認)に、次の判断を確認できる代表例を組み込む。

- 資料だけでは分からない出力やタイミングが方針を左右する場合、最小の観測を行い、結果と適用限界から判断する。
- 既存資料で十分な場合、不要な試作を始めない。
- 目的・許容範囲・権限が未確定の場合、実験結果を合意の代わりにせず、必要な選択と影響を人へ返す。
- 試作が成功しても、本実装・採用の完了とは扱わない。

これは代表的な会話と成果物による確認であり、スキルの文字列一致テストやCLIの成功で意味判断を保証しない。観測結果と未確認範囲を既存の実行記録へ残し、新しい評価基盤・モデル数の固定・性能ベンチマークを設けない。

セットアップは`bun install --frozen-lockfile --ignore-scripts`。提出前は`bun run check`、既存の独立評価、日本語確認を行い、PRでは同じheadの`checks`・`verify`を確認する。商品画面の媒体は不要。人がレビュー・マージを判断する。変更による時間や手戻りの改善量は未測定であり、文言の追加だけで効果を断定しない。
