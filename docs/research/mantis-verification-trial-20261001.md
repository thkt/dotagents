確認日: 2026年10月1日。対象は [Issue #350](https://github.com/thkt/dotagents/issues/350) の反証・正常動作の対照・条件付き再検証です。

追加指示で補うべき判断の不足は実証できず、候補の実行と通常指示への採用は保留しました。変更前後の比較は未実施であり、追加指示の改善効果も未検証です。次に採用を判断するなら、現行が見落とす実例を特定し、その例で候補の効果と負担を比較するのが妥当です。今回の時間切れだけから品質不足や候補の有効性は判断できません。

### 課題の準備にも制約があった

資料不足の課題は、初期案で所有キー検査を取り除いたため、プロトタイプ由来の名前を返す意図外の不具合が混ざっていました。独立評価で発見し、最初のモデル起動前に両コピーを修正しました。実行した変更は所有キー検査を保つ同等な条件式への整理です。`toString`、`constructor`、`__proto__` がnullになることも事前確認しました。この準備中の発見は実モデルの検出結果へ数えていません。

正常動作の課題には、POSIXの相対パスを絶対パスか判定する意図外の冗長性が残りました。現行の具体的な冗長性の規則に照らして指摘は妥当です。実行後は課題を変更・再試行せず、機能判定の充足と、純粋な対照を作れなかった制約を分けました。この `needs_changes` を追加観点の不足へ転用していません。

## 再現するための入力と観測

すべて合成データを使い、実ファイルやネットワークにはアクセスしません。資料不足以外の課題は、無認証の公開API `asset(name)` が任意のクライアント入力を1回だけ復号し、`/srv/assets` 配下の既存内容を返す要求です。配下外・不存在・復号不能はnull、通常名・階層名・エンコード名の読取りは維持します。内部 `loadAsset` は非公開です。

共通の合成ストレージと修正前の読取り経路は次のとおりです。

```ts
import { posix } from 'node:path';
const ROOT = '/srv/assets';
const files: Record<string, string> = {
  '/srv/assets/guide.txt': 'public guide',
  '/srv/assets/docs/help.txt': 'public help',
  '/srv/private.txt': 'private token',
};
function loadAsset(absolutePath: string): string | null {
  return files[absolutePath] ?? null;
}
export function asset(name: string): string | null {
  let decoded: string;
  try { decoded = decodeURIComponent(name); } catch { return null; }
  return loadAsset(posix.resolve(ROOT, decoded));
}
```

正常動作・呼出元防御の修正は、最後のreturnを次の処理へ置き換えたものです。迂回課題の修正は、上記関数の先頭に `if (name.includes('../')) return null;` だけを追加しています。機能停止課題は関数本体を `return null;` へ置き換えています。

```ts
const absolute = posix.resolve(ROOT, decoded);
const relative = posix.relative(ROOT, absolute);
if (relative === '..' || relative.startsWith('../') || posix.isAbsolute(relative)) return null;
return loadAsset(absolute);
```

| 入力 | 修正前 | 正常動作・呼出元防御 | 迂回課題 | 機能停止課題 |
| --- | --- | --- | --- | --- |
| `guide.txt` | `public guide` | `public guide` | `public guide` | null |
| `docs/help.txt` | `public help` | `public help` | `public help` | null |
| `%67uide.txt` | `public guide` | `public guide` | `public guide` | null |
| `../private.txt` | `private token` | null | null | null |
| `%2e%2e%2fprivate.txt` | `private token` | null | `private token` | null |
| `/srv/private.txt` | `private token` | null | `private token` | null |
| `docs/../guide.txt` | `public guide` | `public guide` | null | null |
| `missing.txt`・`%zz` | null | null | null | null |

正常動作課題の保存テストは、表の最初の6入力と `%zz` の7期待値を含みます。呼出元防御・迂回課題は `../private.txt` と `guide.txt` の2期待値、機能停止課題は `../private.txt` の1期待値だけです。各ファイルのテストは1件です。呼出元の防御を扱う課題の要求には「内部loadAssetに配下チェックがないため任意ファイルを読める」という指摘候補を添えました。

資料不足課題は、`/srv/assets/guide.txt` と `/srv/private.txt` を持つ辞書を所有キー検査で読む内部APIです。読取り許可は呼出元の責任であり、そのコード・配備・認証情報は未提供と明記しました。修正前のifと末尾のnullを、次の同等な式へ整理しました。

```ts
return Object.hasOwn(files, absolutePath) ? files[absolutePath]! : null;
```

保存テストは既存キーの内容と不存在キーのnullだけです。privateキーを内部APIへ直接渡せば合成内容を返すこと自体は契約どおりであり、リモート到達性の証拠にはしていません。

実行には固定版のruntimeコピーと、課題ごとの基準commit・要求を返すコマンド・`check: ["bun", "test"]`・`reviewTimeMs: 180000` を渡し、`reviewOnce` を1回呼びました。候補用は課題の要求・ファイル・基準commitが現行用と一致しています。終了後も10コピーのファイルハッシュに変化がないことを確認しました。原記録はホストの一時領域に保全し、共有用本文には上記の再現条件と裁定に必要な観測を残しています。
