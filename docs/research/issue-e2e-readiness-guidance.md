# UI E2Eテストの待機と独立性を、必要時のテスト設計資料へ補う

## 目的

非同期に描画・再取得するUIのE2Eテストで、画面がまだ準備できていない瞬間を「要素がない」と誤判定したり、更新前から成立している表示を更新後の成功と誤認したりすることを防ぐ。テストの実行時間やflakeを理由に検証を弱めず、対象repoで実際に必要な条件だけを選べるようにする。

2026-09-23に[BerryのE2E運用事例](https://zenn.dev/berry_blog/articles/39392e1da7ca71)を検討した。記事はper-testのデータ独立、状態に基づく待機、不在判定前の陽性ランドマーク、表示が変わらない再取得でのレスポンス待機、計測に基づく並列度を説明する。約140ケースを6〜8分で実行した値は同社の10ジョブ・8コアRunner構成の実績であり、このrepoの改善効果とは扱わない。

現行の[#185](https://github.com/thkt/dotagents/issues/185)はテスト一般の失敗条件カタログを追加済みだが、非同期UIの待機条件は扱わない。この共通repoは製品E2Eを持たず、Playwrightは対象repoのテスト・撮影を起動するアダプターとして使う。[trial repo](https://github.com/thkt/dotagents-workflow-trial)の`trial/capture.spec.js`で見つかった`waitForTimeout`は、検証の成立を待つためではなく動画の操作前後を読める間隔として使われる。現時点で具体的なflakyや待ち時間の改善量は確認していない。

## 範囲

- `implement`からテストを作成・更新する際に必要時だけ参照する既存資料へ、UI E2Eに限った短い判断観点を加える。全変更の必須チェックリストにはしない。
- 対象となるUI E2Eでは、テスト間で共有する可変データと後片付けの有無を確認する。成功判定のための固定sleepを避け、状態変化や操作に対応する応答を待つ。不在を主張する場合は画面の準備完了を示す陽性条件を先に確認し、更新後も表示が同じ値になり得る場合は操作に対応する完了を別に確認する。
- これらの観点を、具体的な失敗条件・既存テストとの差・最小の検証層・費用で選ぶ。撮影動画の可読性のための間隔と、正しさの判定に使う待機を混同しない。

## 完了条件

- [ ] 既存のテスト方針と参照資料に、上記のE2E固有条件を重複なく短く記し、適用しない条件も示す。一般の4観点は維持する。
- [ ] 不在判定が早すぎて通る例と、再取得前後で表示が一致する例について、何を待てば誤通過を防げるか説明できる。`waitForTimeout`の一律禁止や全E2EのPOM化を求めない。
- [ ] 現行trialの撮影用待機を誤って不具合と扱わない。記事の実行時間・Runner設定を本repoへ移植せず、E2E並列化・影響spec選択・新しいCIジョブ・Hook・スキルを追加しない。
- [ ] 人向け日本語と参照先を確認し、対象repoの`bun install --frozen-lockfile --ignore-scripts`、`bun run check`、差分の独立評価、同じPR headの`checks`・`verify`を確認する。人がレビューとマージを判断する。

対象は`thkt/dotagents`。今回は文書指針の追加であり、具体的な製品E2Eや既存テストを変更しない。現時点の調査は記事、現行の共通ハーネス、trial repoの静的確認までで、実際のflakeや速度改善は未測定。
