# 既存の独立評価で具体的な冗長性を検出し、通常の修正へつなぐ

## 目的と依頼

implementの内部レビューで、変更に関係する冗長性・重複・不要な処理を具体的に評価し、PR公開後に利用者が同じ観点の追加レビューを依頼する負担を減らす。完成後に残るコード・分岐・受け渡し・状態・テスト準備・運用の全体を小さくし、必要な保証を維持する。

2026-09-18、ユーザーはPR #119の経緯を踏まえ、scopingによる原因調査と、受入条件・検証方法の整理を依頼した。調査後の確認で「根拠のある冗長性は公開前に修正」を選択した。以下の範囲でIssueへ引き継ぎ、実装は別の依頼を待つ。

## 確認した事実と原因の見立て

対象版は `bfeb6c0709b1779def4dcfc1f161885e1ef2e103`。PR #119の修正前headは `b24ba51b3ba92728ab75a4c4a5a671d12c817e27`、修正後headは `316dae6f340f6b39f65f5a2f4b75d53f0b3620db`。

- #119の内部評価1回目は、非default baseの正当なPRを拒否する欠陥と、工程数比較の根拠不足を検出した。2回目は両指摘をfixedとし、acceptedだった。
- 保存された2回目の入力には、Issue #104の最小化要求、差分・追加ファイルへの参照、affected callersを読む指示があった。情報が全く渡されていなかった、または出力の形式検査が3件を捨てた事例ではない。3件は内部評価の指摘に現れていなかった。
- 公開後のレビューでは、correction内の同じIssueの二重取得、同じcheckoutへの開始条件検査の連続実行、publish内の同じ公開対象の重複取得を検出した。公開後の情報を必要とせず、修正前headのソースで追跡できる種類の見逃しである。
- 現行reviewInstructionsのコード観点はcorrectnessを具体化し、テストについては保証と費用の比較を具体化している。一方、コードの取得・検査・分岐等について、保証を維持した削除・統合の検討方法は明示されていない。
- 現行のassessments.codeとnewItemsには、根拠、影響、対応、必須性を記録できる。parseReviewはrequiredな未解決項目から判定するため、新しい評価欄・状態・ループは不要。

正しさ・必要な保証・前回指摘の解消に評価が寄り、同じ保証をより少ない処理で守る検討が弱かった、というのが記録からの見立てである。モデル内部の判断原因や、指示変更による将来の検出率はこの記録だけでは断定できない。

## 最小案

1. 既存のコード評価に、変更に関係する冗長性の検討を含める。差分と必要な呼出元・呼出先を追い、同じ対象・入力・版・目的の取得や検査、同じ条件分岐・状態・受け渡しが重ならないか確認する。無関係なrepo全体の監査は求めない。
2. 繰り返しが同じ保証を担うか、確認時点・対象・失敗時の動作が違うかを区別する。モデル実行、setup、書込み、公開などを挟む再照合と、外部状態の変化や鮮度要求を考慮する。ローカル書込みがないことだけを理由に検査を削除しない。工程を跨ぐキャッシュや再照合の一律削除を誘導しない。
3. 具体的な重複箇所・成立条件・実行や保守への影響・局所的な整理案・残す保証を、既存のnewItemsとassessments.codeで説明する。必要な場合だけ対象を絞ったトレース等で確かめる。見た目の類似、短文化、行数、好みだけでは指摘を作らない。共通化によって引数・分岐・状態・説明がかえって増える場合も比較し、削ることや抽象化自体を正解にしない。指摘ゼロも許容し、読み取り限界や保留理由は正直に記す。
4. 初回評価でも再評価でも現在の差分と関連経路を評価する。再評価では前回項目を裁定しつつ、前回指摘の解消だけでacceptedとしない。既存のupdates/newItemsと修正ループを使い、既指摘の再発・新たな具体的問題を同じ方法で扱う。
5. 方針は既存の開発方針へ必要最小限反映し、実際の評価指示はreviewInstructionsへ集約する。スキルやCLIガイドへ同じ詳細を重ねない。テストの費用・検出力の詳細な整理は既存 #115 が担当し、本Issueでは重複する別のテスト評価基準を作らない。

合意した指摘の扱い: 対象・条件・無駄の影響が確認でき、合意した範囲内の局所修正で必要な保証を保てる冗長性は、既存のrequiredな指摘として通常の修正へ戻し、PR公開前に解消する。程度や行数で一律に必須化せず、効果が不明・好みだけ・範囲外の再設計なら必須にしない。要求や権限に関わる判断は人へ戻す。

## 対象外

新しいレビュー段階・モデル呼出し・スコア・専用Schema・台帳・監査CLI、レビュー上限・修正上限の変更、既存stateの変換や再開、PR公開後レビューや人の判断の廃止、指摘件数・削減行数のノルマ、全repoの一括リファクタリングは行わない。3件の再修正は完了済みであり、本Issueの目的にしない。

## 受入条件と検証

- 既存のコード評価で、同じ保証を保ちながら削除・統合できる具体的な処理を、呼出し経路・入力の一致・観測時点まで根拠付けて扱える。必要な再照合との区別、局所的な整理案、残る保証が説明される。
- 初回と再評価に同じ観点が届き、既存指摘のfixed判定だけで新たな具体的問題の確認を終えない。上記の条件を満たす冗長性はrequiredとして既存の修正へ戻し、好みだけの変更等は必須にしない。既存Schema・状態遷移・修正上限・公開権限は変えない。
- 指示文の変更は、実モデルによる限定した評価で意味を確認する。PR #119の修正前・修正後の固定版を利用し、修正前の既知3件を根拠とともに検出し、修正後ではその3件を再び問題扱いせず、setupや本文更新を挟む必要な再照合の削除を求めないことを確認する。前回指摘のある再評価文脈でも確認する。正解の箇所・指摘本文を評価モデルへ教えた結果を検出能力の証拠にしない。既知3件は今回の回帰確認用の正例であり、通常レビューの指摘件数ノルマではない。
- 実モデル確認は今回の変更の検証であり、通常実行や通常CIのモデル呼出しを増やさない。対象版・モデル・与えた入力・実際の指摘・見逃し・誤指摘を既存のPR/検証記録へ残す。プロンプトの文字列存在や模擬JSONの受理だけで意味的な改善と扱わない。少数事例の成功を将来の完全な検出や一般的な検出率の保証にしない。
- 既存の制御テストで、必須な未解決項目が通常修正へ戻り、解決済み項目と新規項目を扱え、根拠のない形式変更を追加していないことを確認する。既存検証で十分なら追加せず、プロンプト全文の一致や無意味なケース数を固定しない。
- コード・テスト・文書の増減、通常フローのノード・矢印・モデル呼出しに追加がないことを説明する。目的はレビュー内の判断の改善であり、runtimeコードやノードの純減を達成したとは扱わない。

対象repoはthkt/dotagents。セットアップは `bun install --frozen-lockfile --ignore-scripts`、提出前は `bun run check` と独立評価、同じPR headの `checks`・`verify` を確認する。プロダクト媒体は不要。旧run・生ログは保全し、公開repoへ生ログやホスト内パスを含めない。

## 比較と引き継ぎ

現状維持では、具体的な冗長性の見逃しを利用者の追加レビュー依頼で補う負担が残る。専用レビュー役や静的ルールを先に追加すると、モデル呼出し・接続・誤検出対応・保守を増やす。現在の出力欄と評価経路で目的を扱えるため、まず既存指示と判定根拠の具体化を優先する。

関連 #115 はテスト価値判断と既存テストの具体的整理を含む。本Issueはコードの冗長性を既存評価で検出する範囲とし、#115の実装を必須依存としない。両方が同じreviewInstructionsを変更する場合は着手版で重複を整理する。
