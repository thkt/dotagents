ハーネスの変更を採用する人が、何をいつ評価し、どの条件を満たしたか、何が未確認かを判断できるようにする。評価方法を既存の開発方針・CLI案内へ統合し、ケース単位のレビュー試験をローカルHTMLで読みやすくする。

## 評価方法

目的の違いを次のように整理する。全変更に三つの工程を追加せず、通常検証は既存のcheck・独立評価・同じheadのCIへ、必要な実モデル試験や比較は既存の調査・検証へ置く。

| 判断したいこと | 実施するタイミング | 確認するもの |
| --- | --- | --- |
| 変更が要求を満たし、必要な停止・保全・公開条件を守るか | 通常の変更ごとの既存検証で | 影響する正常系・異常系、独立評価、CI。模擬コマンドの成功を実モデルの能力の証拠にしない |
| レビューが問題を見つけ、誤指摘しないか | レビュー指示・入力・モデル等の変更や実際の見落としがあり、既存の証拠や制御テストだけでは採用判断ができないとき | 関連する正常例と既知欠陥例、独立した再現、指摘ごとの裁定。単なる表示変更には実モデル試験を追加しない |
| 改善案を従来より良いと言えるか | 品質・簡素化・速度・費用の改善が採用理由で、既存の根拠だけでは比較できないとき | 同じ要求・入力・環境での変更前後。品質を先に確かめ、実質差分と要求充足までの総費用を比べる |

評価前に、その変更で答えたい問い、対象版、比較で変える要因、期待する結果、必須条件と許容する差を既存Issue・PRへ短く残す。実モデル実行は対象・入力・予算・共有範囲の許可内で行う。評価後に都合よく基準を下げない。固定の実施周期、全PRへの実モデル義務、万能の試行回数は設けない。

### レビュー試験の判定

試験用コードの成功とレビュー試験の成功を区別する。欠陥版が期待値を返さず、その欠陥をレビューが正しく指摘できた場合は、レビュー試験の期待に合う。既存の2ケースは、対象と観測条件の範囲で次を判定する。

- 正常例: 独立した確認で指定の要求を満たし、レビューの誤指摘がなく、判定に必要な指摘の裁定と証拠が揃っている。
- 欠陥例: 指定した既知の欠陥を再現でき、レビューがその欠陥を具体的に指摘し、誤指摘がなく、判定に必要な指摘の裁定と証拠が揃っている。同一原因の複数指摘を複数の欠陥検出とは数えない。
- 見落としや誤指摘が根拠付きで確認された場合は「条件未達」。裁定・対象・必要な観測が足りなければ「判定保留」。レビューを実行できなかった場合は「実行失敗」。未達と未確認が混在する場合は両方を残し、総合表示で隠さない。使用量だけの不足は品質の判定と分け、費用比較を未確認にする。

モデルの`accepted`、制御上の正常終了、指摘0件、修正済みという値だけで判定を確定しない。ホストが要求・同じ対象の再現・指摘の裁定を照合して結論と理由を残す。`needs_changes`だけを検出成功とは扱わない。未知の欠陥がないことや他の課題での能力は保証しない。2ケース各1回の成功は動作例として扱い、品質向上や安定した成功率の証明にはしない。

### 比較と採用

必須条件を満たすことを前提に、狙った改善の証拠と負担の変化を示して人が採用を判断する。コード・テスト・文書を分けた実質差分、分岐・状態・手動受け渡し、同じ粒度のノード・矢印、読取りやモデル呼出し等を見る。数が減った理由と失う保証も確認する。必要な保証を保つためコードが増える案も、手順全体が小さくなる根拠があれば候補となる。

試行数・条件・ばらつきから改善を判断できなければ比較は保留する。追加試行が判断を変え得るときだけ範囲を定めて行い、成功するまで繰り返さない。全試行・未達・実行失敗・判定保留と、失敗・再試行を含む費用を残す。割合を出す場合は分母を明示し、測定できた試行だけの値に全試行の達成割合を添える。料金・子モデル使用量などの不明値はゼロにしない。

## 保存とローカルHTML

既存の`verify-review.ts`が保存するケース単位の結果と関連記録を入力に、静的HTMLを生成する。レポート生成は元のJSON・ログ・評価用checkoutを読み取り参照に限り、生成物はcheckout外の指定先へ保存する。未確認の上書きをせず、生成・閲覧に実モデルの再実行や常駐サーバーを必要としない。

新しい記録には、模擬／実モデルの区分、実行日時とホストが判断した日時、適用した試験の問い・基準、ホストの結論・理由と根拠への対応を、同じケースの記録から辿れるようにする。既存の対象版・モデル・再現・指摘の裁定を再利用し、新しい台帳は作らない。模擬コードを使う実モデル試験と、モデルを呼ばずに作った表示サンプルを区別する。ホスト未裁定の段階では結論・判断日時を未確認として保存・表示できる。

対応する旧記録にない値は不明と表示する。ファイル更新時刻・Issue更新日時・HTML生成時刻から評価日時を推定せず、旧結果へ新基準を遡及適用しない。過去の判定を再検討する場合は元の記録を保ち、今回の基準・判断日時・結果と区別する。新しい自動再判定・採点機能は設けない。

### 表示の構成: 行動ログと評価

レポートの目的は、同じレビュー試験について「どのように実行されたか」と「何を根拠に評価したか」を一緒に確認し、改善すべき箇所を人が判断できることとする。冒頭には「レビュー試験の行動ログと評価」、表示サンプル／実モデル／不明、評価対象、実行日時、記録された結論・理由と確認待ちを置く。ホスト判断日時も区別して示し、HTML生成日時・内部ID・入力パスは記録詳細へ置く。

| 表示する内容 | 判断に必要なこと |
| --- | --- |
| 評価 | 問い・基準、期待値と実結果、ホストの結論・理由を照合できる。指摘とその真偽の裁定、修正状況は区別する。指摘ID・箇所・条件・影響・証拠・対応案、裁定理由と同じ対象の再現へ辿れる |
| 行動ログ | 呼出し一覧を最初から読める主要セクションにする。保存記録の順序、実行主体、ツール・操作、入力・対象、結果・失敗を、記録がある範囲で短い行に整理する。対応する原文へ辿れる |
| 時間・使用量 | 実時間、モデル時間、トークンなど取得済みの値をコンパクトにまとめ、品質の判定と区別する。単位・集計範囲を示し、未確認の子モデル使用量や金額をゼロにしない |
| 記録詳細 | 元の要求、基準版・レビュー対象、モデル・環境、長い条件・パス・原JSON・生ログを必要時に開ける |

評価と行動ログは見出しで明確に分け、単一ページの主要部分として読めるようにする。長い入出力・原文・補足だけを折り畳む。ログ全体を折り畳みの奥へ置かず、結論や警告の重複を統合する。説明文・判定理由は標準16px以上を目安とし、十分な行間と余白を設ける。数値と単位を揃え、状態は色だけでなく文言で示す。狭い画面では横に詰め込まず、条件・結果・根拠を読める配置にする。

行動ログは既存のstateとJSONLを使い、ホストの制御呼出しと、モデルによるツール実行を区別する。制御呼出しは保存順、各JSONLはそのファイル内の行順を保つ。対応するID等の明示的な記録がある場合だけ関連イベントをまとめる。別actor・別ログ間の全体順序や親子関係は、ランダムなファイル名や並びから推定しない。表示に対応していないイベント、不正・未完の行、時刻や結果の欠落は未確認と示し、原記録も読めるようにする。開始と完了を同じ操作として対応づける場合も、途中で失敗・中断した操作を隠さない。

実時間・個々の操作の時刻・応答サイズはそれぞれ記録で確認できる範囲を示す。表示から計算する件数等は対象範囲を明示し、全実行や全子モデルの総量とは扱わない。ツールの呼出しや明示された対象は行動の証拠だが、参照内容の理解・有効利用や、空白時間の原因までは示さない。行動の偏りを人が発見できる表示にし、無駄・原因・改善効果を表示側で自動判定しない。

要求・基準から実結果、判断理由、その判断に使った同じ試行の証拠へ辿れるようにする。保存された対応がある場合は該当する指摘・再現・ログを直接参照し、ログ全体への参照しかない場合は個別行動との対応を未確認とする。別試行や現在の成果物で過去の判定を裏づけず、未知の原因・合否・参照コンテキストを補完しない。裁定未実施でも生成でき、未確認を合格に変えない。未達・失敗・不足の存在と必要な対応は折り畳む前に示す。制御終了理由とモデルstatusは日本語で意味を示し、内部コードも詳細へ残す。

既存の静的HTML・標準のリンクと折り畳みを再利用する。数値・判定・ログは保存記録から取得し、新しいモデル呼出し、計測基盤、台帳、履歴比較画面、状態変更・再実行・採点・承認・マージ操作を追加しない。画面用フレームワークや常駐サーバーも追加しない。Markdown描画の選定は必要な構文、Bunとの適合、実行防止、依存と保守負担で判断する。

## 今回のブラウザー確認・撮影の合意

2026-09-21、依頼者は「今回のHTMLはホスト側で確認・撮影する」を選択した。`.dotagents.json`の`capture: null`を維持し、CLIの自動撮影には追加しない。これは媒体不要ではなく、担当ホストがこのHTMLの表示確認・撮影を行う今回に限る運用合意である。

実装担当は公開可能な模擬データと生成手順を準備する。ホストは元データとの対応、通常／未確認表示、リンク・折り畳みのキーボード操作、実行可能入力の抑止を確認し、画像・結果・対象版を既存の証拠記録へ残す。公開可能な画像を同じPRへ添付し、PR上の表示まで確認する。完了まで公開完了・readyにしない。

この合意はcapture未設定時に停止する一般的な案内より優先する。実装担当にブラウザー起動や新しい撮影基盤の導入を求めず、ホスト側の実行を残していることだけで`needs_human`にはしない。共通check・独立評価・CI・人のマージ判断は維持する。

### Basecoat試作後の詳細表示の再整理（2026-09-21、提案）

上記の比較調査後、依頼者はBasecoatでの試作を選択した。試作はcheckout外の `basecoat-report-prototype` に置いており、ハーネス本体への採用とは区別する。依頼者は評価の要約を読みやすいと評価する一方、行動ログ以降について、背景上の本文、展開内容の区切り、見出し、開閉位置、情報の意味と重複、追従メニューの余白を指摘した。

現状の試作はログの元の5列を展開部分へ移しており、操作名・結果の重複や本文の役割を整理できていない。開閉部分はBasecoatのaccordion構造を使わず、独自のsummaryと文字の矢印で組んでいる。今回の調査からは、Basecoatの部品不足を理由に別ライブラリへ替える根拠は得られていない。要約を活かし、まず情報の配置と展開内容を作り直す。

#### 参考画面と借りる構成

- [Playwrightの公開レポート](https://demo.playwright.dev/reports/todomvc/): 実画面でテストを開き、操作行の展開を確認した。枠のあるグループ、展開後も残る操作名、下に区切って表示するコードを参考にする。

- [BasecoatのCard内Accordion](https://basecoatui.com/components/accordion/#card): 公式例の実画面でカード、項目間の線、開閉アイコンの位置を確認した。標準のdetails/summaryとカードの構成を基礎とし、JavaScriptを使う機能が必要かは個別に判断する。

#### 各項目の扱い

| 現在の表示 | 次の試作での整理案 |
| --- | --- |
| 背景上の本文 | セクション見出しと本文の面を分ける。本文はカード内へ置き、長い原文はさらに背景・境界線のある領域で表示する。太字だけで階層を作らない |
| ホスト制御呼出し／モデルのツール実行・イベント | 主体の区分を維持する。操作行全体を開閉対象とし、操作名・結果・固定位置のSVG矢印を揃える。展開後は入力／結果・出力／関連記録を見出しと境界線で分け、行頭の操作名・状態を繰り返さない |
| ログの保存先 | 独立した節を削り、関連する原記録のメタデータへ移す。出所を辿るためのパスは保持する |
| ログの読み方・記録の範囲 | 独立した説明の折り畳みを削る。全体の時系列が不明、記録不足など、現在の表示を誤読する条件だけを該当箇所に短く示す。一般的な読み方はCLI文書へ置く |
| 根拠と再現 | 「判断に使った根拠を確認」とその内側の「判断の根拠」の重複を解消する。判断理由から対応する再現・指摘へ直接辿れる構成にする |
| 同じ対象の独立した再現 | 「対象コードの動作確認」とし、確認した条件、期待結果、実際の結果、その比較から分かることを順に表示する。指摘ごとの妥当性確認とは区別する |
| 既知の欠陥・裁定記録 | 「試験に仕込んだ欠陥」「モデルが検出できたか」に整理する。各指摘の裁定は指摘側へ集約し、裁定JSON全体をここで重複表示しない |
| 指摘と裁定 | 指摘単位で「モデルの指摘」と「ホストの確認」を別領域にする。指摘ID・箇所・判定を一覧で対応づけ、詳細への入口を明示する。真偽の確認と修正状況は混ぜない |
| モデルのレビュー原文 | 原文は監査・照合用に保持するが、単独の主要節を廃止し、対応する原記録へ集約する。異なる原文や出力を同一とみなして削除しない |
| 呼出しの入出力・関連原記録 | 呼出しに紐づく入力／出力と、プロンプト・標準出力・標準エラー・イベント等の原記録を区別する。種類・有無・出所を見出し側に置き、本文を枠内で読む。原文を開くためだけの多段の折り畳みを減らす |
| 記録詳細 | 実行・判断日時、対象版、モデル・環境等をラベルと値の一覧にする。長いパスや原文と分離し、欠落は未確認として残す |
| 追従メニュー | 不透明な背景でカードの線を覆い、内側の左右余白を本文の配置と揃える。移動先の見出しが隠れないスクロール余白も設ける |

「ログの読み方」が現在担うのは、別主体のログを完全な時系列と誤認したり、未記録を未実行と解釈したりすることの防止である。この意味は保持するが、独立した長文説明を読む手順は必須にしない。

表示サンプルの再現は、入力 `items=[10,20,30,40], offset=2, limit=2` に対し期待結果 `[30,40]`、実結果 `[]` となる。これは試験用コードに仕込んだ欠陥の再現であり、ハーネス自体の欠陥を意味しない。モデルがそれを正しく指摘できたかをホストが確認するのが裁定であり、修正済みかどうかとも別である。未確認サンプルには対象コードの再現結果があっても、指摘ごとの確認は未完了である。表示側で判定を補わない。

次の試作では、一つの展開したログ、一つの指摘とホスト確認、対応する原記録の表示を揃えてから他の項目へ適用する。閉じた状態の短さだけでなく、開いた状態の読み順・境界・クリック範囲を確認する。長い日本語、未確認・失敗、狭い画面、キーボード操作を対象とし、要約と元の評価値・原記録への対応を保持する。

調査では現行ソースと模擬記録を照合し、外部の公式例を確認した。その後の「作り直してみて」により、上記の案をローカル試作の第3版へ反映した。評価の要約、指摘内容、原記録、未確認表示、内部リンク、CSPを元の表示サンプルと静的に照合した。第2版は `basecoat-report-prototype/html/v2/` に保全している。

ローカル試作の表示確認はBrowser Useの制限により未実施であり、公開例の確認や静的照合を代替の検証とは扱わない。変更はローカル試作と説明に限り、ハーネス本体・Issue・PRへは反映していない。
