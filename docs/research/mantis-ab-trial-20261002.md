## 課題と判定

| 課題 | 修正後の実装と主眼 |
| --- | --- |
| `auth-defect` | 単件読取りの別名によるtenant越境は直るが、一括読取りは別名を認可から除外し、別tenantの本文を返す。公開された一括APIの漏えいを見つける |
| `auth-control` | 両APIが解決後の文書へtenant確認を適用する。正常な別名・順序・重複・空配列を保つ実装へ誤った必須修正を求めない |
| `state-defect` | 配布失敗後の再試行は直るが、成功後に権利を削除するため重なる呼出しで二重配布できる。競合や再入の残存を見つける |
| `state-control` | 配布前に同じ権利を処理中にし、重なる要求を拒否する。成功後の消費、失敗後の再試行、別権利の独立処理を保つ実装へ誤った必須修正を求めない |

`Context` は信頼する認証処理が確定済みで、クライアントによる偽装は課題の対象外。配布関数の拒否は配布が行われていないことを契約で保証する。いずれも合成データであり、実際の認証、外部ネットワーク、永続化は含まない。

主眼の充足は、欠陥課題では具体的な残存欠陥を正しく特定し、正常対照では実装の正常性を正しく判断した上で、誤った必須指摘がないこととした。実行完了や `needs_changes` だけでは判定しない。正しい実装にも保存テストの不足があるため、その妥当な指摘は誤陽性に数えない。成果物全体の受入とは別の判定である。テスト不足と冗長性の指摘は別に記録し、指摘の分割・件数増を改善とは扱わない。

## 再利用と確認方法

添付JSONの `fixtures` には要求、開始版・修正後のソース、同じ保存テストを格納した。各課題について6試行のファイルhash、開始版commit、モデル設定の一致を終了後に再照合した。比較runtimeのtracked差分は候補指示を追加した `scripts/implement/review.ts` だけである。

`fixtureVerificationSource` と `fixtureObservations` はモデルへ渡さない事前確認を保存したもの。認可は各14入力、配布処理は制御可能なPromiseによる重なる呼出しを使い、各課題がモデル起動前に期待する挙動を示すことを確認した。欠陥課題の観測に書かれた `expected` は欠陥を含む挙動の確認値であり、要求を満たす正解値ではない。正常対照と要求を併せて読む。
