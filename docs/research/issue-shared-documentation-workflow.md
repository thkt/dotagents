# ClaudeとCodexでwiki・判断記録を共通利用し、過去資料を分類して引き継ぐ

## 目的と合意

Claudeを使う場合もCodexを使う場合も、関連する知識と判断理由を同じ場所から読み、作業で得た知見を同じ方法で蓄積できるようにする。dotclaudeで用いるwikiとdecisionsの形式に揃え、内容は各リポジトリ内で独立して管理する。

依頼者は本会話で「claude使用時もcodex使用時も同じように使うし蓄積されるドキュメントとして揃えましょう」と依頼し、既存資料についても「過去の調査・判断記録も今回まとめて分類・移行する」を選択した。本Issueはそのうち **thkt/dotagents内の文書と利用経路** を対象とする。dotclaude側の変更は別の対応とし、両リポジトリの知識本文を共有ファイルへ統合しない。

このファイルはローカルのIssue下書きであり、公開・実装・検証完了の記録ではない。上記の目的・対象・既存資料の移行は依頼者の合意、以下の実装構成の候補は担当者の設計提案として区別する。

## 現在の不足

- 現行手順、調査根拠、判断理由がREADME、research、docs/evidence、docs/knowledgeなどへ分かれ、読む入口と更新先がwiki・decisionsの共通運用として定まっていない。
- [報告の入力検査](../../scripts/input.ts)は`research/*.md`だけを受け付け、wiki・decisionsを同じ版照合付きの必須資料として指定できない。
- [共有知識の処理](../../scripts/knowledge.ts)はJSONを正本とし、Issueのpath・blob・node IDから選択して各工程へ渡す。人向けの現行知識をwikiへ移す際も、既存Issue・runの参照を失わせない対応が必要である。
- 過去の草案には採用、未採用、保留、後続判断による置換が混在する。保存場所や見出しだけでは現在の採用状態を決められず、未追跡資料と公開済み資料の区別も必要である。

## 今回の要求

### 共通の読む・更新する経路

`docs/wiki/`を現在の手順・構造・適用条件、`docs/decisions/`を選択理由・代替案・判断の状態を読む入口にする。dotclaudeの形式を基に、適用する形式の版と共通項目を示す。要求と許可の正本はIssueと合意記録に保つ。

Claude・Codexのどちらから始めても、今回に関連するwiki・判断記録を選び、現行コード・Issue・出典と照合して使う。文書が存在しない場合も従来の調査から始められ、全資料の読込みや全作業での新規ページ作成は必須にしない。

要求整理で判断が固まったときと、実装差分が揃ったときに、残す価値のある知識・判断と既存ページへの影響を確認する。必要なwiki・判断記録を更新し、既存の独立評価へ含める。適用範囲、合意・提案・観測の区別、出典と対象版、未確認事項、見直し条件を保持し、異なる目的での結論を無条件に再利用しない。

### 現行知識と参照の引き継ぎ

既存JSONモデルが表す現行知識をwikiへ移し、日常の読む・更新する経路を共通運用へ揃える。同じ現行説明をJSONとMarkdownで二重に手修正する運用にしない。JSON正本と生成処理を維持し、人向け生成Markdownをwikiへ置く方式も許容する。旧JSONのnode ID・blob・開始版を参照するIssueと保存済みrunは、対象版の意味を保って読めるようにする。

`--report`でwiki・decisionsのMarkdownも指定できるようにし、既存research資料の参照も維持する。選んだpath・blobと開始commitの照合、通常ファイルの確認、未確認の変更による停止を保ち、初回実装・修正・独立評価へ同じ参照を渡す。旧参照を最新の版へ黙って置き換えず、過去runを変換・再開しない。

### 過去資料の分類と移行

dotagents内の既存`research/`、`docs/evidence/`、`docs/knowledge/`の調査・判断・検証資料を、追跡済み・未追跡の双方について棚卸しする。本文が参照する測定JSONや試行用ファイルも対応を確認し、移行によって根拠や参照を失わせない。

資料の意味に応じ、現行知識はwiki、判断理由はdecisionsへ整理し、実測原本・歴史的資料・旧Issue草案は出典として保全する。複数の役割を含む資料は必要な知見を抽出し、原本への対応を残す。全内容を採用済みに昇格させず、却下・保留・置換済みの判断、効果未確認、当時の対象版を維持する。

移行対応表で全資料を網羅し、元資料、役割・状態とその根拠、移行先または原本を保持する理由、公開・ローカル未共有の区別を辿れるようにする。採用状態は関連Issue・PR・コード・合意記録と照合し、不明な場合は不明とする。実測値や過去の結論を現行の成功証拠へ書き換えない。

既存の未コミット変更、未追跡資料、過去のrunを保全する。未追跡であることを未公開の断定に使わず、公開済みIssue等との対応と共有範囲を確認する。秘密情報、会話全文、生ログ、ホスト専用記録を移行のために一括公開しない。

## 設計案と対象外

既存の報告引き継ぎとGit照合を拡張し、スキル・文書方針・入口の案内から同じ運用へ接続する案を推奨する。旧JSON参照の互換読出し、wikiの識別方法、原本と移行対応表の配置は、既存資産と影響を確認して実装時に決める。移行対応表は今回の移行確認に使い、日常作業に新しい進行台帳や検索サービスを必須化しない。

全リポジトリへの展開、dotclaude本文のdotagentsへの複製、定期自動収集、新しい自動公開・マージ、実装actorのモデル切替、知識利用の時間・品質改善の数値保証は今回の対象外とする。

## 完了条件と検証

- [ ] Claude・Codexそれぞれの入口から、同じ条件で関連wiki・判断記録の選択、現行照合、必要な更新へ辿れる。共通する方法と各環境で確認した範囲を示す。
- [ ] wikiとdecisionsの役割・形式・状態が明確で、出典の版、適用条件、未合意・未確認事項を保った実例がある。文書がない場合と更新不要の場合も扱える。
- [ ] 既存JSON由来の現行知識をwikiから利用・更新でき、旧node ID・blobの参照も対象版の意味で読める。未選択の知識や提案を今回の要求へ混入させない。
- [ ] 新しいwiki・decisions参照と既存research・JSON参照について、正常な引き継ぎと、不正path、欠落、版違い、未コミット変更の拒否を確認する。初回実装・修正・独立評価と既存PR修正で参照の基点を維持する。
- [ ] 移行対応表から過去資料全件の扱いと原本を辿れる。旧Issue草案、実測原本、未共有資料を区別し、採用状態不明を埋めず、元の数値・条件・参照と無関係な変更を保全する。
- [ ] README、スキル、文書方針、CLI説明、生成・検査処理と関連リンクを整合させる。終了・変更する保証と旧資料の読み方を説明し、実体のない旧操作を案内しない。
- [ ] `bun install --frozen-lockfile --ignore-scripts`で準備し、影響する既存検証を再利用して不足する境界だけを補い、`bun run check`を通す。人向けMarkdownを原資料と照合し、日本語と意味を既存の独立評価で確認する。

模擬コマンドによる制御テスト、実際のClaude・Codexからの利用確認、GitHubへの公開は分けて報告する。未実施の環境は未確認とする。画面媒体は不要。実装を公開する段階では通常のdraft PR・同じheadのCI・本文確認へ進み、人がレビュー・マージを判断する。
