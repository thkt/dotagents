# scoping・implementの選択漏れと誤発動を実例で測る

## 目的と根拠

共通ハーネスの`scoping`・`implement`をメンバーが使うとき、必要な依頼で適切なスキルが選ばれ、無関係な依頼では選ばれないかを実際のモデル実行で確かめる。選択できたことと、成果物が要求を満たしたことは別に判定する。失敗が見つかった場合に、入口の説明や適用条件を根拠を持って直せる、小さく再実行可能なevalを用意する。

[TOKIUMの記事「正解データを作らない、簡単なevalの作り方」](https://zenn.dev/tokium_dev/articles/pdm-evals-claude-code-skills)は、実際の修正指示から発動漏れを見つけ、発動すべき依頼とすべきでない依頼の両方を評価した事例である。記事の52%と78%は比較時の正例数が23件から18件へ変わっており、同じ条件での改善率として我々へ転用しない。我々に同種の選択漏れがあるか、現在は未測定である。

現行の[README](https://github.com/thkt/dotagents/blob/227b4849e891398cea33d4ecc44ba433714aff70/README.md)は二つを通常入口として案内し、[scoping](https://github.com/thkt/dotagents/blob/227b4849e891398cea33d4ecc44ba433714aff70/skills/scoping/SKILL.md)と[implement](https://github.com/thkt/dotagents/blob/227b4849e891398cea33d4ecc44ba433714aff70/skills/implement/SKILL.md)には適用範囲がある。しかし、実際の利用者の依頼文で選択率・誤発動率を測るevalは確認できなかった。[#145](https://github.com/thkt/dotagents/issues/145)は改善案の比較方法、[#180](https://github.com/thkt/dotagents/issues/180)は共有入口と互換性の整理であり、今回の選択evalとは範囲が異なる。

## 範囲

1. 実際の利用で観測した選択漏れ・誤発動や、現在のスキル適用条件に近い依頼から、小さな正例・負例・境界例を選ぶ。正例には`scoping`を使う要求整理・Issue化と、合意済みIssueを`implement`で進める依頼を含める。負例には単なる質問・レビューなどを含める。期待ラベルと理由を実行前に決め、曖昧な依頼を推測で正解扱いしない。実際の失敗が未確認なら、その旨と例の由来を区別する。
2. 現在のスキル登録・モデル・設定で依頼を独立に実行し、対象スキルを実際に選択・読取った証拠、誤ったスキルの使用、選択せずに作業を始めた例を記録する。応答でスキル名に触れただけでは発動と数えない。期待ラベルや以前の回答を評価対象へ見せない。再実行に必要な入力・版・条件と、評価不能な試行を区別して残す。
3. 同じ試行で、選択の成否とは別に、要求・失敗条件を満たしたかを関係する成果物と行動から確認する。選択だけで品質を保証せず、選択しなくても偶然要求を満たした試行も区別する。現在のIssue・検証・独立評価を置き換えない。
4. 選択漏れが具体的に確認できた場合だけ、原因がスキルの説明、配置・登録、依頼の曖昧さ、その他のどこにあるかを調べる。改善案を比べるときは同じ依頼集合・モデル・設定を使い、正例の選択と負例の誤発動、成果の要求充足、実行時間・取得できる使用量を併記する。ケース集合や条件が変わる場合は、同条件の改善率として示さない。

## 完了条件と検証

- [ ] 現行の`scoping`・`implement`について、出典と期待ラベルを持つ正例・負例・境界例を用意し、同じ条件で再実行できる。ラベルの根拠と実行入力を分離する。
- [ ] 各試行の選択結果、誤発動、要求充足・未充足・判定不能、根拠の参照先を確認できる。集計の分母に実行失敗や判定不能を黙って含めたり除いたりしない。
- [ ] 少なくとも現行版の測定結果と具体的な失敗・未確認範囲を残す。改善を行う場合は、同じケースの変更前後を比較し、負例と要求充足を悪化させていないか確かめる。単回のモデル実行から安定した率や組織全体への効果を断定しない。
- [ ] 必要な最小のケース保存・実行・読戻し方法を既存資産と比較して選ぶ。専用基盤や定期実行を前提にせず、保守費用とモデル使用量を含めて継続方法を示す。ハーネスの変更を提出する場合は`bun run check`、差分の独立評価、同じPR headの`checks`・`verify`を確認し、人がレビュー・マージを判断する。

## 対象外と合意

全スキル・全依頼の網羅、常時ログ収集、全PRの自動採点、点数による自動採用、スキルを読めば必ず成果が正しいという扱いは含めない。利用者の実際の依頼・ログを使う場合は、その内容と共有先を確認し、必要な範囲だけ扱う。

2026-09-23、依頼者は記事の検討後に「evalは必要」と述べ、`scoping`・`implement`の正例・負例による選択evalと、成果の要求充足を別に確かめる提案を受けて「issueにしましょう」と指示した。本Issueはその範囲の評価実施までを扱う。恒久的なCIゲートや新しい共通評価プラットフォームの採用は合意に含めない。
