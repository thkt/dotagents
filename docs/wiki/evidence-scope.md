# 検証結果を観測した範囲で使う

## 内容

制御テスト、実モデルの観測、変更全体の独立評価、CI、人の採用判断は、それぞれ確認した対象と範囲を分けて記録します。過去の成功や少数の合成課題の結果から、現在の成果物の成功、一般的な検出率、速度・費用の改善を導きません。

## 定型手順

1. 結果を使う前に、対象commit・入力・モデルと環境・比較条件・計測範囲を確認します。今回と条件が異なる場合は、適用できる範囲を説明します。
2. 指摘の件数やモデルの判定だけで不具合を数えず、要求、コード、再現入力で裁定します。一つの機能不具合と、その回帰テスト不足を独立した機能不具合2件とは数えません。
3. 正解や過去の裁定をレビュー入力から分離した試行と、そうでない試行を区別します。実行条件を満たさなかった失敗は原因を残し、有効な品質比較へ混ぜません。
4. 未裁定、見落とし、未確認の操作、計測に含まれない費用を明示します。保存済みの実測を現在の成功へ更新せず、新しい確認は別の対象版の結果として扱います。

## 過去の比較から再利用する注意点

| 比較するもの | 当時分かったこと | 今回確認すること |
| --- | --- | --- |
| 検査ツール | [#174](https://github.com/thkt/dotagents/issues/174)の比較では、自動追加される入口を揃えた追試で検出が一致し、初期の優劣判断を撤回しました | 同じ引数だけでなく、実際に解決された入口・設定・対象が同じか確認します |
| 文書への入口 | [#157](https://github.com/thkt/dotagents/issues/157)では両条件とも必要な調査へ到達し、索引による発見改善は確認できませんでした。採用理由は読む条件の明示でした | 索引を読んだこと、必要資料の発見、判断や費用の改善を分けます |
| 条件付きの参照 | [#228](https://github.com/thkt/dotagents/issues/228)は、短い下書きの経路から必要な確認観点へ到達できない候補を見送りました | 読む量だけでなく、その経路で要求・合意・偏りなど必要な判断を維持できるか確認します |

これらは対象版と条件を持つ事例です。ツール、索引、参照分離そのものの一般的な優劣には広げません。

## 参照コード

- `scripts/verify-review.ts` の `probe`：対象成果物を評価した後、レビュー対象外の再現結果を記録し、裁定を `pending_host_adjudication` として残します。
- `scripts/verify-review.ts` の実行入口：正誤とは独立したケースIDと順序を使い、実モデル試行を通常のcheckから分けます。
- `scripts/review.ts` の `reviewInstructions`：実測と仮説、形式の妥当性と判断の妥当性を区別するよう求めます。
- `.codex/DEVELOPMENT.md` の「改善効果の比較」：同じ条件での比較、観測範囲、費用、未確認事項の扱いを定めています。
